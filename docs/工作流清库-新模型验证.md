## 步骤 1：优先走应用自身 API（最安全，级联引擎）

blade-workflow 删除定义时会**级联**清理节点/操作者/权限/出口/表单布局，并调用
`repositoryService.deleteDeployment(deploymentId, true)`（cascade）卸载引擎部署、连带清理运行/历史。

对每个定义调：

```
DELETE /blade-workflow/definition/{id}
```

> 逐个执行，直到 0.2 的 `definitions` 为 0。执行后建议重跑步骤 0 盘点，看还剩哪些残留（通常是逻辑删除的 `is_deleted=1` 行与未级联干净的实例/待办），再决定是否需要步骤 2。
>
> ⚠️ 该接口是**逻辑删除**（`@TableLogic`），行会以 `is_deleted=1` 留存；这不影响新建流程（新建会拿新 id），若要彻底抹掉请走步骤 2。

### 执行中踩到的两个坑（下次直接照做）
1. **FK 顺序**：`act_ru_job` / `act_ru_*_job` 引用 `act_ru_execution`，必须**先删 job 表再删 execution**；`act_ge_bytearray` 被 `act_re_procdef`、`act_re_deployment`、`act_ru_variable`、job 表引用，**必须最后删**、且 `act_re_deployment` 排在 bytearray **之后**。第一次按"直觉顺序"删到 `ACT_RU_EXECUTION` 即报错中断（事务已自动回滚，无脏数据）。
2. **`ACT_RU_TASK` 有 `ON DELETE CASCADE`**：删任务会自动连带删掉其 execution，所以显式删 execution 时只剩 89 条 —— 属正常，不是漏删。

### ✅ 已修复：测试态配置面板读源指向「测试部署」（2026-10-06）

**症状**：在设计器配好操作菜单/表单内容 →「保存」→「测 试」→ 打开测试页，**操作菜单"消失"**（节点接口 `extJson` 返回空字符串）。

**根因**（两个叠加）：
1. 画布「保存」只更新草稿 `bpmn_xml`，**不刷新部署**；
2. 配置面板（`nodes()`/`links()`）按 `wf_process_definition.proc_def_id` 读**已部署**模型，而 `proc_def_id` 仍指向上一次**正式**部署（可能是很久以前、没有 extJson 的版本）。

于是「测试实际跑的 BPMN」（`__test` 部署，带最新配置）与「配置面板展示的 BPMN」（旧正式部署）成了两个不同版本。

**修复**（迁移 `V2026.10.06_001__wf_process_definition_add_test_proc_def_id.sql`）：
- 新增列 `wf_process_definition.test_proc_def_id`，由 `deployForTest` 写入本次测试部署的 procDefId；
- `WfBpmnExtensionReader` 新增 `resolveConfigProcDefId()`：测试态（`status=3`）且该列非空时优先用它，`nodes()`/`links()` 走该读源；
- **刻意收窄边界**：`node()`/`operators()` 与运行期共用，**仍读正式部署** `proc_def_id`——避免真实实例在测试态读到被 `neutralizeForTest` 降级过的元素（businessRuleTask / ThrowEvent / 带定时器事件 → manualTask）；`status=1`（已发布）时该列不生效。

**修复后行为**：测试态下「保存 → 测 试」即可让面板与测试同版本，**不必再「发布」**。

> 验证方式（反向测试，可复现）：把 `test_proc_def_id` 指向一个不存在的 procDefId，节点接口立刻返回 0 个节点 → 证明配置读源确由该列驱动；恢复后返回 3 个节点且 `extJson` 含 `operateMenu`。

### ⚠️ 用 API 建流程时必须带 `bpmndi`（否则设计器打不开）

若绕过设计器、直接调 `POST /blade-workflow/definition` + `PUT /definition/{id}/bpmn` 建流程，
提交的 BPMN **必须包含 `<bpmndi:BPMNDiagram>` 图形交换信息**（`BPMNShape`/`BPMNEdge`/`dc:Bounds`），
否则设计器加载时 bpmn-js 直接抛：

```
[BpmnDesigner] 画布加载失败： Error: no diagram to display
```

原因：流程**结构**解析不依赖 DI（`saveBpmn` 甚至会主动剔除 bpmndi 再解析），所以后端保存、部署、
运行都正常，`wf_process_node` 也正确 —— 但设计器要靠 DI 渲染画布。带 DI 的最小片段：

```xml
<bpmndi:BPMNDiagram id="BPMNDiagram_1">
  <bpmndi:BPMNPlane id="BPMNPlane_1" bpmnElement="<processId>">
    <bpmndi:BPMNShape id="UserTask_1_di" bpmnElement="UserTask_1">
      <dc:Bounds x="260" y="78" width="100" height="80" />
    </bpmndi:BPMNShape>
    <bpmndi:BPMNEdge id="Flow_1_di" bpmnElement="Flow_1">
      <di:waypoint x="196" y="118" /><di:waypoint x="260" y="118" />
    </bpmndi:BPMNEdge>
  </bpmndi:BPMNPlane>
</bpmndi:BPMNDiagram>
```

且 `definitions` 需声明三个命名空间：
`xmlns:bpmndi=".../BPMN/20100524/DI"`、`xmlns:dc=".../DD/20100524/DC"`、`xmlns:di=".../DD/20100524/DI"`。

> 排查手法：`SELECT LOCATE('BPMNDiagram', bpmn_xml) FROM wf_process_definition WHERE id=<defId>;`
> 返回 0 就是缺 DI（正常应 >0）。

### 附：API 建流程的其它注意点
- `wf_node_operator.node_id` 非空，**创建接口里不能带 operators**（会报 `Field 'node_id' doesn't have a default value`）。
  操作者已下沉 BPMN `wf:operator`，运行时由 `WfOperatorResolver` 经 `bpmnReader.operators()` 读取；
  `PUT /definition/{id}/node/{nodeKey}/operator` 接口已 `@Deprecated`、查询返回空属正常。
- `bpmnXml` 需 **Base64** 编码后提交（规避 XSS 过滤器去标签）；带 `<` 时后端也会直接当 XML 用。
- 保存 BPMN 是乐观锁：需带 `baseRevision` = 当前 `wf_process_definition.draft_revision`。
- Windows 下用命令行重启该服务：classpath 过长超 8191 字符要用 `@argfile`，且 **argfile 内路径必须用正斜杠**
  （Java argfile 把 `\` 当转义符，反斜杠会被吃掉 → `ClassNotFoundException`）。
