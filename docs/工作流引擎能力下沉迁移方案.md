# 工作流：把 `wf_*` 能力下沉到 Flowable 引擎的迁移方案

> 目标：与其双写，不如将 `wf_*` 中**引擎尚未具备**的功能改造后集成进 Flowable，
> 避免重复维护、统一执行路径、提升一致性与可维护性。
> 适用范围：`blade-workflow`（SpringBlade + Flowable **7.1.0**）
> 关联：`工作流双写漂移治理.md`（双写边界 / P0 根因 / 方案 A 收口）
> 关联：`工作流双写漂移治理-方案C-事件驱动落地设计.md`（状态派生的事件驱动设计）

---

## 0. 现状核实（决定迁移边界的两个硬事实）

| 核实项 | 结果 | 影响 |
|---|---|---|
| `FlowableConfig` 是否设置 history level | **未显式设置**（走 Flowable 默认）；`IProcessService` 注释明确「无需 `history=full`」 | `ACT_HI_COMMENT` 需 ≥ **activity**（应满足）；`ACT_HI_DETAIL` 需 **full**（未开）→ 表单快照不可迁 |
| 是否使用 `addComment` / `addUserIdentityLink` | **全模块零处使用** | `ACT_HI_COMMENT` 与自定义 identity link 均为「未启用」状态，迁移即新增依赖，需实测验证 |
| `asyncExecutorActivate` | `false` | 异步路径暂不生效；若开启须满足方案 C §3.4 三项兜底 |
| `ACT_*` 与 `wf_*` 是否同 DataSource | 是（治理文档 §4） | 原子性的唯一来源，迁移后仍需保持 |

## 1. 迁移范围

按「引擎有无原生对应物」分三档。**迁错了比不迁更糟** —— C 档明确不动。

### 1.1 A 档：有原生对应物 —— 建议迁移

| `wf_*` 功能 | 迁入目标 | 引擎承载方式 |
|---|---|---|
| 审批意见 / 流转轨迹 `wf_approval_log` | `ACT_HI_COMMENT` | `taskService.addComment(taskId, procInstId, message)`，原生 comment 表 |
| 抄送(8) / 传阅(11) | 自定义 identity link | `addUserIdentityLink(taskId, userId, "cc"/"circulate")` —— Flowable `TYPE_` 接受任意字符串 |
| 实例运行状态（运行 / 结束 / 暂停） | `ACT_RU_EXECUTION` + `SUSPENSION_STATE_` + `ACT_HI_PROCINST` | 即治理文档 6a/6b/6c 的对齐对象，方案 C 已覆盖 |
| 任务待办 / 已办状态 | `ACT_RU_TASK`（活跃）/ `ACT_HI_TASKINST.END_TIME_` | 原生 |
| 会签 / 或签 / 依次 | BPMN multi-instance | 或签 = `completionCondition` `${nrOfCompletedInstances==1}`；依次 = `isSequential="true"` |

### 1.2 B 档：语义必须先钉死，否则不迁

**协办(7)** —— 唯一悬而未决项：

| 语义判定 | 结论 |
|---|---|
| 「协办人也能办结并推进流程」 | 可迁为 **candidate user** |
| 「仅协助、不推进，由主办人办结」 | 引擎无对应，**留 `wf_*`** |

现有证据倾向前者：`WfWriteHelper#terminate` 把协办与待办一并关闭
（`.in(WfTask::getStatus, WfTask.STATUS_TODO, WfTask.STATUS_COADJUTANT)`），
说明协办是「可被终结的待办态」。但 —— **「协办办结是否推进流程」必须业务确认**后才能定档。

### 1.3 C 档：不建议迁移（迁了更糟）

| 功能 | 为什么不迁 |
|---|---|
| **组织 / 数据权限** | 要迁就得把 org 同步进 `ACT_ID_USER` / `ACT_ID_GROUP` / `ACT_ID_MEMBERSHIP`，等于制造**第二份组织真相源**，与 blade-system 认证体系双写 —— 用更大的双写换掉小双写 |
| **表单快照 `wf_form_snapshot`** | 引擎侧 `ACT_HI_DETAIL` 需 **history=full**（当前未开）；且是扁平 KV 而非按节点 JSON，查「某节点快照」要扫 detail 表 —— **负优化** |
| **草稿(5)** | 引擎未发起，无对应物；本就是纯台账单写，不构成双写 |
| **催办 / 已读** | 纯 OA 通知态，引擎无概念 |
| **`wf_process_definition` / `node` / `link` / `operator`** | 这是**设计态**元数据，BPMN 是其产物（画布生成）。会签/或签可下沉 BPMN（已列 A 档），但操作者配置要**运行时解析**（`WfOperatorResolver`），BPMN 只能存配置、解析仍需自定义监听 —— 省不掉代码，反而把配置藏进 XML 更难维护 |

## 2. 改造目标

1. **统一执行路径** —— A 档各项只写引擎一次，`wf_*` 不再镜像同一事实，根除状态类漂移（P0 的根）。
2. **收口器瘦身** —— 迁完后 `WfWriteHelper` 里「状态镜像」部分可删，只剩 OA 独占写。
3. **减表** —— `wf_approval_log` 可退役（轨迹迁 comment）；`wf_task` 的抄送 / 传阅行可退役（迁 identity link）。
4. **明确保留项** —— B / C 档留在 `wf_*`，**不为「统一」而硬塞**。

### 2.1 迁移后 `wf_*` 残留清单（目标态）

| 表 | 保留内容 |
|---|---|
| `wf_instance` | 标题、业务关联（`form_id` / `data_id`）、`biz_key`、紧急度、草稿态、测试态、展示用节点名 |
| `wf_task` | 协办（依 B 档判定）、催办 / 已读、OA 展示字段 |
| `wf_form_snapshot` | 全保留（C 档） |
| `wf_process_definition` / `node` / `link` / `operator` | 全保留（设计态，C 档） |
| `wf_approval_log` | A 档迁移后可退役；若 `log_type` 分类仍需 OA 侧区分，则保留轻量版 |

> **目标不是消灭 `wf_*`，而是消灭重复维护。**

---

## 3. 约束条件（硬约束，违反即不可行）

1. **Flowable 表不可加列**
   只能用原生表 + 原生字段 + 变量表。不能给 `ACT_HI_COMMENT` 加 `node_key` 列 ——
   升级即丢 / 即崩，且废掉「可换引擎」演进位（治理文档 §5.4）。

2. **history level 门槛**
   `ACT_HI_COMMENT` 需 ≥ **activity**；`ACT_HI_DETAIL` 需 **full**。
   **开工前必须实测确认引擎实际 history level** —— 这是 A 档能否落地的第一道闸。

3. **禁止隐式约定**
   若某功能只能靠「把 `node_key` 塞进 `ACTION_` 字段」实现，等于把耦合从表结构搬到字符串约定，
   可读性下降。**此类宁可留在 `wf_*`**。

4. **查询不能退化**
   OA 高频查询（我的待办含协办 / 抄送、部门范围、多类型聚合）必须仍在关系层高效完成。
   任何「迁后要扫变量表或扫 FULL history」的方案都是负优化。

5. **同库事务前提不变**
   `ACT_*` 与 `wf_*` 同 DataSource，这是原子性唯一来源（治理文档 §4）。分库则一切免谈。

6. **版本锁定 7.1.0**
   升级 Flowable 必须回归 identity link type 与 comment 语义。

7. **存量数据迁移**
   历史 `wf_approval_log`、抄送 / 传阅行需一次性迁移，或双轨只读保留。

8. **可灰度、可回滚**
   A 档每项独立 `@ConditionalOnProperty` 开关，逐个迁移，**禁止一次性切换**。

9. **异步路径同样受方案 C §3.4 约束**
   若开 `asyncExecutor`，comment / identity link 的写入也需「禁 `HISTORIC_*` 事件
   + 常驻对账修复 + deadletter 告警」三项兜底。

---

## 4. 推进顺序

| 序 | 事项 | 理由与前置 |
|---|---|---|
| **0** | 实测确认 history level | 硬门槛，决定 A 档第 1 项能否落地 |
| **1** | 审批轨迹 → `ACT_HI_COMMENT` | 收益大、风险最小（只读展示型数据，不影响流转） |
| **2** | 抄送 / 传阅 → identity link | 需先确认「抄送不产生可办任务」 |
| **3** | 实例 / 任务状态 | 即方案 C，设计已就绪 |
| **4** | 会签 / 或签 / 依次下沉 BPMN | 改动面最大，需全量流程回归，**最后做** |
| **5** | 协办（B 档） | 待业务确认语义后再定档 |

---

## 5. 与既有方案的关系

```
方案 A（已落地）  WfWriteHelper 双写收口        → 防「漏写」复发
方案 C（设计就绪）引擎事件派生台账状态          → 消灭「状态镜像」双写
本方案（待启动）  把 OA 能力下沉进引擎原生能力  → 消灭「功能重复实现」
```

三者递进而非互斥：本方案第 3 步（实例 / 任务状态）即方案 C；
第 1、2 步完成后，`wf_approval_log` 与抄送 / 传阅行随之退役，`wf_*` 维护面进一步收窄。
