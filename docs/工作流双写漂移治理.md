# 工作流双写漂移治理

> 适用范围：`blade-workflow` 模块（SpringBlade + Flowable）
> 关键词：双写边界 · `wf_*` 业务台账 vs `ACT_*` 引擎表 · 待办漂移
> 关联文档：`工作流双写漂移治理-方案C-事件驱动落地设计.md`（方案 C：事件驱动反写，设计完成 / 未实现）
> 关联文档：`drift_check.sql`（对账 SQL，与本文档同级）

---

## 1. 背景与问题

工作流同时维护两套数据：

- **业务台账（`wf_*`）**：`wf_instance` / `wf_task` / `wf_approval_log` / `wf_form_snapshot` 等，由 `blade-workflow` 手写，承载 OA 语义（待办/已办/协办/抄送/传阅、权限、轨迹）。
- **引擎表（`ACT_*`）**：Flowable 自动维护的运行态/历史态表（`ACT_RU_*` / `ACT_HI_*` / `ACT_RE_*`）。

两套数据由不同代码路径写入，存在**双写漂移**风险：一边写了、另一边没写，或写入顺序/事务不一致，导致「业务显示待办但引擎已结束」或「业务已终止但引擎仍运行中」等不一致。

---

## 2. 双写架构边界

| 层 | 类 | 职责 | 持有的写能力 |
|---|---|---|---|
| **引擎适配层** | `ProcessServiceImpl`（`service/impl/ProcessServiceImpl.java`） | 只封装 Flowable 原子能力 | 持有 `RuntimeService`/`TaskService`/`RepositoryService`/`HistoryService`/`ManagementService`（由 `FlowableConfig` 注入）；**全模块唯一**调用 Flowable API 的地方 |
| **业务台账层** | `WfInstanceServiceImpl`、`WfTaskServiceImpl` | `wf_*` 业务语义 | 持 `wf_*` Mapper，通过注入的 `IProcessService` 触发引擎写；`@Transactional` 在此层 |

`ProcessServiceImpl` **本身无任何 `@Transactional`**（类注释明确「只封装引擎原子能力，不写 wf_* 表」），因此引擎写会**加入调用方的事务**（默认 `REQUIRED`），前提是与 `wf_*` **共用同一 DataSource / 事务管理器**。

---

## 3. 操作级双写映射

| 操作 | 入口(@Transactional) | 写 `ACT_*`(引擎) | 写 `wf_*` | 同事务 |
|---|---|---|---|---|
| 发起 `start` | `WfInstanceServiceImpl.start` (230) | ✅ `startInstance/ById` | instance/snapshot/log/task | ✅ |
| 审批 `approve`→`doApprove` | `WfTaskServiceImpl.approve` (131) | ✅ `completeTask`/`moveActivity` | task+log→advance | ✅ |
| 驳回 `reject` | `WfTaskServiceImpl.reject` (336) | ✅ `moveActivity` | task+log→重生成 | ✅ |
| 推进 `advance` | `WfInstanceServiceImpl` (1071+) | ⚠️ 仅异常兜底 `moveActivity` | instance+task+log | ✅ |
| 保存草稿 `saveDraft` | 424 | ❌ | instance/task/snapshot | 纯台账 |
| 删除草稿 `deleteDraft` | 531 | ❌ | task/snapshot/log/instance | 纯台账 |
| **撤销/撤回 `withdraw`/`cancel`→`terminate`** | 1020/1063 | ❌ **缺失（P0）** | instance+task+log | 只改 `wf_*` |
| **暂停 `stop`** | 1027 | ❌ **缺失（P0）** | instance+log | 只改 `wf_*` |
| **恢复 `resume`** | 1044 | ❌ **缺失（P0）** | instance+log | 只改 `wf_*` |
| 转办 `forward` | 509 | ❌（复用同 `engineTaskId`） | task+log | 纯台账（设计内） |
| 加签 `addSign` / 抄送 `circulate` / 催办 `urge` / 已读 `markViewed` | 546/577/609/632 | ❌ | task/log | 纯台账（设计内） |

`forward`/`addSign`/`circulate` 复用同一 `engine_task_id`，属**设计内**的台账/引擎分离，审计时需知两份语义此处有意不同步。

---

## 4. 漂移根因

### 🔴 P0 — 撤销/终止/暂停/恢复不写引擎（持久漂移，已修复）
`withdraw`/`cancel`→`terminate`、`stop`、`resume` 只改 `wf_instance/wf_task/wf_approval_log`，**全模块无任何 `deleteProcessInstance`/`suspendProcessInstance`/`activateProcessInstance` 调用**。后果：业务已终态/暂停，但 `ACT_RU_EXECUTION`/`ACT_RU_TASK` 仍标记运行中，与 `wf_instance.status` 永久不一致。

### 🟠 P1 — `deleteDraft` 不删引擎实例
已发起实例没有「删实例并清引擎」的入口（靠草稿态边界规避），提升/边界场景有留孤儿 `ACT_RU_*` 风险。

### ⚪ 部署侧前提（影响原子性）
- 同事务成立前提：`ACT_*` 与 `wf_*` **同 DataSource**。若分库，双写不再原子。
- 若启用 `flowable.async-executor` 或节点 `flowable:async`，`completeTask` 后推进由**异步 Job 另起事务**完成，同步 `advance` 可能读到旧节点 → 落点错位。

## 5. 代码修复（P0）

> 文件：`IProcessService.java`、`ProcessServiceImpl.java`、`WfInstanceServiceImpl.java`

### 5.1 接口新增 3 个引擎同步方法（`IProcessService`）
```java
void deleteProcessInstance(String engineInstId, String reason);
void suspendProcessInstance(String engineInstId);
void activateProcessInstance(String engineInstId);
```

### 5.2 实现（`ProcessServiceImpl`）
均 `runtimeService.*` 调用，**尽力而为**：捕获 `FlowableException`（实例已结束/已挂起/缺失）只记 warn、不抛，避免引擎异常把业务事务一起回滚（`deleteProcessInstance` 对不存在的实例是安全 no-op）。

### 5.3 接线（`WfInstanceServiceImpl`）
- `terminate`（被 `withdraw`/`cancel` 复用）末尾：`processService.deleteProcessInstance(inst.getEngineInstId(), action)`
- `stop` 末尾：`processService.suspendProcessInstance(inst.getEngineInstId())`
- `resume` 末尾：`processService.activateProcessInstance(inst.getEngineInstId())`

三者都在各自的 `@Transactional` 内，引擎调用以 `REQUIRED` 加入同一事务（同数据源时原子）；失败整体回滚。

### 5.4 设计权衡
`WfInstance.engineInstId` 原注释定义为「弱关联、保留替换引擎演进位」，原作者因此有意不调引擎。本次改动削弱了弱耦合（业务终态现在依赖引擎动作成功，但已用 try-catch 兜底不让其阻断业务）。若后续更看重可换引擎，替代方案是：保留不调引擎，让待办查询/巡检以 `wf_*` 为准、`ACT_*` 视为只读副本并容忍差异。

### 5.5 双写收口器 `WfWriteHelper`（方案 A，已落地）

> 状态：**已实现**。文件：`blade-workflow/.../service/helper/WfWriteHelper.java`

P0 的直接成因是「业务代码写 `wf_*` 时漏了调引擎」。5.1~5.3 补齐了缺失的引擎调用，
但要让这类漏写**不再复发**，靠的是把「台账写 + 引擎写」收口为不可跳过的一步 ——
引擎调用被固化在收口器方法内部，**不是可选参数**，调用方无法再只写一边。

| 入口 | 台账写 | 引擎写（固定步骤） |
|---|---|---|
| `terminate(inst, status, opinion, action)` | 置终态 + `end_time`、关全部待办、追加流转日志 | `deleteProcessInstance` |
| `suspend(inst)` | 置 `status=暂停4`、追加流转日志 | `suspendProcessInstance` |
| `activate(inst)` | 置 `status=运行中0`、追加流转日志 | `activateProcessInstance` |

配套改造（`WfInstanceServiceImpl`，纯抽取、行为零变化）：
- `terminate` / `stop` / `resume` 保留鉴权与测试态守卫，**写操作整体委托收口器**；
- 私有 `appendLog` 委托至 `WfWriteHelper.appendLog`，全模块流转日志收敛为一份实现。

**边界**：只收口会改变实例**生命周期状态**的操作（漂移就出在这里）。
`start` / `approve` / `advance` 的双写本就正确且台账逻辑各异，未强行收口，避免回归风险。
协办/抄送/传阅、草稿、审批轨迹、表单快照等 OA 独占写**不在收口范围内** —— 引擎无对应物，本就是单写。

**下一步（方案 C）**：本方案消灭的是「漏写」，未消灭「两处写」。
若要让引擎成为状态的唯一写入方、`wf_*` 状态改由 Flowable 事件派生，见
`工作流双写漂移治理-方案C-事件驱动落地设计.md`（设计完成，尚未实现）。

## 6. 对账 SQL — `drift_check.sql`

只读对账单（位于本目录 `drift_check.sql`，按需在 workflow 库执行），6 段：

1. **数量概览**：待办去重 vs 引擎运行态。
2. **A 类漂移**：引擎有任务、`wf_task` 缺记录（孤儿任务 → 用户看不到待办）。
3. **B 类漂移**：`wf_task` 待办、引擎无任务（悬挂/陈旧 → 永远待办）。
4. **漂移分布**：按租户/日期定位「全局 bug」还是「个别流程」。
5. **去重计数对比**：`wf_todo_distinct_engine` 应与 `engine_ru_task` 接近。
6. **反向漂移（P0 历史漂移）**：用 `ACT_RU_EXECUTION`（根执行 `PARENT_ID_ IS NULL`）对齐 `wf_instance`：
   - `6a` 业务已终态(1/2/3) 引擎仍运行 → 需 `deleteProcessInstance`
   - `6b` 业务已暂停(4) 引擎仍活跃(`SUSPENSION_STATE_=1`) → 需 `suspendProcessInstance`
   - `6c` 业务运行中(0) 引擎却挂起(`SUSPENSION_STATE_=2`) → 需 `activateProcessInstance`

> 注意：`wf_task` 的协办(7)/抄送(8)/传阅(11) 复用同一 `engine_task_id`，行数不可直接比，须按 ID 关联；对账排除 `is_test=1` 测试实例。

## 7. 一次性修复脚本 — `HistoricalDriftFixer`

> 文件：`blade-workflow/.../job/HistoricalDriftFixer.java`
> 用途：P0 止血后的**存量**清理，调用第 5 节新增的引擎方法回滚历史孤儿。

特性：**幂等、可重复执行、默认不启用**（`@ConditionalOnProperty`）。

逻辑：
- `fixTerminalInstances()`：`wf_instance` 状态∈{通过1/不通过2/撤销3} → `deleteProcessInstance`。
- `fixSuspendedInstances()`：`wf_instance`=暂停4 且引擎仍活跃 → `suspendProcessInstance`（先 `active()` 查避免重复）。
- `fixDanglingTasks()`：`wf_task` status=0 但 `engine_task_id` 不在 `ACT_RU_TASK` → 置办结(4)，消除永远待办（用 `notInSql` 关联，正常待办不被误伤）。

### 使用顺序
1. 跑 `drift_check.sql` 确认第 6 段（尤其 6a/6b）的存量范围。
2. 启动 blade-workflow 加 `--workflow.drift-fix.enabled=true`（保持默认 `dry-run=true`）→ 看日志核对将修复条数。
3. 确认无误后加 `--workflow.drift-fix.dry-run=false` 真正执行。
4. 再跑 `drift_check.sql` 复核：第 2/3/6 段应为 0。
5. **移除该启动参数（或改回 false），并删除 `HistoricalDriftFixer` 类**（临时脚本，不应留在正式代码）。

## 8. 状态常量速查

`WfInstance.status`：0运行中 / 1通过 / 2不通过 / 3撤销 / 4暂停 / 5草稿
`WfTask.status`：0待办 / 2已办 / 4办结 / 6自动提交 / 7协办 / 8抄送 / 11传阅

`wf_task.engine_task_id` == `ACT_RU_TASK.ID_` == `ACT_HI_TASKINST.ID_`
`wf_instance.engine_inst_id` == `ACT_RU_EXECUTION.PROC_INST_ID_`（根执行 `PARENT_ID_ IS NULL`）
