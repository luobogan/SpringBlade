# 组织数据取数路径核实（`WfOperatorResolver`）

> 目的：确认 blade-workflow 如何获取组织数据（**Feign** 还是**本地表**），据此评估
> 「路径 a（`taskCandidateGroupIn` 自解析组列表）」的落地基础。
> 关联：`工作流引擎能力下沉迁移方案.md` §1.3 C 档（组织 / 数据权限）
> 关联：`工作流双写漂移治理.md`

---

## 1. 结论（先说）

1. **取数方式：Feign 远程调用，零本地表读取。**
2. **路径 a 对本项目不成立、也不必要** —— 本项目**不是「候选组」模式**：组织在应用侧就被解析成
   **确定的 `userId` 集合**，`wf_task` 据此建行；**引擎根本不参与「谁能看到」的判定**。

> 因此更进一步的结论：**组织 / 数据权限本就不构成双写，也不需要迁移。**

---

## 3. 路径 a 的落地基础：不成立

### 3.1 路径 a 的前提

「任务以**候选组**形式存在，某人能看到是因为属于该组；查询时用组列表过滤」
→ 需要 `ACT_RU_IDENTITYLINK.GROUP_ID_` + `taskCandidateGroupIn(...)`，
且**不需要** `ACT_ID_*`（引擎不解析 membership）。

### 3.2 本项目的实际模式

```
wf_node_operator（配置：部门/角色/岗位/…）
        │
        ▼  WfOperatorResolver（Feign → blade-system）
  确定的 userId 集合                      ← 组织解析在此完成，引擎不参与
        │
        ▼
  wf_task 建行（待办/协办/…）              ← 可见性由 wf_task 决定
```

**组织在应用侧就被"拍平"成具体人**了，任务不是候选组。

### 3.3 推论

- 引擎侧**没有**可见性判定的需求 → 也就**不需要** `ACT_ID_*` / 组织副本 / candidateGroup
- 组织数据是**应用侧单写**（Feign → userId → `wf_task`），引擎只收到最终结果
- **路径 a 要解决的前提问题（"引擎如何知道谁能看"）在本项目不存在**

## 4. 对「迁移方案 C 档」的修正

原 C 档表述：

> 组织 / 数据权限 —— 要迁就得把 org 同步进 `ACT_ID_*`，制造第二份组织真相源

**应修正为：**

> 组织 / 数据权限 —— **引擎不参与可见性判定**（应用侧 Feign 解析成 `userId` → `wf_task` 单写），
> **本就不存在双写可消除**。若强行把可见性判定交给引擎，反而才需要引入组织副本（`ACT_ID_*`）——
> 那是**引入**问题，不是**解决**问题。故：不迁移。

同时把原「必然制造双写」的理由拆成两个独立判断（见 §5）。

---

## 5. 两个必须分开的决策

| 决策 | 性质 | 是否解决组织问题 | 代价 |
|---|---|---|---|
| **A. 合库**（`blade_workflow` → `blade`） | 运维 | ❌ 不解决（瓶颈是 Feign 服务边界，不是库位置） | 低，但引入「共享库」反模式风险 |
| **B. 把 Feign 换成直连 SQL 读 `blade_user`** | 架构 | ✅ 能本地化 | **破坏微服务边界**；两个服务 schema 演进耦合；**丢失现有的"远端降级不阻塞流转"保护** |

> 注意：合库（A）本身**不会**让组织解析变本地 —— Feign 仍是 Feign。

---

## 6. 附带结论：合库对双写漂移零收益

`wf_*` 与 `ACT_*` **本来就在同一个库（`blade_workflow`）、同一个事务** ——
这正是方案 A（双写收口）与方案 C（事件派生）能够成立的前提。
把库并进 `blade` 对漂移治理**没有任何增益**，只改变运维形态。
