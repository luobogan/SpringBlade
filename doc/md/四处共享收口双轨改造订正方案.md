## 0. 统一开关设计

参照项目现有范式（`WfLedgerModeProperties.java:21-33`、`WfRetirementProperties.java:25-34`、`WfActionProperties` 的 `@ConfigurationProperties`），新建一个集中的兼容开关类，**代码默认 false 即安全值**（配置缺失时零行为变化）：

```java
// config/WfFlowtableCompatProperties.java（建议）
@Data
@Component
@ConfigurationProperties(prefix = "blade.workflow.compat")
public class WfFlowtableCompatProperties {
    /** 归档判定新信号源：true=按引擎实例 ended/execution 判定；false=沿用 ACT_RU_TASK 空判定 */
    private boolean archiveSignal = false;
    /** 事件失败策略：true=台账投影 listener 回滚引擎；false=沿用 catch→warn 最终一致 */
    private boolean strictEventFail = false;
    /** 动作统一闸门：true=执行器层做 is_test/租户/白名单校验；false=沿用调用方守卫 */
    private boolean actionGate = false;
    /** 会签推进灰度：定义 ID 白名单，空=全部走现有全局开关 */
    private List<Long> engineMiGrayDefIds = List.of();
}
```

`application.yml` 在 `blade.workflow` 下新增 `compat:` 段，四项全部显式配 `false`（默认安全），每项注释写明"翻转前置条件 + 回退方式 + 在途实例不受影响"。

**总原则**：任何一处改造都必须满足——
1. `false` 分支与改造前**逐字节等价**（不是"语义差不多"，是同一段旧代码原样保留）；
2. `true` 分支只对新发起流程生效（依赖在途钉版本，见 `WfInstanceServiceImpl.java:506-539`）；
3. 每处都有独立回归用例，且"两轨同跑"结果可比对。

## 1. 收口一：归档判定（`advanceInternal`）

### 1.1 现状与问题

- 位置：`WfInstanceServiceImpl.java:3120-3152`。
- 现状：`engineTasks.isEmpty()` → 直接置 `STATUS_APPROVED` + `endTime` + 双写 ACT 终态（`:3130-3136`），唯一额外信号是 `holdForSubflow`（`:3126`）。
- 问题：`currentTasks` 只查 `ACT_RU_TASK`（`ProcessServiceImpl.java:126-130`）；ReceiveTask / Timer / message catch 等待时该表为空 → **误判归档且终态双写不可逆**。

### 1.2 双轨设计

```java
// advanceInternal 内，原 3123 行前插入判定
boolean engineEnded = processService.isProcessInstanceEnded(inst.getEngineInstId()); // 新增只读封装
boolean useNewSignal = compat.isArchiveSignal();

if (engineTasks.isEmpty()) {
    if (useNewSignal && !engineEnded) {
        // 新轨：引擎仍 active 但无 UserTask → 等待态，不归档
        String waitNode = processService.activeWaitActivityId(inst.getEngineInstId()); // 只读
        inst.setCurrentNodeKey(waitNode == null ? inst.getCurrentNodeKey() : waitNode);
        instanceMapper.updateById(inst);
        actWriter.writeCurrentNodeKey(inst.getEngineInstId(), inst.getCurrentNodeKey());
        log.info("[compat-archive] 引擎等待态不归档. instId={}, waitNode={}", instId, waitNode);
        return;
    }
    // 旧轨：原 3124-3151 行整体原样保留（含 holdForSubflow、归档日志、子流程回调）
    ...
}
```

- `false`：完全走原 3124-3151，零变化。
- `true`：仅当"引擎实例已结束"才归档；等待态保持 `status=0` 并更新 `current_node_key` 到等待节点。
- `isProcessInstanceEnded` / `activeWaitActivityId` 是新增的**只读**封装（内部用 `runtimeService.createProcessInstanceQuery().active().count()` 与 execution 查询），不改任何写入。

### 1.3 回归点

| 用例 | `false` 期望 | `true` 期望 |
|---|---|---|
| 现有 E2E `e2e_freeflow_full.py`（26 项，3 步/单步/退回重提） | 26/26 PASS | 26/26 PASS（**必须一致**） |
| 普通流程末步提交 | status=1、endTime 非空、ACT_HI_PROCINST 终态 | 同左 |
| 含 ReceiveTask 的流程发起后等待 | status=1（旧误判，记录为已知缺陷） | **status=0、endTime 空、ACT 终态未写** |
| 上述流程发消息唤醒后完成 | — | 继续走到 UserTask → 完成 → status=1 |
| 子流程 holdForSubflow 场景 | 暂缓归档 | 同左 |

**回退**：`compat.archive-signal=false`，无需改数据；已误归档的等待态实例需按 `HistoricalDriftFixer` 同类逻辑修复（属数据修复，不在双轨方案内）。

## 2. 收口二：事件失败策略（先订正口径，再谈双轨）

### 2.1 现状：三处口径不一致（P0）

| 位置 | 写的 | 实际 |
|---|---|---|
| `WfEngineEventListener.java:40-42` Javadoc | "isFailOnException = true 让引擎整体回滚（C1 强一致）" | `:99` `return false` |
| `application.yml:167` 注释 | "C1 强一致，isFailOnException=true" | 代码 false |
| `WfEngineEventListener.java:99` 注释 | 说明批次 1 后改为 false（ACT 直写 catch-warn） | — |
| `WfMiEmptyGuardListener.java:130-134` | 必须 true（空集合拦截需回滚） | true（**正确，保留**） |
| `WfBizCallbackListener.java:88-92` / `WfProcessNoticeListener.java:211-215` | false | false（**正确，保留**） |

### 2.2 第一步：纯文档订正（不做代码分支，立即做）

把 `WfEngineEventListener.java:40-42` Javadoc 与 `application.yml:167` 注释改成实际语义：

> 台账投影已切 ACT 直写（批次 1），写失败由 `WfTaskActDirectWriter` catch→warn 兜住，`isFailOnException=false` 表示**最终一致（C2）**；不再宣称 C1 强一致。通知/回调类失败不应回滚审批；MI 空集合守卫保持 true 是职责所需，不是口径冲突。

这一步**零代码行为变化**，但消除排障误导，是 P0 必须项。

### 2.3 第二步：若要恢复强一致，按职责分级加开关（不一刀切）

```java
// WfEngineEventListener
@Override
public boolean isFailOnException() {
    return compat.isStrictEventFail();   // 默认 false = 现状
}
// WfBizCallbackListener / WfProcessNoticeListener：保持 return false（副作用失败不回滚审批）
// WfMiEmptyGuardListener：保持 return true（空集合拦截必须回滚），不受开关影响
```

**关键**：绝不能把 4 个 listener 统一成一个开关值——通知发送失败回滚审批是设计错误。开关只作用于**台账投影**那一个 listener。

### 2.4 回归点

| 用例 | `false` 期望 | `true` 期望 |
|---|---|---|
| 注入 ACT 业务列写失败 | 审批提交成功、日志 warn、无回滚 | 引擎操作回滚、用户收到明确错误 |
| 注入通知发送失败 | 审批成功、通知缺失仅日志 | **审批仍成功**（通知 listener 不受开关影响） |
| MI 空集合（操作者离职） | 抛 FlowableException 回滚、点名节点 | 同左（MI guard 不受开关影响） |
| 文档一致性 | grep 所有 `isFailOnException` 注释与 yml，无 "C1 强一致=true" 残留 | 同左 |

**回退**：`compat.strict-event-fail=false`；文档订正不需要回退。

## 3. 收口三：动作统一闸门（`WfActionExecutor.execute`）

### 3.1 现状与问题

- 位置：`WfActionExecutor.java:77-95`（入口无 `is_test` / 租户 / 白名单校验）。
- `http`/`sql` 有各自开关与 URL 白名单（`:236-265,590-598`），但 `is_test` 守卫**全在调用方**（`WfTaskServiceImpl.java:403/405/436/549-552` 等），引擎直接触发 ServiceTask 时会绕过。
- 问题：扩展自动节点后，测试态流程可能真实发 HTTP / 改库。

### 3.2 双轨设计

```java
public void execute(WfInstance inst, WfProcessNode node, String phase, String script, Long operator) {
    if (script == null || script.isBlank()) return;
    String s = script.trim();

    if (compat.isActionGate()) {
        // 新轨：统一闸门（短路前先记日志，避免"静默不执行"变成新的语义替换）
        if (isTestInst(inst) && isExternalAction(s)) {
            log.info("[compat-action-gate] 测试态跳过外部动作. instId={}, script={}", instId, s);
            appendLog(inst, ..., "测试态跳过外部动作：" + s);   // 用户可见
            return;
        }
        if (!tenantMatches(inst, s)) {
            throw new ServiceException("动作租户不匹配");
        }
    }
    // 旧轨：原 81-94 行前缀分派原样保留
    ...
}
```

- `false`：现状，调用方守卫决定是否调用，执行器不拦。
- `true`：执行器层统一拦 `is_test` + 租户 + 动作白名单；`field:`/`set:`（写自身表单快照）不短路，只拦 `http/sql/action` 外部动作。
- **可观测性要求**：每次短路都写审批日志，不能默默跳过。

### 3.3 回归点

| 用例 | `false` 期望 | `true` 期望 |
|---|---|---|
| 测试态流程配 `http:` 动作 | 真实发请求（现状） | **不发请求 + 审批日志有"测试态跳过"** |
| 正式流程配 `http:` 动作 | 执行 | **执行**（零回归，关键） |
| 测试态配 `field:` | 执行 | **执行**（内部快照不受闸门影响） |
| 跨租户 `action:` | 现状按注册表执行 | 拒绝 + 明确错误 |
| 现有 E2E 26 项（无外部动作） | 26/26 | 26/26（必须一致） |

**回退**：`compat.action-gate=false`；已产生的外部副作用无法自动回滚，因此**建议先开闸门再启用自动节点**（顺序不可颠倒）。

## 4. 收口四：会签推进（按定义灰度，而非全局切换）

### 4.1 现状

- 位置：`WfTaskServiceImpl.java:346-372`。
- 现状已是双形态：`if (!isEngineMultiInstance(inst, nodeKey))` → 自研 `countPending/nextPending/closeSiblings`；否则让位引擎 MI 完成条件。
- 切换靠全局 `blade.workflow.engine-multi-instance.enabled`（默认 true，yml true）+ 部署期注入（`WfDefinitionServiceImpl.java:2370-2427`）。
- 问题：切换是**全局的**，无法逐个流程灰度；改一处影响全部会签流程。

### 4.2 双轨设计（在现有全局开关之上加灰度层）

```java
// 建议抽成私有方法，保持 doApprove 主链不动
private boolean useEngineMiFor(WfInstance inst, String nodeKey) {
    if (!engineMiEnabled) return false;                 // 全局关 → 自研（现有语义）
    if (compat.getEngineMiGrayDefIds().isEmpty()) return true;  // 白名单空 → 全部走引擎（现状）
    return compat.getEngineMiGrayDefIds().contains(inst.getDefId()); // 灰度内走引擎，否则自研
}
// doApprove:346 行改为 if (!useEngineMiFor(inst, task.getNodeKey())) { ...原自研计数原样保留... }
```

- 白名单为空 = **完全等同现状**（全局开、全部走引擎）。
- 白名单非空 = 仅列出的定义走引擎 MI，其余**回退自研计数**——实现逐流程灰度。
- `advanceInternal:3183` 的 `isEngineMultiInstance` 判定同步改用 `useEngineMiFor`，保持"生成待办"与"推进门禁"两处口径一致（这是最容易漏的一点）。

### 4.3 回归点

| 用例 | 自研轨 | 引擎 MI 轨 |
|---|---|---|
| 会签（SIGN_ALL）3 人 | 第 1、2 人不推进；第 3 人推进归档 | 同左 |
| 或签（SIGN_OR）3 人 | 第 1 人推进 + 关闭其余待办，**无幽灵待办** | 同左（引擎删兄弟任务，`WfMiEmptyGuard` + ENTITY_DELETED 投影生效） |
| 依次（SIGN_SEQUENCE）3 人 | 逐个激活、最后一人归档 | 同左 |
| 待办数 | 每条待办可见、无重复 | "1 引擎任务 = 1 人"，无 N×N 重复 |
| 审批日志条数 | 逐人留痕 | 逐人留痕 |

**必须做的比对**：同一流程定义分别用两轨跑同一组用例，断言归档终态、待办集合、日志条数一致——不一致说明某轨有缺陷，不许放量。

**回退**：白名单移除该 defId → 该流程回自研轨；全局 `engine-multi-instance.enabled=false` → 全部回自研（现有回退路径已验证）。

## 5. 四处统一回归基线（每次改造后必跑）

| # | 基线 | 来源 |
|---|---|---|
| 1 | `e2e_freeflow_full.py` 26/26（发起/3步/退回重提/单步/自选办理人/超容量） | `log/e2e_freeflow_full.py`，自带清理可重复跑 |
| 2 | 普通 UserTask 流程：发起 → 审批 → 归档 | 手工或已有 E2E |
| 3 | 会签三形态（SIGN_ALL/OR/SEQUENCE）两轨比对 | 本方案 §4.3 |
| 4 | 归档判定：普通流程两轨一致、等待态流程两轨不同且新轨正确 | 本方案 §1.3 |
| 5 | 测试态隔离：`is_test=1` 外部动作不外溢 | 本方案 §3.3 |
| 6 | 事件失败口径：文档/注释/代码无 true 残留 | 本方案 §2.4 |
| 7 | ACT 读源：待办/已办/实例列表/进度图正常 | 现有监控与列表 E2E |
| 8 | odoc 正文/套红/转版式 | 验收清单实测项 |

**红线**：任何一项基线不通过，**不许放量**，回退开关后再排查。

## 6. 放量顺序（建议）

```
Step 0  文档订正（§2.2，零风险，立即做）
Step 1  归档判定双轨（§1）→ 基线 1/2/4 通过 → 灰度开 archive-signal
Step 2  动作闸门双轨（§3）→ 基线 1/5 通过 → 灰度开 action-gate
        ↑ 必须在启用任何自动节点之前完成
Step 3  会签灰度（§4）→ 基线 3 两轨比对通过 → 白名单逐_def 加入
Step 4  事件失败策略双轨（§2.3）→ 基线 6 通过 → 按需开 strict-event-fail
        ↑ 通常不必开（通知类失败回滚审批是错误设计）
```

**注意顺序**：闸门（Step 2）先于自动节点启用；归档判定（Step 1）先于 ReceiveTask/Timer 启用。

## 7. 结论

- 4 处收口全部可通过"**开关默认 false + 旧代码原样保留 + 新轨只读/灰度**"完成双轨，不需要改表结构、不需要迁移数据。
- 唯一**不需要开关、必须立即做**的是 §2.2 的文档口径订正——它零代码风险但当前误导最严重。
- 真正的红线只有一条：**旧分支必须与改造前逐字节等价**；做不到就不叫双轨，叫重构。
