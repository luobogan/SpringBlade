## 1. 文档目标与结论摘要

### 1.1 目标

1. 摸清泛微 ecology E9 审批能力的**真实实现模型**（流程定义、节点、流转、表单、权限），作为自建审批的功能基线。
2. 设计**已实现的自定义 Excel 布局**与审批流程的集成方案，明确前后端改造点。
3. 在 Camunda 8 与 Flowable 之间给出**可落地的选型结论**（含嵌入式 / 独立集群两种形态）。
4. 给出可直接进入开发的数据模型、接口清单、迁移方案与实施路线图。

### 1.2 核心结论（TL;DR）

| 主题 | 结论 |
|---|---|
| **ecology 审批模型** | 「流程定义（`workflow_base`）+ 节点（`workflow_flownode`/`workflow_nodebase`）+ 出口（`workflow_nodelink`）+ 操作者（`workflow_nodegroup`/`workflow_groupdetail`）+ 实例（`workflow_requestbase`）+ 当前操作人员（`workflow_currentoperator`）+ 流转日志（`workflow_requestlog`）」七张核心表构成；**无 BPMN**，是自主研发的"节点-出口"图模型，合并/并行靠 `nodeattribute` 拓扑标记 + `ismustpass` 必经标记表达 |
| **选型（推荐·待复核）** | **方案 A：嵌入式流程引擎 + 独立微服务**（`blade-service/blade-workflow` + `blade-service-api/blade-workflow-api`，放置论证见 **11.5 节**）。⚠️ **内核路线需拍板**：Flowable 开源引擎为 **Apache-2.0，自行集成合法无碍**（§14.6 仅限制依赖 BladeX 商业封装 `blade-starter-flowable`，非禁止使用 Flowable 本身）；但**实际技术栈为 Java 21 + Spring Boot 4.x**（非初版所写 Boot 3.5.9/JDK17），Flowable 7 官方基线为 JDK17+Boot3.3，兼容性需 PoC。三条路径：自行集成 Flowable（Apache-2.0）/ 自研轻量审批内核 /（可选）切 BladeX 商业版。见 **10.2 第 8、9 项** |
| **选型（备选）** | **方案 B：Camunda 8 独立集群**。仅在需要水平扩展/高并发编排、且具备 K8s 与运维能力、并**已落实生产许可（Camunda 自托管免费版仅限非生产）**时采用 |
| **关键许可风险** | Camunda 8 Self-Managed Free Edition **仅允许非生产使用**，生产需 Enterprise 许可；Web Modeler/Console 为专有许可。`bpmn-js` 为 **bpmn.io License（非 OSI 许可）**，商用前需法务确认 |
| **Excel 布局集成** | 布局不动、模型不双造：**渲染层按"节点字段权限矩阵"降级**。复用已有 `fieldDomId` 的 `data-excelp-scope`（`main` / `dt{idx}_r{row}`）+ `data-excelp-field` 作为权限定位锚点；表单数据另存快照，与布局解耦 |
| **最大改造缺口** | 现有系统**没有节点级字段权限**：`modefieldauthorize` 仅 1可见/2可编辑，无必填、无隐藏、无节点维度；`ExcelPreview` 只有布尔 `readOnly`；`ApprovalTriggerServiceImpl` 仅 `TODO` + 打日志，未真正发起流程 |
| **已有资产冲突（新增）** | 已盘点（**第 11 章**）：`blade-workflow` 模块与流程表**均未创建**（SQL 0 命中）、前端**无** WorkflowDesign 页面（只有 `FormMode/ExcelDesign`）；但 Feign 契约 `IWorkflowClient` 已**写死服务名 `blade-flow`** 与 `/api/blade-flow/workflow/request/create`，且同目录旧方案文档规划沿用 ecology 表名 —— **存在 3 项需立即拍板的冲突**（服务名 / 表名前缀 / 设计器画布） |

## 2. ecology 审批现状分析

### 2.1 总体模型

ecology E9 的审批**不是 BPMN 引擎**，而是一套以关系表为中心的"节点-出口"自研引擎：

```
流程定义 workflow_base
   ├─ 节点 workflow_flownode(流程内属性) / workflow_nodebase(全局节点属性)
   │     └─ 操作组 workflow_nodegroup → 操作者明细 workflow_groupdetail
   ├─ 出口（连线）workflow_nodelink（含条件、退回标记、必经标记）
   └─ 节点字段权限 workflow_nodeform / 明细权限 workflow_nodeformgroup

流程实例 workflow_requestbase
   ├─ 当前操作人员 workflow_currentoperator（isremark 状态机）
   └─ 流转日志 workflow_requestlog（logtype 动作类型）
```

**关键澄清（与常见假设不符）**：

| 常见假设 | 实际情况 |
|---|---|
| 存在 `workflow_nodeoperator` 表 | **不存在**（全源码 0 命中）。操作者是 `workflow_nodegroup`（组）+ `workflow_groupdetail`（明细）两级 |
| `nodeattribute` 表示会签/或签 | **错误**。`nodeattribute` 是**分叉-合并拓扑属性**（0普通/1分叉起点/2分叉中间/3按通过分支数合并/4指定分支合并/5比例合并）。会签关系在 `workflow_groupdetail.SIGNORDER` |
| `passnum` 是会签人数 | **错误**。`passnum` 是**合并节点的通过阈值**（分支数或百分比） |
| `workflow_requestbase.status` 是状态码 | **错误**。`status` 是**状态文字描述**；真正的状态码是 `currentstatus`（-1正常 / 0暂停 / 1撤销） |

### 2.2 流程定义

**主表 `workflow_base`**（权威 DDL 见 `D:\Weaver2020\ecology\data\ST\1table.sql:20366`）

| 字段 | 语义 |
|---|---|
| `ID` | 流程 ID（= workflowid） |
| `WORKFLOWNAME` / `WORKFLOWTYPE` | 名称 / 所属类型目录 |
| `FORMID` | 表单 ID。`isbill=1` 时指向 `workflow_bill.id` |
| `ISBILL` | 1=单据/新表单（数据在 `workflow_bill.TABLENAME`）；0=老式自定义表单（数据在 `workflow_form` 大宽表） |
| `ISVALID` | 状态：1=活动版本有效 / 2=测试 / 3=非活动历史版本 |
| `ISTEMPLATE` | 是否流程模板 |
| `VERSION` / `ACTIVEVERSIONID` | 版本号 / 主版本 ID |
| `ISFREE` / `FREEWFTYPE` | 是否自由流程 / 自由模式（1简易 / 2高级） |
| `ISAUTOAPPROVE` / `ISAUTOCOMMIT` | 自动批准 / 自动提交开关 |
| `SUBCOMPANYID` / `DSPORDER` | 分部（分权） / 排序 |

**版本模型**：「主版本行 + 历史版本行」同表存储，`ACTIVEVERSIONID` 指向主版本；新版本是整条流程（节点、出口、操作者）的**完整复制（另存）**，节点 ID 重新生成，由 `WorkflowVersion` 维护新旧节点映射（`D:\workproject\ecology\src\weaver\workflow\workflow\WorkflowVersion.java`）。

### 2.6 节点级字段权限（与本项目最相关）

ecology 的 Excel 设计器**天然是"按节点配置字段权限"的**——这正是本项目要补齐的核心能力。

**`workflow_nodeform`（节点级字段权限）**：`NODEID, FIELDID, ISVIEW, ISEDIT, ISMANDATORY, ISALONEROW, ISONLYSHOW`。
**权限编码 `fieldattr`（行为级结论，见 `ExcelLayoutManager` 保存逻辑）**：

| fieldattr | 语义 | 落库 isview / isedit / ismandatory |
|---|---|---|
| `0` | **不显示** | 空 / 空 / 空 |
| `1` | **只读** | 1 / 空 / 空 |
| `2` | **可编辑** | 1 / 1 / 空 |

## 2.7 审批数据库表深度剖析（DDL 级）

> **DDL 权威来源**：`D:\Weaver2020\ecology\data\ST\1table.sql`（E9 全库建表脚本，Oracle 语法，标识符带双引号）；
> **索引来源**：`D:\Weaver2020\ecology\data\ST\7index.sql`。
> 本节为第 2 章的字段级补充，用于指导第 5 章新表设计（文档中的 `wf_*` 表）与第 8 章存量迁移映射。

### 2.7.0 三条对新建表设计有直接影响的总体结论

1. **`1table.sql` 不创建任何主键 / 外键约束**。全文检索 `PRIMARY KEY`、`ADD CONSTRAINT` **命中 0 次**；各表的"主键"是**约定式主键**——由 `ID` 字段 + 同名 Oracle Sequence 生成（如 `CREATE SEQUENCE "WORKFLOW_BASE_ID"`，`1table.sql:928`）。唯一有索引层面唯一性保证的是 `workflow_requestbase.requestid`（`7index.sql` 中的 UNIQUE 索引 `WORKFLOW_REQUESTID`）。
   → **新建 `wf_*` 表必须显式定义主键与索引**，不能沿用 ecology 的"无约束"风格。
2. **大量表没有索引**。`workflow_nodegroup`、`workflow_groupdetail_matrix`、`workflow_hrmoperator`、`workflow_nodeformgroup`、`workflow_nodeform_form`、`workflow_requestbase_dellog`、`workflow_type`、`modeinfo`、`modeformgroup`、`modehtmllayout`、`rule_expressionbase`、`rule_expressions`、`rule_maplist`、`rule_mapitem`、`rule_variablebase` 在 `7index.sql` 中均无索引。
   → 迁移到 MySQL 后，待办查询等高频路径必须按 5.6 节补索引，否则性能不可控。
3. **Oracle → MySQL 类型映射**：`NUMBER(38,0)`→`BIGINT`、`CHAR(1)`→`TINYINT`/`CHAR(1)`（标志位）、`VARCHAR2(n)`→`VARCHAR(n)`、`CLOB`→`LONGTEXT`/`JSON`、`FLOAT`→`DECIMAL`/`DOUBLE`、`CHAR(10)` 日期 + `CHAR(8)` 时间 → 合并为 `DATETIME`（ecology 把日期与时间拆成两列，新设计应合并）。

### 3.2 集成模型（核心设计决策）

> **决策 1：不另造一套审批表单模型。** 布局 JSON 已是「字段坐标 + 元数据 + 明细表子画布」的完整描述，审批态复用同一布局，只在**渲染层按节点权限降级**。
>
> **决策 2：权限定位锚点复用 `fieldDomId`。** 现有 `data-excelp-scope`（`main` / `dt{idx}_r{row}`）+ `data-excelp-field` 已能唯一定位「主表某字段」或「明细表 N 第 R 行某字段」，与节点权限矩阵的行键天然对齐，无需新增坐标体系。
>
> **决策 3：表单数据与布局解耦。** 布局引用（`form_id` + 快照 ID）+ 数据快照（`wf_form_snapshot`）分离，避免流程表被大 JSON 撑大。

```
┌─ 流程侧（新） ─────────────────┐        ┌─ 表单侧（已有） ─────────────┐
│ wf_process_definition          │        │ form_layout                  │
│ wf_process_node ── wf_node_operator   │  │  └─ layout_json（含 detailTables）│
│ wf_node_link                   │        │ workflow_billfield（字段定义） │
│ wf_node_field_perm ────────────┼───────▶│  scope=main|dt{idx}_r{row}    │
│ wf_instance / wf_task          │        │ formtable_main_{id}（业务数据）│
│ wf_approval_log                │        └───────────────────────────────┘
│ wf_form_snapshot（数据快照）    │
└────────────────────────────────┘
```

## 4. 流程引擎选型：Camunda 8 vs Flowable

### 4.1 事实核对（联网核实，2026-09）

| 事实 | Flowable | Camunda 8 |
|---|---|---|
| 开源许可 | **Apache License 2.0**（`github.com/flowable/flowable-engine` 明确 "Apache 2.0 licensed open source"；`flowable.com/open-source-code` 确认） | **非 Apache**。Self-Managed Free Edition **仅允许非生产使用**（开发/测试），生产需 Enterprise 许可；Web Modeler / Console 为**专有许可** |
| 运行基线 | 7.x：**JDK 17+ / Spring Boot 3.3+ / Spring 6 / jakarta.***；已移除表单引擎、内容引擎、Mule、JMS 与传统异步历史 | Zeebe（Java）+ Operate/Tasklist/Identity/Connectors；8.x 起提供 **Orchestration Cluster** 统一部署形态 |
| 存储 | 关系库（MySQL/PostgreSQL 等） | Zeebe 自身不依赖关系库；**Operate / Tasklist 依赖 Elasticsearch 或 OpenSearch** 作为后端数据存储 |
| 部署形态 | **嵌入式**（随 Spring Boot 启动）或独立服务 | **独立集群**（K8s 推荐；Zeebe broker + Gateway + ES/OS + Web Apps） |
| 建模 | 支持 BPMN 2.0；可用 bpmn-js / Flowable Modeler | Camunda Modeler（Desktop，免费；Web Modeler 专有） |
| 最新主版本 | 开源引擎 7.x（7.0/7.1）；官方产品线最新为 **2026.1** | 8.x（8.8 及后续，2025-10 文档在更新） |

> ⚠️ **许可提示（须法务确认）**：Camunda 8 自托管免费版仅限非生产；`bpmn-js` 采用 **bpmn.io License（非 OSI 许可）**，与 Apache-2.0 不同。若项目要求全链路 OSI 许可，需重新评估设计器选型（见第 7 章）。

### 4.2 多维度对比

| 维度 | Flowable 7（嵌入式） | Camunda 8（独立集群） | 权重说明 |
|---|---|---|---|
| **许可成本** | ✅ Apache-2.0，生产零许可费 | ⚠️ 生产需 Enterprise 许可 | 高 |
| **与当前技术栈匹配** | ⚠️ **勘误**：官方基线为 JDK 17 + Spring Boot 3.3；本项目实为 **Java 21 + Spring Boot 4.x**，**兼容性须 PoC 验证**（原判"完全契合"不成立） | ⚠️ 需引入 K8s、ES/OS、gRPC 等新组件 | 高 |
| **运维复杂度** | ✅ 与业务同进程，复用现有 MySQL/Redis/Nacos | ❌ 需独立运维 Zeebe 集群 + ES/OS + Web Apps | 高 |
| **承载 ecology 语义** | ✅ 自建语义层，会签/退回/转发/加签/催办/代理/自由流可自由建模 | ⚠️ 需映射到 BPMN 标准元素，部分 ecology 特有语义（自由流、加签）表达成本高 | 高 |
| **存量迁移成本** | ✅ 直接落关系表，bulk 导入与对账简单 | ⚠️ 需经 BPMN XML 中转 + 集群导入，链路长 | 高 |
| **水平扩展 / 高吞吐** | ⚠️ 受单库限制（可通过分库分表/异步执行器缓解） | ✅ Zeebe 原生分布式、高并发编排 | 中 |
| **可观测性** | ⚠️ 需自建（Actuator + Prometheus） | ✅ 原生 Operate/Tasklist 提供流程监控与运维界面 | 中 |
| **社区与国产落地** | ✅ 国内社区活跃、案例丰富 | ✅ 国际生态强，国内案例相对少 | 中 |
| **流程版本/热更新** | ✅ 天然支持多版本并存 | ✅ 支持 | 低 |

### 4.3 方案 A：嵌入式（推荐 · 首选落地）

**形态**：新增**独立微服务** `blade-service/blade-workflow` + 契约模块 `blade-service-api/blade-workflow-api`（放置论证见 **11.5 节**），内嵌流程引擎，复用现有 MySQL / Redis / Nacos。

```
blade-gateway
   └─ blade-service/blade-workflow        （Java 21 + Spring Boot 4.x，见下方版本勘误）
        ├─ 流程引擎（Flowable 7 或自研内核，见下方 Flowable 许可勘误）
        │    └─ ACT_* 运行时表（若用 Flowable）→ 独立库 blade_workflow
        ├─ 自建语义层表（wf_process_* / wf_node_* / wf_instance / wf_task / wf_approval_log）
        ├─ feign/ → IWorkflowClient 服务端实现（供 blade-formmode 发起流程）
        ├─ Feign → blade-formmode-api（反向读布局 / 字段定义 / 业务数据）
        └─ Redis（待办计数缓存）
blade-service-api/blade-workflow-api      （★ 先建：Entity / VO / DTO / IWorkflowClient + Fallback）
blade-service/blade-formmode（已有）
   └─ form_layout / workflow_billfield / formtable_main_*（业务数据）
   └─ 依赖 blade-workflow-api，通过 Feign 发起流程（替换现有 TODO 打日志）
```

> ⚠️ **版本勘误（重要）**：本文档初版按"Spring Boot 3.5.9 + JDK 17"编写，但**实际工程为 Java 21 + Spring Boot 4.x**——root `pom.xml` 中 `java.version=21`、`spring-boot-maven-plugin` 为 `4.1.0`、依赖 `dynamic-datasource-spring-boot4-starter`，`CLAUDE.md` §6.7 亦明确"由 Spring Boot 4 配置 `spring.threads.virtual.enabled`"。因此**所有涉及 Spring Boot 3.5.9 / JDK 17 的表述均需按 Boot 4 / Java 21 复核**（见第 10.2 节新增开放问题）。
>
> ⚠️ **Flowable 许可/版本勘误（重要）**：`springBlade/CLAUDE.md` §14.6 提到开源版"不要引用商业版特有能力（**Flowable**…）"，需**澄清其真实含义**——它约束的是**不要依赖 BladeX 商业版的 `blade-starter-flowable` 封装模块**（那是 BladeX 自己的商业产品，需授权），**并非**禁止使用 Flowable 引擎本身。Flowable 引擎（含 `flowable-spring-boot-starter-process` 等）以 **Apache License 2.0** 发布，**可合法商用、自行集成、零许可费**。因此"引入 Flowable"的实情是：①**自行引入 Flowable 开源依赖**（Apache-2.0，合法无碍；代价仅为自行写适配层接入 blade 的租户/数据权限/Feign，属**技术工作量而非法律风险**）②切换到 BladeX 商业版代码库以获得官方封装（需商务授权）③**自研轻量审批内核**（对齐 ecology 的"节点-出口"模型，见下方补充）。故第 8 项开放问题的性质是**技术选型**，而非合规审批。详见 10.2 节。

**优点**：改造成本最低、许可无风险、迁移链路最短、与现有栈完全对齐。
**代价**：吞吐量受单库约束；监控界面需自建。
**适用**：当前阶段（表单驱动、审批为主、并发量中等）**推荐**。

### 4.4 方案 B：独立集群（条件成熟时演进）

**形态**：K8s 部署 Camunda 8 Orchestration Cluster（Zeebe + Operate + Tasklist + Identity）+ Elasticsearch/OpenSearch；`blade-workflow` 退化为 **Camunda 适配层**，对上暴露与方案 A 相同的业务接口。

**优点**：原生水平扩展、原生流程监控与运维界面、适合大规模编排。
**代价**：
- 新增中间件（K8s、ES/OS、Zeebe 集群），运维成本高；
- **生产许可费用**（自托管免费版不可用于生产）；
- ecology 存量需经 BPMN XML 中转迁移；
- 自由流 / 加签等 ecology 特有语义需额外建模。

**适用**：并发量显著增长、需要跨系统编排（非单纯审批）、且已具备云原生运维能力与预算。

> **补充**：若坚持 Camunda 品牌但又要嵌入式形态，对应的是 **Camunda 7**（Apache-2.0、嵌入式），但其研发重心已转向 8，且需核实目标版本对 **Spring Boot 4.x / Java 21** 的支持（原写"Spring Boot 3.5 / JDK 17"已按实际技术栈勘误，列入开放问题）。

### 4.5 选型结论

> **推荐：方案 A（Flowable 7 嵌入式）作为一期落地；方案 B（Camunda 8 独立集群）作为演进预留。**

理由：
1. **许可确定性**：Apache-2.0 可商用，无 Camunda 8 生产许可风险。（⚠️ 前提：BladeX 开源版未内置 Flowable，需自行集成或切商业版——见 10.2 第 8 项）
2. **栈契合度**：⚠️ **勘误**——本项目实为 **Java 21 + Spring Boot 4.x**（非 JDK 17 + Boot 3），Flowable 7 官方基线为 JDK 17 + Boot 3.3，**兼容性必须 P1 PoC 验证**；PoC 不通过则转"自研轻量内核"。
3. **迁移友好**：存量解析后直接落关系表，比对/回滚简单，契合"需迁移在途数据"的硬要求。
4. **语义契合（若选自研内核）**：可直接沿用 ecology 的"节点-出口 + 操作者 + 出口条件"模型，**无 BPMN 映射损耗**，与本项目表单域"复刻 ecology 命名与模型"的整体思路一致。

> ⚠️ **结论前置条件**：上述推荐成立的**前提**是"引擎路线已拍板 且 Boot 4 兼容性 PoC 通过"。在 **10.2 第 8 项**（自研轻量内核 / 自行集成 Flowable / 切换商业版）拍板前，**第 4 章选型结论视为待定**。
4. **语义可控**：ecology 的会签/或签/依次、退回/撤回/转发/加签/催办/代理/自由流属**国产 OA 特有语义**，自建语义层比硬套 BPMN 更可控。

**保留演进位**：自建语义层与引擎解耦（`wf_*` 表不依赖 Flowable 内部表），二期可将引擎替换为 Camunda 8 而业务接口不变。

## 5. 数据模型设计（表结构）

> **表名前缀以第 11.2 节第 3 项结论为准**：本文档按 `wf_*` 编写；若团队决定沿用 ecology 命名（`workflow_base` 等），需同步替换全部表名并评估与 ecology 源库同实例时的撞表风险。

设计原则（遵循 MySQL/InnoDB 最佳实践）：
- 主键 `BIGINT UNSIGNED AUTO_INCREMENT`（窄、单调）；业务唯一键放**二级唯一索引**，不用随机 UUID 做聚簇主键。
- 统一 `utf8mb4` / `utf8mb4_0900_ai_ci`；时间用 `DATETIME`（非 `TIMESTAMP`）；尽量 `NOT NULL`。
- 复合索引遵循**最左前缀**：等值列在前，范围/排序列在后。
- 大 JSON（布局快照、表单数据）独立成表或独立列，避免撑大主表热点行。
- 日志类大表（`wf_approval_log`）预留**分区**能力（按月 RANGE，含 `MAXVALUE` 兜底）。

### 5.6 索引与性能要点

| 关注点 | 措施 |
|---|---|
| 待办列表高频 | `wf_task(assignee, status)` 复合索引（等值在前）；待办**计数**走 Redis，任务状态变更时失效 |
| 实例查询 | `wf_instance.biz_key` 唯一索引，支持按业务数据反查流程 |
| 日志膨胀 | `wf_approval_log` 按月分区 + 历史归档；**分区列须纳入 PK**，并设 `MAXVALUE` 兜底分区 |
| 大 JSON | 布局与表单数据快照独立表/独立列，不与流程主表同表，避免热点行膨胀 |
| 并发审批 | Flowable 侧开启**异步执行器**；审批动作加幂等控制（同一 task 重复提交拦截） |
| 死锁 | 统一按 `inst_id → task_id` 顺序加锁；重试错误 1213 并退避 |

## 6. 接口清单

> 统一前缀 `/api/blade-workflow`，经 `blade-gateway` 路由。所有接口需携带 `x-correlation-id` 便于链路追踪。

> **Cloud 版路由约定（`CLAUDE.md` §6.3）**：后端 Controller **直接用资源路径**（如 `@RequestMapping("/definition")`、`@RequestMapping("/instance")`），网关按服务名路由，**不带** `AppConstant` 前缀（这是与 Boot 版的区别点）。上表 `/api/blade-workflow/...` 为**前端/网关侧**访问路径，与现有 formmode（前端 `/api/blade-formmode/form-layout` ↔ 后端 `@RequestMapping("/form-layout")`）一致。

## 8. ecology 存量流程迁移方案

### 8.1 迁移范围

| 类别 | 源 | 目标 |
|---|---|---|
| 流程定义 | `workflow_base` | `wf_process_definition` |
| 节点 | `workflow_flownode` / `workflow_nodebase` | `wf_process_node` |
| 操作者 | `workflow_nodegroup` / `workflow_groupdetail` | `wf_node_operator` |
| 出口 | `workflow_nodelink` | `wf_node_link` |
| 节点字段权限 | `workflow_nodeform` | `wf_node_field_perm` |
| 明细权限 | `workflow_nodeformgroup` | `wf_node_detail_perm` |
| 在途实例 | `workflow_requestbase` | `wf_instance` |
| 当前操作人员 | `workflow_currentoperator` | `wf_task` |
| 流转日志 | `workflow_requestlog` | `wf_approval_log` |
| 表单数据 | `formtable_main_<N>[_dt<K>]` / `uf_<xxx>[_dt<K>]` / `workflow_form` | 对应新 `formtable_main_{billId}[_dtN]` + `wf_form_snapshot` |
| 布局 | `workflow_nodehtmllayout.DATAJSON` / `modehtmllayout` | `form_layout.layout_json` |

### 8.2 迁移步骤

1. **抽取（只读）**：直连 ecology 库（或从 `1table.sql` 结构 + 数据导出），按上表抽取定义与在途数据到中间库，**不修改源库**。
2. **语义转换**：
   - `nodetype` → 节点类型；`signorder` → 审批方式；`nodeattribute`+`passnum` → 合并策略（映射为 BPMN 网关 + 扩展属性）；
   - 操作者 `type`/`objid`/`level_n`/`bhxj` → 新操作者规则（**表单字段类操作者需按新表单字段重新绑定**）；
   - 出口 `condition`/`newrule` → 条件表达式（⚠️ 老规则引擎表达式需人工/半自动转换，见风险）。
3. **生成 BPMN**：由转换结果生成 BPMN 2.0 XML → 部署到引擎；同时写 `wf_*` 业务语义表。
4. **在途接管**：
   - 在途 `requestbase` 生成 `wf_instance`（`status` 由 `currentstatus` + 当前节点推算）；
   - `workflow_currentoperator` 生成 `wf_task`（`isremark` → `status`）；
   - **旧 `requestid` 冗余存入 `wf_migration_map`**，支持双轨期间反查与回滚。
5. **双轨校验**：新旧系统并行跑一批真实流程，按「实例数、当前节点、处理人、日志条数、表单字段值」五项对账，差异清单逐条人工确认。
6. **切换与回滚**：切换窗口内停写旧系统；回滚依赖 `wf_migration_map` 与数据快照（旧系统数据保留只读 ≥ 1 个结算周期）。

### 8.3 迁移对账指标

| 指标 | 校验方式 |
|---|---|
| 流程定义数 | `count(workflow_base)` vs `count(wf_process_definition)` |
| 节点/出口数 | 按 `workflowid` 分组比对 |
| 在途实例数 | `count(requestbase where 未归档)` vs `count(wf_instance where status=0)` |
| 当前待办人 | 按 `requestid` 比对 `currentoperator` 与 `wf_task` 的 `assignee` 集合 |
| 日志条数 | 按 `requestid` 比对 `requestlog` 与 `wf_approval_log` |
| 表单字段值 | 抽样比对主表 + 明细表每条记录的字段值 |

### 11.5 `blade-workflow` 放置方案论证（基于 springBlade 项目结构梳理）

> 本节回答：**流程能力应该作为独立微服务，还是直接放进 `blade-service/blade-formmode`？** 结论基于 `springBlade/CLAUDE.md`（项目权威规范）与实际目录/pom 核验。

#### 11.5.1 springBlade 真实项目结构


**分层约定（`CLAUDE.md` §2.1 / §2.2，强制）**：

| 层次 | 所在模块 |
|---|---|
| Controller / ServiceImpl / Mapper / Wrapper / Excel | **Service 模块**（`blade-service/*`） |
| `feign/`（Feign 的**服务端实现**，`@RestController` 实现接口） | Service 模块 |
| Entity / VO / DTO | **API 模块**（`blade-*-api`） |
| `feign/`（Feign **Client + Fallback**） | **API 模块** |

关键约束：
- 跨服务调用**必须**经由 `blade-*-api` + Feign，**禁止** `blade-service/A` 直接依赖 `blade-service/B`（§2.2、§4.2）；
- **新增业务域时，先建 API 模块再建 Service 模块**（§14.2）；
- 标准样板：`blade-system` + `blade-system-api`（最完整）、`blade-desk` + `blade-desk-api`（最简）；
- 已验证：`blade-formmode/pom.xml` 依赖 `blade-formmode-api`（符合上述约定）。

#### 11.5.2 两种放置方案对比

| 维度 | 方案 A：独立微服务（**`blade-service/blade-workflow` + `blade-service-api/blade-workflow-api`**） | 方案 B：内嵌 `blade-formmode`（新增 `workflow` 子包） |
|---|---|---|
| **是否符合项目规范** | ✅ 完全符合（§2.2 新增业务域先建 API；跨服务走 Feign） | ❌ 违反：同进程却保留 Feign 契约自相矛盾；业务域未独立建模 |
| **限界上下文** | ✅ 流程域（定义/节点/实例/任务/待办/流转日志/迁移映射）边界清晰 | ⚠️ 与表单域（布局/字段/业务数据）混在一个模块 |
| **与已有 Feign 契约一致性** | ✅ `IWorkflowClient` 正是"跨服务调用"的语义，独立服务才说得通 | ❌ 同进程无需 Feign，需删除契约或改本地调用，改动面反而更大 |
| **数据库隔离** | ✅ 可独立库 `blade_workflow`，符合 database-per-service | ⚠️ 与 formmode 共用库，流程表与表单表混杂 |
| **依赖隔离** | ✅ 流程引擎（Flowable / 自研内核）只影响本服务 | ❌ 引擎依赖（较重）进入 formmode，影响表单服务启动与打包 |
| **独立扩缩容 / 替换引擎** | ✅ 可按审批负载单独扩容；引擎可替换（第 4.5 演进位） | ❌ 与表单服务绑定 |
| **跨服务成本** | ⚠️ formmode ↔ workflow **双向**调用；"存数据+发起流程"跨服务需 Seata `@GlobalTransactional`（项目已支持） | ✅ 本地调用、本地事务，无网络与一致性成本 |
| **节点字段权限读取成本** | ⚠️ workflow 渲染审批态需读布局/字段/权限 → 经 Feign 或**布局快照**（3.6 已设计）解耦 | ✅ 同库直读最省事 |
| **运维成本** | ⚠️ 多一个服务：Nacos 配置 + 端口 + 容器 | ✅ 零新增 |

#### 11.5.3 结论

> **采用方案 A：独立微服务。**
> `blade-service-api/blade-workflow-api`（契约）+ `blade-service/blade-workflow`（实现），**不要**放进 `blade-formmode`。

决定性理由（按权重）：
1. **项目规范强制**：`CLAUDE.md` §14.2 明确"新增业务域先建 API 模块再建 Service 模块"，§2.2 禁止 Service 间直接依赖。放 formmode 内属于新增业务域却不分模块，评审不会通过。
2. **已有契约已假定独立服务**：`IWorkflowClient` 用 `@FeignClient` 声明，语义上就是跨服务调用。
3. **流程是独立限界上下文**：且它还要承载流程设计器、待办中心、流程监控、ecology 迁移——这些都不属于表单域。
4. **耦合点已有解法**：表单与流程的高频耦合（节点字段权限需读布局/字段定义）由 3.6 节的**布局快照 + 审批态渲染包接口**（`GET /form/render`）解耦，不必靠同进程。

> **补充**：若团队短期人力/运维极受限，可采用折中——**先建独立服务，但数据库与 formmode 共用同一 MySQL 实例**（独立 schema 与 `wf_`/`blade_wf_` 前缀表），运维成本与内嵌几乎相同，后续再按需拆库。**不建议**直接内嵌。
