# 归档管理 / 撤回管理 配置设计说明

> 目的：在流程设计页新增「归档管理」「撤回管理」两项配置（每条流程单独设置），流程监控端据此按节点决定归档与撤回相关操作的显隐与执行。
>
> 设计原则：**对齐泛微 E9（参考 `D:\Weaver2020\ecology` 与 `D:\workproject\ecology`）的真实分层**，而非凭空设计。

## 二、字段结构与存储分层（本系统落点）

> 关键结论：`wf_process_definition` 是**真实静态定义表**（`@TableName("wf_process_definition")`，专属 `WfProcessDefinitionMapper`，原生 `SELECT * FROM wf_process_definition`），对标 ecology `workflow_base`，可直接加列。
> 项目里的 "flowtable / `formtable_main_*`" 是**实例级表单业务数据表**（由 formmode 动态生成，每实例一行字段值），与定义表是两层，不冲突、不影响加列。

### 1. 归档管理（流程级 → `wf_process_definition`）
新增列（建议两列布尔，或合并为 `archive_manage` JSON 串）：

```json
{
  "allowForceRecallWhenArchived": true,   // 归档可强制收回  ← isoverrb
  "allowInterveneWhenArchived": true      // 归档可干预      ← isoveriv
}
```
- 列名建议：`is_over_recall`、`is_over_intervene`（或 `archive_manage` TEXT）。
- 直接对标 `workflow_base.isoverrb / isoveriv` 的同表同层级。

### 2. 撤回管理（分两层）
**A. 流程级开关 → `wf_process_definition` 新增列**
```json
{
  "allowFrontendRemindChoice": true       // 允许前端用户选择是否提醒  ← isrejectremind / ischangrejectnode
}
```
（若需"退回时是否可选择退回节点"，再加一列 `is_select_reject_node` ← `isselectrejectnode`。）

**B. 节点级项 → BPMN 节点 `extJson`（存于 `wf_process_definition.bpmnXml` 的 `wf:node` 扩展）**
复用本系统**已有**的节点级机制，不另起流程级列：
- `允许被撤回的节点（全部/指定）` + `排除选择` → 已有 `extJson.settings.reject.nodeKeys`（退回目标白名单），扩展"全部/指定/排除"模式。
- `启用节点前附加操作` → 已有 `extJson.settings.preOperate`（节点前附加操作）。
- `能够撤回流程的节点操作者` → 节点级"谁可撤回"权限，落地到该节点 `extJson.settings`（新增 `allowDrawback` / 操作者白名单）。

> 即：撤回管理的"节点级子项"本质是**每节点**配置（E9 在 `workflow_flownode` 每行），本系统天然应落在 BPMN 节点扩展，归属「流转设置 → 节点信息」面板，而非流程定义表。

## 五、设计决策（已定，2026-11-03）

> 原"待确认事项"三项均已拍板，按以下规格实现。字段命名以本节为准：第四节监控显隐所用的 `archive_manage.allowForceRecallWhenArchived` / `allowInterveneWhenArchived` 统一改回 `recallFromArchiveEnabled` / `interveneFromArchiveEnabled`（与第七节、第八节一致）。

1. **撤回管理的分层 → 采用方案 A（贴合 E9，节点级落 BPMN）**
   - 节点级项（允许被撤回的节点 / 排除选择 / 谁可撤回 / 节点前附加操作）落 **BPMN 节点 `extJson`**，复用现有：
     - `extJson.settings.reject.nodeKeys`（退回/被撤回目标白名单，对应"允许被撤回的节点 + 排除选择"）；
     - `extJson.settings.preOperate`（节点前附加操作）。
   - 流程级"提醒选择"开关（`isrejectremind` 同款，含"是否允许前端选择提醒节点"）进 **`wf_process_definition.recall_manage`** JSON 列。
   - 前端统一在「撤回管理」页签配置，保存时分写两处（节点级 → `saveBpmn`；流程级 → `updateDefinition`），底层存储仍按 E9 分层。
   - 不采用方案 B（压平流程级 JSON），以免监控"按节点决定能否收回/回退"变粗、偏离 E9 语义。

2. **"流程干预"语义 → 分阶段，第一阶段取 A**
   - **A（第一阶段，本次实现）**：复用现有"回退到已办/创建节点"语义（退回去）。即 `monitorRejectTo` 现有能力 + 放开归档态拦截（见第八节"复活"方案），满足"归档后可干预/回退"基本诉求。
   - **B（第二阶段，单独排期）**：E9 同款"任意节点重路由 + 改操作者"。需新增"指定操作者"引擎能力与前端节点重选 UI，工作量大，不纳入本次；仅在 `interveneFromArchiveEnabled` 开启且目标为任意节点时预留扩展点。

3. **开关粒度 → 按流程（行级 JSON），不做全局一把闸**
   - 归档管理 `archive_manage` 与撤回管理 `recall_manage` 均为 **`wf_process_definition` 行级 JSON 列**，按每条流程单独设置（已实现路径：`updateById` 自动落库）。
   - 全局 Nacos 一把闸**本次不做**（如后续确需"全租户统一策略"，再按需补充，不影响当前按流程粒度）。
   - 监控端按 `defId` 读取并缓存策略，逐实例裁决显隐与后端强制校验。

## 六、一句话总结
- 归档管理 = 流程级两开关，落 `wf_process_definition`，对标 `workflow_base.isoverrb/isoveriv`。
- 撤回管理 = 流程级"提醒选择"开关（落 `wf_process_definition`）+ 节点级退回配置（落 BPMN 节点 `extJson`，复用现有 `reject.nodeKeys` / `preOperate`）。

## 七、归档流程在 flowtable 回退的可行性（已核查 formmode，2026-11-03）

### 结论
**flowtable 业务行在归档态不存在锁定，归档流程回退后重新编辑保存完全可行；formmode 侧不构成障碍。**

### 核查证据
1. **`IFormmodeClient` 无归档/锁接口**：写接口仅 `saveFormData` / `saveBusinessData` / `deleteBusinessData`，不存在 `archive` / `lock` / `unlock` / `setStatus`（`IFormmodeClient.java:36-112`）。
2. **`saveBusinessData` 不写任何 workflow 状态列**：`FormDataServiceImpl.saveBusinessData`（`:827-954`）只写三类——① 业务字段值（按列名匹配，不存在的列忽略）；② `request_id`（仅用于"单据↔流程"双向反查，`:912-920`）；③ 审计列（`modedatacreator/modifydate/lastMod*`）。`isSystemField`（`:1086-1094`）排除项也仅为 `id/requestId/modedata*/lastMod*`，**无 status/locked/archived 列**。
3. **workflow 归档不通知 formmode**：`forceArchive` → `terminate`（`WfInstanceServiceImpl.java:2021-2030`）只改 `wf_instance` 状态 + 结束 Flowable 引擎，**从不调用 formmode** 标记业务行归档。

### 回退时 flowtable 的实际行为
- 归档实例被收回/回退后，用户重新编辑表单 → 仍走 `saveBusinessData(dataId)` → **直接 `UPDATE` 同一行**（`:945-949`），无锁可挡，不产生孤儿行/多行。
- 渲染端不读 flowtable，读本地 `wf_form_snapshot`（`WfFormRenderServiceImpl.java:207-211`），重编辑会 `upsertSnapshot`（`:361-366`）保持显示一致。
- 副作用：因业务行无"冻结"标记，理论上任何人直调 `saveBusinessData` 都能改归档数据——对"回退"是利好（无需解锁）；访问管控由 workflow 侧负责，不由 formmode。

### 真正剩下的硬骨头（与 flowtable 无关）
1. **引擎侧"复活运行态"（核心）**：归档 = Flowable 流程已结束、`forceRecallTo` 硬拒 `status != RUNNING/SUSPENDED`（`WfInstanceServiceImpl.java:2090-2092`）且依赖活的 `engineInstId`；回退归档实例必须新建/激活 execution 到目标节点。
2. **新鲜度守卫 + 快照一致性（小修）**：`WfFormRenderServiceImpl` 保存守卫（`:323-334`）含"已归档后拒绝保存"，引入"归档→收回"翻转后要保持判定一致。

## 八、`forceRecallTo` 对归档态（status=1）的改造方案（2026-11-03）

### 一、现状约束（已核实的代码事实）
- **归档 = 运行态被删**：`forceArchive` → `WfWriteHelper.terminate` → `processService.deleteProcessInstance(inst.getEngineInstId())`（`WfWriteHelper.java:145`），`wf_instance.status=1`，但 `engineInstId` 仍指向**已删除**的运行态。
- **`forceRecallTo` 现状**：`:2090-2092` 硬拒 `status != RUNNING/SUSPENDED`；其回退核心是 `processService.moveActivity`（依赖**活**的 `processInstanceId`，`ProcessServiceImpl.java:284-298`），归档态无活运行态，**无法原地回退**。
- **同步入口现成**：`advance` 按 `inst.engineInstId` 从引擎读当前任务同步 `wf_task`（`WfInstanceServiceImpl.java:2708`），只要把 `engineInstId` 重定向到新运行态即可复用。
- **历史镜像无冲突**：`WfInstanceActWriter.writeOnStart` 按 `engineInstId` 写 ACT_HI_PROCINST（`:90`），新运行态=新行，旧归档行（APPROVED+END_TIME）保留审计。

### 二、核心思路
归档实例无法"原地回退"，只能**以新运行态在目标节点重启**：用 Flowable `startAtActivityId` 从目标节点（默认创建节点）启动一个全新运行态，并把 `wf_instance.engineInstId` 重定向到它、`status` 置 RUNNING。E9 语义即"同一 request（wf_instance.id 不变）状态翻回运行，归档历史保留审计"。

### 三、改造步骤
1. **入口策略校验（改 `forceRecallTo` 开头 `:2090`）**
   ```java
   boolean archived = inst.getStatus() == WfInstance.STATUS_APPROVED;
   if (!archived && inst.getStatus() != RUNNING && inst.getStatus() != SUSPENDED)
       throw new ServiceException("仅运行中或暂停中的实例可强制收回");
   if (archived) {
       WfProcessDefinition def = defMapper.selectById(inst.getDefId());
       if (!archiveManageEnabled(def, "recallFromArchiveEnabled"))
           throw new ServiceException("该流程未开启归档后可强制收回");
   }
   ```
   其余状态（撤销/草稿）仍拒。
2. **分支**：RUNNING/SUSPENDED 走原路径（关当前待办 `:2121-2131` → moveActivity `:2148` → advance `:2151`）；APPROVED 走**复活**分支（不关待办、不 moveActivity）。
3. **新增 `reviveArchivedAt(inst, target, starter)`**
   - `procDefId = inst.getProcDefId()`（跑过的版本；null 回退 `processService.latestProcDefId(procKey)`）。
   - `injectMiCollectionVars(defId, inst, vars, starter)`（复用 `:2139`，保证 MI 节点展开正确）。
   - 调新增 `processService.startInstanceAtActivity(procDefId, inst.getBizKey(), target, vars)`。
     > ⚠️ 实现口径修正（详见第十节）：Flowable 8.x 的 `ProcessInstanceBuilder` **没有** `startAtActivityId`
     > （只有 `startEventId`，仅能指定开始事件），实际实现为「**正常发起 → 用
     > `createChangeActivityStateBuilder().moveActivityIdTo()` 把 token 移到目标节点**」两步。
   - `inst.setEngineInstId(pi.getId()); setStatus(RUNNING); setEndTime(null); setProcDefId(procDefId); setCurrentNodeKey(target); updateById`。
   - `actWriter.writeOnStart(inst, pi.getId(), RUNNING)`（默认关，无副作用）。
4. **共同收尾**：`recordLog(... "[强制收回]" ...)`（归档也记一条）+ `advance(instId, starter, null, null, REJECT)`（从新 engineInstId 同步目标节点待办到 `wf_task`）。
5. **`monitorRejectTo` 同理**：加 `interveneFromArchiveEnabled` 校验 + 同样的 revive 分支（复用 `reviveArchivedAt`，target 来自入参，src=REJECT，可带 `runPreOperate`）。

### 四、衔接风险与注意点
- **`startAtActivityId` 跳过上游**：不执行上游网关节点/执行监听器。目标默认创建节点（UserTask）安全；若指定中间带上游条件/监听器的节点需评估。
- **变量重建**：归档期间非持久化的运行时变量，新运行态从 `inst`/`vars` 重建，`injectMiCollectionVars` 已覆盖 MI；其余业务变量按需从快照/`wf_approval_log` 恢复（E9 重开同样重算）。
- **`resolveCurrentNodeKey` 对归档返回 null**（`WfInstanceServiceImpl.java:2574` 读未办待办）：归档分支不依赖它，已隔离。
- **新鲜度守卫**：`WfFormRenderServiceImpl` 保存守卫（`:323-334`）"已归档后拒绝保存"——收回后 status 翻回 RUNNING 自然放行，但需确认守卫判定与翻转一致（已记入第七节小修）。
- **并发**：revive 在 `@Transactional` 内；第二次并发收回会因 status 已 RUNNING 走原分支（对新 engineInstId 做 moveActivity），不会双开。归档分支根本不调 moveActivity，已隔离。
- **ACT_HI 双写**：新运行态新行、旧归档行保留；read-source=act 时按 businessKey/请求聚合，新旧同属一个 request，符合 E9"同一请求重开"语义。

### 五、最小新增
- `IProcessService.startInstanceAtActivity(procDefId, bizKey, activityId, vars)` + `ProcessServiceImpl` 实现（约 10 行）。
- 读取 `archiveManage` JSON 的 `recallFromArchiveEnabled` / `interveneFromArchiveEnabled` 的小解析器。

> ⚠️ **实现口径统一（详见第十节）**：除 `startAtActivityId` 不可用（改为「正常发起 + 状态变更跳转」）外，
> 另统一了「**未配置 = 保持既有行为**」的默认值口径：既有能力（强制归档 / 强制收回 / 监控回退）缺省开启、

## 九、设计配置 → 监控跟随的数据链路（已确认，2026-11-03）

- 后端已有读取入口：`GET /wf/definition/{id}` → `R<WfProcessDefinition> detail`（`WfDefinitionController.java:209-214`），**直接返回实体**，新列加进去后自动随实体暴露，无需改 DTO/VO。

### 二、与原设计的偏差（重要，已落地）

1. **Flowable 8.x 无 `startAtActivityId`**：`ProcessInstanceBuilder` 只提供 `startEventId`（仅能指定开始事件），
   无法"从任意节点启动"。故 `startInstanceAtActivity` 改为**两步**：
   ① 正常发起新实例（token 落在首个等待节点）→ ② 用 `createChangeActivityStateBuilder().moveActivityIdTo()`
   把 token 移到目标节点。收益：走的是与「强制收回」完全同源的引擎跳转机制，目标节点任务由引擎正常创建
   （监听器照常触发 → 操作者照常解析）。边界：第 ② 步是状态变更跳转，中间节点的条件与监听器不执行。
2. **统一为「未配置 = 保持既有行为」口径**（原设计只区分"开/关"）：
   - **既有能力**（允许强制归档 / 允许强制收回 / 允许监控回退）：缺省**开启**，仅显式 `false` 才关闭
     → 存量流程**零行为变更**；
   - **全新能力**（归档后允许强制收回 / 归档后允许流程干预）：缺省**关闭**，必须显式开启。
   后端 `WfArchiveRecallPolicy` 与前端 `resolveArchiveRecall` 完全同口径。
3. **落点范围 `specified` 需要指定清单**：新增 `recall_manage.recallTargetNodeKeys`（nodeKey 列表），
   设计面板在范围=指定清单时展示多选；后端 `forceRecallTo` 强校验落点范围。

### 缺陷 3：归档实例的回退候选接口 400「无法确定当前节点」（UI 联调发现，已修复复验）

**现象**：流程设计开启「归档后允许流程干预」后，监控端对归档实例点「回退 / 强制收回」，弹窗报
「流程无法确定当前节点，无法回退」。

**根因**：前端弹窗先调 `GET monitor/instances/{id}/rejectable-nodes`，而 `monitorRejectableNodes`
对**所有**实例都要求 `current_node_key` 非空——已办结实例该字段为**空串**（办结时清空）→ 接口 400，
弹窗根本打不开。`monitorRejectTo` 的归档分支本身不需要当前节点（复活路径），是被这个前置候选接口卡死的；
「强制收回」共用同一候选接口，同样被卡。

**修复**（`WfInstanceServiceImpl#monitorRejectableNodes` + 新增 `archivedCandidates`）：
归档实例（status=APPROVED）不再要求当前节点，候选直接取 wf_task 台账（DONE）真实走过的节点
**∪ 创建节点**（与 `monitorRejectTo` 归档硬校验「已办理过 ∪ 创建节点」同口径），按最近一次办理由近及远排序，
并按 `requireRecallTargetNode` 同口径剔除引擎停不住的类型（3/5/6/7，未配置放行），保证弹窗里选得到的
项回退时一定能通过硬校验。

**复验**（沿用户正在测的 defId=2117206127369306114 综合费用报销流程，实例 2117206468097785857）：
候选接口 200 返回 10 个候选（出纳付款确认→…→申请填单，操作者正常解析）→ 回退到 `Task_Cashier` 200/True
→ 实例回运行态（新 engine 432501、`end_time=NULL`）、待办生成给出纳办理人、`fresh` 判定 stale=false 可继续办理 ✅。
模块全量回归 270/273（3 项失败为既有问题，与本次无关）。

1. **复活后 `end_time` 残留**：`reviveArchivedAt` 用 `updateById`，MP 默认 NOT_NULL 策略跳过 null 字段，
   `setEndTime(null)` 不落库。→ 改为显式 `LambdaUpdateWrapper` UPDATE（`WfInstanceServiceImpl`）。
   复验：第三次复活后 `end_time=NULL` ✅。
2. **`fresh()`/表单渲染读到旧归档行**：`ActInstanceConverter.queryByBusinessId` 用 `LIMIT 1` **无排序**，
   复活后同一 `BUSINESS_ID_` 在 `ACT_HI_PROCINST` 存在多条行（每次 revive 新建引擎运行态，旧行保留），

   → 改为 `ORDER BY END_TIME_ IS NULL DESC, START_TIME_ DESC LIMIT 1`（活跃行优先，其次最新归档行）。
