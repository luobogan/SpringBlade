## 0. 结论速览

| 问题 | 结论 |
|---|---|
| **节点操作者能否看到测试实例？** | ✅ **能，而且能办理**。测试待办 `assignee` 就是节点操作者本人，`待办/已办/角标/实例详情` 的查询**全部没有过滤 `is_test`** |
| 标记完善吗？ | ✅ **完善**：`wf_instance.is_test` / `wf_task.is_test` / 标题「【测试】」/ 不回填业务表 `request_id` 都已落地 |
| 过滤完善吗？ | ❌ **零过滤**——`is_test` 在全模块只出现在「写标记、副作用跳过、清理」三处，**没有任何一处用于查询过滤** |
| 引擎路由会串吗？ | ❌ 不会。测试实例绑定 `__test` 的 `processDefinitionId`，与正式定义物理隔离（**路由拦截天然满足**） |
| 漏洞在哪？ | **业务查询层**（实例/任务列表）+ **通知与超时驱动**（会主动给真人产生新任务/留痕） |
| 通知机制现状 | 提醒 = 写流转意见留痕（`WfTimeoutServiceImpl.java:212-241`）；但**超时扫描会扫到测试任务**（`WfTimeoutJob.java:46-51` 无 `is_test` 过滤）→ 可触发自动通过 / 转办给真人 / 催办留痕 |

## 2. 可见性漏洞逐条（V1–V9）

> 严重度：**S1**=生产用户可见并可操作（必须立即修）；**S2**=可见但影响可控；**S3**=数据/体验层面。

| # | 漏洞 | 严重度 | 证据 | 后果 |
|---|---|---|---|---|
| **V1** | **测试待办出现在节点操作者的「待办」列表** | **S1** | `WfTaskServiceImpl.java:572-584` 无过滤；测试任务 `assignee`=节点操作者（`:1166`） | 真实用户在待办里看到「【测试】xxx」，可点开办理；误办会推进测试实例 |
| **V2** | **顶栏待办红点把测试单算进去** | **S1** | `WfTaskServiceImpl.java:555-568` | 用户被红点误导去处理测试单 |
| **V3** | **节点操作者可打开测试实例详情并办理** | **S1** | `canView` = 发起人/参与人/管理员 → 有 `wf_task` 记录即为参与人；`detail()` `WfInstanceServiceImpl.java:509-512` 无过滤 | 不只是"看到"，是"可办" |
| **V4** | **我的请求里出现测试实例** | S2 | `WfInstanceServiceImpl.java:519` 只按 `starter` | 测试发起人（多为管理员）列表被污染 |
| **V5** | **超时扫描命中测试任务 → 给真人建任务/转办** | **S1** | `WfTimeoutJob.java:46-51` 无 `is_test` 过滤；`WfTimeoutServiceImpl.java:201` 超时转办 | ①干扰测试结果；②`assign` 会给**真人**创建任务 → 主动扩大可见面 |
| **V6** | **超时提醒/催办留痕落在测试实例上** | S2 | `WfTimeoutServiceImpl.java:212-241`（remind 写流转意见）；`WfTaskServiceImpl.urge` 写 `LOG_SUPERVISE` | 被提醒人收到与测试相关的留痕 |
| **V7** | **测试面板的非提交动作走生产接口** | **S1** | `FlowFormPanel.tsx:325-358`（退回/加签/转办/催办调 `rejectTask/addSignTask/forwardTask/urgeTask`） | 转办会**给真人新建任务**（同 V5 效果）；退回/加签改变测试实例状态 |
| **V8** | **测试面板打开即写生产「已查看」** | S2 | `FlowFormPanel.tsx:220-224` `markTaskViewed` | 污染生产 `wf_task.view_time` 与流程图「已查看」分组 |
| **V9** | **抄送/传阅任务进入「已办」列表** | S2 | `circulate` 建 `status=8` 任务；`done()` 含 `STATUS_CIRCULATE`（`WfTaskServiceImpl.java:109-113`） | 测试实例的抄送对象在自己的已办里看到测试单 |
| **V10** ⚠️ | **标记断层：加签/转办/抄送新建的任务没继承 `is_test`** | **S1** | `addSign` `WfTaskServiceImpl.java:458-481`（`added` 未 `setIsTest`）；`forward`（`:395-425`）、`circulate` 同样未设 | **比"没过滤"更严重**：这些任务是 `is_test=0`，即使将来所有查询都加了 `is_test=0` 过滤**也漏不掉** —— 会实打实出现在真人的生产待办里 |

**补充：引擎路由侧反而是安全的。** 测试实例绑定的是 `procKey + "__test"` 的 `processDefinitionId`（`WfDefinitionServiceImpl.java:330`），与正式定义物理隔离，**不会串到正式流程的路由/节点/在途实例上**。所以"路由拦截"这一项在引擎层已天然满足；**所有漏洞都集中在业务查询层与定时/通知驱动**。

## 3. 隔离设计要求（按三域 × 三类约束）

### 3.1 通用原则

1. **默认不可见**：生产查询**一律显式排除** `is_test=1`；测试态数据只经 `/test/**` 暴露（白名单式，而非黑名单式）。
2. **标记先行、过滤兜底**：`is_test` 必须随实例→任务→抄送/协办/转办**全链路继承**（现状已有，需覆盖到"转办/抄送新建的任务"）。
3. **VO 必须带标记**：`InstanceVO` / `WfTaskVO` 增加 `isTest`，前端才能在列表着色/分栏/禁用操作。
4. **驱动类任务（超时/定时）必须跳过测试**：扫描查询显式排除 `is_test=1`，而非"跑完再判断"。
5. **副作用与通知默认关闭**：测试态不触发任何对外动作（消息/短信/邮件/子流程/外部接口/转办建任务）。

### 3.2 三域要求矩阵

| 域 | 权限过滤 | 数据标记 | 路由 / 入口拦截 |
|---|---|---|---|
| **① 流程实例** | `mine()`、`detail()`、`getByBiz()`、`countByForm()` 全部加 `.eq(isTest, 0)`；`canView` 对 `is_test=1` 仅允许**管理员 + 测试发起人本人** | `wf_instance.is_test` + `test_deployment_id` + `test_proc_def_id`（方案 §3 新增）；标题「【测试】」保留 | `/formmode/test` 与统一入口 `mode=test` 为唯一入口；**`/workflow/**`、`/formmode/approval/**` 对 `is_test=1` 实例返回 404/403** |
| **② 任务列表** | `list()`（待办/已办）、`count()`（角标）加 `.eq(isTest, 0)`；抄送(8)/协办(7)/传阅(11) 一并排除 | `wf_task.is_test` 必须继承——**含 `forward`/`circulate`/`addSign` 新建的任务**（现状只有 `advance` 建任务时继承） | 测试待办只经 `GET /test/todo` 返回；生产 `GET /task/todo|done` 不返回测试任务 |
| **③ 通知机制** | 超时扫描（`WfTimeoutJob.java:46-51`）加 `.eq(isTest, 0)`；`remind`/`urge`/子流程提醒对 `is_test=1` **直接 return** | 通知留痕同样打 `is_test`（若保留，则只在测试实例内可见） | 测试态**不调用**任何外发通道（站内信/短信/邮件）；提醒降级为"仅写测试实例流转意见"或完全不写 |
| **④ 测试态动作**（防 V7/V8） | 测试面板的 退回/加签/转办/催办：要么走 `/test/**` 专用接口，要么**在测试态禁用** | — | `ApprovalPage`（生产办理页）对 `is_test=1` 任务拒绝打开；`markTaskViewed` 测试态跳过 |

### 3.3 具体约束（可直接写进代码评审清单）

| 编号 | 约束 | 落点 |
|---|---|---|
| C1 | 生产查询**默认加** `.eq(WfInstance::getIsTest, 0)` / `.eq(WfTask::getIsTest, 0)` | `WfInstanceServiceImpl.java:519/509/528/546`；`WfTaskServiceImpl.java:575/559-565` |
| **C2** ⚠️ | **`WfTask.is_test` 必须在所有新建路径继承**：普通待办(`WfInstanceServiceImpl.java:1166`) ✅、协办(`:1041`) ✅；**转办 `forward`(`WfTaskServiceImpl.java:395-425`)、抄送 `circulate`、加签 `addSign`(`:458-481`) 三处均未设置 → 必须补齐**。这是"标记断层"，不做的话后续任何 `is_test` 过滤都拦不住这三类任务 | `WfTaskServiceImpl` 三处 insert |
| C3 | `InstanceVO` / `WfTaskVO` 增加 `isTest` 字段 | api `vo` 包 |
| C4 | 超时扫描排除测试任务 | `WfTimeoutJob.java:46-51` |
| C5 | 提醒 / 催办 / 子流程提醒对测试态 return | `WfTimeoutServiceImpl.java:212`；`WfTaskServiceImpl.urge`；`WfSubflowServiceImpl.java:98-104` |
| C6 | 测试态禁用 退回/加签/转办/催办（或改走 `/test/**`） | `FlowFormPanel.tsx:325-358` |
| C7 | 测试态跳过 `markTaskViewed` | `FlowFormPanel.tsx:220-224` |
| C8 | 生产办理页拒绝打开 `is_test=1` 任务 | `ApprovalPage.tsx` / `WfFormRenderServiceImpl#render` 增加守卫 |
| C9 | 测试结束后**强制清理**并校验（巡检④=0、⑪=0） | `WfTestServiceImpl.java:730-757`；巡检脚本 |
| C10 | 清理补全 `wf_test_log` 与孤儿部署 | `WfTestServiceImpl.java:730-757`（现状未清） |

### 5.1 功能用例（必须全部通过）

### 5.2 数据巡检 SQL（可定时执行）

```sql
-- ⑪ 【关键】生产待办中的测试条目：期望恒为 0
SELECT COUNT(*) AS test_items_in_prod_todo
FROM blade_workflow.wf_task t
JOIN blade_workflow.wf_instance i ON i.id = t.inst_id
WHERE i.is_test = 1 AND t.is_deleted = 0;

-- ⑫ 测试任务未继承 is_test（标记断层）：期望恒为 0
SELECT COUNT(*) AS task_mark_missing
FROM blade_workflow.wf_task t
JOIN blade_workflow.wf_instance i ON i.id = t.inst_id
WHERE i.is_test = 1 AND (t.is_test IS NULL OR t.is_test = 0);

-- ⑬ 测试实例被超时/提醒驱动过（有非提交类留痕）：期望为 0（或可解释）
SELECT l.inst_id, l.log_type, l.operate_time
FROM blade_workflow.wf_approval_log l
JOIN blade_workflow.wf_instance i ON i.id = l.inst_id
WHERE i.is_test = 1 AND l.log_type IN ('s', 'h', '9');

-- ⑭ 未清理的测试实例 + 孤儿 __test 部署
SELECT id, def_id, title, test_deployment_id FROM blade_workflow.wf_instance
WHERE is_test = 1 AND is_deleted = 0;
SELECT pd.KEY_, pd.ID_, pd.VERSION_
FROM blade_workflow.ACT_RE_PROCDEF pd WHERE pd.KEY_ LIKE '%__test';

-- ⑮ 测试实例是否误写业务表（request_id 被回填）
SELECT id, data_id, request_id_bound FROM blade_workflow.wf_instance
WHERE is_test = 1 AND request_id_bound = 1;   -- 期望为 0
```

### 5.3 验收判据

- 全部用例通过；
- 巡检 ⑪⑫⑬⑮ 恒为 0，⑭ 在清理后为 0；
- **在"未清理"状态下执行一次 V-1/V-2**（模拟最坏情况）→ 仍需通过（说明过滤生效，而不依赖"记得清理"）。
