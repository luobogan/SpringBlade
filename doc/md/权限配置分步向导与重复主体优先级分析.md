# 权限配置分步向导与重复主体优先级分析

> 目标页面：`http://192.168.1.4:8000/formmode/formmanage`
>
> 本文只做方案设计与问题分析，不改代码。
>
> 讨论对象：
>
> - SpringBlade 当前权限配置流程
> - `D:\Weaver2020\ecology`
> - `E:\project\ecology\ecology`

---

## 一、结论摘要

### 1. 当前配置确实不合理

当前 SpringBlade 的“权限配置”是一个抽屉里的三个平铺 Tab：

```text
模块权限
字段权限
数据范围
```

存在一个统一“保存”按钮，所有配置一次性提交。

但它缺少一个核心概念：

```text
当前这一整套配置到底属于哪个授权对象类型、哪些授权对象
```

现在的情况是：

- 每个列表逐行选择 `objtype + objid`
- 字段权限“授权对象组”只看第一个主体的类型
- 菜单授权又单独维护在 `blade_menu_share`
- 三个 Tab 没有一个共同的“授权方案”归属
- 每个页签列表也没有统一的“当前授权对象类型”标识

所以用户看到的结果是：

```text
配置割裂、类型混乱、无法判断这一页配置是给谁的
```

### 2. 推荐改成“授权方案 + 三步向导”

新增顶层概念：

```text
授权方案 AuthScheme
```

最终口径：**一个授权方案 = 一个具体授权对象 + 该对象下的三类配置**。

授权对象类型：

```text
1 角色
2 部门
3 岗位
4 人员
5 分部
6 矩阵
7 全员
```

安全级别不作为授权对象类型，而是每个方案上的规则过滤条件：

```text
showlevel <= user.security_level <= showlevel2
```

如果用户一次选择多个对象：

```text
生成多个独立方案，逐对象配置；不在同一个方案里共享一份配置。
```

围绕每个方案做三步：

```text
第 0 步：选择授权对象类型 + 选择一个具体对象，并配置安全级别过滤
第 1 步：模块权限与菜单设置
第 2 步：字段权限设置
第 3 步：数据范围设置
```

所有步骤共享同一个方案，因此整套配置始终有清晰的归属。

### 3. 跨方案权限合并口径

Ecology 的处理原则是：

```text
授权对象类型是“身份维度”，不是“权限优先级”
```

同一个用户同时通过人员、部门、角色、分部、岗位、全员、矩阵命中多个方案时，采用：

```text
菜单：任一命中即可见
模块权限：权限码取并集
字段权限：同一字段取最大权限
数据范围：行范围 OR 合并，权限等级取最大
布局：命中多个布局时按 priority 取一个
```

注意：`priority` 只用于布局选择，不用于吞掉其它方案授予的权限。

### 4. 重复配置要禁止，跨方案重叠要合并

#### 同一方案同一对象重复

```text
同一表单存在两个有效“人员 lh”方案
```

这是脏数据，应：

```text
阻止创建
数据库加 tenant_id + mode_id + subject_type + subject_id 唯一约束
```

#### 不同类型重叠到同一人

```text
lh 本人被授权
lh 又在“财务部”部门里
lh 又属于“部门领导”角色
```

这是合法场景，允许命中多个方案，并按第 3 节规则合并权限。

## 三、推荐目标模型：授权方案 AuthScheme

### 3.1 核心概念

新增：

```text
mode_auth_scheme   授权方案主表
```

一个授权方案表示：

```text
某个表单下，针对一个具体授权对象的一整套权限配置
```

例如：

```text
方案名称：人员授权方案-lh
表单：01.2、差旅报销表单-old
授权对象类型：人员
授权对象：lh
```

如果用户选择多个对象：

```text
lh              → 一个方案
部门领导        → 一个方案
报销矩阵        → 一个方案
全员            → 一个方案
```

每个方案下再包含：

```text
模块权限
菜单设置
字段权限
数据范围
```

### 3.2 建议表结构

#### `mode_auth_scheme`

| 字段 | 说明 |
|---|---|
| `id` | 主键 |
| `tenant_id` | 租户 |
| `mode_id` | 模块ID；无 modeinfo 时用 formId |
| `form_id` | 表单ID，便于菜单/布局定位 |
| `scheme_name` | 方案名称 |
| `subject_type` | 1角色 2部门 3岗位 4人员 5分部 6矩阵 7全员 |
| `subject_id` | 具体对象ID；全员可为0 |
| `subject_name` | 名称快照 |
| `include_sub` | 部门/分部含子级 |
| `matrix_value_field` | 矩阵主体结果字段（subject_type=6 时使用） |
| `showlevel` | 安全级别下限（规则过滤条件） |
| `showlevel2` | 安全级别上限（规则过滤条件） |
| `priority` | 布局优先级，数值越小优先级越高 |
| `status` | 1正常 |
| `version` | 乐观锁版本 |
| `create_user/time` | 审计 |
| `update_user/time` | 审计 |

唯一键建议：

```text
tenant_id + mode_id + subject_type + subject_id
```

说明：

```text
不再需要 mode_auth_scheme_subject 子表。
安全级别不是 subject_type，而是每个方案上的过滤条件。
矩阵作为 subject_type=6 进入向导。
全员作为 subject_type=7，并可叠加 showlevel/showlevel2。
priority 只用于布局选择，不影响权限合并。
```

### 3.3 子表如何关联方案

给现有表增加：

```text
scheme_id
```

包括：

```text
moderightinfo.scheme_id
mode_field_auth_group.scheme_id
modedatasharerule.scheme_id
blade_menu_share.scheme_id
```

字段权限老的 `modefieldauthorize` 如果继续支持旧模式，也建议加：

```text
scheme_id
```

运行期先按用户解析命中的所有方案，再合并权限；只有布局选择使用 `priority`。

### 3.4 字段权限组不再允许混合主体类型

字段授权对象组 `mode_field_auth_group` 必须属于某个方案。

因为一个方案只有一个主体：

```text
字段组的主体就是 scheme 的 subject
```

不再出现：

```text
组里角色、部门、人员混选
```

字段组结构建议：

```text
mode_field_auth_group
  id
  scheme_id
  group_name
  group_key
```

主体表 `mode_field_auth_subject` 可以保留兼容，但新方案下：

```text
每个字段组只放一个主体，且等于 scheme.subject
```

或者不再使用 subject 子表，直接由 scheme 推导主体。

## 四、三步向导流程设计

### 4.1 第 0 步：选择授权对象类型

页面进入时先展示选择卡片：

```text
请选择本套授权配置的授权对象类型

角色 | 部门 | 岗位 | 人员 | 分部 | 矩阵 | 全员
```

选择类型后，授权对象选择器必须支持多选：

```text
人员：lh、zhangsan
角色：部门领导、文秘
部门：财务部、行政部
岗位：会计、出纳
分部：总部、华东分部
矩阵：报销矩阵A、报销矩阵B
全员：所有登录用户（固定单选项）
```

多选不是把多个对象塞进同一个方案，而是：

```text
每个对象生成一个独立方案；
所有方案共享当前向导里的模块权限、字段权限、数据范围草稿；
保存后每个方案可单独编辑；
每个方案重新生成独立 groupKey，避免共用 Univer 布局。
```

安全级别不在这里选为类型，而是在方案属性中配置：

```text
密级下限 showlevel
密级上限 showlevel2
```

选择后展示醒目横幅：

```text
当前授权方案：人员授权方案-lh
授权对象类型：人员
授权对象：lh
安全级别：不限 / 60~80
布局优先级：10
```

如果用户一次选多个对象：

```text
生成多个方案；每次只编辑一个方案；方案列表可返回切换。
```

之后所有步骤都在这个上下文中进行。

### 4.2 第 1 步：模块权限与菜单设置

包含当前分散在“模块权限 Tab”的内容：

```text
模块权限列表
菜单名称
菜单可见范围
角色级菜单显示名
```

变化点：

- 列表不再每行选择 `objtype`
- `objtype` 固定显示在上方面板
- 每行只维护当前方案对象的权限
- 菜单可见范围来自当前方案对象，而不是任意主体
- 全员方案可叠加安全级别过滤
- 矩阵方案需要菜单共享支持矩阵主体

菜单处理：

```text
从当前 scheme.subject 生成 blade_menu_share
列表菜单与 AAE 组件菜单一起授权
角色方案继续兼容写 blade_role_menu
```

### 4.3 第 2 步：字段权限设置

包含：

```text
授权对象组列表
配置字段弹窗
Univer设计入口
字段权限组 groupKey
```

变化点：

- 授权对象组属于当前 scheme
- 组内主体固定为当前方案对象
- 列表头部显示当前方案对象
- `groupKey` 仍作为 Univer 设计器 `nodeKey`
- 每组字段和布局保持独立

旧数据兼容：

```text
不做兼容；旧数据直接删除。
```

### 4.4 第 3 步：数据范围设置

包含：

```text
数据范围五档：
  全部可见
  本人可见
  所在机构可见
  所在机构及子级可见
  自定义（列 IN 数字列表 / 列 = 数字）

条件化授权
密级范围
```

变化点：

- 每行对象类型固定为当前方案类型
- 数据范围规则归属当前 scheme
- 矩阵作为 `subject_type=6` 进入统一向导
- 全员作为 `subject_type=7` 进入统一向导
- 安全级别仍作为方案过滤条件，不作为主体类型
- 自定义值域复用 `DataScopeValueResolver`
- 自定义值域允许 `${...}` 占位符，但解析后必须仍是受限数字语法
- 非法自定义值域导致整个方案保存失败
- 详细方案见：`SpringBlade/doc/md/数据范围五档值域与数据权限一致性方案.md`

在每个步骤顶部固定显示：

```text
当前授权对象类型：人员
授权对象：lh、张三
```

列表中：

- 可以隐藏每行的类型下拉
- 或显示只读 Tag

继续复用：

```text
AuthObjectTypeSelect
AuthObjectPicker
```

但在向导中：

```text
AuthObjectTypeSelect 只用于第 0 步
后续步骤只使用 AuthObjectPicker，并锁定 objtype
```

### 5.5 保存策略

推荐：


- 保持现有 `/right/all` 原子保存优势
- 避免每一步写一半导致数据不一致
- 避免版本号频繁推进

离开向导时提示：


## 七、旧数据处理与方案删除

### 7.1 旧数据直接删除，不迁移

用户确认：

```text
旧数据全部清除，直接删除，不做迁移。
```

因此不再保留：

```text
按 objtype 生成历史方案
混合类型字段组只读兼容
groupKey 保留兼容
旧 /right/all 数据兼容
```

删除范围：

```text
moderightinfo
modefieldauthorize
mode_field_auth_group
mode_field_auth_subject
modedatasharerule
form_layout 中旧字段组 node_key 对应的布局
当前 form 相关 blade_menu_share
当前 form 数据菜单相关 blade_role_menu / blade_role_menu_name
```

不要删除：

```text
workflow_bill
workflow_billfield
业务数据表
审计日志
```

建议在删除前导出一次 SQL/JSON 备份；方案语义上不迁移、不回退。

### 7.2 方案删除必须级联

用户确认：

```text
方案删除时级联删除菜单共享和字段组布局
```

删除范围：

```text
mode_auth_scheme 当前方案
moderightinfo.scheme_id = 当前方案
mode_field_auth_group.scheme_id = 当前方案
mode_field_auth_subject（按字段组ID级联）
modefieldauthorize.group_id（按字段组ID级联）
modedatasharerule.scheme_id = 当前方案
blade_menu_share.scheme_id = 当前方案
blade_role_menu / blade_role_menu_name 中该方案生成的记录
form_layout 中 node_key = 当前方案字段组 group_key 的布局
```

## 八、重复与重叠授权分析

### 8.1 先区分两个概念

#### 重复

```text
同一类型 + 同一对象 + 同类规则被配置多次
```

例如：

```text
人员 lh 的查看权限配置两条
```

这是配置冗余/脏数据。

#### 重叠

```text
同一自然人通过不同主体类型命中多条规则
```

例如：

```text
lh 本人命中
lh 所在部门命中
lh 所属角色命中
```

这是合法业务场景。

## 十、推荐的最终规则

### 10.1 总则

```text
授权对象类型不是权限优先级。
对象是身份维度。
权限默认按授权合并，不按方案覆盖。
priority 只用于布局选择。
```

### 10.2 跨方案命中

```text
先解析当前用户命中的所有方案
菜单 / 模块权限 / 字段权限 / 数据范围按规则合并
布局命中多个候选时按 priority 升序取一个
```

### 10.3 菜单

```text
任一命中方案授权菜单 → 菜单可见
```

### 10.4 模块权限

```text
所有命中方案的 righttype 取并集
```

### 10.5 字段权限

```text
所有命中方案中，同一字段取最大 rightvalue
```

### 10.6 数据范围

```text
先按范围类型计算行集合，再按权限等级合并；不能直接对 scope_type 取 max。
```

五档：

```text
1 全部可见
2 本人可见
3 所在机构可见
4 所在机构及子级可见
5 自定义
```

合并算法：

```text
任一 scope_type=1 → 全部可见
否则受限范围按列 OR 合并
同列 ids 求并集
不同列生成多个 IN 条件 OR
权限等级取最大
```

### 10.7 自定义值域与 placeholders

允许 `${...}` 占位符，例如 `${deptId}`。

约束：

```text
先按当前用户解析占位符
解析后仍必须匹配「数字列 IN 数字列表」或「数字列 = 数字」
解析后不是数字语法 → REJECTED
```

### 10.8 非法自定义值域

```text
保存时整体拒绝，事务回滚，不允许部分保存。
运行期若发现历史非法规则，该规则不授予数据；其它合法规则仍可生效。
```

### 10.9 安全级别

```text
showlevel <= user.security_level <= showlevel2
```

不满足时该方案不参与命中。全员方案也可以配置安全级别。

### 10.10 矩阵

```text
matrix 作为 subject_type=6 进入统一向导
必须支持菜单、模块权限、字段权限、数据范围
```

不能只在数据范围里支持矩阵。

## 十三、验收场景

## 十五、复查结论：遗漏点与需要继续分析的功能

本节是对本文档的二次复查结论。保留作为分析过程记录。

**注意：本节中的历史建议如果与 15.4 最终决策冲突，一律以 15.4 为准。**

---

### 15.1 P0 级遗漏：必须补进主方案

#### 1. 数据范围五档没有并入主方案

当前第 4.4 节仍写的是：

```text
查看全量/仅本人
条件化授权
creatorSelf
密级范围
```

但用户后续已经明确要求数据范围增加：

```text
全部可见
本人可见
所在机构可见
所在机构及子级可见
自定义（列 IN 数字列表 / 列 = 数字）
```

这部分已经单独分析在：

```text
SpringBlade/doc/md/数据范围五档值域与数据权限一致性方案.md
```

主方案必须吸收该文档，至少补充：

```text
modedatasharerule.scope_type
modedatasharerule.scope_column
modedatasharerule.scope_value
```

不能只靠 `creatorSelf` 和 `condition_*` 表达五档范围。

---

#### 2. “scope_type”与“权限等级”存在命名冲突风险

本文档第 10.5 节写的是：

```text
数据范围：所有命中规则取最大等级
1 查看
2 编辑
3 完全控制
```

但数据权限五档里的 `scope_type` 是：

```text
1 全部
2 本人
3 所在机构
4 所在机构及子级
5 自定义
```

这两个“数字大小”含义完全不同。

必须明确：

```text
scope_type = 数据行范围类型
rightlevel/sharelevel = 权限强度
```

绝不能写：

```text
scope_type 取最大
```

否则“自定义(5)”会被误认为高于“全部可见(1)”，这是错误的。

---

#### 3. 授权方案的粒度没有定清楚

当前文档说：

```text
一个授权方案固定一个授权对象类型，并选择多个授权对象
```

但没有明确：

```text
方案内多个对象共享一份配置，还是每个对象单独配置？
```

例如方案是：

```text
角色方案：部门领导、文秘、会签
```

可能出现两种情况：

##### 情况 A：共享配置

```text
三个角色共用同一份模块权限、字段权限、数据范围
```

##### 情况 B：逐对象配置

```text
部门领导：可编辑、看全部数据
文秘：只读、看本部门数据
会签：只读、看本人数据
```

当前文档在这两种模式之间摇摆，必须二选一或都支持。

建议：

```text
第 0 步先选授权对象类型 + 选择多个对象；
第 1~3 步的规则行按“方案对象”逐条配置；
字段权限组可以选择方案对象的一个子集。
```

这样既保持单一类型，又不会把不同对象的权限强行合并。

---

#### 4. 旧数据迁移“按 objtype 分组”不安全

当前文档第 7.1 节建议：

```text
按 mode_id + objtype 分组，每一组 objtype 自动创建一个历史方案
```

这个方案会破坏原有权限差异。

例如：

```text
角色 A → 可见
角色 B → 编辑
```

如果都迁移到“角色方案”，且方案内共享一份配置，最终会变成：

```text
角色 A、角色 B 都有可见 + 编辑
```

这是越权。

最终决策已改为：

```text
旧数据不迁移，直接删除
```

因此不再需要按 `form/mode + objtype + objid` 生成历史方案，也不需要在迁移后手动合并。
上线前只做备份和删除预览确认，旧权限数据不进入新模型。

---

#### 5. 运行期“当前用户命中哪些方案”没有设计

文档前面设计了：

```text
mode_auth_scheme
mode_auth_scheme_subject
```

但运行期只写了：

```text
先按用户解析命中的方案，再加载方案下所有配置
```

缺少具体算法。

必须补充：

```text
resolveMatchedSchemeIds(modeId, user)
```

需要支持：

- 人员 subjectId = userId
- 部门 subjectId ∈ 用户部门集合，考虑 includeSub
- 岗位 subjectId ∈ 用户岗位集合
- 分部 subjectId ∈ 用户分部集合
- 角色 subjectId ∈ 用户角色集合
- 全员
- 安全级别区间
- 管理员豁免

否则新增方案表只是配置表，运行期不会消费。

---

#### 6. 多方案命中后的合并规则只写了原则，没有写算法

当前只写：

```text
菜单 any
模块权限并集
字段权限 max
数据范围 max
布局 priority
```

但缺少实现级语义。

尤其数据范围不能简单“取最大”，因为五档范围不是权限等级。

需要明确算法：

##### 菜单

```text
任一方案命中菜单共享 → 可见
```

##### 模块权限

```text
righttype 集合并集
```

##### 字段权限

```text
同 fieldId 取 max(rightvalue)
```

##### 数据范围

分成两步：

```text
1. 先按命中规则计算行范围
2. 再按权限等级合并
```

若为五档范围：

```text
任一命中规则 scope_type=1 → 全部可见
否则受限范围按列 OR 合并
同列 ids 求并集
不同列生成多个 IN 条件 OR
解析失败 REJECTED → 该规则不授予数据
若所有规则都无效 → 无可见数据
```

##### 布局

```text
命中多个字段组时，按 priority 升序；
priority 相同按 groupKey/schemeId 兜底；
不再做表单级通用布局兜底。
```

#### 7. 数据范围写链路没有覆盖

当前文档重点讨论了读链路，但编辑/删除也要受同样范围控制。

```text
没配建模权限 → 才用 blade_scope
```

引入五档后必须补充：

```text

```

否则会出现：

```text
列表看不到，但直接调用编辑接口能改
```

这是严重越权。

#### 8. 单条共享与矩阵共享如何叠加没有写清

```text
最终可见行 =
  五档范围过滤出的行
  OR 单条共享给我的行
  OR 矩阵共享命中的行
```

如果是“全部可见”，则不再叠加。

如果是 REJECTED，需要确认：

```text
是否仍允许单条共享行命中
```

建议：

```text
非法配置本身不授权，但其它合法授权仍可生效；
全部非法时无可见数据。
```

---

#### 9. `creatorSelf` 与新的“本人可见”重叠

当前字段：

```text
creator_self = 1 仅本人创建可见
```

新五档：

```text
scope_type = 2 本人可见
```

两者语义很接近，但实现不同。

必须明确：

```text
新规则 scope_type != NULL 时，以 scope_type 为准；
creator_self 只兼容旧规则；
两者同时存在时不能互相矛盾。
```

建议保存时：

```text
scope_type=2 → creatorSelf 可清 0
scope_type=1/3/4/5 → creatorSelf 不允许为 1，除非明确表示“范围内再看本人创建”
```

---

#### 10. 菜单范围缺少“全员”和“安全级别”

第 6.5 节的菜单映射只写了：

```text
角色、人员、部门、分部、岗位
```

但前面用户已经确认菜单可见性还要支持：

```text
全员
安全级别
```

应补充映射：

| 授权主体 | `blade_menu_share.shareType` |
|---|---|
| 全员 | 1 |
| 部门 | 2 |
| 人员 | 3 |
| 角色 | 4 |
| 分部 | 5 |
| 岗位 | 6 |
| 安全级别 | 3 或新增专用编码 |

注意当前 `PortalConstant` 中：

```text
SHARE_ALL=1
SHARE_DEPT=2
SHARE_USER=3
SHARE_ROLE=4
SHARE_BRANCH=5
SHARE_LIMIT=6
```

岗位和安全级别在 portal 菜单共享中并未完整落地，需要确认是否扩展 `blade_menu_share` 的 shareType 编码。

#### 11. AAE 组件菜单没有纳入方案

用户已经遇到并通过补菜单解决：

```text
/formmode/formview/aae
```

它是列表“查看/编辑/新增”按钮的目标组件页。

向导方案里必须写清楚：

```text
保存方案时，列表菜单和 AAE 组件菜单都要同步共享给当前方案主体。
```

否则人员级用户又会能看列表但点按钮 404。

同时保留：

```text
formdata_view_{formId}
formdata_aae_{formId}
```

两条菜单记录。

#### 12. 字段权限组、groupKey 与方案的关系还不够明确

当前只写：

```text
groupKey 仍作为 Univer 设计器 nodeKey
```

但新增 scheme 后必须明确：

```text
scheme → fieldGroup → groupKey → form_layout(nodeKey)
```

需要补充：

- groupKey 不能因方案迁移改变；
- 一个字段组只能属于一个 scheme；
- 字段组的 subjects 必须是 scheme subjects 的子集；
- 运行期取当前用户命中字段组的 groupKey；
- 没有对应布局时只提示，不做表单级兜底。

### 15.2 P1 级遗漏：建议补充

#### 1. 方案列表管理页

当前只设计了“打开权限按钮后进入向导”，但没有设计：

```text
查看已有方案
编辑方案
复制方案
删除方案
停用方案
重命名方案
```

建议进入权限按钮后先展示方案列表：

```text
当前表单已有方案：
- 角色方案-部门领导
- 人员方案-lh
- 部门方案-财务部

[新建方案]
```

否则方案多了以后无法管理。

---

#### 2. 方案复制功能

用户以前已接受“同步布局/共享配置”的思路。

建议新增：

```text
复制授权方案
```

复制时明确：

```text
是否复制字段权限
是否复制 Univer 布局
是否复制数据范围
是否复制菜单设置
groupKey 是否重新生成
```

注意：

```text
复制布局时 groupKey 必须重新生成；
复制字段组时 groupKey 也必须重新生成；
否则两个方案会共用同一份 Univer 布局。
```

---

#### 3. 草稿保存

当前建议是：

```text
前三步本地草稿，最后统一提交
```

但大型表单配置很多，必须考虑：

```text
浏览器刷新/误关闭/超时
```

建议补充：

```text
方案草稿表 或 localStorage 草稿
```

不需要立即落正式权限表。

---

#### 4. 运行期诊断功能

现在这类问题排查非常依赖数据库和 token。

建议增加管理端诊断页：

```text
输入 formId + userId
展示：
  - 命中哪些方案
  - 命中哪些模块权限
  - 命中哪些字段组
  - 命中哪个布局 groupKey 和 layoutType
  - 命中哪些数据范围规则
  - 最终 rowScope SQL 片段
  - 菜单是否可见及原因
```

这能大幅减少“为什么看不到/为什么 404/为什么没布局”的排查成本。

---

#### 5. 权限预览

在向导最后一步增加：

```text
预览当前方案对某个用户的最终效果
```

展示：

```text
可见菜单
可点击按钮
可见字段
使用布局
可见数据范围
```

```text
布局中不允许出现当前字段组白名单之外的字段
```

已有设计器打开时会过滤，但运行期保存布局时也建议校验。
