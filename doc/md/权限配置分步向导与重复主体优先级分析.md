# 权限配置分步向导与重复主体优先级分析

> 目标页面：`http://192.168.1.4:8000/formmode/formmanage`
>
> 本文只做方案设计与问题分析，不改代码。
>
> 讨论对象：
>
> - SpringBlade 当前权限配置流程
> - `D:\Weaver2020\ecology`
> - `E:\project\ecology\ecology`

---

## 一、结论摘要

### 1. 当前配置确实不合理

当前 SpringBlade 的“权限配置”是一个抽屉里的三个平铺 Tab：

```text
模块权限
字段权限
数据范围
```

存在一个统一“保存”按钮，所有配置一次性提交。

但它缺少一个核心概念：

```text
当前这一整套配置到底属于哪个授权对象类型、哪些授权对象
```

现在的情况是：

- 每个列表逐行选择 `objtype + objid`
- 字段权限“授权对象组”只看第一个主体的类型
- 菜单授权又单独维护在 `blade_menu_share`
- 三个 Tab 没有一个共同的“授权方案”归属
- 每个页签列表也没有统一的“当前授权对象类型”标识

所以用户看到的结果是：

```text
配置割裂、类型混乱、无法判断这一页配置是给谁的
```

### 2. 推荐改成“授权方案 + 三步向导”

建议新增一个顶层概念：

```text
授权方案 AuthScheme
```

一个授权方案固定一个授权对象类型：

```text
角色 / 部门 / 岗位 / 人员 / 分部
```

并选择该类型下的一个或多个具体授权对象。

然后围绕这个授权方案做三步：

```text
第 0 步：选择授权对象类型 + 选择授权对象
第 1 步：模块权限与菜单设置
第 2 步：字段权限设置
第 3 步：数据范围设置
```

所有步骤共享同一个授权方案，因此整套配置始终有清晰的归属。

### 3. 授权对象类型不应该决定优先级

Ecology 的处理原则是：

```text
授权对象类型是“身份维度”，不是“权限优先级”
```

同一个用户同时通过：

```text
人员
部门
角色
分部
岗位
所有人
矩阵
```

命中多条规则时，不是“人员优先于角色”或“角色优先于部门”，而是：

```text
能命中就算命中，最终按权限等级合并
```

推荐 SpringBlade 采用：

```text
菜单：任一命中即可见
模块权限：权限码取并集
字段权限：同一字段取最大权限
数据范围：多条命中取最宽松等级
布局：用明确 priority 决定，不用主体类型决定
```

### 4. 重复配置要禁止，重叠配置要合并

必须区分两种情况：

#### 同一类型同一对象重复

例如：

```text
同一方案里配置两次 人员 lh
```

这是脏数据，应：

```text
保存时去重
数据库加唯一约束
已存在重复数据要在迁移时清理
```

#### 不同类型重叠到同一人

例如：

```text
lh 本人被单独授权
lh 又在“财务部”部门里
lh 又属于“部门领导”角色
```

这是合法场景，不应强行禁止，也不应由类型决定谁赢。

应按权限合并：

```text
查看 + 编辑 = 编辑
只读 + 可编辑 = 可编辑
可见 + 可新增 = 可见且可新增
```

## 三、推荐目标模型：授权方案 AuthScheme

### 3.1 核心概念

新增：

```text
mode_auth_scheme       授权方案主表
mode_auth_scheme_subject 授权方案对象表
```

一个授权方案表示：

```text
某个表单下，针对同一授权对象类型的一整套权限配置
```

例如：

```text
方案名称：角色授权方案-部门领导
表单：01.2、差旅报销表单-old
授权对象类型：角色
授权对象：部门领导、文秘、会签
```

这个方案下再包含：

```text
模块权限
菜单设置
字段权限
数据范围
```

### 3.2 建议表结构

#### `mode_auth_scheme`

| 字段 | 说明 |
|---|---|
| `id` | 主键 |
| `tenant_id` | 租户 |
| `mode_id` | 模块ID；无 modeinfo 时用 formId |
| `form_id` | 表单ID，便于菜单/布局定位 |
| `scheme_name` | 方案名称 |
| `subject_type` | 1角色 2部门 3岗位 4人员 5分部 |
| `status` | 1正常 |
| `version` | 乐观锁版本 |
| `create_user/time` | 审计 |
| `update_user/time` | 审计 |

唯一键建议：

```text
tenant_id + mode_id + scheme_name
```

#### `mode_auth_scheme_subject`

| 字段 | 说明 |
|---|---|
| `id` | 主键 |
| `tenant_id` | 租户 |
| `scheme_id` | 授权方案ID |
| `subject_type` | 与方案一致，冗余便于校验 |
| `subject_id` | 角色/部门/岗位/人员/分部ID |
| `subject_name` | 名称快照 |
| `include_sub` | 部门含子级 |
| `status` | 1正常 |

唯一键：

```text
tenant_id + scheme_id + subject_type + subject_id
```

### 3.3 子表如何关联方案

建议给现有表增加：

```text
scheme_id
```

包括：

```text
moderightinfo.scheme_id
mode_field_auth_group.scheme_id
modedatasharerule.scheme_id
blade_menu_share.scheme_id
```

字段权限老的 `modefieldauthorize` 如果继续支持旧模式，也建议加：

```text
scheme_id
```

这样运行期可以先按用户解析命中的方案，再加载方案下所有配置。

### 3.4 是否让每组字段权限都属于同一类型

建议是。

字段授权对象组 `mode_field_auth_group` 下面仍可有多个主体，但必须全部满足：

```text
subject.objtype == scheme.subject_type
```

这样可以解决当前“组里第一个主体类型代表整组”的混乱。

## 四、三步向导流程设计

### 4.1 第 0 步：选择授权对象类型

页面进入时先展示选择卡片：

```text
请选择本套授权配置的授权对象类型

角色 | 部门 | 岗位 | 人员 | 分部
```

选择后展示醒目横幅：

```text
当前授权方案：角色授权方案-部门领导
授权对象类型：角色
授权对象：部门领导、文秘、会签
```

之后所有步骤都在这个上下文中进行。

### 4.2 第 1 步：模块权限与菜单设置

包含当前分散在“模块权限 Tab”的内容：

```text
模块权限列表
菜单名称
菜单可见范围
角色级菜单显示名
```

#### 变化点

- 列表不再每行选择 `objtype`
- `objtype` 固定显示在上方面板
- 每行只选具体对象
- 新增对象时默认带入当前方案 `subject_type`
- 菜单可见范围来自当前方案的授权对象，而不是任意主体

#### 菜单处理

当前：

```text
ensureFormMenuAndGrant() 只从 rights 中取 objtype=1 角色
```

建议改为：

```text
从 scheme.subjects 生成 blade_menu_share
```

同时继续保留 `blade_role_menu` 兼容：

```text
当 scheme.subject_type = 角色时，写 blade_role_menu
```

### 4.3 第 2 步：字段权限设置

包含：

```text
授权对象组列表
配置字段弹窗
Univer设计入口
字段权限组 groupKey
```

#### 变化点

- 授权对象组属于当前 scheme
- 组内主体类型固定为当前方案类型
- 列表头部显示：
  ```text
  当前授权对象类型：人员
  ```
- 字段配置弹窗内选择对象时，只能选当前类型
- `groupKey` 仍作为 Univer 设计器 `nodeKey`
- 每组字段和布局保持独立

#### 兼容旧数据

当前旧数据兼容逻辑：

```text
FormRightDrawer.tsx:202-226
```

保留。

对没有 scheme 的旧字段组：

```text
按 objtype 归类生成临时方案
或迁移时自动建方案
```

### 4.4 第 3 步：数据范围设置

包含：

```text
数据范围规则
查看全量/仅本人
条件化授权
creatorSelf
密级范围
```

#### 变化点

- 每行对象类型固定为当前方案类型
- 数据范围规则归属当前 scheme
- 如果当前类型不支持矩阵，则向导中不出现矩阵
- 矩阵建议继续作为数据范围高级类型单独处理

## 七、数据迁移与兼容

### 7.1 旧数据没有 scheme

建议迁移策略：

```text
按 mode_id + objtype 分组
每一组 objtype 自动创建一个历史授权方案
```

例如：

```text
方案名：历史迁移-角色
subjectType=1
```

然后把该 objtype 下的对象写入 `mode_auth_scheme_subject`。

### 7.2 字段授权对象组混合类型

历史字段组可能混合多种主体类型。

处理方式：

```text
1. 如果组内所有主体 objtype 相同 → 自动归属该类型方案
2. 如果组内主体类型混合 → 标记为“历史混合组”
3. 只在旧视图中可编辑
4. 新向导中只读展示，提示重新按方案配置
```

不要强行拆分，否则可能破坏已有 Univer 布局 `groupKey`。

### 7.3 groupKey 必须保留

`group_key` 是 Univer 组级布局的 `nodeKey`。

迁移时：

```text
原 group_key 不变
```

否则历史布局会找不到。

### 7.4 老字段权限唯一索引影响

已有唯一索引：

```text
uk_field_auth_subject(tenant_id, objtype, objid, modeid, fieldid)
```

如果向导允许同一主体出现在多个组并配置同一字段，会冲突。

建议：

- 同一方案内同一主体同一字段只允许在一组配置
- 或调整索引，把 `group_id` 纳入唯一键

需要业务确认：

```text
同一主体是否允许出现在多个字段组
```

## 八、重复与重叠授权分析

### 8.1 先区分两个概念

#### 重复

```text
同一类型 + 同一对象 + 同类规则被配置多次
```

例如：

```text
人员 lh 的查看权限配置两条
```

这是配置冗余/脏数据。

#### 重叠

```text
同一自然人通过不同主体类型命中多条规则
```

例如：

```text
lh 本人命中
lh 所在部门命中
lh 所属角色命中
```

这是合法业务场景。

### 8.2 Ecology 对模块权限的处理

核心类：

```text
E:\project\ecology\ecology\src\weaver\formmode\setup\ModeRightInfo.java
```

证据：

```text
:4899-4945  按 modeid + righttype + 密级条件查询规则
:4950-5068 按 sharetype 遍历人员/分部/部门/角色/所有人/岗位
:5069       命中即 break
```

结论：

```text
多条模块权限命中时，any 命中即通过。
没有“人员优先于角色”或“部门优先于角色”的规则。
```

更高权限覆盖低权限：

```text
:5161-5185
```

`temprighttype > rightType` 时参与判断，含义是：

```text
完全控制可以满足查看/编辑
```

这是权限等级覆盖，不是主体类型覆盖。

### 8.3 Ecology 对数据权限的处理

核心类：

```text
E:\project\ecology\ecology\src\weaver\formmode\view\ModeShareManager.java
```

证据：

```text
:263-296  所有命中条件用 OR 拼接
:175-184  使用 MAX(sharelevel) AS sharelevel，并按 sourceid 分组
:300-332  角色受限规则也取 maxrighttype
```

结论：

```text
同一条数据命中多条共享规则时：
1. 规则是 OR
2. 权限取 MAX
3. 不是第一条生效
4. 不是主体类型优先
```

权限等级：

```text
1 查看
2 编辑
3 完全控制
```

如果同时命中：

```text
人员 lh → 查看
角色“部门领导” → 编辑
部门“财务部” → 完全控制
```

最终：

```text
lh 对这条数据是完全控制
```

### 8.4 rolelevel 和 security_level 的定位

## 十、推荐的最终优先级规则

### 10.1 总则

```text
授权对象类型不是优先级。
对象是身份维度。
权限等级才是强弱维度。
```

### 10.2 菜单

```text
任一方案/主体命中 → 菜单可见
```

不做覆盖。

### 10.3 模块权限

```text
righttype 取并集
```

例如：

```text
人员 lh 命中 righttype=1 可见
角色 R 命中 righttype=3 编辑
```

最终：

```text
lh 拥有 1、3
```

### 10.4 字段权限

```text
同一字段取最大 rightvalue
```

```text
0 隐藏
1 只读
2 可编辑
```

### 10.5 数据范围

```text
所有命中规则取最大等级
```

建议定义：

```text
1 查看
2 编辑
3 完全控制
```

当前系统没有完整“完全控制”概念时，可先按：

```text
canViewAll / creatorSelf / 条件
```

推导等级。

### 10.6 布局

如果多个组命中且都有布局：

```text
按 priority 升序
priority 相同按 schemeId / groupKey 升序
```

建议给方案或字段组增加：

```text
priority int default 0
```

不要用主体类型决定布局优先级。

### 10.7 密级

```text
showlevel <= user.security_level <= showlevel2
```

密级是过滤条件，不是优先级。

### 10.8 角色级别

```text
rolelevel <= 用户在该角色中的级别
```

角色级别是命中条件，不是优先级。

## 十一、用户问题直接回答

### Q1：授权对象类型重复了，以哪个为准？

如果指的是：

```text
同一方案里选了两次同一个授权对象类型下的同一个对象
```

比如两次选了人员 `lh`：

```text
不允许。
保存时去重。
数据库加唯一索引。
```

如果指的是：

```text
同一表单存在多个方案，一个类型是角色，一个类型是人员
```

这是允许的。

最终按用户身份合并，不按类型选一个。

### Q2：人员重叠了，以哪个为准？

比如：

```text
lh 本人被授权
lh 所在部门被授权
lh 所属角色被授权
```

最终不是某个类型赢，而是：

```text
菜单：任一命中即可见
模块权限：并集
字段权限：同字段取最大
数据范围：取最大权限等级
布局：按 priority 取一个
```

### Q3：Ecology 是怎么处理的？

Ecology 总体是：

```text
主体之间 OR
权限取 MAX
布局取最小 layoutorder/layoutlevel
菜单 any 命中即可
rolelevel/security_level 只是过滤条件
```

但 Ecology 字段授权是首条读取，数据重复保存也不去重，这是它的历史实现问题，不建议照搬。

### Q4：是否应该在前置步骤强制只能选一种授权对象类型？

建议：

```text
一次向导只能选一种授权对象类型。
但一个表单可以存在多个授权方案。
```

这样兼顾：

```text
配置视图清晰
和业务规则灵活
```

不能因为向导固定类型，就在运行期把用户限制成只能属于一种主体类型。

### 15.1 P0 级遗漏：必须补进主方案

#### 1. 数据范围五档没有并入主方案

当前第 4.4 节仍写的是：

```text

条件化授权
```

但用户后续已经明确要求数据范围增加：

```text
全部可见
本人可见
所在机构可见
所在机构及子级可见
自定义（列 IN 数字列表 / 列 = 数字）
```

这部分已经单独分析在：

```text
SpringBlade/doc/md/数据范围五档值域与数据权限一致性方案.md
```

主方案必须吸收该文档，至少补充：

```text
modedatasharerule.scope_type
modedatasharerule.scope_column
modedatasharerule.scope_value
```

不能只靠 `creatorSelf` 和 `condition_*` 表达五档范围。

---

#### 2. “scope_type”与“权限等级”存在命名冲突风险

本文档第 10.5 节写的是：

```text
数据范围：所有命中规则取最大等级
1 查看
2 编辑
3 完全控制
```

但数据权限五档里的 `scope_type` 是：

```text
1 全部
2 本人
3 所在机构
4 所在机构及子级
5 自定义
```

这两个“数字大小”含义完全不同。

必须明确：

```text
scope_type = 数据行范围类型
rightlevel/sharelevel = 权限强度
```

绝不能写：

```text
scope_type 取最大
```

否则“自定义(5)”会被误认为高于“全部可见(1)”，这是错误的。

---

#### 3. 授权方案的粒度没有定清楚

当前文档说：

```text
一个授权方案固定一个授权对象类型，并选择多个授权对象
```

但没有明确：

```text
方案内多个对象共享一份配置，还是每个对象单独配置？
```

例如方案是：

```text
角色方案：部门领导、文秘、会签
```

可能出现两种情况：

##### 情况 A：共享配置

```text
三个角色共用同一份模块权限、字段权限、数据范围
```

##### 情况 B：逐对象配置

```text
部门领导：可编辑、看全部数据
文秘：只读、看本部门数据
会签：只读、看本人数据
```

当前文档在这两种模式之间摇摆，必须二选一或都支持。

建议：

```text
第 0 步先选授权对象类型 + 选择多个对象；
第 1~3 步的规则行按“方案对象”逐条配置；
字段权限组可以选择方案对象的一个子集。
```

这样既保持单一类型，又不会把不同对象的权限强行合并。

---

#### 4. 旧数据迁移“按 objtype 分组”不安全

当前文档第 7.1 节建议：

```text
按 mode_id + objtype 分组，每一组 objtype 自动创建一个历史方案
```

这个方案会破坏原有权限差异。

例如：

```text
角色 A → 可见
角色 B → 编辑
```

如果都迁移到“角色方案”，且方案内共享一份配置，最终会变成：

```text
角色 A、角色 B 都有可见 + 编辑
```

这是越权。

建议改成保守迁移：

```text
按 form/mode + objtype + objid 分组生成历史方案
```

也就是：

```text
一个历史授权对象一个方案
```

迁移后再由管理员决定是否合并为共享方案。

---

#### 5. 运行期“当前用户命中哪些方案”没有设计

文档前面设计了：

```text
mode_auth_scheme
mode_auth_scheme_subject
```

但运行期只写了：

```text
先按用户解析命中的方案，再加载方案下所有配置
```

缺少具体算法。

必须补充：

```text
resolveMatchedSchemeIds(modeId, user)
```

需要支持：

- 人员 subjectId = userId
- 部门 subjectId ∈ 用户部门集合，考虑 includeSub
- 岗位 subjectId ∈ 用户岗位集合
- 分部 subjectId ∈ 用户分部集合
- 角色 subjectId ∈ 用户角色集合
- 全员
- 安全级别区间
- 管理员豁免

否则新增方案表只是配置表，运行期不会消费。

---

#### 6. 多方案命中后的合并规则只写了原则，没有写算法

当前只写：

```text
菜单 any
模块权限并集
字段权限 max
数据范围 max
布局 priority
```

但缺少实现级语义。

尤其数据范围不能简单“取最大”，因为五档范围不是权限等级。

需要明确算法：

##### 菜单

```text
任一方案命中菜单共享 → 可见
```

##### 模块权限

```text
righttype 集合并集
```

##### 字段权限

```text
同 fieldId 取 max(rightvalue)
```

##### 数据范围

分成两步：

```text
1. 先按命中规则计算行范围
2. 再按权限等级合并
```

若为五档范围：

```text
任一命中规则 scope_type=1 → 全部可见
否则受限范围按列 OR 合并
同列 ids 求并集
不同列生成多个 IN 条件 OR
解析失败 REJECTED → 该规则不授予数据
若所有规则都无效 → 无可见数据
```

##### 布局

```text
命中多个字段组时，按 priority 升序；
priority 相同按 groupKey/schemeId 兜底；
不再做表单级通用布局兜底。
```

```text
当前表单已有方案：
- 角色方案-部门领导
- 人员方案-lh
- 部门方案-财务部

[新建方案]
```

否则方案多了以后无法管理。

---

#### 2. 方案复制功能

用户以前已接受“同步布局/共享配置”的思路。

建议新增：

```text
复制授权方案
```

复制时明确：

```text
是否复制字段权限
是否复制 Univer 布局
是否复制数据范围
是否复制菜单设置
groupKey 是否重新生成
```

注意：

```text
复制布局时 groupKey 必须重新生成；
复制字段组时 groupKey 也必须重新生成；
否则两个方案会共用同一份 Univer 布局。
```

#### 3. 草稿保存

当前建议是：

```text

```

但大型表单配置很多，必须考虑：

```text
浏览器刷新/误关闭/超时
```

建议补充：

```text
方案草稿表 或 localStorage 草稿
```

不需要立即落正式权限表。

#### 4. 运行期诊断功能

现在这类问题排查非常依赖数据库和 token。

建议增加管理端诊断页：

```text
输入 formId + userId
展示：
  - 命中哪些方案
  - 命中哪些模块权限
  - 命中哪些字段组
  - 命中哪个布局 groupKey 和 layoutType
  - 命中哪些数据范围规则
  - 最终 rowScope SQL 片段
  - 菜单是否可见及原因
```

这能大幅减少“为什么看不到/为什么 404/为什么没布局”的排查成本。


展示：

```text
可见菜单
可点击按钮
可见字段
使用布局
可见数据范围
```

### 15.5 还需要业务确认的问题

下面这些问题不能由技术方案单方面决定：

1. 一个方案内多个授权对象，是共享一份配置，还是逐对象配置？
2. 是否允许同一人员同时出现在多个方案？
3. 同一人员跨方案命中时，数据范围是 OR 合并，还是按方案 priority 取一个？
4. “全员”是否作为授权对象类型，还是只作为菜单共享类型？
5. “安全级别”是否进入统一授权对象类型，还是只作为规则过滤条件？
6. 矩阵主体是否进入新向导，还是继续作为数据范围高级功能？
7. 自定义权限值域是否允许 placeholders，例如 `${deptId}`？
8. 非法自定义值域是“本规则不授权”，还是“整体拒绝”？
9. 方案删除时是否级联删除菜单共享和字段组布局？
10. 旧数据迁移是一个对象一个方案，还是允许管理员手动合并？
