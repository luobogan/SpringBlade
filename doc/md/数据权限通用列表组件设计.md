# 数据权限 · 通用列表组件（ScopeGrid）设计说明

> 适用范围：SpringBlade + ant-design-pro 前端（Umi Max + antd v6 + ProTable）
> 配套改造：`blade_scope_field` 动态列、`BladeDataScopeHandler` 数据权限 SQL 拦截、菜单按钮权限 `/menu/buttons`
> 版本：2026-11-16（草案 · 已推进至 Phase AD）

---

## 0. 关键前提：项目里原本有「三套」可见性，不能混

| 层 | 数据源 | 语义 | 是否按当前用户 |
|---|---|---|---|
| **SQL 层** | `blade_scope_data.scope_field` | `select {scopeField} from (原SQL) scope where scope.{scopeColumn} in (...)`，后端 `BladeDataScopeHandler` 原样拼接、**不转义** | 否（但仅 `scopeType != ALL` 且非管理员才生效） |
| **展示层静态列** | `blade_scope_field.is_visible` | `DynamicScopeTable` 按 `menuId` 生成表头，**fail-open**（配置缺失则回退 `fallbackColumns`） | 否（按菜单，不区分用户） |
| **运行期字段权限** | `/right/field-perm/by-form/{formId}` → `modefieldauthorize` 聚合 | `{fieldName, visible, editable, perm}` 三态 | **是**（角色/部门/人员） |

另有：
- **按钮权限**：`useAccess().hasButton(pageCode, buttonCode)` ← `/menu/buttons`，按角色下发、前端集中缓存。
- **接口权限**：后端 `@PreAuth` / `ApiScope` 判定，前端**不下载**权限清单，只在调用失败时兜底。

> ⚠️ Sword 项目里「可见字段」`scopeField` 只在**配置表单提交**、前端列表**完全不消费**。我们项目已额外做了 `blade_scope_field`，但二者此前**不同步**（DDL 注释要求一致，实际靠管理员手工保持）——这是本设计要修的核心缺口。

### 1.4 双写缺口（已修复 · Phase E）

原先高级页保存时会回写 `is_visible`，但**不会**回写 `scopeField`，两处交替保存会让 SQL 可见字段与前端动态列失配。

修复：`FieldPermission.handleSave` 在提交 `blade_scope_field` 前先 `listScopeFields({menuId, scopeId:0})` 读服务端现值，`isVisible` **恒取服务端值**（忽略本页勾选），只写中文名 / 类型 / 说明 / 顺序 / 可编辑性；同时把「服务端有、但本页字段清单里没有」的记录一并回传，避免后端差集合并误删。若用户在本页改过可见勾选，保存后给出 `message.warning` 明确「本页勾选不生效」。

自此**可见性的唯一写入口**是数据权限弹窗的「可见字段」区域，与 §1.1 的「一个集合驱动两处」口径闭合。

### 2.0 界面路径与落地位置（已实现）

| 项 | 路径 | 说明 |

> `<ScopeGrid menuId pageCode formId request />`，**沿用原业务页路由，不新增 URL**。
> 本轮额外提供 `/authority/datascope/grid` 作为整条链路的可视化验证页。
>
> **菜单策略**：按 `db-menu-driven` 规范判定，该页与 `/authority/datascope/fields` 同属
> 「由数据权限页面按钮进入、不进左侧菜单」的辅助页，因此**不新增 `blade_menu` 行**，
> 沿用现有 fields 的静态路由模式，零数据库改动。若后续需要侧边栏可见，再按普通菜单
> `category=1` 补一行并移除静态声明。

### 2.1 Sword 的可借鉴点与缺口

`Grid.js`（页面级容器：搜索表单 / 工具栏 / 分页状态 / 权限按钮分发 / 自动追加操作列）+ `StandardTable`（纯表格），约 20 个业务页只写 `columns + renderSearchForm + onSearch`。最值得抄的三条：

1. **两层封装、职责分离**：业务 `columns` 只写数据列，操作列由容器依据权限自动追加。
2. **按钮元数据驱动**：`{code, alias, action, path, source}`，`action` 1=工具栏 / 2=行内 / 3=两者，`alias` 决定默认行为（增删改查跳转 / 删除接口）；**无权限不渲染**。
3. **render props 扩展点**：`renderLeftButton` / `renderRightButton` / `renderActionButton` / `btnCallBack` / `renderSearchForm`。

Sword **缺失**、新组件必须补齐：
- 列显隐 / 拖拽排序 / 列宽 / **持久化**（服务端 + 个人偏好）
- **字段级权限**（按当前用户）
- `filters` / `sorter` **透传**（`StandardTable → Grid` 把二者丢了）
- **权限动态刷新**（`Grid` 只在 constructor 读一次 `getButton`）
- 导入导出绕过权限

### 2.2 组件定位

`ScopeGrid`：基于现有 `ProTable` / `StandardTable` 的页面级容器，统一收口「列配置（静态 + 用户字段权限）+ 数据请求 + 按钮/操作列权限 + 列设置交互」。业务页只声明数据来源、静态列、`menuId`/`pageCode`/`formId`，其余交给组件。

### 2.3 功能模块（7 个）

| # | 模块 | 职责 |
|---|---|---|
| 1 | **列配置解析层** | 拉 `/scope-field/list` → 过滤 `isVisible!==0` → `sort` 升序 → `fieldLabel || fieldName` 作表头 → `fieldDbType` 推导 `valueType` → 生成 `ProColumns` |
| 2 | **用户字段权限叠加层** | 传 `formId` 时拉 `/right/field-perm/by-form/{formId}`，与静态列取**交集**（更严格者优先）；产出 `visible/editable` 三态；不传则跳过 |
| 3 | **数据层** | `request | dataSource` 二选一；`{current, pageSize, ...formValues, sorter, filter}` **全量透传**后端；分页归一化复用 `StandardTable` |
| 4 | **按钮/操作列层（操作栏）** | `useAccess().hasButton(pageCode, buttonCode)` + `getPageButtons`；按 `action` 分派工具栏/行内；自动追加固定在右侧的「操作」列；`onButtonClick({btn, keys, rows, refresh})`。**`rowActions(record, refresh)` 可与权限按钮合并渲染，且即使该 pageCode 在 `/menu/buttons` 里没有任何按钮，也会渲染操作列**（避免动态列表无操作栏） |
| 5 | **工具栏 / 搜索区** | `renderSearchForm(onReset)` / `renderLeftButton` / `renderRightButton` / `renderActionButton`；行选择 `onSelectRow(keys, rows)` |
| 6 | **列设置交互** | 列显隐、拖拽排序、列宽、密度、全屏；个人偏好存 `localStorage`（键含 `menuId + userId`），服务端配置作基线；「恢复默认」；管理员「保存为默认」才 `submitScopeFields` |
| 7 | **状态与容错** | 配置为空/请求失败 → `fallbackColumns` **fail-open**；`loading`/`error` Alert + 重试；`refreshToken` 支持配置保存后即时刷新；空态 |
| 8 | **编辑态管理** | `defaultEditable=true` 时 `is_editable=1` 的单元格**打开即常驻输入控件**、失焦保存、可连续修改（对应参考实现 `EditableProTable` 把 `editableKeys` 初始化为所有行 id）；关闭则回到「点击单元格才编辑」。控件仍按字段类型加载 |

**权限叠加顺序**：`静态 is_visible` → `用户字段权限 visible/editable` → `按钮权限`（操作列）→ 行级数据权限交给后端。
任一请求失败该层 fail-open，绝不白屏。

### 2.4 数据结构

```ts
// 1) 服务端列配置基线（已有，直接复用 services/authority/dataPermission.ts）
interface ScopeFieldConfig {
  fieldName: string;
  fieldLabel?: string;
  fieldDbType?: string;
  fieldHtmlType?: string;
  description?: string;
  isVisible?: number;   // 1=展示, 0/缺省=不展示
  isEditable?: number;  // 1=可编辑, 0=只读
  sort?: number;
  width?: number;
  align?: 'left' | 'center' | 'right';
  id?: string;
  scopeId?: string;     // 0 = 菜单级默认配置
  menuId?: string;
  fieldId?: string;
  resourceCode?: string;
}

// 2) 运行期「按当前用户」字段权限（已有 fieldPermApi）
interface FieldPerm {
  fieldName: string;
  visible: boolean;
  editable: boolean;
  perm: number;
}

// 3) 按钮元数据（/menu/buttons，Sword 模型在本项目的映射）
interface ButtonMeta {
  code: string;
  alias: string;
  action: 1 | 2 | 3; // 1=工具栏 2=行内 3=两者
  path?: string;
  source?: string;
}

// 4) 组件契约
interface ScopeGridProps<T> {
  menuId: string | number;        // 列配置主键（雪花 ID 用 string，避免 JS 精度丢失）
  scopeId?: string | number;      // 0 = 菜单级默认配置
  resourceCode?: string;
  pageCode?: string;              // 按钮取数 key = 菜单 code
  formId?: string | number;       // 传了才叠加用户字段权限
  rowKey?: string;                // 默认 'id'
  request?: ProTableProps<T, any>['request'];
  dataSource?: T[];
  fallbackColumns?: ProColumns<T>[];
  extraColumns?: ProColumns<T>[];   // 固定渲染在动态列之后
  renderSearchForm?: (onReset: () => void) => React.ReactNode;
  renderLeftButton?: () => React.ReactNode;
  renderRightButton?: () => React.ReactNode;
  onButtonClick?: (p: ScopeGridActionPayload<T>) => void;
  /** `is_editable=1` 的单元格保存回调；不传则这些列只读 */
  onCellSave?: (p: ScopeGridCellSavePayload<T>) => void | Promise<void>;
  /** 默认编辑态：打开即常驻输入控件、失焦保存（对应 EditableProTable 把 editableKeys 初始化为所有行） */
  defaultEditable?: boolean;
  /** 自定义行操作，与按钮权限行内按钮合并到同一「操作」列；传了就一定会渲染操作列 */
  rowActions?: (record: T, refresh: () => void) => React.ReactNode[];
  onSelectRow?: (keys: React.Key[], rows: T[]) => void;
  onConfigsChange?: (configs: ScopeFieldConfig[]) => void;
  onSaveColumns?: (configs: ScopeFieldConfig[]) => void;  // 管理员保存为默认列（组件不直接写库）
  actionColumnTitle?: string;
  actionColumnWidth?: number;
  enableColumnSetting?: boolean;  // 默认 true
  refreshToken?: string | number;
  tableProps?: Partial<ProTableProps<T, any>>;
}

// 5) 内部解析结果
interface ResolvedColumn<T> extends ProColumns<T> {
  fieldName: string;
  origin: 'scope' | 'fallback' | 'extra' | 'action';
  fieldPerm?: FieldPerm;
}
```

### 2.5 交互逻辑（时序）

1. **挂载**：并行 ① `/scope-field/list(menuId, scopeId=0)` ② `useAccess()` 读已按角色下发的按钮树 ③ 有 `formId` 才拉 `/right/field-perm/by-form/{formId}`。
2. **生成列**：可见过滤 → `sort` 升序 → 叠加字段权限 → 追加 `extraColumns` → 按 `action` 追加操作列 → 合并本地列偏好（显隐/顺序/宽度）。
3. **首屏请求**：`request` 带分页 + 查询表单 + `sorter`/`filter`（补齐 Sword 丢参数的坑）。
4. **列设置**：只改本地偏好、不写库；管理员点「保存为默认」才 `submitScopeFields({scopeId:0, menuId, resourceCode, fields})`，成功后 `refresh()`。
5. **权限动态刷新**：`refreshToken` 变化重拉列配置；角色授权后 `useModel('@@initialState')` 刷新按钮树，避免 Sword 只在构造时读一次的缺陷。
6. **失败降级**：任一配置请求失败 → 该层 fail-open（列用 `fallbackColumns`、字段权限视为全可见），顶部 Alert + 重试按钮。

### 2.6 与现有体系的一致性清单

- **主键口径**：`menuId` 为主、`scopeId=0` 菜单级默认、`resourceCode` 冗余；沿用 `useScopeFieldColumns` / `DynamicScopeTable` 的 `fallbackColumns` + `extraColumns` + `refreshToken` 契约，表头继续走 `StandardTable`。
- **SQL 安全**：`fieldName` 必须匹配 `^[A-Za-z_][A-Za-z0-9_$]*$`（前端 `VisibleFieldSelector` 与后端 `SAFE_FIELD_NAME` 双重校验）；`scopeColumn` 必须包含在可见字段集合中（否则派生表缺列、SQL 报错），Phase D 已把该检查从告警升级为**阻断**。`*` 模式下不校验（派生表含全部列）。
- **接口权限**：读接口登录即可（`/scope-field/list` 无 `@PreAuth`），写接口必须 `@PreAuth(HAS_ROLE_ADMIN)`；沿用 `blade-auth: bearer <token>`，不要在前端下载接口权限清单。
- **语义隔离**：`blade_scope_field` 是**按菜单的静态列配置**，不是「按用户的字段权限」；`modefieldauthorize` 中 `objtype=99/objid=-1` 只是配置存储，运行期 `matchAuthorizeObject` 只认 `1/2/4`，绝不能拿来当权限判定。
- **已知坑（Phase C 已实证并修掉一处）**：
  - `ScopeFieldServiceImpl.listByScope` 对多参数是 **AND** 而非「优先 scopeId 回退」（Controller 注释写的「优先按 scopeId 精确查」与实现不符）。保存端 `saveBatchConfig` 固定写 `scope_id=0`，查询若不传 `scopeId` 会命中同菜单下其它 `scope_id` 的记录 → 重复列 / 顺序错乱。**`ScopeGrid` 已默认 `scopeId=0`**；直接调用 `DynamicScopeTable` 的页面也必须显式传 0。
  - `saveBatchConfig` 的差集合并按 `scopeId + menuId` 查存量、不按 `resourceCode`，因此两个写入口会互相覆盖同一批记录；本次明确「可见性只由可见字段区域写」，高级页只补元数据。
  - 业务页不能硬编码雪花 `menuId`（各环境不同）：`useAutoMenuId` 从 `getRoutes()`（登录时落盘的 `/menu/routes` 菜单树）按当前路由 `path`/末段 `code` 反查，返回字符串避免 JS 精度丢失。
  - `scopeType=ALL` / 超管时后端不改写 SQL，但前端动态列仍生效，需产品层面明确这一差异。
  - 雪花 `menuId` 一律用字符串传递（JS `Number.MAX_SAFE_INTEGER` 约 9.0e15，雪花 ~2.1e18）。
  - **Umi Max 的 `useLocation()` 没有 `query` 属性**（`location.query` 是 Umi 3 写法）：`location.query?.menuId` 恒为 `undefined`，`?menuId=` 被丢弃 → 列配置请求根本不发 → 列表退化为 `fallbackColumns`。必须 `new URLSearchParams(location.search).get('menuId')`。`GridPreview.tsx` 与 `FieldPermission.tsx` 已修正，全仓已无同类写法。
  - `blade_scope_field` 里同名 `field_name` 出现多行不一定是脏数据：`saveBatchConfig` 差集合并会逻辑删除旧行，需按 `is_deleted=0` 过滤后再判断（实测该菜单 72 行中 54 行已逻辑删除，有效 18 个字段、无重复）。
  - **`is_editable` 必须有消费端**：`useScopeFieldColumns` 只生成静态列，若列表侧不按 `configs.isEditable === 1` 挂行内编辑，配置会正常落库、弹窗也能正常回显，但用户看到的是「设置了可编辑没生效」。`ScopeGrid` 现已用 `EditableCell` + `onCellSave` 补齐；运行期用户字段权限 `editable === false` 会覆盖静态配置、降级为只读（更严格者优先）。表单侧的字段权限走 `modefieldauthorize` + `useFieldPerm`，是另一条链路，不在本组件内。

### 2.7 「可编辑」的两套体系（结论：不要打通）

| 体系 | 存储 | 配置入口 | 运行期消费 | 语义 |
|---|---|---|---|---|
| **列表列级可编辑** | `blade_scope_field.is_editable`（按 `menuId`） | 数据权限弹窗「可见字段」区域 / 字段元数据页 | `ScopeGrid` → `EditableCell` + `onCellSave` | 通用列表单元格是否可行内编辑 |
| **表单字段级限制** | `modefieldauthorize`（按 `modeId` + 角色/部门/岗位/人员） | `FormRightDrawer`（表单建模 → 表单权限） | `FormRightServiceImpl.listFieldPerm` → `useFieldPerm` | 业务表单字段隐藏 / 只读；**无记录 = fail-open = 全可见可编辑** |

**2026-11-14 实证结论**：

- `matchAuthorizeObject` 只认 `objtype` 1-4 和 `objid=0`（`OBJ_ID_ALL`，所有人）；`objtype=99, objid=-1` 是字段管理页旧实现的「配置存储」命名空间，运行期**永不匹配**。
- 该命名空间记录还把 `formId` 当 `modeId` 传给 `/right/field/{modeId}`（后端按 `modefieldauthorize.modeid` 查/删），与真实 `modeinfo.id` 不是同一套 ID（实测 `modeinfo.id=2106000000000000001`、`billid=5`），因此 `listFieldPerm(modeId)` 也查不到。实测 `modefieldauthorize` 全表 **88 条全是这类死数据**。
- `saveFieldAuthorizes` 是**全量替换**（先 delete 该 `modeId` 全部记录再 insert），任何新写入口都可能误删 `FormRightDrawer` 配置的真实按角色授权。
- 若强行写 `objid=0` 默认记录去「打通」，`listFieldPerm` 会从「空数组 = fail-open」变成返回非空记录，使原本默认可编辑的字段变成 `editable=false`（只读），**反而破坏表单**。

因此本轮的处理是：字段管理页**停止写入** `modefieldauthorize`（保留读取以兼容历史回显），`blade_scope_field` 成为列表配置的唯一数据源；表单字段权限仍只由 `FormRightDrawer` 维护。**数据库现有 88 条历史记录未改动**。弹窗与字段管理页的文案已明确「此处的可编辑作用于通用列表，表单字段权限请到表单建模 → 表单权限按角色配置」。

> 如后续确实要「弹窗配置驱动表单字段权限」，需先做产品决策（授权对象取谁、是否接受 fail-open 语义变更），再改**后端** `listFieldPerm` 增加静态默认源，而不是在前端全量替换 `modefieldauthorize`。
