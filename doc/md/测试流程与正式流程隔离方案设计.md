# 测试流程与正式流程隔离方案设计

> 配套阅读：[Flowable7工作流引擎精讲.md](Flowable7工作流引擎精讲.md) 第五章（分层设计）、第六章（测试流转正）、第七章（category/tenantId）、第八章（定时任务）、第九章（单库混布）、第十章（人员一致性）。
>
> 本文是**落地视角的隔离方案设计**：先盘点本项目（springBlade / blade-workflow / Flowable 7.1+8.1）已有的隔离机制，再系统化给出候选方案、对比矩阵、分场景推荐与实施要点。

## 一、现状盘点：本项目已经落地了什么

当前架构：blade-workflow 单服务 + 单 MySQL 库（dev 共享环境），Flowable 引擎与业务表（`wf_*`）同库，测试与正式**同引擎、同库混布**。已落地的隔离机制：

| # | 机制 | 实现 | 对应方案编号 |
| :-- | :-- | :-- | :-- |
| 1 | 数据标记隔离 | `wf_instance`/`wf_task` 等业务表 `is_test` 字段；ACT 双写列 `IS_TEST_`（`ACT_RU_TASK`/`ACT_HI_TASKINST`/`ACT_HI_PROCINST`），待办/已办读源统一 `COALESCE(IS_TEST_,0)=0` 排除测试单 | S4 |
| 2 | 部署隔离 | 测试部署用独立引擎 key：`procKey + "__test"`（`WorkflowConstant.TEST_DEPLOY_KEY_SUFFIX`），`deployForTest` 与发起时 `engineKey` 成对使用，**避免测试部署顶掉正式最新版本**；`test_deployment_id` 记录测试部署 | S6（部署维度） |
| 3 | 行为隔离 | `is_test=1` 实例不执行任何超时动作（`WfTimeoutJob` 扫描排除 + `WfTimeoutServiceImpl` 服务内纵深防御）；测试实例标题强制 `【测试】` 前缀 | S6（行为维度） |
| 4 | 权限隔离 | 测试接口服务层断言 `is_test=1`；真人模式允许节点操作者本人办理测试单（无需 `workflow` 角色） | S5 |
| 5 | 数据清理 | `cleanupTestData` 一键删除全部 `is_test=1` 实例/待办/日志/快照，并级联卸载测试部署（清 ACT_* 数据） | S8（清理维度） |
| 6 | 状态机 | `wf_process_definition.status`：0=草稿 / 1=已发布 / 3=测试态；`deployForTest` 不改发布状态、不刷新 `proc_def_id` | S6 |

**尚未覆盖的缺口**（本文重点补齐）：

- 引擎侧 **tenantId 语义隔离**未启用（`TENANT_ID_` 目前只承载 blade 业务多租户，不承载测试/正式隔离）；
- 无**独立环境**（测试与正式共用同一 blade-workflow 实例与同一 MySQL 库）；
- 无**发布前引用校验**（精讲 §10.6：BPMN 里的测试账号/部门/通知渠道可能随发布进入正式）;
- 无**测试历史定期清理**的自动化 Job（目前靠手动 `cleanupTestData`）;
- 无**数据脱敏**（测试实例可能使用真实业务数据）;
- 已知读源坑：测试态下测试页配置面板读 `proc_def_id` 指向的**正式部署**，与测试实际运行的 `__test` 部署可能不一致（见 §6.1 P0-1）。

## 二、隔离的目标与原则

### 2.1 目标

一句话：**测试可以尽情折腾，正式绝不感知、绝不外溢、绝不被污染。** 拆开为五个"绝不"：

1. **不可见**：正式用户的待办/已办/实例列表/报表/搜索中，测试数据"隐身"；
2. **不外溢**：测试实例触发的通知、回调、超时动作、消息推送，绝不送达真实用户/真实外部系统；
3. **不污染**：测试数据可识别、可清理、可度量，不留脏数据在历史表里无限膨胀；
4. **不干扰**：测试的部署、重试、Job 触发，不改变正式流程定义的版本语义（不顶版本、不抢 Job、不误触发）；
5. **可回滚**：测试发现问题时能一键清理重来；测试通过的版本能一键转正且可秒级回退。

### 2.2 六个隔离维度

| 维度 | 隔离对象 | 典型手段 | 本项目现状 |
| :-- | :-- | :-- | :-- |
| **环境隔离** | 进程/引擎/数据库实例 | 独立部署单元、独立库、独立 Redis/MQ | ❌ 共用 |
| **数据隔离** | 实例/任务/变量/历史 | tenantId 行级隔离、is_test 标记、独立 schema | ✅ is_test 标记 |
| **配置隔离** | 开关/地址/密钥/时间刻度 | Profile、Nacos namespace、testMode 变量、独立部署 key | ✅ 独立 key；⚠️ Nacos 共享 |
| **权限隔离** | 谁能发起/办理/管理测试 | 测试角色、服务层断言、测试账号白名单 | ✅ 已做 |
| **网络隔离** | 测试对外部系统的调用 | Mock 服务、出口白名单、网关路由染色 | ❌ 未做 |
| **标识隔离** | 数据"打标"以便过滤与审计 | category、tenantId、is_test、标题前缀 | ✅ 已做 |

### 2.3 设计原则（判断任何隔离决策的四条准绳）

1. **失败安全默认（fail-safe default）**：一切过滤的缺省值必须是"排除测试"，而非"包含测试"。如读源查询 `COALESCE(IS_TEST_,0)=0`——漏写过滤条件时宁可少显示，不可多显示。**testMode 类开关默认值必须是 false/正式**。
2. **纵深防御**：任何单一隔离手段都可能被未来的代码改动绕过（如扫描条件变化、新增调用路径），关键外溢点（超时动作、通知、回调）必须有第二道防线。
3. **同定义异部署**：测试与正式永远复用同一份 BPMN 源（改测试不改副本），差异只通过部署标记/变量/配置注入。**禁止复制 BPMN 加 `-test` 后缀维护两份源**（精讲 §五 反模式）。
4. **可清理、可度量**：测试数据必须有统一标记（可 `COUNT`、可 `DELETE`），清理必须级联（业务表 + ACT_* + 引擎部署 + 定时 Job），且清理动作本身要有留痕。

## 三、候选隔离方案

### S1 独立环境部署（物理隔离）

测试与正式使用**完全独立的部署单元**：独立 blade-workflow 进程 + 独立 MySQL 库（甚至独立实例）+ 独立 Redis。BPMN 源码同仓库，通过 CI 分别部署。

- **优点**：隔离强度最高——进程、连接池、Job Executor、数据全部物理隔离；正式库零测试数据；排障最简单（看日志就知道是谁）。
- **缺点**：成本最高：双倍基础设施 + 双倍发布流水线；"测试流转正"变成跨环境制品迁移（导出 BPMN/表单配置 → 在正式环境重新部署），需要额外的发布工具或人工卡点；两套环境的**人员/组织主数据必须同步**（精讲 §10.5 单一身份源原则），否则测试通过的审批人在正式环境不存在。
- **适用**：团队 ≥ 20 人、有专职运维、强合规行业（金融/政务/国企）、正式环境已有明确安全边界的情况。

### S2 独立 Schema（同实例、不同库）

同一 MySQL 实例上建 `blade`（正式）与 `blade_test`（测试）两个 schema，blade-workflow 可配双数据源或部署两个实例分别指向。

- **优点**：数据物理分离但硬件共享，成本低一半；备份/清理可整库 `DROP/RESTORE`，最干净；Flowable 的 `databaseSchema` 可按环境配置。
- **缺点**：仍是两套引擎实例（若双实例部署）；跨库查询/联表统计麻烦；"测试流转正"同样是跨库迁移；开发本地联调要维护两份配置。
- **适用**：中型团队（5~20 人）、希望比 S4 更彻底但预算有限的场景。**注意**：如果只做单实例双数据源动态切换，复杂度反而高于双实例，不推荐动态切换。

### S3 tenantId 行级隔离（单库"伪装租户"）

精讲 §九 的原生方案：测试部署打 `tenantId("TEST_TENANT")`，正式打 `PROD_TENANT`（或用 blade 已有业务租户 + 约定保留一个测试租户 ID）；运行期实例/任务/历史自动继承 `TENANT_ID_`；所有查询显式（或经 ThreadLocal/CommandInterceptor 自动）追加 `TENANT_ID_ = ?`。

- **优点**：**行级隔离是 Flowable 原生能力**，RU/HI 全表自动继承，查询过滤走索引、性能最好；单库即可实现"正式人员自动隐身"；与 blade 已有的 ACT 查询租户过滤骨架（`WfTaskActReader.appendActTenant`）天然契合——只是把"业务租户"扩为"业务租户 × 测试标记"两个维度。
- **缺点**：单库共享所有风险：Job Executor 不认 tenantId，测试/正式的定时 Job 会互相抢占（精讲 §8.4/§9.5 强制要求物理隔离或测试态禁用异步执行器）；`startProcessInstanceByKey` 不带 tenantId 会在同 key 多租户下找错版本，所有启动点必须显式指定；漏写过滤条件即泄露（必须封装统一查询入口或 CommandInterceptor）；测试历史膨胀需定期清理。
- **适用**：单库混布且要长期共存的中大型项目；本项目中期演进的目标形态。

### S4 数据标记隔离（is_test 业务标记 —— 本项目现状）

在业务表与 ACT 扩展列上打 `is_test` 标记，读侧统一排除。

- **优点**：实现简单、与业务语义贴合（能表达"测试实例"而 tenantId 只能表达"归属"）；不依赖 Flowable 多租户机制，同 key 部署冲突用**独立引擎 key（`__test` 后缀）**绕开，避免顶掉正式版本；配合 `cleanupTestData` 可一键清理；已在本项目验证可用。
- **缺点**：**标记靠代码自觉维护**——每张新表、每个新查询都要记得带 `is_test` 条件，漏写即泄露（比 tenantId 的"引擎自动继承"更易出错）；只隔离数据，不隔离 Job/通知等行为外溢点（本项目靠超时豁免补了一处，但通知/回调需要逐点排查）；ACT 原生表靠双写扩展列承载标记，任何绕过 Writer 的直写路径都会丢标记。
- **适用**：小团队、单库、快速起步——**本项目已验证此路线可行**，缺点靠"统一读源封装 + 纵深防御"对冲。

### S5 独立账号与权限隔离

- **测试账号白名单**：预置 `test_user_01` 等测试账号（`is_test_user` 标记，不复制一套用户表——精讲 §10.5），BPMN 发布前校验不存在测试前缀引用（精讲 §10.6）；
- **角色隔离**：`workflow_test` 角色才能进测试入口；测试接口服务层断言目标实例 `is_test=1` 且本人为节点操作者（本项目已实现 `WfTestController` 模式）；
- **审批人解耦**：测试实例的审批人解析走同一套组织服务（保证"测的就是正式逻辑"），但通知渠道打测试标记。

- **优点**：成本极低，防"用正式账号做测试"引发的审计与数据污染问题。
- **缺点**：只管"人"，不管"数据"；测试账号若复用真实组织架构，通知/外溢仍需 S6/S8 配合。
- **适用**：所有团队的**必做基线**。

### S6 特性开关 / 变量路由 / Profile（行为差异隔离）

精讲 §5.1/§5.2 推荐方案，三个层次：

1. **流程变量路由**：BPMN 内 `${testMode ? 'PT5M' : 'P3D'}`、`${testMode ? @mockNotifyService : @realNotifyService}`——测试的就是真正要上线的定义，`testMode` 默认 false（失败安全）。
2. **Spring Profile + Bean 别名**：`@Profile("prod")` 真 Bean / `@Profile({"dev","test"})` Mock Bean，BPMN 永远写 `${@notifyService}`，流程图不感知环境。
3. **部署级开关（本项目已用）**：测试部署用独立引擎 key（`procKey__test`），配合 `testDeploymentId` 与 `deployForTest` 不刷新 `proc_def_id` 的语义，把"测试部署"与"正式版本"在 Flowable 的 key→最新版本映射上彻底分开。**这是对精讲 §六"同 key 重新部署"的改进**：同 key 转正方案下，每次测试部署都会把正式版本顶成"最新"，本项目用 key 后缀规避了该风险。

- **优点**：维护成本最低（同一份 BPMN）；行为差异（时间刻度、通知渠道、外部地址）集中在变量与配置，不散落 `if(env==test)` 硬编码。
- **缺点**：变量路由要求所有 BPMN 模板预埋 testMode 表达式（模板治理成本）；Nacos 共享环境下的配置开关属**项目级决策**，不能为单次测试随手改共享 dataId（本项目纪律，见 §6.3）。
- **适用**：所有团队的**核心推荐**，与 S3/S4 组合使用。

### S7 流量染色（网关染色 + 灰度路由）

请求经网关打染色 header（如 `X-Flow-Env: test`），路由到测试实例或为流程变量注入 `testMode=true`；前端测试入口统一带染色标识。

- **优点**：对应用代码零侵入；天然支持"同一系统、按请求分流"；与灰度发布体系复用。
- **缺点**：需要网关/注册中心配合（本项目网关 81 + Nacos，需加全局过滤器与路由规则）；异步链路（MQ、定时 Job）没有"请求上下文"，染色会丢，需在消息头/任务表落染色标记；运维与排障复杂度上升。
- **适用**：已有灰度/全链路压测基础设施的中大型团队；微服务数量多、希望按流量而非按环境隔离时。

### S8 数据脱敏与清理

- **脱敏**：测试实例若基于真实业务数据发起（如"把某真实单据走一遍流程"），进入测试态前对手机号/金额/证件号做掩码；表单渲染读源对 `is_test=1` 统一走脱敏出口。
- **清理**：定时 Job 每日清理 N 天前已归档的 `is_test=1` 实例（对齐精讲 §9.5 的历史清理 SQL，并级联 `ACT_HI_TASKINST/ACT_HI_VARINST` 与测试部署）；清理前可导出测试覆盖率报告留存。

- **优点**：满足合规（测试环境不能囤真实个人信息）；防止 ACT 历史表无限膨胀拖慢全库。
- **缺点**：脱敏要逐字段定义规则，有开发成本；清理 Job 需处理级联完整性（漏清关联表会留孤儿行）。
- **适用**：强合规行业**必做**；一般项目至少做"定期清理"。

## 四、方案对比矩阵

隔离强度：★★★（物理不可穿透）＞ ★★（引擎/行级强制）＞ ★（靠代码自觉）。

| 方案 | 隔离强度 | 成本 | 安全性 | 可维护性 | 部署复杂度 | 主要风险 |
| :-- | :-- | :-- | :-- | :-- | :-- | :-- |
| S1 独立环境 | ★★★ | 高（双倍设施+流水线） | 最高 | 高（环境互不影响） | 高（双部署+跨环境发布工具） | 主数据不同步；转正需跨环境迁移 |
| S2 独立 Schema | ★★☆ | 中 | 高 | 中高 | 中 | 双配置维护；转正跨库 |
| S3 tenantId 行级 | ★★ | 低中 | 高（引擎自动继承） | 中（漏过滤即泄露，需封装） | 低（单库） | Job 串台；key 多租户歧义；历史膨胀 |
| S4 is_test 标记（现状） | ★ | 最低（已建成） | 中（靠代码自觉+纵深防御） | 中（新表/新查询要记得带条件） | 最低 | 漏写过滤泄露；直写 ACT 丢标记 |
| S5 独立账号权限 | ★（管人不管数据） | 最低 | 中 | 高 | 最低 | 只防人因失误，不防数据外溢 |
| S6 开关/变量/Profile | ★（行为维度） | 低 | 中 | 高（差异集中管理） | 最低 | 模板需预埋变量；共享配置误改 |
| S7 流量染色 | ★★ | 中高（网关改造） | 中高 | 中（异步链路易丢染） | 中高 | 异步上下文丢失；排障复杂 |
| S8 脱敏+清理 | ★（合规维度） | 中 | 高（合规） | 中（规则要维护） | 低 | 脱敏规则遗漏；清理漏级联 |

**关键结论**：这些方案不是互斥选择，而是**分层的组合**——S5/S6 是所有人的基线，S3/S4 二选一作为数据隔离主干，S1/S2 是预算允许时的强化项，S7 是流量场景的可选增强，S8 是合规底线。

## 五、分场景推荐

### 5.1 按团队规模与业务场景

| 团队/场景 | 推荐组合 | 理由 |
| :-- | :-- | :-- |
| 小团队（1~5 人）、单库快速起步 | **S4 + S5 + S6**（即本项目现状） | 成本最低；用"统一读源封装 + 纵深防御"对冲 S4 的自觉性风险 |
| 中型团队（5~20 人）、多业务线共用工作流 | **S4 → S3 渐进迁移 + S5 + S6 + S8（清理）** | 测试单量上升后，标记遗漏风险变大，tenantId 的引擎自动继承更可靠 |
| 大型团队（20+ 人）、独立运维 | **S1（独立环境）+ S5 + S6 + S8（脱敏+清理）** | 物理隔离一步到位；转正用制品化发布工具 |
| 强合规（金融/政务/国企） | **S1 + S3（若必须单库）+ S5 + S6 + S7（可选）+ S8（必做）+ 发布卡点** | 合规审计要求测试数据不出生产边界、真实数据必须脱敏、发布必须有引用校验卡点 |
| 已有灰度/全链路压测平台 | 在上述基础上叠加 **S7** | 复用既有染色基础设施，边际成本低 |

### 5.2 本项目（springBlade）的推荐路线

dev 为共享环境、单 MySQL 库、blade-workflow 单实例——**维持 S4+S5+S6 为主干（已建成），按三期演进**：

- **近期（P0，补缺口）**：见 §6.1，全部在现有单库标记体系内完成，不动环境；
- **中期（P1，强化）**：若测试单量/并发上升，在 S4 之上叠加 **S3 tenantId 语义隔离**（利用 `WfTaskActReader` 已有的 ACT 租户过滤骨架扩展）+ 测试历史清理 Job（S8 清理维度）；
- **远期（P2，按需）**：若工作流平台化为多团队共用服务，再评估 **S1/S2 独立环境**与 **S7 染色**；届时本项目积累的"统一读源 + is_test 标记"可整体平移为测试环境的实现，代码不用重写。

## 六、落地实施要点（针对本项目）

### 6.1 P0：现有体系内的缺口补齐

| 项 | 问题 | 要点 |
| :-- | :-- | :-- |
| **P0-1 测试页读源一致性** | 测试态 `proc_def_id` 仍指向正式部署，测试页配置面板读到的是正式部署 BPMN，与实际运行的 `__test` 部署可能不一致（已验证的真实缺口） | 测试入口（`testMode=true`）的节点配置/字段权限读源改为：优先取 `test_deployment_id` 对应部署的 BPMN，兜底再走 `proc_def_id` |
| **P0-2 发布前引用校验** | BPMN 里的测试账号/部门/通知渠道可能随"发布"进入正式（精讲 §10.6） | 发布动作前解析 BPMN 全部 `assignee/candidateUsers/candidateGroups/操作者`，命中 `test_`/`mock_`/`dev_` 前缀或测试账号白名单即**拒绝发布** |
| **P0-3 测试历史定期清理** | `cleanupTestData` 仅手动触发，ACT 历史无限膨胀 | 定时 Job：每日归档/删除 N 天前已结束的 `is_test=1` 实例，级联 `ACT_HI_*`、`wf_*`、测试部署；清理量落日志 |
| **P0-4 外溢点纵深盘点** | 超时动作已豁免，但通知/回调/消息推送等出口需逐点确认对 `is_test=1` 的处理 | 盘点所有"离开系统"的出口（`WfProcessNoticeListener`、外部回调、催办），逐一加测试守卫或改投测试通道 |
| **P0-5 新表/新查询纪律** | S4 的固有风险：新增读源漏带 `is_test=0` 条件 | 读源只允许经统一封装（`WfTaskActReader`/读源 helper）；Code Review 检查项 + 一条回归测试：任意新查询默认不含测试数据 |

### 6.2 P1：tenantId 语义隔离叠加（可选，测试量上升时）

在保留 `is_test` 的前提下叠加 Flowable 原生 tenantId（**双保险，不替换**）：

1. **部署打标**：`deployForTest` 增加 `.tenantId(WorkflowConstant.TEST_TENANT_ID)`；正式部署维持业务租户语义不变；
2. **启动显式指定**：所有 `startProcessInstanceByKey` 改为 `ProcessInstanceBuilder.processDefinitionKey(...).tenantId(...)`（精讲 §9.5 风险 2）；
3. **读侧自动注入**：复用 `WfTaskActReader.appendActTenant` 骨架，把过滤条件扩为 `TENANT_ID_ = ? AND COALESCE(IS_TEST_,0)=0`；更彻底可加 CommandInterceptor 全局注入（精讲 §9.4）；
4. **Job 防串台**：本项目的超时扫描已自带 `is_test` 排除（等效于"测试 Job 手动/豁免"），若未来启用 Flowable 原生异步执行器，必须按精讲 §8.4 物理隔离或对测试租户关闭轮询。

### 6.3 P1：配置隔离纪律（共享 dev 环境专用）

- 读侧/数据侧的**项目级开关**（如 `blade.workflow.operator-from-bpmn.enabled` 类 Nacos dataId）不得为"把某个测试跑通"而临时修改——Nacos 发布是全服务广播，曾实测导致 blade-auth 路由 404。测试驱动的缺陷一律先修代码侧，开关变更作为结论提请项目负责人决策；
- 需要"测试专属配置"时，优先用 S6 的变量/Bean 层手段（随请求或随测试实例走），而不是改共享配置中心。

### 6.4 P2：独立环境与脱敏（按需）

- 独立环境：blade-test 库 + 独立 blade-workflow 实例；`wf_process_definition`（BPMN 源）、表单配置经导出/导入接口跨环境迁移；人员组织走统一用户中心（精讲 §10.5），禁止复制两套用户表；
- 脱敏：在"真实数据发起测试"的场景（测试态基于真实单据）进入口加掩码处理器；字段规则维护在表单元数据（复用字段权限的元数据结构），避免散落硬编码。

### 6.5 验收清单（任何隔离改造完成后必测）

1. 正式账号的待办/已办/实例列表/搜索/统计，均不出现 `is_test=1` 数据；
2. 测试实例跑超时节点：无提醒、无自动通过、无转办（纵深防御生效）;
3. 测试实例触达通知/回调出口：真实用户/真实外部系统零感知；
4. 测试部署前后，正式流程定义的"最新版本"不变（`__test` key 隔离生效）；
5. `cleanupTestData` 后：`wf_*` 与 `ACT_*` 无测试残留、无孤儿行，测试部署已卸载；
6. 带测试前缀引用的 BPMN 无法"发布"（P0-2 卡点生效）。

## 七、反模式（禁止）

1. 复制 BPMN 维护 `-test` 副本（改正式忘改测试，维护灾难）；
2. 代码里 `if(env.equals("test"))` 散落硬编码（差异应收敛到变量/Profile/部署标记）;
3. 测试与正式共用数据库且**不做任何标记/过滤**；
4. 用正式账号做测试、或在正式流程定义里直接配测试审批人后发布；
5. 为跑通一次测试修改共享 Nacos/网关等全局配置；
6. 测试环境开启全量异步 + 多线程 Job 与正式同库抢任务（精讲 §8.4）;
7. 把测试实例"转正"（转的是定义不是实例，精讲 §6.5）。

## 全文一句话总结

**本项目已用最低成本跑通"同库标记隔离"（S4+S5+S6），当前正确动作不是推倒重来，而是补齐 P0 缺口（测试读源一致性、发布引用校验、自动清理、外溢点盘点）；数据隔离主干在测试量上升时向 tenantId 行级隔离（S3）演进，环境级隔离（S1/S2）仅在平台化或强合规时启动——隔离手段按"标记 → 行级 → 环境"逐级加码，每一级都保留上一级的纵深防御。**
