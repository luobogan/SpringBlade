## 3. 出口链路选择算法（核心）

位置：`RequestNodeFlow.java` 正向提交分支（L1750 起 `else` 主分支）与「退回到/提交到指定节点」分支（L1473-1749）。二者共用同一套**逐条出口求值 + 短路**逻辑。

// L1765 按设置顺序排序取出当前节点的所有 workflow_nodelink

// L1770 若出口未设置且无指定目标 → 报错返回 false（LINK_NOE_SET）

每条 `workflow_nodelink` 取出 6 个属性（L1794-1801）：
`condition`（旧公式）、`newrule`（新规则 ID）、`id`、`linkname`、`destnodeid`、`ismustpass`、`newconditioncn`。

### 3.2 逐条求值（开源代码实证）

```java
// L1672-1742（指定节点分支的同构逻辑，主分支相同）
for (int linkindex = 0; linkindex < linkids.size(); linkindex++) {
    String whereclause = (String) whereclauses.get(linkindex);   // 旧公式
    String newrule     = (String) newrules.get(linkindex);       // 新规则 ID
    boolean oldcop = false, newcop = false;

    if (whereclause.trim().equals("") && newrule.trim().equals("")) {
        break;                                                   // 无条件出口 → 直接命中
    }
    // 取规则间关系（并且/或者），存于 workflow_nodelink.ruleRelationship
    // L1688: select ruleRelationship from workflow_nodelink where id = <linkid>
    int ruleRelationship = ...; // 1=并且, 2=或者

    // —— 旧公式求值 ——
    if (!whereclause.trim().equals("")) {
        if (isbill == 1)
            sql = "select count(id) from " + billtablename
                + " where id=" + billid + " and " + whereclause;        // ← 直接拼接
        else
            sql = "select count(requestid) from workflow_form "
                + " where requestid=" + requestid + " and " + whereclause;
        rs.executeSql(sql);
        if (rs.next() && rs.getInt(1) > 0) oldcop = true;

        if (ruleRelationship == 2 && oldcop) break;     // 或：旧条件已满足，跳过新规则
        if (ruleRelationship == 1 && !oldcop) continue; // 且：旧条件不满足，直接下一出口
    } else if (ruleRelationship == 1) {
        oldcop = true;   // 且无新规则时视为满足
    }

    // —— 新规则引擎求值 ——
    if (!newrule.trim().equals("")) {
        RuleInterface rif = new RuleInterface();
        rif.setUserid(this.userid + "");
        rif.setAutoForecast(this.autoForecast);
        rif.setForecastManagerInfo(this.forecastManagerInfo);
        newcop = rif.compareRuleforWF(newrule, requestid + "",
                                      nextlinkid + "", RuleInterface.RULESRC_CK);
    } else if (ruleRelationship == 1) {
        newcop = true;
    }

    // —— 组合判定 + 短路 ——
    if (ruleRelationship == 1) { if (oldcop && newcop) break; }   // 并且
    else                       { if (oldcop || newcop) break; }   // 或者
}
```

### 3.3 算法语义（精炼）

| 要素 | 行为 |
|---|---|
| **顺序** | 严格按 `linkorder, id` 升序；**首条命中即短路**（`break`） |
| **无条件出口** | `condition` 与 `newrule` 皆空 → 直接命中（通常作为「默认/else」出口放在最后） |
| **旧公式判定** | 把 `condition` 当作 `WHERE` 子句拼进 `select count(...) from <单据表> where id=? and <condition>`；`count>0` 即真 |
| **新规则判定** | `RuleInterface.compareRuleforWF(newrule, requestid, linkid, RULESRC_CK)` 调规则引擎（**求值内部实现详见《泛微E9-流程规则引擎(条件求值)深度分析.md》**） |
| **组合关系** | `ruleRelationship=1`（并且）：需两者皆真；`=2`（或者）：一真即真 |
| **未设出口** | `getNodeLinkrs` 返回 0 行且无指定目标 → 返回 `false`，报错 `LINK_NOE_SET`（L1766-1777） |

> ⚠️ **关键架构事实**：出口选择是 **「有序 + 首匹配」** 而非「所有满足条件的出口都走」。这意味着若多条出口条件都为 true，只有 `linkorder` 最小的那条被选中——设计时必须把「更具体」的出口排在前面，否则会被「默认出口」截胡。这一点在现有文档/UI 中容易被忽视。

## 4. 条件求值：旧公式 vs 新规则引擎

| 维度 | 旧公式 `condition` | 新规则 `newrule` |
|---|---|---|
| 存储 | `workflow_nodelink.condition`（文本） | `workflow_nodelink.newrule`（规则 ID，→ `rule_*` 表） |
| 求值 | 拼进 `select count from <bill> where ... and <condition>` | `RuleInterface.compareRuleforWF` → `weaver.workflow.ruleDesign.RuleBusiness` |
| 引擎 | 无（纯 SQL 谓词） | 独立规则引擎 `ruleDesign`（IKExpression/`Expressions`） |
| 表达力 | 单表字段比较（形如 `col > 5`） | 多字段/函数/跨表/复杂逻辑 |
| 优先级 | 由 `ruleRelationship` 与 `newrule` 共存组合 | 同上 |
| 兼容 | 老流程数据仍依赖 | 新设计器主推 |

**安全口径（重要，避免误报）**：旧公式 `condition` 在运行时**被直接字符串拼接进 SQL**，但该字符串是**设计期由管理员在流程设计器配置的固定谓词**（引用单据表列名，不插值运行期表单值），所以**不是终端用户可触发的前端注入点**——属于「非参数化 SQL 构建」的设计异味 + 仅管理员可控的注入面。这与本文档 §9 提到的 `GroupDetailMatrix` 等**运行期用户可控注入**性质不同，不应混入同一 P0 项。

## 5. 分支 / 合并（分叉合并）

实现：`WFLinkInfo.FlowToNextNode(int requestid, int nodeid, int nextnodeid, String nextnodesttr, int passnum, int ismustpass)`（`WFLinkInfo.java:81`）。`WFLinkInfo` 实为 `weaver/workflow/request/WFLinkInfo`（非 `workflow/workflow/`），继承 `BaseBean`。

### 5.1 合并策略（`nextnodesttr`）

| 值 | 含义 | 源码 |
|---|---|---|
| `"3"` | 按**通过分支数**合并 | L113 `select distinct nodeid,isremark from workflow_currentoperator ... nodeid in(<nownodeids>) ...` 统计已到达的分支 |
| `"4"` | **指定分支**合并 | L138/L369 取 `ismustpass='1'` 的分叉起点，校验其是否全部流转完毕 |

### 5.2 依赖的图遍历辅助方法（同文件）

- `getStartNodeidByEndNodeid(workflowid, nextnodeid)`（L198/398）
- `getMustPassStartBrancheNode(...)`（L741/1480/1761）
- `getBrancheLastNode(...)`、`getLastBrancheNodes(...)`、`getBrancheTOMergerNode(...)`（L512-564）
- `getSummaryNodes(...)`（L482）、`getFirstBrancheNode` / `getBrancheMergerNode`（L545-546）

这些函数基于三张表做图遍历：
- `workflow_nodelink`（`nodeid→destnodeid` 有向边，过滤 `wfrequestid is null and isreject is null/<>'1'`）
- `workflow_nownode` + `workflow_freenode`（记录实际已走过的自由/分叉节点，`L98`）
- `workflow_currentoperator` / `workflow_requestlog` / `workflow_requestflowinfo`（判定某分支是否已处理完，L200-214）

### 5.3 源码自带的风险提示

`WFLinkInfo.java:203` 注释原文：
> `rs.executeSql(sql);//按照实际走的流程出口来计算比例，通过分叉起始节点走的出口分支数计算.多次流转可能有bug`

即**多次流转（驳回后重新走分叉）时合并计数可能出错**——这是已确认的算法级隐患（对应登记册 WF-P1 类「逻辑正确性」）。

## 6. 退回机制

`RequestNodeFlow` 中 `isreject==1` 分支，由 `RejectToType` 决定去向：

| RejectToType | 行为 | 证据 |
|---|---|---|
| `0` | 退回到**创建节点**（`nodetype='0'`）；若无 `isreject='1'` 的退回出口则回创建节点 | L790-794 `select nodeid from workflow_flownode where workflowid=? and nodetype='0'` |
| `1` | **重新分叉**：取 `RejectToNodeid` 的全部 `workflow_nodelink`（`isreject is null or <> '1'`）逐条求值 `condition/newrule` | L1484-1492 |
| `2` | **取消合并**：取 `RejectToNodeid` 对应分叉末节点的 `workflow_nodelink` | L1498-1502 |

退回出口以 `workflow_nodelink.isreject='1'` 标记（L1770 `order by linkorder,id`）。

## 7. 线程安全与幂等

`RequestManager.flowNextNode` 注释（L2759-2765）明确：
- 进入时把当前请求放入 `application` 变量 `GCONST.WFProcessing`，防止**同一节点的多个操作人重复提交**；
- 方法执行完毕后**必须**从 `GCONST.WFProcessing` 清除当前请求。

> 这是**进程内、基于 application 作用域**的粗粒度锁，跨 JVM（集群多节点）**不生效**——在负载均衡/多实例部署下，同节点的并发提交仍可能竞态。若需强一致需引入分布式锁（登记册未单列，建议作为 P1 新增）。

## 9. 与风险登记册的对应 & 新增发现

### 9.1 与现有登记册对应
- **WF-P0-2**（`WorkflowVersion`/`WorkflowActionManager` 拼接）：属设计期 SQL，与运行时出口无关；本文未新增该处证据。
- **WF-P1-1/2**（图形设计器 iframe / 两套设计器）：属设计期 UI，与运行时算法正交。
- **WF-P1-5**（`printStackTrace` ≥54 处）：流转代码本身也大量使用，建议补充 `RequestNodeFlow`/`RequestManager` 到该清单。

### 9.2 本文新增的可登记风险
| 新 ID | 严重度 | 问题 | 证据 |
|---|---|---|---|
| WF-N1 | P1 | **出口「首匹配短路」语义隐蔽**：多条出口皆真时只走 `linkorder` 最小者，设计不当会被默认出口截胡 | `RequestNodeFlow.java:1672-1742`（`break` 首命中） |
| WF-N2 | P1 | **分叉合并多次流转计数可能有 bug**（源码注释自承） | `WFLinkInfo.java:203` |
| WF-N3 | P1 | **进程内 `GCONST.WFProcessing` 锁跨集群无效**，多实例下同节点并发提交可竞态 | `RequestManager.java:2759-2765` |
| WF-N4 | P2 | 旧公式 `condition` **非参数化拼接**进 SQL（管理员可控，非终端用户注入） | `RequestNodeFlow.java:1698-1700` |
| WF-N5 | P2 | 调试残留：L764 `System.out.println("nextnodecount = ...")` 等直接 `System.out` 输出 | `RequestNodeFlow.java:764` |

> 建议在《泛微E9-跨模块风险登记册.md》的 workflow P1/P2 区补充 WF-N1~WF-N5（尤其 WF-N1/N2/N3 属流转正确性与集群安全的实打实隐患）。
