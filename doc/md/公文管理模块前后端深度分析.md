> 分析对象：泛微 e-cology「公文管理」模块
> - 前端代码根：`D:\Weaver2020\ecology`（JSP/JS 传统 webapp；模块目录 `odoc/`）
> - 后端代码根：`D:\workproject\ecology\src`（Java，约 2.99 万 .java）
> - 分析方式：源码静态探查 + 本地 MySQL（ecology* 三套库）菜单表检索 + SQL Server `ecology2020_demo`（生产态 schema 与菜单实证）

## 0. 模块概览

公文管理是 e-cology 的核心业务模块，实现**发文 / 收文**全生命周期：拟稿 → 流转（审批） → 办结/归档，并配套待办、已办、监控、模板、权限、统计等能力。

- **核心领域模型**：一条公文 = 一条工作流请求（`workflow_requestbase`）+ 一组公文扩展属性（`odoc_*` 表）。公文本质上跑在 e-cology 工作流引擎之上，公文模块在流程引擎外再叠加了"种类/密级/缓急/字号/收文单位/签批套红/督办"等公文专属语义。
- **关键维度 `officalType`**：`1=发文`、`2=收文`、`3=签批`——大量接口用该参数区分发文/收文/签批多套界面与逻辑。
- **包分布**：
  | 后端包 | 角色 | 路径 |
  |---|---|---|
  | `com.engine.odoc` | 公文引擎主体（新建/主流架构） | `src\com\engine\odoc\` |
  | `com.api.odoc` | 公文 API / 工具 / 前端对接（含 `@Path` REST） | `src\com\api\odoc\` |
  | `weaver.docs` | 旧版发文/收文实现（遗留，`senddoc`/`change`） | `src\weaver\docs\` |

## 1. 总体架构与分层

后端统一采用 **REST Action（JAX-RS `@Path`）→ Service / ServiceImpl → Command（Cmd）→ RecordSet / ORM** 的分层模式：

```
前端 JSP/HTML（或 SPA 页）
   │  AJAX / 表单提交
   ▼
 ecology servlet 框架 / JAX-RS 分发
   ▼
 *Action（@Path 端点）  e.g. OdocRequestAction / OdocTodoListAction
   ▼
 *ServiceImpl（业务编排）
   ▼
 *Cmd（命令模式，单条事务；继承 OdocAbstractCommonCommand 统一鉴权）
   ▼
 RecordSet（JDBC）/ 实体 ORM（@Table）→ MySQL
```

- **统一权限校验基类**：`com\engine\odoc\cmd\OdocAbstractCommonCommand.java`
  用 `HrmUserVarify.checkUserRight(...)` 集中校验公文权限字，例如：
  `SRDoc:Edit`、`SendDoc:Manage`、`OdoSpecification:Edit`、`DocOdocType:All`、`DocInstancyLevel:All`、`DocSecretLevel:All`、`DocTopicType:All`、`DocReceiveUnit:All`、`DocProcessDefine:All`、`DocCommReceiveGroup:All`、`OdocApplication`、`DocChange:Setting`、`odocDictionary:Edit`、`OdocInnerChange:Setting`、`OdocMould:Edit`。
- **前端交互范式**（详见第 4、5 节）：
1. **odoc SPA / REST（主流）**：odoc 7 大功能及基础数据配置均以 SPA 形式挂载（菜单 `linkAddress` 指向 `/spa/odoc/static/` 或 `/spa/odoc/static4engine/` 的 hash 路由），SPA 经 AJAX 调 `/api/odoc/*` 的 `@Path` 端点（详见第 4、5 节）。
2. **遗留 server-rendered（weaver.docs）**：仅旧版发文/收文（`senddoc`/`change`）与旧 socket 公文传输走服务端渲染 JSP 页，调 `weaver.docs.*` 旧 Action。

## 4. 与门户菜单（menuIds=1366,10139）的关联逻辑

### 4.1 菜单挂载机制（E9 实测）
e-cology 将各模块挂接到**门户/左侧菜单**靠菜单系统：
- 菜单条目存储在 `leftmenuinfo` 表，每条含 `id`（即 menuId）、`linkAddress`/`routeurl`（真实路由）、`relatedModuleId`/`module`（模块）、`parentId`、`customName`/`labelId`（显示名）、`defaultIndex` 等（已核对 SQL Server `ecology2020_demo` 真实列名）。
- **公文管理在 E9 是以 SPA 形式挂载的**，而非传统 JSP 列表页：每个左侧菜单条目的 `linkAddress` 指向 odoc 单页应用——
  - 业务功能页：`/spa/odoc/static/index.html#/main/offical/<功能路由>`
  - 基础数据/引擎配置页：`/spa/odoc/static4engine/engine.html#/odocengine/<配置路由>`

## 10. flowable8 迁移落地评估（基于已坐实架构）

> 判定依据：本分析已确认 odoc = **工作流引擎（workflow_* 表）+ odoc 扩展属性（odoc_* 表）双层模型**，二者经 `requestid` 关联；对外契约是 `/api/odoc/*` REST（SPA 消费）；正文编辑（onlineEdit）与基础数据（odocType 等）相对独立。迁移到 flowable8 时，按"依赖工作流引擎的程度"分三档。

### 10.1 复用度分档总览

| 档位 | 含义 | 涉及功能 |
|---|---|---|
| **A. 数据/配置层，基本可平移** | 纯关系表 + 轻逻辑，不依赖 Weaver 工作流内部表 | 基础数据（公文种类/主题/密级/缓急/字号/机构代字/收文单位）、模板管理（odoc 模板表 + iWebOffice）、正文在线编辑组件 |
| **B. 需重写数据访问，契约可保留** | 业务逻辑依赖 `workflow_*` 待办/已办/监控查询，须改为 flowable Task/History API，但对外 REST 契约与 SPA 可保留 | 待办处理、已办查询、流程监控、数据统计 |
| **C. 需重写（引擎强耦合）** | 直接驱动 Weaver 流程命令/节点/表单/交换 | 发起流程（saveData/flowNext 流转）、交换/文种转换、权限字体系 |

### 10.2 七大类功能逐条评估

| 功能 | 当前核心依赖 | flowable8 策略 | 复用度 |
|---|---|---|---|
| **1. 发起流程** | `OdocRequestAction.saveData/flowNext` → Weaver 流程提交命令；表单来自 workflow 字段库 | 改为 flowable `startProcessInstance` + 表单数据落 `odoc_requestdoc`；字段库/表单模型需随流程一起迁移 | C（重写流转，数据模型可复用） |
| **2. 待办处理** | `OdocReqListCmd` 三联表 SQL（`workflow_requestbase×workflow_currentoperator×odoc_requestdoc`） | 改为 flowable `TaskService.createTaskQuery`（RU_TASK）+ `HistoryService`（已办）+ 关联 `odoc_requestdoc`；`officalType` 过滤改为在流程定义/分类维度上实现 | B（契约+数据可留，查询重写） |
| **3. 已办查询** | 待办接口 `iscomplete=true` 复用同一 Cmd | 同待办，走 flowable 历史任务查询 | B |
| **4. 流程监控** | `OdocMonitorListAction` 复用 workflow monitor Cmd（delete/archiving/stop/open/intervention） | 改为 flowable `ProcessInstance`/`Activity` 管理 + 管理 API（`runtimeService`/`historyService`/admin）；管控动作需重做 | B→C（查询 B，管控动作 C） |
| **5. 模板管理** | `OdocMouldAction` + odoc 模板表 + iWebOffice | 模板表与编辑组件独立，**基本平移**；仅 API 壳需从 Weaver JAX-RS 迁到 Spring 控制器 | A |
| **6. 权限配置** | `OdocRightMenuAction` + Weaver 权限字（`OdocMould:Edit` 等） | 权限字体系替换为 Spring Security / flowable candidate group；功能菜单/转办配置需重新建模 | C（鉴权模型替换） |
| **7. 数据统计** | `OdocReportAction` 聚合 Cmd（条件→计数→ECharts→明细） | 聚合逻辑改为 flowable HistoryService 查询 + 同样的 `odoc_*` 维度；ECharts 前端可复用 | B |

### 10.3 关键结论与建议
- **可整体保留的"契约"**：SPA 前端（`#/main/offical/*`）与 `/api/odoc/*` 的 JSON 形态——这是前后端解耦点，迁移时尽量**保持接口契约不变**，仅替换后端实现，前端改动最小。
- **必重写的核心**：所有直接读写 `workflow_*` 待办/已办/流程命令的代码（第 9 节走读的 `OdocReqListCmd` 是最典型样本），整体替换为 flowable 的 Task/History/Runtime API；`requestid` 映射为 flowable `processInstanceId`/`businessKey`。
- **可平移的资产**：`odoc_*` 扩展表（公文专属属性）、基础数据表、模板与正文编辑组件——这些是"公文"业务的真正载体，与流程引擎无关，迁移成本低、价值高。
- **最高风险点**：发起流程的流转语义（`flowNext`/`flowReject`/强制归档/干预）与 Weaver 节点模型深度绑定，是迁移工作量最大、最需逐动作对齐的部分（对应 10.2 的 C 档）。

## 14. 改造 POC：发起流转迁移到 flowable8（C 档样板）

> 针对第 12 节定位的耦合点（`FlowNextCmd` 委托 Weaver `RequestManager` 推进流转）。这是 C 档（引擎强耦合）最难、也最具代表性的重写。本节给出"发起流转"在 flowable8 的等价建模与改写路径。

### 14.1 现状路由模型（从 FlowNextCmd 提取）
`flowNext` 在运行时**动态**决定下一节点与操作者，而非由固定 BPMN 连线决定：
- **入参**：`requestid`、`workflowid`、`nodeid`、`isend`、`remark`、`assignRemark`、`submitType`、`nextDirections`(JSON)。
- **`nextDirections`**：前端传的流转去向数组，每项含 `nodeid`(目标节点)、`userIds`(操作者)、`ccUserIds`(抄送)、`userSignType`(会签类型)、`userTransferType`(流转方式)、`userCopyType`(抄送方式)。
- **节点配置**（`OdocFlowTransferBiz.getNodeConfig`）：`signType`(会签/或签/不签)、`transferType`、`copyType`、`endRequestType`(强制结束本人)、`assignment`(可否交办)。
- **动作**：组装 `OdocRequestEntity`+`OdocOperatorEntity`，调 `RequestManager.setSrc("submit")` 提交。

### 14.2 flowable 等价建模
| odoc 概念 | flowable8 等价 | 说明 |
|---|---|---|
| `workflowid` + 流程定义 | `ProcessDefinition`（`processDefinitionKey` 区分发文/收文/签批） | 见 13.2 |
| `nodeid`（节点） | 通用 `UserTask`（每节点一个 task 定义，`taskDefinitionKey` 对应） | 采用**通用审批节点**而非每节点特化 |
| `nextDirections[].userIds` | `Task` 的 `candidateUsers` / `assignee` | 运行时动态指派，不走固定连线 |
| `signType`(会签/或签) | **多实例（Multi-Instance）** + `completionCondition`（`nrOfCompletedInstances==nrOfInstances` 会签 / `>=1` 或签） | 用 `ParallelGateway`+ 多实例任务 |
| `copyType`(抄送) | **非阻塞任务**（`historic` 仅记录 / 抄送通知），不进入待办阻塞链 | 抄送不阻塞主流程 |
| `transferType`(流转方式) | 转办=改 `assignee`；加签=插入多实例；退回=`flowReject`→回退到历史节点 | 见 14.4 |
| `assignRemark`(交办意见) | `taskService.addComment` / 流程变量 | 随任务存意见 |
| `endRequestType=2`(强制结束本人) | `taskService.complete` 后该节点不再生成本人待办 | complete 即释放 |

### 14.4 配套动作映射
- **退回（`flowReject`）**：flowable 用 `runtimeService.createChangeActivityStateBuilder()` 把执行流移回历史节点，或用"退回任务"模式（新增退回线）。
- **强制归档（`forceArchive`）**：直接 `runtimeService.deleteProcessInstance` + 置 `odoc_requestdoc.isLasttime`/归档状态；归档动作保持写 `odoc_requestdoc`（B 档数据）。
- **收回/干预（监控动作）**：flowable admin API（`ProcessInstance`/`Activity` 迁移）+ `runtimeService` 操作，对应 `OdocMonitorListAction` 的 `repossessed`/`intervention`。

### 14.5 难点与风险
1. **自由路由的"节点"语义**：odoc 的 `nodeid` 是 Weaver 流程节点，flowable 需把每个公文节点映射为一个通用 task 定义（同 `taskDefinitionKey`），路由信息存变量，避免 BPMN 连线膨胀。
2. **会签/或签 completionCondition**：odoc 的 `signType` 必须精确映射，`userSignType` 用户选择项（signType=4）需在多实例创建时按前端值设定。
3. **抄送非阻塞**：必须保证抄送不生成阻塞待办（否则破坏 odoc 的"知悉"语义）。
4. **与 B 档联动**：流转后生成的待办须可被第 13 节的 `TaskService` 查询正确捞取（同 `businessKey`/`processDefinitionKey` 体系）。

> 结论：**A/B/C 三档迁移至此均已给出落地样本**——A 档（基础数据/模板表平移，第 11 节）、B 档（待办查询 POC，第 13 节）、C 档（发起流转重写 POC，本节）。发起流转是迁移工作量最大处，但其核心可归纳为"通用节点 + 运行时动态指派 + 多实例会签 + 抄送非阻塞"，无需把 Weaver 节点模型 1:1 搬到 flowable。

> 注：`odoc_requestdoc` 的**写入时机**（流程创建/提交触发）由 workflow 自动动作调用 `OdocRequestdocInit*` 完成——本文件只证实了"写什么/从哪读"，触发钩子未在 odoc 包内定位，待核实。但第 12.2 节"由工作流自动动作/触发器写入"的推测方向已被本实证支持：机制是**表单表→镜像同步**，而非魔法触发器。

**迁移含义**：flowable 侧表单字段将落在流程变量/独立表单表，`odoc_requestdoc` 镜像的"表单表→odoc_requestdoc"同步逻辑须重写为"流程变量/表单表→odoc_requestdoc"（或改用视图/JOIN 替代镜像）；字段语义与 `odoc_field_lib` 映射配置可平移——这是 B 档数据完整保留的关键细节，第 11 节未点明。

### 15.2 交换与文种转换链路（C 档补全）
#### 15.2.1 文种转换（DocTypeChange）
把一条公文的"文种/流程类型"在流转中变更并重新路由。端点在 `OdocDocTypeChangeAction`（根 `/api/odoc/odocDocTypeChange/*`，全部 `@POST`）：

| 端点 | 用途 |
|---|---|
| `/getDocTypeChangeSetting` / `saveDocTypeChangeSetting` / `delateDocTypeChange` | 变更流程配置 查/存/删 |
| `/saveDocTypeChangeBasic` | 保存基础设置 |
| `/getAssignmentSettings` / `saveAssignmentSettings` | 赋值设置（字段重新映射） |
| `/getDocTypeChangeRevisionInfo` / `getIsMobileRevisionInfo` | 变更记录（PC/移动） |
| `/submitDocTypeChange` | 表单内提交变更 → `OdocSubmitDocTypeChangeCmd` |

关联：`odoc_field_lib`（字段映射）、`DocChangeSetting`(entity)、`OdocTypeChangeWorkflow`(standard entity)、`odoc_chanwfsetdetail`、`OdocTypeChangeRevision`。本质：**改 `officaltype`/`odoctype` 并重跑归档/文库路由**，绑定 workflowid 的字段映射 + 流程重路由 → C 档。

#### 15.2.2 交换（Exchange）
| 子能力 | 实现类（根） | 对接方式 | 关键表 |
|---|---|---|---|
| 外部交换（对接其他 OA 平台） | `OdocExchangeWorkflowAction`(20KB) + `OdocExchangeSettingAction`（`/api/odoc/odocExchange*`） | WebService（`CallExchangePlatformFieldsSettingWsCmd`）/ FTP（`OdocExchangeWorkflowExchangeFieldsForFtp*`） | `odoc_exchange_*`（com_admin/com_fieldattr/com_user/company/docbase/docreceiveunit/field/recieveinfo/status）、`odoc_sendtoexchange` |
| 内部交换（本单位机构间） | `OdocInnerChangeAction`（`/getForm`/`getList`/`getSearchCondition`） | 本系统数据交换 | `exchange_senddocinfo_inner`、`exchange_receive_doc_inner`（由 `OdocRequestdocUtil.updateInnerChangeData` 按 `issued_number_of_document` 关联维护） |

> 第 9 节 `OdocReqListCmd.fromSql` 中 `exchange_sendDocInfo_oa eso` 左连接，正是外部交换发文的关联表。

**迁移含义**：
- 外部交换是 C 档中**外部依赖最强**的部分——依赖对方 OA 平台的 webservice/FTP 契约，**flowable 迁移无法替代**，须保留为独立适配层（仅把"本端公文数据来源"从 workflow 表单改为 flowable 变量/odoc_requestdoc 镜像）。
- 内部交换可随流程重写（本质是"把本条 requestid 推送给目标机构并回写接收状态"），`exchange_senddocinfo_inner`/`exchange_receive_doc_inner` 归 C 档。

### 15.3 迁移约束补充：前端 SPA 源码不在仓库（回应评审第 10 项）
第 7 节已指出 SPA 仅以构建产物存在于 tree。这对"保留前端契约"策略是**硬约束**：你无法修改 SPA 源码，意味着 `/api/odoc/*` 的 JSON 契约在迁移中**必须严格保持**（否则 SPA 无法工作），任何新增字段须向后兼容。第 13/14 节 POC 默认"前端零改动"正是基于此；若目标环境要重构 SPA，应单列前端迁移项目，不在后端 odoc 迁移范围内。
