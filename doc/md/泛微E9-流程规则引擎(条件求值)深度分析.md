## 1. 规则引擎在流程中的角色

`RuleInterface`（包 `weaver.workflow.ruleDesign`）是流程里**所有结构化条件**的统一求值器，被以下场景复用（由 `rulesrc` 区分）：

| rulesrc | 场景 | 取 `ruleRelationship` 的表 |
|---|---|---|
| 1 | 节点出口条件（`workflow_nodelink`） | `workflow_nodelink` |
| 2 | 批次/组条件（`workflow_groupdetail`） | `workflow_groupdetail` |
| 5 | 流入流程设置（`wfec_indatawfset`） | `wfec_indatawfset` |
| 6 | 代理人条件（`workflow_agentConditionSet`） | `workflow_agentConditionSet` |
| 7 | 子流程触发（`Workflow_SubwfSet`） | `Workflow_SubwfSet` |
| 8 | 差异子流程（`Workflow_TriDiffWfDiffField`） | `Workflow_TriDiffWfDiffField` |
| 9 | 节点超时（`workflow_nodeovertime`） | `workflow_nodeovertime` |
| 3 | 合规校验（`ConformCheckBiz` 内部另走一套） | — |

> 即「出口条件只是规则引擎的 1/8 用法」。因此本文结论对批次、代理人、子流程等同样适用。

### 1.1 规则存储模型（DB）

| 表 | 关键列 | 作用 |
|---|---|---|
| `rule_base` | `id, formid, isbill, rulesrc, linkid` | 规则主体，关联表单 |
| `rule_expression` | `ruleid, datafield` | 表达式定义（`getRuleConditionString` L1146 读；`getDataField` L347 读 `select datafield from rule_expression where ruleid=?`） |
| `rule_condition` | `ruleid, ...` | 条件明细（字段/比较符/值） |

`Expressions.toIKExpressionMap()` 把上述结构化为一个 IKExpression 字符串 + 变量元数据列表。

## 3. 求值主流程（L123-343）

```
for 每个 ruleid (L187):
  ① 读 rule_base (id,formid,isbill,rulesrc)            [L189 select ... from rule_base where id=<ruleid>]
  ② 解析表单字段元数据:
       isbill=0 → workflow_formfield + workflow_formdict
       isbill=1 → workflow_billfield (经 workflow_bill 取 tablename)   [L213-226]
  ③ 取实际表单值:
       select <fields> from workflow_form / <billtable> where requestid=<requestid>  [L264-266]
       rsformvalue.isReturnDecryptData(true)  // 加密字段解密
  ④ 值预处理 fieldValPreProc(htmltype,type,value) → val_map   [L284]
  ⑤ getRuleConditionStringByIKE(ruleid, ids_map, val_map, ...) → "true"/"false"   [L320]
  ⑥ 按 ruleRelationship(1=且/2=或) 短路合并   [L328-338]
```

**`ruleRelationship` 来源**（L151-181）：`rulesrc==1` 时 `select ruleRelationship from workflow_nodelink where id=<linkid>`；初始 `result = (ruleRelationship==1)`（且→true / 或→false），与出口选择的 `ruleRelationship` **同源同义**。

> **与流转核心 §3 的衔接**：流转核心的「旧公式 `condition`」与「新规则 `newrule`」二者在 `RequestNodeFlow` 中按 `ruleRelationship` 组合；而 `newrule` 内部又是一组 `ruleid` 按**同一个 `ruleRelationship`** 再组合——即**两层 and/or 嵌套**，设计器需同时配置两处关系。

## 4. `getRuleConditionStringByIKE` 内部（L603-985）—— 核心

```java
// L604-617
Expressions expressions = RuleBusiness.getExpressionsByAll(ruleid, isMapitem, linkid, rulesrc);
expressions.setUserid(this.userid);
Map ruleall = expressions.toIKExpressionMap();      // 生成 IKExpression
String expression = ruleall.get("exp");             // 形如 "VAR_12 > 20 && container(VAR_12, '98')"
String ruleids   = ruleall.get("ids");              // 变量元数据列表
```

随后构建 `List<Variable> variables`，把每个规则变量绑定到表单实际值：
- 变量名 `VAR_<fieldid>`（或 `_STR` 字符串型、`VAR_A<id>_<n>` 重命名型、系统字段 `VAR__10~_13`）。
- 值来自 `val_map`（第 ③ 步取的表单值），按 `htmltype`/`type` 做**类型化绑定**：整数 `Util.getIntValue`、小数 `Util.getDoubleValue`、浏览框/选择框空值特殊处理。

**最终求值（L941）**：
```java
Object result = ExpressionEvaluator.evaluate(expression, variables);
```
- 返回 `Boolean`（"true"/"false"）。
- 异常时 catch（L966-981）：记日志 + `e.printStackTrace()` + **`return false`**（即求值异常**默认 fail-closed**，该规则视为不满足）。

## 5. 变量绑定边界（代码量最大的部分，L656-935）

| 场景 | 处理 | 证据 |
|---|---|---|
| 人力资源字段同时映射「整数(安全级别)」+「HR值」 | 正则把 `VAR_1233` 重命名为 `VAR_A1233_0/1` 以区分（避免单次传值导致规则错判） | L750-794 |
| 复选框空值 | 置 `"NULL"` | L685-687 |
| 选择框/浏览框空值 | 整数型置 `-1`；其余保留空串 + `replaceExpression` 改写为 `false`/`true` | L834-842 |
| 数值/小数空值 | 追加 `_STR` 字符串变量供 `$ISEMPTY`/`$ISNOTEMPTY` 宏使用 | L802-808, L845-863 |
| 系统字段 创建人/经理/部门/分部 | `VAR__10`~`VAR__13`（来自 `workflow_requestbase.creater` 的 manager/dept/subco） | L876-935 |
| 含下级比较（compareoption 11/12） | 值以 `~~##~~` 分隔拼接，交给 `container()` 做子树归属判断 | L877-890 |

宏函数：`container(x, y)`（属于/包含）、`$BROWSERCONTAINS`、`$ISEMPTY`、`$ISNOTEMPTY` 等，由 `ExpressionEvaluator` 识别。

## 6. 安全结论：新规则 vs 旧公式（核心对比）

| 维度 | 旧公式 `condition` | 新规则 `newrule`（规则引擎） |
|---|---|---|
| 求值方式 | 拼进 `select count(...) from <单据表> where id=? and <condition>` | `ExpressionEvaluator.evaluate(exp, variables)` |
| 值如何进入求值 | **字符串拼接进 SQL 谓词** | **类型化 `Variable` 绑定**，表达式本身不变 |
| 注入风险 | 设计期公式非参数化（仅管理员可控，非终端用户注入） | **参数化绑定，无注入面** |
| 表达力 | 单表列比较 | 多字段/函数/`container`/系统字段/加密字段解密 |
| 异常行为 | 取决于 SQL 报错 | **fail-closed 返回 false** |

> ✅ **关键结论**：流程出口条件的「新规则」路径是**安全且参数化**的，与流转核心 §3 的旧公式拼接形成对照。改造时**应优先/统一使用新规则引擎**，旧公式仅作兼容保留。
