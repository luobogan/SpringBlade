## 1. 功能定位

「流程测试」是**流程引擎的路径（Path）调试工具**：在流程**正式发布前**，由管理员指定一个「发起人身份」，让这条流程在**真实的流程引擎上完整跑一遍**（自动流转直到归档节点），从而验证配置是否正确：

- 创建节点的操作者是否配得对（选的人能不能发起）
- 各节点的操作者是否能正确计算出来
- 出口（连线）条件是否按预期命中
- 节点前/后附加操作、出口附加规则、出口生成流程编号是否被触发
- 表单必填/提交是否被卡住

产出物是一份**逐节点的测试日志**（到达节点 → 操作者 → 提交 → 通过节点 → 执行出口 → 到达下一节点 …），可保存、可下载。

**它不是另写一套模拟引擎，而是「真实引擎 + 测试态开关 + 身份模拟」。**

## 4. 前置条件

### 4.1 功能权限

所有后端 Cmd 首行校验：

```java
if (!HrmUserVarify.checkUserRight("Delete:TestRequest", user)) { ... }
```

无权限 → 返回 `authority:false` → 前端渲染「对不起，您暂时没有权限 ！」。

### 4.2 流程必须处于「未发布/可测试」状态

```sql
-- GetWfTestInfoCmd：只有 isvalid='2' 且存在创建节点(nodetype=0)的流程可被测试
select base.id, base.workflowtype, base.workflowname
from workflow_base base
where base.isvalid = '2'
  and exists(select * from workflow_flownode node where node.workflowid = base.id and node.nodetype = 0)
```

`TestWorkflowComInfo` 正是 `workflow_base` 在 `isvalid='2'` 上的缓存类。

### 4.3 支持性校验（`judgeSupportSpaTest`）

| 表单类型 | 条件 | 结果 |
|---|---|---|
| 系统单据（`isbill=1 && formid>0`） | `SystemBillManagerBiz.judgeSupportCustom()` | 不支持 → 「此系统单据暂不支持测试！」 |
| 自定义表单 | 存在「模板模式」节点（`ismode='1'` 且非自由节点） | 不支持 → 「此流程节点包含模板模式显示模板，暂不支持测试！」 |

## 6. 核心原理

### 6.1 身份模拟（Impersonate）

`RequestFormBiz` 取用户时插入测试逻辑：

```java
TestWorkflowCheckBiz testBiz = new TestWorkflowCheckBiz();
boolean belongTest = testBiz.judgeBelongTest(request, isfirst);
User returnUser = belongTest ? testBiz.readTestUser(request, currentUser, isfirst) : currentUser;
if (belongTest && returnUser != null) {
    returnUser.setUseAttrLanguage(true);
    returnUser.setLanguage(currentUser.getLanguage());   // 界面语言仍用真实管理员的
}
```

`readTestUser` 按 `wftest_usertype` 构造 User：`0`=HR 人员 / `1`=CRM 客户（`CRM_CustomerInfo`）/ `2`=其他。
→ **后续表单加载、权限计算、流转全部以「被测试的发起人」身份执行。**

### 6.2 测试态的传递与数据隔离

**发起阶段**（`iscreate=1`）：靠 URL 参数 `belongTest=true` + `wftest_userid` + `wftest_usertype`，并校验 `TestWorkflowComInfo.getIsValid(workflowid)=="2"`。

**后续节点**：靠 `wfTestStr` + session。

```java
// 编码：true|userid|usertype → Base64
encodeTestStr(wftest_userid, wftest_usertype);

// 每次提交后，取【下一节点的操作者】重新生成 wfTestStr 并写入 session
calculateNextOperator(session, workflowid, requestid, nextnodeid);
  → session.setAttribute("wfTestStr_" + requestid, result);

// 下次请求校验
verifySessionValue(request): wfTestStr 与 session["wfTestStr_"+requestid] 是否一致
```

→ **这就是「自动以下一个操作者身份继续流转」的实现**：引擎算出下一节点操作者后，把该操作者编码进 `wfTestStr`，下一次请求就自动切换成该用户。

**数据隔离**：

```java
// 提交后把这条 request 标记为测试流程
update workflow_requestbase set deleted=1 where requestid=?
```

`deleted=1` 的 request 不会出现在正常流程列表/待办中；`judgeBelongTest` 在加载表单时也会校验 `deleted=1`，防止测试态被滥用。

### 6.3 引擎副作用屏蔽（`RequestManager.istest`）

```java
// istest：流程 isvalid==2 时置 1；istestwf：requestbase.deleted
if (isvalid_t == 2) istest = 1;
istestwf = Util.getIntValue(rs.getString("deleted"));
```

当 `istest == 1` 时，引擎逐项关闭副作用：

| 位置 | 屏蔽内容 |
|---|---|
| 4238 / 4421 | 不发送短信、邮件、微信提醒 |
| 5269 | 不触发子流程 |
| 5401 | 不写入分享/待办 |
| 8409 | 干预（intervenor）不写 `requestlog` |
| 8654 | 跳过字段权限过滤 |
| 5444-5446 | 自动批准走 `excuteflownextnodeForTest()`，并先 `GCONST.WFProcessing.remove` 防「依次逐个处理」卡死 |
| 5575 | 机器人/自动处理节点特殊处理 |

### 6.4 测试过程快照

每次流转后（`RequestManager` 5110）：

```java
if (this.istest == 1) {
    WorkflowTestBiz.setWorkflowTestInfo(this.src, this.requestid, this.nodeid,
                                        this.status, this.nextlinkids, this.getNextNodeid());
}
```

`WorkflowTestBiz` 把快照写入缓存（`Util_TableMap`，key = `workflowTetInfo`），内容包括：

`requestId`、`currentNodeId/Name/Type`、`currentOperators`（当前操作者列表）、`currentLinkName`（出口名）、`currentLinkHasOperate`（出口附加规则）、`currentLinkBuildCode`（出口生成编号）、`currentNodeHasPreOperate/HasOperate`（节点前/后附加操作）、`nodeTimes`（各节点经过次数）、`operatorType`。

前端通过 `getNodeInfo({type:'testInfo'})` 读取这份快照（`GetNodeInfoCmd.getTestInfo()`）。

> 注意：快照存**内存缓存**而非数据库，因此是「单次会话内」的，重开测试会 `resetWorkflowTestInfo()` 清空。

## 7. 自动测试主循环（AutoTest.js）

### 布局

- **左侧**：节点列表（Tab：全部 / 已流转 / 未经过），每行显示「节点名 + 经过次数」，带 loading 图标指示当前节点；下方是**测试日志**滚动区。
- **右侧**：`iframe#test_frame` 承载真实流程表单。
- **顶部**：重新发起流程 / 开始自动测试 / 暂停 / 测试日志下载。

### 回调桥

`AutoTest.js` 暴露全局对象供 iframe 内的表单回调：

```js
window.workflowAutoTestUtil = { returnStatus(status) { ... } }
```

| status | 处理 |
|---|---|
| `signInputReady` | 表单加载完毕 → 打开签字意见框；若处于自动测试，自动填入「流程测试自动填写签字意见」，延迟 2s 调 `wfform.doSubmit({actiontype:'requestOperation', src:'submit', needwfback:'0'})` |
| `SUCCESS` | 调 `getNodeInfo({type:'testInfo'})` → 更新节点经过次数 → 追加日志 → `saveLog()`；若当前节点类型 `=="3"`（归档）则停止自动测试并提示「流程已到达归档节点，测试完成」 |
| `FAILD` | 停止自动测试，提示「流程提交失败，请检查流程设置」 |

### 日志内容

按顺序记录：发起人身份 → 到达节点 + 操作者 → 节点前附加操作 → 提交 → 通过节点 → 节点后附加操作 → 执行出口 → 出口附加规则 → 出口生成流程编号 → 到达下一节点 ……

### 干预跳转

左侧节点列表点击可「跳转到该节点」：

```js
switchNode → getInterventionUser(...) → setInvertionInfo / changeSubmitParam
           → iframe.wfform.doIntervenor4AutoTest({actiontype:'requestOperation', src:'intervenor'})
```

用于跳过中间节点、直接验证目标节点（干预时不计 `nodeTimes`，见 `WorkflowTestBiz` 中 `!"intervenor".equals(src)`）。

### 必填阻塞

表单有必填未填时，提示条变为「请填写流程表单信息后 **点击这里** 继续测试」，用户填完点链接继续。

## 8. 测试日志的保存与下载

`saveLog({requestId, workflowId, createTime, jsonStr})` → `DoSaveTestLogCmd`：

1. 日志数组拼成文本，落盘为 `.txt`（走 `ImageFile_Insert` 生成 `imagefileid`），文件名 `username + yyyyMMddHHmmss`
2. 写入/更新表：

```sql
insert into workflow_testlog(requestId, workflowId, testTime, fileid, tester) values (?,?,?,?,?)
```

下载：`getTestLog({workflowId})` → `GetTestLogCmd` 返回列表 sessionkey（列：测试时间 / 测试人 / 文件大小）；勾选后 `batchDownloadLog({fileIds})` 返回 `downloadUrl`。

## 9. 删除与清理

`#/workflowengine/path/test/delete`：

- `getSessionkey` → 列表 SQL 核心条件：

```sql
where t1.workflowid = t2.id
  and (t1.deleted = 1 and (t2.isvalid='2' or t2.isvalid='0' or t2.isvalid='3'))
```

（支持按流程、创建日期、创建人、流程标题高级查询，叠加工作流分权过滤）

- 批量删除 → `delete({deleteids})` → `DoDeleteWorkflowTestCmd` → `TestWorkflowCheck.deleteTestRequest(ids, user, ip)`
  内部再次校验 `Delete:TestRequest`，并检查流程是否关联资产模块等后清理。

## 12. 关键结论与可借鉴点

1. **不造模拟引擎**：直接复用真实流程引擎，用一个 `istest` 开关 + 清单化的副作用屏蔽（消息、子流程、分享、日志、权限过滤、自动批准改造）来避免污染生产数据。这是最省成本、也最贴近真实的做法。
2. **身份模拟 + 状态传递解耦**：发起用 URL 参数，后续用 `wfTestStr`（Base64 + session 校验）自动切换到下一操作者，天然支持「按真实出口条件流转到不同人」。
3. **数据隔离靠字段而非分表**：`workflow_requestbase.deleted=1` 一字段隔离，查询侧统一过滤，避免测试数据另建一套表带来的同步成本。
4. **前置校验做足**：权限 → 流程状态 → 支持性 → 发起人是否有创建权限，四层校验在真正加载表单前完成，避免在不支持的流程上白跑。
5. **前后端协作方式**：外层页面通过 iframe 嵌真实表单，表单侧通过 `window.workflowAutoTestUtil.returnStatus()` 回调驱动外层状态机（加载完 → 提交 → 成功/失败），实现「自动测试」循环；人工补填必填项后可从中断处继续。
6. **过程数据用缓存**：流转快照写入 `Util_TableMap` 内存缓存而非数据库，轻量、无残留，代价是仅会话内有效。
7. **干预能力**：允许强制跳转到指定节点（`doIntervenor4AutoTest`），便于只验证后半段路径。
