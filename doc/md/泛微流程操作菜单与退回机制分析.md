## 二、操作菜单是怎么「算」出来的

核心在 `RequestMenu.getRightMenu()`，它返回一个字符串：

```
是否显示,名称|是否显示,名称|...|reject,退回|save,保存|...
```

源码（经典实现）：

```777:777:ecology/src/weaver/workflow/request/RequestMenu.java
return submit + "," + submitName + "|" + subnoback + "," + subnobackName + "|" + ... + "|" + reject + "," + rejectName + "|" + save + "," + saveName + "|" + isSubmitDirect + "," + submitDirectName + "|" + isretractback + "," + isretractName;
```

每个按钮「是否显示」由以下因素共同决定：

1. **节点菜单配置表** `workflow_nodecustomrcmenu`（按 `wfid+nodeid`）：存各操作的名称与开关 `hasback / hasnoback / hasforback / hasforhandback / hascoad ...` 以及"提交需反馈/不需反馈"等变体（`getCustMenuName`）。
2. **操作者身份** `workflow_currentoperator.isremark`：0 待办 / 1 被转发 / 5 抄送 / 7 / 9 …（不同身份显示不同按钮，如转发、回复、抄送提交）。
3. **节点类型** `workflow_flownode.nodetype`：0 创建 / 1 审批 / 2 实现 / 3 归档，决定"提交"叫"创建/批准/实现"。
4. **转发 / 协办 / 代理 / 功能管理开关**：`WFForwardManager`、`WFCoadjutantManager`、`wfFunctionManageByNodeid(rb)`。
5. **强制收回**：`WfForceDrawBack.isHavePurview`（管理员 / 发起人权限）。

## 三、退回（reject）专门机制

### 1. 可退回哪些节点 —— 反向回溯算法

`RequestRejectManager.getPathWayNodes` / `getPreNode` 从当前节点沿 `workflow_nodelink` **反向**走到创建节点，并排除：

- **出口级封锁**：连线 `workflow_nodelink.isreject='1'` 的方向不可退：

```296:317:ecology/src/weaver/workflow/request/RequestRejectManager.java

    String sql = "SELECT nodeid, nd.nodeattribute, nd.isstart, destnodeid FROM workflow_nodelink nl, workflow_nodebase nd "
        + "WHERE nd.id = nl.nodeid AND destnodeid = "+nodeId+" AND (nl.isreject is null or nl.isreject <> '1') ";
    ...
}
```

- **分叉中间节点** `nodeattribute=2`：单独处理（`getAllNodeidByNodeid`），避免分叉死循环。
- **自由节点**（FreeNode）：走专门的 `RequestFreeNodeFlowBiz.getFreeRejectNodeids`。

### 2. 默认退回节点（不弹窗时的目标）

`getDefaultRejectNode`：取本节点配置的**退回出口**（`workflow_NodeLink_Select` type=1），按出口条件 `whereclause` 匹配表单字段，命中第一条，否则取最后一条：

```416:437:ecology/src/weaver/workflow/request/RequestRejectManager.java

while (rs.next()) { ... nextnodeids.add(destnodeid); }
for (...) {  // 按出口条件匹配表单，命中即停
    if (whereclause.trim().equals("")) break;
    else if (符合条件) break;
}
```

### 3. 退回方式判定（现代 `judgeRejectWay` → `rejecttype`）

由节点配置 `isselectrejectnode / isrejectremind / ischangrejectnode / isSubmitDirectNode / belongFree` 决定（`GetCanRejectNodesCmd.java:77-123`）：

- `rejecttype=1`：**直接退回**（退到默认节点，不弹窗）
- `rejecttype=2`：**选择退回节点**（弹 `RejectNodeSet.jsp`，列出可退节点，还带"重新分叉 / 取消合并"等 `nodeattr` 变体）

### 4. 前端退回节点选择弹窗

`RejectNodeSet.jsp` 把选择结果回传父页面：

```361:362:Weaver2020/ecology/workflow/request/RejectNodeSet.jsp
var returnjson = {id:"reject", name:nodeids+"|"+rejectnodeid+"|"+nodeattr}
callback(returnjson);
```

- `nodeids` = 已走过、需提醒的节点（`isrejectremind==1 && ischangrejectnode==1` 时勾选）
- `rejectnodeid` = 退回目标节点
- `nodeattr` = 是否"重走分叉(_1) / 取消合并(_2) / 普通(_0)"

可退节点列表由 `RequestRejectManager.getPathWayNodes` + 默认节点 `getDefaultRejectNode` 计算，并叠加：
- 当前节点自身过滤掉；
- `isselectrejectnode==2` 时按 `workflow_flownode.rejectableNodes` 白名单过滤；
- `nodeattribute==2`（分叉中间点）时按分支过滤。

## 六、对 SpringBlade 工作流的借鉴

你们当前 `WfTaskVO` / 待办里的「退回」是独立接口，没有"节点操作菜单"概念。泛微这套设计的关键数据模型可直接参考落地到 `WfProcessNode` / `WfInstanceServiceImpl`：

1. **把操作类型收敛成节点级菜单配置**：节点加 `operateMenu`（`extJson.settings.operateMenu.menus`，null=不限制 / []=全禁用），前端按它渲染 提交/退回/转办/加签/抄送/催办 等按钮（你们已在 `ApprovalPage` 落地这一口径）。
2. **退回目标 = 已走过路径反向回溯 ∩ 节点白名单 ∩ 默认出口条件命中**：
   - 退出口开关：节点配置 `canReject`（对应 `isreject`）；
   - 出口方向封锁：连线配置 `rejectBlocked`（对应 `nodelink.isreject`）；
   - 分叉/并行处理：节点 `nodeType`(网关/并行) 对应 `nodeattribute`，退回时按结构收敛；
   - 白名单：节点 `rejectableNodeKeys`（对应 `rejectableNodes`）。
3. **退回方式分两档**：`rejecttype=1` 直接退回默认上一节点（`rejectDirect`）、`rejecttype=2` 弹窗选节点（`rejectSelect`）。
4. **统一引擎入口**：无论提交还是退回，都走同一个 `flowNextNode(src)` 推进逻辑（你们已有 `WfInstanceServiceImpl` 推进，退回只需把 `src` 置为 `reject` 并定位目标活动）。

核心差异点：泛微强调"**把操作类型收敛到节点配置 + 同一引擎推进入口**"，而你们当前"提交即推进、退回单独处理"——若要做"可选退回到任意历史节点 / 默认退回上一节点 / 分叉处理"，可直接复用上述数据模型。

### 8.4 终止 vs 撤回：本质区别与触发时机

| 维度 | 终止（暂停） | 撤回（强制收回） |
|---|---|---|
| **本质** | **冻结**（停住不动） | **回退**（往回拉一格） |
| 判定身份 | 发起人 / 管理员（**身份判定**） | **上一操作人**（**行为判定**：谁刚提交） |
| 流程位置 | **不变**，停在当前节点 | **回退一格**，回到自己节点变我的待办 |
| 终态性 | 非终态，管理员可「启用」恢复 | 非终态，重新提交后继续往下走 |
| 状态字段 | `currentstatus: -1 → 0`，`status='终止'` | 撤销当前节点待办，重建上一节点待办 |
| 对他人影响 | **所有**操作人 `isremark=null`，全部看不见 | 只取消**下游那一个节点**的待办 |
| 触发时机 | 运行中即可（非创建/归档节点） | 提交后、下游未处理（`retract=1` 还要求**未查看**） |
| 配置来源 | 全局开关 `getWorkflowStopOrCancel` + 节点类型排除 | 节点级 `workflow_function_manage.retract`（0/1/2） |
| 可恢复 | 是（管理员「启用」） | 不需要，自己重新提交即可 |

一句话概括：**终止是「这单先冻起来谁也别动」，撤回是「我刚交错了，收回来重填」。**

### 8.6 对照 SpringBlade：现状差距与补齐建议

| 泛微口径 | SpringBlade 现状 | 差距 |
|---|---|---|
| 撤回 = 收回重办（回退上一节点、重建待办） | `WfInstanceServiceImpl.withdraw()` → `terminate(STATUS_CANCELED)` **直接作废** | **语义错位**：把「撤回」做成了「撤销」，不是收回重办 |
| 撤回需「最后操作人 + 下游未查看」 | 只校验发起人或管理员（`WfAuthUtil.requireStarterOrAdmin`），**无下游状态判定** | 下一节点已审批完仍能撤回 |
| 撤回策略可配（0/1/2） | 无节点级配置 | 缺少开关与时机策略 |
| 终止会冻结他人待办（`isremark=null` + 备份） | `stop()` **只 `setStatus(STATUS_SUSPENDED)` + 记日志，未动任何任务** | 「终止」形同虚设，下一节点照样能办 |
| 终止可恢复（备份 `laststatus` / `stoplastisremark`） | 仅 `resume()` 改回 `RUNNING`，未恢复任务 | 恢复后任务状态可能不一致 |
| 显隐由「状态 + 身份 + 节点类型」共同决定 | `Request.tsx:78` 只判 `status===0 \|\| status===4` | 与节点位置、流转进度无关 |

补齐建议（按改动量从小到大）：

1. **（最小、风险最低）让「终止」真正冻结待办**：`stop()` 里把该实例下所有 `STATUS_TODO` 的 `wf_task` 挂起（新增挂起态或复用字段），并备份原状态；`resume()` 时还原；任务办理入口校验实例为「暂停」则拒绝。对应泛微 `setStopOperation` 的 ①②。
2. **拆分「撤回」与「撤销」**：`withdraw()` 改为泛微口径——校验当前用户是**最后操作人**且下游任务未被处理（可配 `retract=1` 时还要求未被查看），通过后 `processService.moveActivity` 回退上一节点并重建待办、实例保持 `RUNNING`；真正的「作废」走已有的 `cancel()`/`terminate()`。
3. **节点级收回策略**：`wf_process_node.ext_json.settings` 增加 `retract`（`0` 不允许 / `1` 查看前 / `2` 查看后），与第七章的 `settings.reject` 并列；办理页/我的请求页按它决定是否渲染「撤回」。
4. **前端显隐对齐**：`Request.tsx` 的操作列除 `status` 外，叠加「是否最后操作人 / 下游任务是否已查看或处理」，从前端先收敛按钮可见性（后端仍需独立校验，不能只靠前端）。
