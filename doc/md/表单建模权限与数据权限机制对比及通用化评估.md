# 表单建模权限 vs 数据权限：机制对比与通用化评估

> 分析日期：2026-11-17
> 分析对象：`/formmode/formmanage`（表单建模权限） 与 `/authority/datascope`（数据权限）
> 目的：评估表单建模的权限机制能否通用到数据权限场景，供自审

---

## 一、两套权限机制现状

### 1.1 表单建模（`/formmode/formmanage`）——以 modeId 为中心的三层体系

前端行操作「权限」打开 `FormRightDrawer`，含 **模块权限 / 字段权限 / 数据范围** 三个 Tab。

- 前端入口：`ant-design-pro/src/pages/Formmode/FormManage/FormManage.tsx:130-134,431-440,564-569`
- 抽屉三 Tab：`ant-design-pro/src/pages/Formmode/FormRight/FormRightDrawer.tsx:486-546`（保存 `:254-276`）
- API：`ant-design-pro/src/services/formmode/rightApi.ts:78-112`（`right/mode`、`right/field`、`right/scope`）
- 运行期字段权限查询：`ant-design-pro/src/services/formmode/fieldPermApi.ts:36-47`

后端落库在三张表（均在 `blade-formmode-api/.../entity/`）：

| 层 | 表 / 实体 | 关键字段 | 粒度 |
|---|---|---|---|
| 模块权限 | `moderightinfo` / `ModeRightInfo.java` | `modeid/righttype/objtype/objid/includesub/tenantId` | 7 类操作：可见/新建/编辑/删除/详情/导入/导出（`enums/RightType.java:11-17`） |
| 字段权限 | `modefieldauthorize` / `ModeFieldAuthorize.java` | `modeid/fieldid/objtype/objid/rightvalue` | `rightvalue` 1=可见 2=可编辑（`:33-48`） |

授权对象统一为 `objtype`：1角色 2部门 3岗位 4人员（`ModeDataShareRuleServiceImpl.java:29-38`）。鉴权靠 `@PreAuth(角色级)` + `AuthUtil.getUser()` 手写判断，核心是 `FormRightServiceImpl.checkRight()`（`FormRightServiceImpl.java:64-117`）。

数据过滤在动态 JDBC 拼接里落地：

- `pageFormData` 拼 `AND modedatacreator/modedatacreater = 当前用户`（`FormDataServiceImpl.java:681-721`）
- `getFormDataById` 对越权行返回 `null`（`:628-656`）
- `pageFormDataByScope` 叠加 `blade_scope_data` 列/行规则（`:753-818`、过滤实现 `:916-958`）

### 1.2 数据权限（`/authority/datascope`）——行 + 列 + 身份的通用拦截体系

一条规则落 `blade_scope_data`（实体 `DataScope.java:36-99`，字段 `menuId/resourceCode/scopeName/scopeField/scopeClass/scopeColumn/scopeType/scopeValue/remark`），由 `blade_scope_field` 存列展示元数据。

核心是外部 jar `blade-starter-datascope` 5.0.2 的 MyBatis 拦截器 `BladeDataScopeHandler`（依赖见 `blade-scope-api/pom.xml:25-28`，源码不在本仓），SQL 模板：

```
select {scopeField} from (原SQL) scope where scope.{scopeColumn} in (...)
```

五档范围由 `DataScopeValueResolver.resolve()` 收口（`blade-scope-api/.../DataScopeValueResolver.java:200-267`）：

- 1全部 2本人 3本部门 4本部门及子级 5自定义（`DataScopeValueResolver.java:193`）
- admin/ALL 直接放行（`:206-212`）
- 非法规则 fail-closed（`:265-266`）
- 自定义值域只接受受限形态「列 IN (数字列表)」/「列 = 数字」（`parseCustomScope` `:278-300`）

规则绑定 `menuId/resourceCode` + 角色：取规则链路 `DataScopeModelHandler`（`:38-63`）→ `DataScopeCache`（`:58-82`）→ `DataScopeClient#getDataScopeByMapper(mapperId, roleId)` / `getDataScopeByCode(resourceCode)`（`DataScopeClient.java:54-93`）。

## 二、权限模型核心差异

| 对比维度 | 表单建模权限 | 数据权限 | 差异性质 |
|---|---|---|---|
| **作用对象** | `modeId`（表单实例，关联 `workflow_bill`） | 任意业务表查询结果 / 列表（`menuId`+`resourceCode`） | 根本不同 |
| **权限粒度** | 模块7类操作 + 字段级 + 行级三层 | 行级 + 列级两层，**无操作/功能粒度** | 建模更细 |
| **控制维度** | 功能权限 + 运行期字段权限 + 粗粒度数据范围 | 纯数据范围（谁看哪些行、哪些列） | 维度错位 |
| **授权对象绑定** | 角色/部门/岗位/人员写进业务表 `objid` | 角色 + 菜单资源码 | 部分重叠 |
| **字段权限按用户** | **是**：`/right/field-perm` 返回 `{visible,editable,perm}` 三态，按当前用户角色聚合 | **否**：`blade_scope_field.is_visible` 是按菜单的静态配置，不区分用户 | 数据权限缺失 |
| **数据范围档位** | 仅「全量 or 仅本人创建」两态 | 五档（全部/本人/本部门/本部门及子级/自定义） | 数据权限更丰富 |
| **鉴权流程** | `@PreAuth` + 手写 `checkRight`，fail-open（未配置放行） | 网关 `AuthFilter` JWT → MyBatis 拦截器 → 值域解析，fail-closed | 安全口径相反 |
| **数据过滤方式** | 自写 `JdbcTemplate` 动态 SQL 拼 `modedatacreator` | MyBatis `DataScopeInterceptor` 统一改写 SQL | 执行路径双轨 |

### 最关键的三点结构性差异

1. **层语义不同**：建模权限本质是「业务对象权限」（一张表单谁能看/改/导），数据权限本质是「查询结果集权限」（一条 SQL 返回哪些行列）。前者锚定业务实体，后者锚定查询。
2. **字段权限的"按用户"能力不对等**：建模有 `modefieldauthorize` 运行期按角色返回三态；数据权限只有全菜单共享的静态 `is_visible`——这是数据权限场景目前**没有**的能力，恰恰是建模机制最值得移植的部分。
3. **执行路径双轨**：表单走动态 JDBC 绕过 MyBatis 拦截器（`formmode/config/MybatisPlusConfig.java:20-43` 的插件只做动态表名/分页），因此只能另建 `page-scope` 接口复用 `DataScopeValueResolver`；数据权限走框架拦截器。两条链只能靠"值域语义收敛"对齐，无法共用拦截器。

## 三、可直接复用 vs 需要改造

### 可直接复用

- **身份与鉴权底座**：网关 `AuthFilter`（JWT 校验，`blade-gateway/.../filter/AuthFilter.java:55,62-93`）、`AuthUtil.getUser()`、`@PreAuth`、前端 `sword-token` + `/menu/routes` `/menu/buttons`——两套已共用，无需改造。
- **值域解析语义**：`DataScopeValueResolver` 的五档 + 自定义占位符（含 fail-closed）是纯函数，建模侧 `pageByScope` 已在用（`FormDataServiceImpl.java:916-958`）。这是最有价值的复用点。
- **授权对象模型**：`objtype`（角色/部门/岗位/人员）概念一致，可统一为一套授权主体解析器。
- **前端展示组件**：`ScopeGrid` / `VisibleFieldSelector` 的列配置与勾选口径可作为数据权限场景的统一列表 UI。

### 需要改造

- **绑定键映射**：建模用 `modeId`，数据权限用 `menuId+resourceCode+roleId`。要通用化需建立 `表单modeId ↔ 菜单menuId/resourceCode` 的映射关系，否则规则无法互相命中。
- **字段权限"按用户"能力下沉**：把 `modefieldauthorize` 的三态模型抽象为通用的"运行期字段权限"，让数据权限列表也能按当前用户返回 `visible/editable/perm`，替换目前静态 `is_visible` 的单维控制。
- **数据范围档位对齐**：建模的"全量/仅本人"要映射到数据权限五档（本人=`scopeType=2` 且 `scopeColumn=创建人列`），并补齐建模侧未实现的岗位匹配、子部门展开（`FormRightServiceImpl.java:81,104-110` 明确留白）。
- **执行路径统一**：要么让表单动态 SQL 也接入 `DataScopeInterceptor`（动态表场景下拦截器改造成本高），要么统一走 `pageByScope` 这种"先取规则、再拼 SQL"的自助模式——**推荐后者**，因为 `DataScopeValueResolver` 已经把安全口径收口。
- **安全口径统一**：建模 fail-open（未配置即放行）与数据权限 fail-closed 必须择一。数据权限场景应采用 fail-closed，避免"配了等于没配"。

---

## 四、可行性结论

**结论：不能整体通用，但可以以数据权限为底座做"分层复用"——功能权限共用底座、值域语义共用实现、业务语义层各自保留。**

- 两套机制共享的是**底座**（身份、JWT、`@PreAuth`、值域解析、授权对象模型），这部分已经通用。
- 不通用的是**业务语义层**：建模的 modeId 锚定、模块7类操作、字段三态权限，与数据权限的菜单/资源码锚定、行列过滤目标是两个维度。强行把建模权限"搬"到数据权限场景，会把"功能操作权限"错误地塞进"数据范围权限"，导致维度混淆。
- 正确的通用化方向是：**以 `blade_scope_data` + `DataScopeValueResolver` 作为统一的数据权限内核**，把建模的"字段权限"和"操作权限"作为其上的业务扩展层，通过 `modeId↔menuId` 映射挂接，而非让二者互为替代。

---

## 五、需要补充的设计要点

1. **建立锚点映射表**：`表单modeId / 菜单menuId / resourceCode` 三者映射，作为两套权限互相命中的桥梁。这是通用化的前提，当前完全缺失。
2. **抽象统一授权主体**：把角色/部门/岗位/人员封装成 `AuthSubject` 解析器，一次解析供模块权限、字段权限、数据范围共用；补齐 token 未携带 `postId`、部门子级展开的实现缺口。
3. **运行期字段权限通用化**：将 `modefieldauthorize` 三态抽象为通用字段权限服务，数据权限列表按用户返回 `visible/editable/perm`，与静态 `is_visible` 合并为"菜单默认 + 用户覆盖"的两级模型。
4. **统一 fail-closed 口径**：建模侧 `checkRight` 未配置放行、`fieldPerm` 空数组放行，需改为与数据权限一致的 fail-closed，否则通用后会出现安全洼地。
5. **SQL 注入安全收口**：数据权限的 `scopeField/scopeColumn` 原样拼 SQL 不转义，通用化时必须复用 `DataScopeValueResolver` 的受限形态校验（`parseCustomScope` 只接受数字列表），禁止自由文本入 SQL。
6. **拦截器与动态 SQL 二选一**：明确数据过滤只走一条路径。建议统一为 `pageByScope` 自助模式，并把 `DataScopeInterceptor` 的 `mapper-exclude` 配置覆盖所有动态 SQL 接口，避免两套过滤叠加或互相绕过。
7. **缓存一致性**：`DataScopeCache`（Feign+Redis）与建模权限查询目前无缓存联动，通用化需设计统一的权限缓存失效策略（角色变更、字段配置变更时同步刷新）。

# 第二部分：以泛微 E9 双目录为基准的 formmode 权限深化分析

> 分析日期：2026-11-17
> 基准一（源码版）：`E:\project\ecology\ecology\src`（约 3 万个 `.java`）
> 基准二（部署版）：`D:\Weaver2020\ecology`（JSP + SQL 脚本 + `.class` 字节码）

## P0. 分析口径与基准定位

两处 ecology 并非两个独立版本，而是**同一产品泛微 E9 的两个视图**：源码版提供权限判定逻辑、主体枚举、冲突裁决的实现细节；部署版提供建表 DDL、配置界面流程、运行期校验入口的落地形态。两者互相印证。部署版 `data` 目录还并存 2012 年 6 字段旧版 `moderightinfo` 与当前 27 字段新版，且新旧两套权限配置 UI（sharetype 语义不同）并存——说明该实例经历过版本升级。

**必须先纠正一个基准认知**：E9 里**没有** `modedatasharerule` 这张表，`objtype/objid/rightvalue/creatorSelf/includesub` 也**不是** E9 的字段名。当前 SpringBlade 的三表结构里，`modedatasharerule` 及这些字段是**复刻时新造的命名**。E9 的真实模型是：

- 配置层 `moderightinfo`（`SHARETYPE/RELATEDID/SHOWLEVEL/CONDITIONSQL`）
- 运行期物化层 `modeDataShare_<modeId>` / `_set`（按数据行授权，`sharelevel`）
- 字段层：`modefieldauthorize`（**仅对浏览按钮字段的跨模块授权**）+ `modeformfield(ISVIEW/ISEDIT/ISMANDATORY)`（真正的字段可见/只读三态）

## P1. 现有 formmanage 权限机制深入剖析

### P1.1 三层模型与主链路

前端 `FormRightDrawer.tsx:486-546` 三个 Tab 对应三表，API 在 `rightApi.ts:78-112`。

- **模块权限** `checkRight()`（`FormRightServiceImpl.java:64-117`）：查出 `modeid+righttype` 全部规则，`for` 循环任一主体命中即 `return true`（`:90-107`），全落空才 `false`（`:116`）——**OR 裁决，无 deny**。
- **字段权限** `listFieldPerm()`（`:273-326`）：`matchAuthorizeObject()` 筛出命中当前用户的授权 → `fieldRight.merge(fieldid, rightvalue, Math::max)`（`:306`）→ `rv>=1 visible / rv>=2 editable`（`:321-324`）——**多条取最宽松**。
- **数据范围** `ModeDataShareRuleServiceImpl.resolve()`（`:41-65`）：遍历规则，任一 `matchRule()` 命中即 `canViewAll=true` 提前返回（`:59-64`），否则退化为"仅本人创建"——**OR + 全量/本人二分**。

运行期过滤：`pageFormData()` 命中全量则不加条件，否则拼 `AND modedatacreator/modedatacreater = 当前用户`（`FormDataServiceImpl.java:709-721`），creator 列缺失则 `AND 1=0`（`:717-720`）。`pageFormDataByScope()` 再叠加 `blade_scope_data` 的 `AND col IN (...)`（`:916-958`）——与 creator 过滤是 **AND 取交集**。

### P1.2 关键结构性缺陷（深挖确认）

**(1) 空壳字段——存了不生效**

| 字段 | 前端可配 | 后端读取 | 证据 |
|---|---|---|---|
| `moderightinfo.includesub` | Switch（`FormRightDrawer.tsx:328-335`） | ❌ 注释"暂按精确匹配" | `FormRightServiceImpl.java:104,109` |
| `modedatasharerule.includeSub` | Switch（`:461-468`） | ❌ 注释"留作后续增强" | `ModeDataShareRuleServiceImpl.java:81` |
| `modedatasharerule.creatorSelf` | Switch（`:470-476`） | ❌ **全链路零引用** | 该文件 resolve/matchRule 通读无读取 |
| 三表 `tenantId` | 实体有字段 | ❌ 所有 wrapper 无 tenant 条件 | `MybatisPlusConfig.java:20-43` 无租户插件 |
| `RightType.IMPORT/EXPORT` | 前端可配（`:53-61`） | ❌ 后端零调用 | `RightType.java:16-17`，`IMPORT\|EXPORT` 搜索 0 结果 |

**(2) 端点覆盖缺口**——`assertModeRight()`（`FormDataController.java:71-90`）只在 6 处调用（`:136,155,178,198,214,228`）。以下端点**完全跳过模块权限校验**：`save`(`:95`)、`saveByForm`(`:116`)、`delete`(`:265`)、`deleteByForm`(`:279`)、`batchDelete`(`:322`)、`pageByScope`(`:250`)、`getByForm`(`:294`)。

**(3) 安全口径 fail-open 三处**：`modeId==null` 放行（`:72-74`）；`checkRight` 抛异常放行（`:78-81`）；读操作 `readRightEnforce` 默认 false 仅告警（`:55,88-89`）。

**(4) 创建人权限缺位**：`checkRight()` 内无任何创建人比对；`deleteFormData()`（`:1034-1043`）不校验行 creator——**创建人可改删他人数据**，且模块配了 EDIT/DELETE 而创建人未命中授权对象时，创建人反而被拒。

**(5) 岗位维度恒空**：`BladeUser` 不承载 `postId`，`objtype=3` 的 switch 分支是空的（`FormRightServiceImpl.java:81,109`）。

**(6) 明细表字段权限未实现**：`listFieldPerm()` 固定产出 `new FieldPermVO("main", ...)`（`:323`），不支持 workflow 侧已有的 `dt{idx}` 作用域。

## P2. 以 E9 为基准的逐项对比

### P2.1 权限分配方式

- **E9 基准**：主体 `sharetype` 极为丰富——`1人/2分部/3部门/4角色(含rolelevel分部级/总部级+isrolelimited)/5所有人/6岗位(joblevel)/7矩阵/1000流程主字段/1001Java接口`，另有 `80创建人本人/81直接上级/84同分部/85同部门/90所有上级/本岗位`（`ModeRightInfoBean.java:148-318`、`ModeRightInfo.java:8016-8018`）。一套授权 = `modeid+sharetype+relatedid+rolelevel+conditionsql`。
- **SB 现状**：`objtype` 仅 `1角色/2部门/3岗位/4人员`，无"所有人/分部/矩阵/创建人系列/流程字段/Java 扩展"，无 `rolelevel` 分级、无 `conditionsql`。
- **偏差与影响**：❌ **重大缺失**。无法表达"所有人""创建人的同部门上级"等 E9 常用授权场景；岗位维度虽在表中却恒不匹配；`conditionsql` 条件化授权完全缺位，导致数据范围只能做粗粒度二分。**位置**：`ModeRightInfo.java:33-51`、`FormRightServiceImpl.java:83-113`。

### P2.2 权限粒度

- **E9 基准**：`righttype` = `0创建/1查看/2编辑/3完全控制/4监控/5批量导入`，**数值越大越高**，判定用 `temprighttype > rightType`（`ModeRightInfo.java:5177`）。数据级另有 `sharelevel` = `1查看/2编辑/3完全控制`（`ModeShareManager.java`）。按钮 ID（`btn_print=13/btn_del=7` 等）属 UI 层，与权限等级分离（`ModeRightType.java:5-51`）。

# 第四部分：方案设计可行性分析——菜单驱动动态列表 + 建模权限与数据权限打通

> 分析日期：2026-11-17
> 方案目标：① 菜单配置进 `blade_menu` 并通过数据权限控制动态列表；② 建模侧权限与数据权限打通，配置一次全局生效。

## R0. 方案拆解与可行性总判

| 子目标 | 可行性 | 判断依据 |
|---|---|---|
| 菜单配置进 `blade_menu` + 数据权限控制动态列表 | **高（80%）** | 现有双键对齐链路已通，缺的只是「grid 页转正」和自动化菜单生成 |
| 建模权限与数据权限打通，配置一次全局生效 | **中偏低（45%）** | 字段权限与数据范围可映射，但**操作权限与数据权限存在维度错位**；且建模权限自身完成度仅 25~30%，打通等于把残缺能力放大到全局 |

**总判**：方案架构方向正确，但不能整体一次打通。建议**分两步**：先做「菜单驱动动态列表」（低风险、高收益），再做「建模→数据权限」的部分打通（字段权限 + 数据范围），**操作权限留在功能权限层，不塞进数据权限**。

## R1. 整体架构思路

正确分层：

```
                  ┌─────────────────────────────────┐
                  │  建模配置入口（FormRightDrawer）  │  ← 唯一配置面
                  └──────────────┬──────────────────┘
                                 │ 一次配置
              ┌──────────────────┼──────────────────┐
              ▼                  ▼                  ▼
      模块操作权限          字段权限            数据范围
      (CREATE/EDIT/        (modefield          (modedata
       DELETE/VIEW)        authorize)          sharerule)
              │                  │                  │
              ▼                  ▼                  ▼
      @PreAuth + 按钮权限   blade_scope_field   blade_scope_data
      （功能权限层）         （列展示）          （行过滤+列裁剪）
              │                  │                  │
              └──────────────────┼──────────────────┘
                                 ▼
                    菜单锚点（menuId + code）
                                 ▼
              动态列表页（menuId 驱动，ScopeGrid + pageByScope）
```

**三个必须建立的契约**：

1. **锚点契约**：`modeId ↔ menuId ↔ resourceCode(code)` 三者映射——当前完全缺失的桥梁（`blade_scope_field.field_id` 全为 NULL，无法反查）。
2. **配置契约**：建模抽屉一次保存，联动写入 `blade_scope_data` + `blade_scope_field`。
3. **执行契约**：所有动态列表统一走 `pageByScope` + `DataScopeValueResolver`，不再有「建模自己的 creator 过滤」与「数据权限五档」两套并行。

## R2. 菜单表与数据权限的关联设计

### R2.1 现状事实（决定设计的硬约束）

- `blade_menu` 26 列，**无 `permission`/`resource_code` 专属列**（`doc/sql/blade/blade.sql:2299-2328`），资源标识只能复用 `code`/`source`；实体 `Menu.java:38-173` 一致。
- **前端路由只认 `path`，不读 `component` 字段**——组件靠 `pages/{Module}/{page}.tsx` 路径约定推导（`ant-design-pro/src/app.tsx:220-260`、`src/utils/Func.ts:18-30`）。`component`/`component_type`/`remote_url` 目前是死字段。
- `/authority/datascope/grid` **无 blade_menu 行**，是 `config/routes.ts:61-67` 静态路由 + `?menuId=` query 驱动（`GridPreview.tsx:1-17,71-78`）。
- 数据权限命中是**双键对齐**：`blade_scope_data.menu_id = blade_menu.id`（授权树，`MenuMapper.xml:224-264`）+ `resource_code = blade_menu.code`（运行时规则与列配置的唯一键，`FormDataServiceImpl.java:988-997`）。
- **不存在「建模→自动生成菜单」功能**（formmode 全模块对 menu 0 命中）。
- `blade_menu.code` **无唯一索引**，而 `loadScopeRule` 取 `LIMIT 1` —— 重复 code 会规则错配。

### R2.2 设计要点

1. **grid 页「转正」**：参照 `doc/sql/migration/V2026.09.16_001__excel_preview_page_menu.sql:60-85`，为动态列表页插入 `blade_menu` 记录（`category=1` 普通菜单或 `category=2 + is_component=1 + is_open=2` 独立组件页），并同步 `blade_role_menu` 授权（`:94-106`）。
2. **path 必须遵循推导约定**：`path` 如 `/someModule/dataList` 时磁盘须有 `pages/SomeModule/DataList/DataList.tsx`；否则路由解析失败（参考 `defaultportal→DefaultPortal` 大小写坑）。
3. **code 唯一性改造**：给 `blade_menu.code` 加唯一索引或在配置界面强校验，消除 `LIMIT 1` 错配风险。
4. **menuId 来源统一**：动态列表页不再依赖 URL query，改用 `useAutoMenuId`（`ScopeGrid/useAutoMenuId.ts:18-73`）按当前路由反查——菜单授权树、数据权限规则、动态列配置三者自动对齐。
5. **新建菜单自动化**：建模表单创建时提供「生成动态列表菜单」按钮，原子化插入 `blade_menu + blade_role_menu + blade_scope_data + blade_scope_field` 四张表。

## R3. 建模权限与数据权限的统一配置模型

### R3.1 三类建模权限不可一视同仁

| 建模权限 | 能否映射到数据权限 | 处理方式 |
|---|---|---|
| 模块操作权限（CREATE/EDIT/DELETE/VIEW/IMPORT/EXPORT） | ❌ **不能** | 留在功能权限层：`@PreAuth` + 菜单按钮（`formmanage_*`）。数据权限是「看得见哪些行列」，不是「能不能点新建」 |
| 字段权限（`modefieldauthorize` 可见/可编辑） | ✅ 可以 | 映射为 `blade_scope_field.is_visible` + 运行期字段权限服务 |
| 数据范围（`modedatasharerule` 全量/本人） | ✅ 可以 | 映射为 `blade_scope_data.scope_type=2(本人)` 且 `scope_column=创建人列` |

### R3.2 统一配置模型的建议形态

```
一条规则 = 锚点(menuId, code, modeId)
         + 授权对象(objtype/objid → 角色id集合)
         + 字段集(可见列 + 每列 visible/editable)
         + 行范围(scope_type + scope_column + scope_value)
```

- **授权对象统一**：建模 `objtype(1角色2部门3岗位4人员)` 与数据权限 `roleId` 必须通过 `AuthSubject` 解析器归一——但 `BladeUser` 缺 postId/subcompany/seclevel（第三部分 Q1.5），岗位、分部维度暂无法落地，只能先支持角色/部门/人员。
- **字段集统一**：`blade_scope_field` 增加 `editable` 字段（当前仅 `is_visible`），承载建模 `rightvalue=1可见/2可编辑`。
- **行范围对齐**：建模「命中共享规则=全量」映射 `scope_type=1(全部)`，「未命中=仅本人」映射 `scope_type=2(本人)`。

### R3.3 必须回避的陷阱

- **不要把操作权限塞进数据权限**：否则出现「用 `scope_type` 表达能不能删除」的荒谬语义，且 `BladeDataScopeHandler` 只做 SQL 列/行裁剪，管不了写操作。
- **不要照搬 E9 物化共享表**：SB 走运行时求值（`DataScopeValueResolver`），不需要 `modeDataShare_<id>`；打通时统一到运行时求值，避免两套执行引擎。
- **建模权限自身的空壳字段**（includesub/creatorSelf/tenant_id/IMPORT/EXPORT）不能在打通时被「顺带激活」——要么先补齐实现，要么从配置界面移除，否则全局生效后影响面放大。

## R4. 配置一次全链路生效的实现逻辑

```
用户在建模抽屉点"保存"
        │
        ├─ ① 写建模三表（moderightinfo / modefieldauthorize / modedatasharerule）
        │
        ├─ ② 联动写入数据权限：
        │     ├─ blade_scope_data（upsert: menu_id + resource_code 定位，
        │     │     scope_type 由 modedatasharerule 推导）
        │     └─ blade_scope_field（按 (menuId,0,code) 差集合并，
        │          复用 ScopeFieldServiceImpl.saveBatchConfig）
        │
        ├─ ③ 刷新缓存（DataScopeCache 的 Redis key）
        │
        └─ ④ 前端动态列表按 menuId 自动生效：
              ├─ ScopeGrid 读 blade_scope_field → 动态列
              └─ pageByScope 读 blade_scope_data → 行过滤 + 列裁剪
```

**关键实现约束**：

1. **事务边界**：建模三表 + 数据权限两表必须同一事务。当前前端 `Promise.all` 并发调三个接口、后端各自事务（第三部分 Q2.3）必须改为**单一聚合接口 + 单事务**，否则出现「建模改了、数据权限没改」的不一致。
2. **差集合并**：`blade_scope_field` 已有 `ScopeFieldServiceImpl.saveBatchConfig` 的差集合并逻辑（按 scope_id+menu_id），可直接复用；`blade_scope_data` 需补类似 upsert（当前按 resource_code `LIMIT 1` 查，重复配置会覆盖）。
3. **缓存失效**：`DataScopeCache` 走 Feign + Redis，联动写入后必须主动清理对应 key（前面分析发现当前无失效联动）。
4. **fail-closed 统一**：建模侧 `checkRight` 未配置放行、字段权限空数组放行，打通后必须统一为数据权限的 fail-closed，否则「配了等于没配」的问题会全局化。

## R5. 优势分析（如果做对）

1. **消除双写不同步**：当前 `blade_scope_data.scope_field` 与 `blade_scope_field` 靠管理员手工保持一致（第一部分文档第 21 行明确这是「核心缺口」），打通后单一真相源。
2. **权限随菜单授权树统一管理**：菜单即资源，数据权限按 menuId 挂载，角色授权菜单时天然获得对应数据范围，无需 separately 配。
3. **安全口径统一**：数据权限的 fail-closed + `DataScopeValueResolver` 受限值域校验，比建模侧的 fail-open + creator 字符串拼接安全。
4. **扩展性**：新增表单只需「建表 + 建菜单 + 建模配置」，动态列表、列裁剪、行过滤全部自动获得。
5. **维护性**：授权对象解析、值域解析、字段权限三套逻辑收敛到一处（`AuthSubject` + `DataScopeValueResolver` + 字段权限服务）。

## R6. 潜在问题与风险

| 风险 | 严重度 | 说明 |
|---|---|---|
| **维度错位** | 高 | 操作权限无法用数据权限表达，强行统一会导致语义混乱 |
| **建模权限自身残缺被放大** | 高 | 25~30% 完成度，空壳字段全局生效后影响面剧增 |
| **锚点映射维护成本** | 高 | modeId↔menuId↔code 需持久化映射表；表单/菜单删除时级联清理复杂 |
| **事务一致性** | 高 | 跨 5 张表的联动写入，任一失败需整体回滚 |
| **code 重复错配** | 中 | `LIMIT 1` + 无唯一索引，重复 code 导致规则错配 |
| **缓存脏读** | 中 | `DataScopeCache` 无失效联动，配置后权限可能延迟生效 |
| **性能** | 中 | 建模权限当前每次查库（缓存空架子），打通后高频列表叠加更重 |
| **岗位/分部/密级无法落地** | 中 | `BladeUser` 缺维度，E9 高级授权场景仍无法表达 |
| **grid 页转正的兼容** | 低 | 现有 `?menuId=` 外部入口（`VisibleFieldSelector.tsx:1049-1061` 的 `window.open`）需保留兼容 |

## R7. 结论与建议

**可行性结论**：方案**局部可行、整体需分期**。

- **第一期（推荐立即做）**：菜单驱动动态列表——grid 页转正为菜单页、补自动化菜单生成、code 唯一性改造、menuId 改用 `useAutoMenuId`。风险低，收益明确。
- **第二期（条件成熟后做）**：建模权限与数据权限打通——**只打通字段权限与数据范围**，操作权限留在功能权限层；前置条件是先把建模侧 P0 五项整改完、空壳字段处理掉、统一 fail-closed。
- **不建议**：把三类建模权限揉成一个「统一权限模型」一次性全局生效——维度错位 + 建模权限残缺会导致全局性权限事故。

**待决策点**：建模侧的「数据范围」是继续用当前二分（全量/本人），还是直接采用数据权限的五档（`scope_type 1~5`）？前者简单但表达力弱，后者强但需要先把 `scope_column` 的创建人列映射规则设计清楚。

## S2. 数据权限（blade-scope）专项探查：三大缺口

> 探查范围：`blade-scope-api`（`DataScopeValueResolver`/`DataScopeCache`/`ScopeConfiguration`）、`blade-system`（`DataScopeController`/`IDataScopeService` 等）、`blade-formmode` 的 `loadScopeRule`/`applyScopeRuleFilter`/`pageFormDataByScope`、前端 `pages/Authority/Datascope/`。
> 事实：**没有独立 blade-scope-service 模块**；能力分布在 `blade-scope-api` 与 `blade-system`；不存在 `@TableName("blade_scope")`/`blade_scope_rule` 这类表，实际表为 `blade_scope_data`/`blade_scope_field`/`blade_role_scope` 等。

### S2.1 P0｜写链路不套数据权限行规则（可直接越权写/删）

- 位置：`FormDataServiceImpl.assertRowWriteScope`、`updateFormDataCell`、`deleteFormData`，以及 `FormDataController` 各写端点。
- 现状：写校验只调 `formRightService.canEditDataRow`（建模权限），**不校验 `blade_scope_data` 行规则**；且 `assertRowWriteScope` 存在多处 fail-open（开关关闭、无创建人列、异常放行）。
- 风险：建模侧一条 `canViewAll=true` 的共享规则即 `canEditDataRow=true`，即使数据权限限定「仅本部门」，仍可更新/删除其它部门数据。
- 这是当前**唯一可直接造成越权写/删**的缺口，优先级最高。

### S2.2 P0｜`loadScopeRule` 只按 resourceCode 取第一条且忽略角色

- 位置：`FormDataServiceImpl.loadScopeRule`（约 1290-1315）、`DataScope.java`、`Datascope.tsx`（约 510-521）、`DataScopeCache.getDataScopeByMapper`。
- 现状：框架正规链路是 `DataScopeCache.getDataScopeByMapper(mapperId, roleId)`，而 formmode 只按 `resourceCode` 取第一条，**不带 roleId/menuId/tenantId**；规则读取失败/无规则即不过滤（fail-open）。
- 风险：五档 `scope_type(1~5)` 绕开 `blade_role_scope` 角色绑定，任何调用者命中同一条规则；`LIMIT 1` + `blade_menu.code` 无唯一索引导致错配；配了权限等于没配。
- 直接使通用数据权限在 formmode 场景失效。

### S2.3 P1｜两套权限仅在单点叠加，锚点映射缺失

- 位置：`pageFormDataByScope`（约 1051-1144）是唯一 AND 叠加点；普通 `pageFormData`（约 990-1019）只有建模过滤；`FormRightServiceImpl.saveAll` 写三表不写 `blade_scope_data/blade_scope_field`；前端 `FieldPermission.tsx` 另写 `blade_scope_field`。
- 现状：`modeId ↔ menuId ↔ resourceCode` 映射完全缺失；`blade_scope_field.isEditable` 有存储但列表展示/裁剪不消费；`objtype=99` 是遗留命名空间、运行期不消费；前端「是否可见」勾选仅弹 warning 不生效。
- 风险：建模抽屉配的「数据范围/字段权限」与动态列表实际看到的不一致，持续制造「配置无效」客诉与配置漂移。

# 第六部分：建模权限完善后的「通用化」再分析（2026-11-18）

> 分析口径：第五部分确认**建模权限自身**已基本完善（17 项修复 + 多账号 E2E 36/36）。本部分不再讨论建模权限自身，而是专门回答：**把这些能力推广到通用数据权限场景，还有哪些结构性障碍？**

## T0. 结论

**建模权限的「点」已修好，但「面」还没打通。** 7 条通用化设计要点中：

| # | 第一部分设计要点 | 当前状态 | 判断 |
|---|---|---|---|
| 1 | 锚点映射表（modeId↔menuId↔resourceCode） | **完全缺失**；`resolveModeIdByFormId` 只做 formId→modeId，无 menu 侧 | ❌ 阻塞 |
| 2 | 统一授权主体 `AuthSubject` | `RightSubjectResolver` 已覆盖角色/部门/岗位/人员/分部/矩阵/密级，但**仅供 formmode 使用**，未下沉为公共能力 | ⚠️ 半成品 |
| 3 | 运行期字段权限通用化 | 建模侧已成熟（`field-perm` 三态 + ScopeGrid 前端消费）；**2026-11-18 已补后端脱敏**（读路径按 `visible=false` 剔除列），前端后端口径一致；注意建模侧无法配置"显式隐藏"（`rightvalue` 仅 1/2），脱敏主要覆盖 fail-closed 与异常数据 | ✅ 已对齐 |
| 4 | 统一 fail-closed | 建模侧仍默认 fail-open（`field-perm.fail-closed=false`、写校验开关可关、未配置放行）；数据权限 fail-closed | ❌ 口径冲突 |
| 5 | SQL 注入安全收口 | 建模侧条件化授权已白名单+参数化；但 `pageFormData` 的 `params` 拼接、自定义值域仍依赖调用方 | ⚠️ 部分 |
| 6 | 执行路径二选一 | 仍是双轨：formmode 自拼 JDBC + blade-scope 拦截器；`pageByScope` 单点自助 | ❌ 未统一 |
| 7 | 缓存一致性 | 建模侧已加 `@CacheEvict`；`DataScopeCache` 与建模缓存**无联动**，角色变更/配置变更互不知晓 | ❌ 阻塞 |

**净结论**：建模权限可以作为「能力样板」，但**还不能直接通用**——因为它锚定 `modeId`、执行路径双轨、fail 口径相反、缓存各自为政。强行通用会把已修好的建模侧拖回 fail-open。（注：此前列出的"双写不同步"经复核为误判，见 T1.2 修正。）

## T1. 新识别的通用化障碍（第五部分未覆盖）

### T1.1 字段权限「前端隐藏 ≠ 后端脱敏」

- 证据：`ScopeGrid/index.tsx:916-930` 用 `getFieldPermByForm(formId)` 取按用户字段权限，`:1043`/`:1087` 按 `visible/editable !== false` 隐藏列/降级只读；但服务端 `FormDataServiceImpl.pageFormDataByScope:1073-1097` 只按 `scope_field`（静态、全菜单共享）裁剪 `SELECT` 列，**没有按当前用户 field-perm 再裁剪**。
- 后果：用户 A 被隐藏的敏感字段，`pageByScope` 响应体里仍返回完整值，只是前端不渲染。任何直接调 API/抓包即可绕过。
- 通用化影响：数据权限场景若照搬此模式，会得到「界面看着有权限、接口裸奔」的假安全。

### T1.2 建模保存 vs 数据权限配置：职责已正确拆分（修正此前误判）

> **2026-11-18 复核修正**：初稿把此处判为「双写不同步的 P1 缺口」，深入核实前端写链后确认**该判断不成立**，特此更正。

- 事实：两条写链职责不同且**不重叠**：
  - `FormRightServiceImpl.saveAll` 写 `moderightinfo/modefieldauthorize/modedatasharerule` = **业务表单**按角色/人员的操作权 + 字段权 + 数据范围；
  - 数据权限弹窗 `VisibleFieldSelector` → `submitScopeFields` 写 `blade_scope_data.scope_field` + `blade_scope_field.is_visible` = **通用列表**的展示列 + SQL 裁剪；
  - `FieldPermission.tsx` 只维护 `blade_scope_field` 元数据（中文名/顺序/可编辑），保存时**可见性恒取服务端现值**，注释明确"不再写 modefieldauthorize（objtype=99 是死配置）"。
- 后端 `ScopeFieldServiceImpl.saveBatchConfig:96-113` 是**差集合并**（提交的 update、未提交的逻辑删除），前端 `VisibleFieldSelector` 输出全部字段（含未勾选 isVisible=0），不会误删。
- 结论：**不存在"同一配置两处写、互相覆盖"**。`objtype=99` 死配置已被前端移除。真正缺的不是"双写联动"，而是 **S2.3 的锚点映射**——没有 modeId↔menuId，两套配置无法对照/批量迁移，但这不是安全缺口。
- 通用化影响：职责拆分方向正确，可作为"业务权限与列表元数据分层"的样板；通用化时需保留这个分层，而不是强行合并配置源。

### T1.3 `loadScopeRule` 的 `LIMIT 1` + 无角色维度，使五档形同虚设

- 证据：`FormDataServiceImpl.loadScopeRule:1295-1298` 只按 `resource_code` 取第一条，`DataScopeCache.getDataScopeByMapper(mapperId, roleId)`（`:58-67`）才是框架正规链路却未被 formmode 使用。
- 后果：`blade_role_scope` 角色绑定在 formmode 场景完全断链；多角色用户、菜单码重复时随机命中；异常返回 null = 不过滤。
- 通用化影响：通用数据权限的"按角色差异化"这一核心价值在 formmode 直接丢失。

## T2. 通用化仍缺的最小闭环（按依赖顺序）

1. **建锚点映射表**（`modeId ↔ menuId ↔ resourceCode`），并提供 `resolveMenuByMode(modeId)` 供 `loadScopeRule` 使用——没有它，后面所有打通都落不了地。
2. **`loadScopeRule` 改用 `DataScopeCache.getDataScopeByMapper(mapperId, roleId)`**，异常 fail-closed；`resourceCode` 保留为兜底且要求唯一索引。
3. ~~服务端字段权限二次裁剪~~ **2026-11-18 已完成**：三个读入口（pageFormData / pageFormDataByScope / getFormDataById）均按 `visible=false` 剔除列，E2E 验证隐藏字段不再出现在响应中。
4. **统一 fail-closed 开关**：`blade.formmode.field-perm.fail-closed` 与 `row-write-scope.enforce` 默认值在通用场景应可强制为 true；建模场景保留默认 false 仅供兼容。
5. **缓存联动**：建模 `saveAll` / 数据权限规则保存时，互清对方缓存（`DataScopeCache` + `formmode:field-perm`），或在映射表变更时统一失效。
6. **执行路径收敛**：长期让 formmode 自拼 SQL 也走 `DataScopeValueResolver`（已部分做到），并明确 `DataScopeInterceptor` 对 formmode 动态表接口的排除清单，避免双轨重复过滤。

## T3. 建议的决策口径

- **不要**把三类建模权限揉成一个"统一模型"全局生效（维度错位 + 上述 6 个障碍会导致全局性事故）。
- **可以**先做「轻量通用化」：只把 `RightSubjectResolver`（授权主体解析）+ `FieldPermVO` 三态模型 + `DataScopeValueResolver` 五档值域**抽成公共库/接口**，各自保留锚点与执行路径。这是低风险、高复用的部分。
- **必须**在做「配置一次全链路生效」前先解决 T1.1（前端隐藏≠后端脱敏，2026-11-18 已完成）与 S2.2（`loadScopeRule` 忽略角色 + fail-open），否则通用化只会放大越权面。T1.2（双写不同步）经复核为误判，已撤销。
