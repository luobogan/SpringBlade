# 泛微 E9 自由流程（路由复用）分析 —— 是否复用同一出口选择算法

> 续《泛微E9-流程引擎流转核心深度分析》§10 未深入点 #5。回答一个具体问题：**自由流程（WFFreeFlowManager）在运行时是否复用 RequestNodeFlow 的「自动出口条件选择」算法？**
> 源码根：`e:/project/ecology/ecology/src`。**只读分析，未修改任何代码。**

---

## 1. 结论（一句话）

**部分复用**：自由流程复用 `RequestNodeFlow` 的**代码路径**与 `workflow_nodelink` 的**数据模型**，但运行时走 `isSelectNextFlow` 快路径（L1891-1894）**完全跳过出口条件求值**——即**不复用**「按 linkorder 自动求条件、首匹配短路」的出口选择子算法，而是直接采用用户手动选定的下一节点。

---

## 2. 自由流程的两层

| 层 | 类 | 职责 | 是否复用既有机制 |
|---|---|---|---|
| **定义层** | `weaver/workflow/request/WFFreeFlowManager.java` | 设计/保存自由流程时，把步骤写成 `workflow_nodelink` 行 | ✅ 复用 `workflow_nodelink` 表结构（L698-848 大量 `insert into workflow_nodelink`，含 `condition,conditioncn` L918） |
| **运行时** | `weaver/workflow/request/RequestNodeFlow.java` | 提交时计算下一节点 | ✅ 复用同一 `getNextNodes()` 主流程；❌ 条件求值被 `isSelectNextFlow` 短路 |

## 3. 定义层：复用 `workflow_nodelink`

`WFFreeFlowManager.java` 在保存自由流程时，把每一步写成一条 `workflow_nodelink`：

```java
// L698-703（新行多个步骤）
sql = "insert into workflow_nodelink(workflowid,nodeid,destnodeid,linkname,directionfrom,...) "
    + "values(" + workflowid + "," + startnodeid + "," + newnodeids.get(i) + ",'" + newnodenames.get(i) + "'...)";
// L918 连条件也一并写入
sql = "select condition,conditioncn from workflow_nodelink where workflowid = " + workflowid + "and nodeid=" + newnodeids.get(i);
```

→ 自由流程的链路在**存储形态上与普通流程完全一致**，都落在 `workflow_nodelink`。

---

## 4. 运行时：指定流转快路径跳过条件求值

提交自由流程时，前端会让用户**手动选定下一节点**，结果写入 `selectNextFlowNodeList` 并置 `isSelectNextFlow = true`（`RequestNodeFlow.java:183` 字段，`:7288 setSelectNextFlow`）。

在 `RequestNodeFlow.getNextNodes()` 的出口选择段：

```java
// L1832-1861 指定流转的节点：把用户所选 link 装入 whereclauses/linkids/nextnodeids
if (selectNextFlowNodeList.size() > 0) {
    int selectNodeId = selectNextFlowNodeList.get(0);
    ...
    rs.executeQuery("select * from workflow_nodelink where workflowid = ? and id = ? ...", workflowid, selectLinkId);
    if (rs.next()) {
        selectLink_whereClause = rs.getString("condition");   // 条件被读取…
        selectLink_newrule    = rs.getString("newrule");       // …但不求值
    }
    whereclauses.add(selectLink_whereClause);
    newrules.add(selectLink_newrule);
    ...
}

// L1889-1894 主求值循环开头
for (linkindex = 0; linkindex < nextnodeids.size(); linkindex++) {
    //指定流转，不再计算出口条件
    if (isSelectNextFlow) {
        break;                       // ← 直接跳过条件求值，采用用户所选节点
    }
    String whereclause = ...;        // 此后才是 L1919+ 的旧公式/新规则求值（与 §3 同算法）
    ...
}
```

> **关键证据**：L1891-1894 的 `if (isSelectNextFlow) break;` 意味着——只要处于「指定流转/自由流程」模式，**出口的 `condition`/`newrule` 不会被求值**，循环直接 `break` 采用 `selectNextFlowNodeList` 里的节点。

## 5. 固定节点段的再进入

自由流程中若包含**固定节点**（非自由节点），进入该段时会恢复自动算法：

```java
// L1184-1188 进入自由节点后的递归
nodeid = nextnodeid;
eh_callAgainNextNodes = true;     // 模拟分叉起始点调用 getNextNodes()
this.isSelectNextFlow = false;    // ← 关闭指定流转，恢复条件求值
freeNodeFlowBiz = null;
getNextNodes();                   // 重新跑正常算法（含条件求值）
```

即：**自由流程段 = 用户选节点（跳过条件）；其间的固定节点段 = 自动条件选择。** 两者在同一 `getNextNodes()` 内按 `isSelectNextFlow` 切换。

---

## 6. 与 §3「出口选择算法」的对照

| 维度 | 普通固定流程（§3） | 自由流程/指定流转 |
|---|---|---|
| 下一节点来源 | 按 `linkorder,id` 遍历 `workflow_nodelink`，逐条求值条件 | 用户手动选定（`selectNextFlowNodeList`） |
| 条件求值 | ✅ 旧公式 SQL count + 新规则 `RuleInterface`（L1919-2006） | ❌ 被 `isSelectNextFlow` 短路（L1892） |
| 首匹配短路 | ✅ `break` 首命中 | N/A（直接采用所选） |
| `ruleRelationship` 且/或 | ✅ 生效 | 不生效 |
| 必经分叉 `mustpassnodeids` | ✅ 参与 | 仅固定节点段参与（L1953/1991/2001） |
| 数据表 | `workflow_nodelink` | 同左（由 `WFFreeFlowManager` 写入） |

## 7. 治理提示（建议登记）

- **WF-N9（P2 / 治理须知）**：在「指定流转 / 自由流程」模式下，出口的 `condition`/`newrule` **不被求值**。若某 link 配置了本应拦截的条件，手动选择该节点会绕过它。这属于设计预期（手动选择即代表人工决策），但要求**节点级提交权限**仍必须到位——条件门禁不能替代权限校验。建议在权限设计文档中明确「条件≠权限」。
