### 1.4 如何进入详细设置页面

两条路径，本质都走 `jumpPath()`：

```js
// 列表行「编辑」或点击流程名称
onEdit(id, workflowName)  →  jumpPath(id, workflowName)

jumpPath(id, workflowName) {
    const _routeStr = '/workflowengine/path/pathSet/pathDetail/baseSet/baseInfo';
    this.context.router.push({
        pathname: _routeStr,
        query: { ...query, id, isBill },   // 关键参数：流程 id
        state: { workflowName }            // 面包屑显示用
    });
}
```

**结论**：

- 详细设置**不是弹窗，而是整页路由跳转**，落到 `pathDetail/baseSet/baseInfo`（路径详情 → 基本信息），后续在该页内用页签切换到「节点 / 出口 / 操作者 / 字段权限」等子设置。
- 新建保存后通过 `func(workflowId)` 回调**可直接跳进该详情页**（E9 也支持"保存后继续配置"）。

## 第三部分：创建流程落地实现方案（P0）

> **更正（执行开发时发现）**：`POST /definition` **后端接口已存在**（`WfDefinitionController:41`，签名 `create(@RequestBody DefinitionSaveDTO dto)`）。真正的问题是**前后端契约不匹配**——前端传扁平 `{name, procKey, formId}`，后端要 `{definition:{...}}`，`dto.getDefinition()` 为 null → `save()` 抛「流程定义不能为空」→ 创建必然失败（不是 405，是业务异常）。该问题已在 `services/workflow/index.ts` 通过 `wrapDefinitionPayload` 统一包装解决，无需改后端。
>
> 因此本节重点改为：**前端创建入口的完善 + 创建成功后跳转详细设置页**（对齐 E9 的"保存后立即进入路径详情"）。

### 3.1 后端：`POST /definition`（已存在，仅说明契约）

**位置**：`blade-service/blade-workflow/.../controller/WfDefinitionController.java`（现有 `@RequestMapping("/definition")`）

```java
/**
 * 创建流程定义
 */
@PostMapping
@Operation(summary = "创建流程定义", description = "创建流程定义（仅基础信息，节点/出口/权限在详细设置页配置）")
public R<Long> create(@RequestBody DefinitionSaveDTO dto) {
    return R.data(wfDefinitionService.create(dto));
}
```

**入参 `DefinitionSaveDTO` 最小集**（对齐 E9 新建弹窗 + `WfProcessDefinition` 实体）：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `name` | String | ✅ | 流程名称（E9 `workflowName`） |
| `procKey` | String | ✅ | 引擎流程 Key，= BPMN process id |
| `formId` | Long | ✅ | 关联表单（`workflow_bill.id`） |
| `isFree` | Integer | 否 | 是否自由流程，默认 0 |
| `nodes` / `links` / `operators` | List | 否 | **一期新建时不传**，进详情后单独保存 |

**落库逻辑**（可复用 `WfDefinitionServiceImpl.save` 中 `def.getId() == null → insert` 的既有分支）：

1. `version` 置 1；`status` 置 0（草稿）；`tenantId` 取当前用户租户；
2. 校验 `(proc_key, version)` 唯一（表上有 `uk_proc_key_version`），冲突时抛业务异常提示"该流程标识已存在"；
3. `bpmnXml` 一期可为空（画布保存时通过 `PUT /definition/{id}/bpmn` 写入）；
4. 返回新 `id`。

### B1 `wf_process_definition` 缺 `bpmn_xml` 列（阻断）

**现象**：`GET /definition/list` 报 `java.sql.SQLSyntaxErrorException: Unknown column 'bpmn_xml' in 'field list'`。
**原因**：实体 `WfProcessDefinition.bpmnXml` 与建表脚本都已加该列，但线上库未执行 ALTER（项目无 Flyway/Liquibase，schema 变更靠手工）。

```sql
USE `blade_workflow`;

ALTER TABLE `wf_process_definition`
  ADD COLUMN `bpmn_xml` MEDIUMTEXT NULL
  COMMENT 'BPMN 2.0 流程定义 XML（bpmn-js 画布产出，部署时下发引擎）'
  AFTER `name`;
```

> 改完**无需重启**（MyBatis-Plus 不缓存表结构）。
>
> ⚠️ **严禁**直接跑 `blade-workflow/src/main/resources/sql/workflow-schema.sql` 来"同步结构"——该脚本第 29~39 行 `DROP TABLE IF EXISTS` 全部 9 张 `wf_*` 表再重建，会清空数据，仅适用全新库。

**建议一次性把列漂移查全**（把结果贴给负责人，逐列比对脚本后统一出 `ALTER`）：

```sql
-- ① 现有 wf_* 表清单
SELECT TABLE_NAME, TABLE_ROWS
FROM information_schema.TABLES
WHERE TABLE_SCHEMA = 'blade_workflow' AND TABLE_NAME LIKE 'wf\_%'
ORDER BY TABLE_NAME;

-- ② 全表列清单（与 workflow-schema.sql 逐列比对）
SELECT TABLE_NAME, COLUMN_NAME, COLUMN_TYPE, IS_NULLABLE, COLUMN_DEFAULT
FROM information_schema.COLUMNS
WHERE TABLE_SCHEMA = 'blade_workflow' AND TABLE_NAME LIKE 'wf\_%'
ORDER BY TABLE_NAME, ORDINAL_POSITION;
```

### B2 前端创建契约不匹配（已修复）

**已更正结论**：`POST /definition` 后端接口**存在**（`WfDefinitionController:41`）。问题不是缺失，而是：

- 后端 `create` 接收 `DefinitionSaveDTO`：`{ definition:{...}, nodes:[], links:[], operators:[] }`

**修复**（已完成，无需改后端）：

`ant-design-pro/src/services/workflow/index.ts` 新增 `wrapDefinitionPayload()`，调用 `createDefinition` / `updateDefinition` 时若入参不含 `definition` 字段则自动包一层 `{ definition: values }`；同时新增 `DefinitionSaveDTO` 类型定义。

**已补齐的前端体验**（对齐 E9"保存后立即进入路径详情"）：

- `pages/System/Workflow/Workflow.tsx`：创建成功后 `Modal.confirm` 询问"是否立即进入流程设计"，确认则 `history.push('/formmode/workflow-design?defId={id}')`
- `pages/FormMode/WorkflowDesign/index.tsx`：新增 `?defId=` 参数消费，自动选中该定义并默认打开「流程画布」Tab

> 注：路由 `/formmode/workflow-design` 需经 `blade_menu` 菜单配置可访问（参见数据库结构文档 §5.1 初始化数据说明）；若设计页尚未挂菜单，跳转前请先由后端补菜单记录。

### B3 `mode_triggerworkflowset.workflowid` 类型溢出（高危，静默出错）

- 该列是 **INT**；
- 新流程定义主键 `wf_process_definition.id` 是 **BIGINT UNSIGNED**（雪花 ID，远超 INT 上限 2147483647）。

`ApprovalTriggerServiceImpl` 里 `dto.setDefId(triggerSet.getWorkflowid().longValue())` 会把新定义 ID 写回该列 → **截断/溢出**，且不会报错。

**处置**（二选一，建议①）：

```sql
-- ① 扩列（推荐）
ALTER TABLE `mode_triggerworkflowset` MODIFY COLUMN `workflowid` BIGINT NULL COMMENT '流程定义ID（wf_process_definition.id）';

-- ② 或另加一列 def_id BIGINT，保留 workflowid 作为 ecology 存量 ID
```

### B4 三套字段权限源未定优先级（会打架）

| 权限源 | 位置 | 语义 | 现状 |
|---|---|---|---|
| `fieldAttr` | `workflow_billfield` 字段定义 | 1只读 / 2可编辑 / 3必填（**方案要求补 0=隐藏**） | 设计期默认 |
| `modefieldauthorize.rightvalue` | formmode `FormRightController` | 1可见 / 2可编辑 | 已存在，但 `checkRight` **硬编码 `0L` 用户** |
| `wf_node_field_perm.perm` | blade-workflow `WfPermController` | 0隐藏 / 1只读 / 2可编辑 / 3必填 | 已实现 |

《方案》§3.5 只规定了「节点权限 > 单元格 fieldAttr > Excel 样式 > 默认」，**未界定 `modefieldauthorize` 的位置**。

**建议明确优先级链**（写入开发规范）：

```
wf_node_field_perm（节点级） > modefieldauthorize（角色/模块级） > fieldAttr（字段定义默认） > Excel 单元格样式 > 默认
```

**同时必修**：`FormRightServiceImpl.checkRight` 硬编码 `0L` → 换成 `SecureUtil.getUser()`（否则审批态权限形同虚设）。

### B5 scope 行级授权（**决策：支持行级**）

**决策**：节点字段权限的 `scope` **要支持行级** `dt{idx}_r{row}`（对齐《方案》§3.2 决策 2 与前端 `data-excelp-scope`），而非脚本注释里的 `dt{idx}` 整表粒度。

**改动清单**：

1. **DDL 注释与文档勘误**：`wf_node_field_perm.scope` 注释改为 `main | dt{idx} | dt{idx}_r{row}`。
   - 好消息：现有 `VARCHAR(32)` 与唯一键 `uk_node_scope_field(def_id, node_key, scope, field_name)` **已兼容行级**，无需改列结构。
2. **匹配与回退规则**（渲染端实现时必须遵守）：
   ```
   精确行级 dt{idx}_r{row}  →  回退明细表级 dt{idx}  →  回退主表级 main  →  无权限定义则用 fieldAttr
   ```
3. **前端权限矩阵 UI**：按明细行展开，允许逐行设置（未设置的行走 `dt{idx}` 级回退）。
4. ⚠️ **待确认风险**：明细行可动态增/删/排序，**行号会漂移**，行级授权可能错位。需明确：
   - 方案 A：行级授权仅作用于"模板行/固定行"，新增行走 `dt{idx}` 级；
   - 方案 B：授权锚定到行数据特征（如某字段值）而非行号（改造量大）。
   → 建议先按方案 A，并在 UI 上明确提示。

## 附录 B：环境要点（本次排障沉淀）

- **Nacos 配置优先级高于本地 `application.yml`**；`blade-workflow-dev.yaml` 指向 `localhost:3306/blade_workflow`（root/123456）。改本地数据源不生效。
- **Nacos 3.x 读配置**：`POST /nacos/v3/auth/user/login`（nacos/nacos）取 token → `GET /nacos/v3/admin/cs/config?dataId=&groupName=DEFAULT_GROUP&namespaceId=public&accessToken=`（旧 v1 / v3-console 路径均 404）。
- **Flowable schema 策略**：`blade.flowable.database-schema-update`，默认 `none`（表已存在、启动不碰 schema）。Flowable 合法值仅 `false / create / create-drop / drop-create / true`，其它值（含 `none`）为 no-op。改成 `create` 时务必确认库为空，否则建表脚本撞已存在的 `ACT_*` 表会导致启动失败。
- **本机无 mysql CLI**，查库需借 Nacos/应用侧或由 DBA 执行。
- MySQL Connector/J 9.x 的 `characterEncoding` 必须是 **`UTF-8`**，不能写 `utf8mb4`（Nacos 中 `blade.datasource.order.url` 用的就是 `utf8mb4`，同隐患）。
