## 1. 背景与目标

用户反馈的两类场景：

1. **流程通知被点开了** —— 消息中心的通知卡片点击后跳审批页，但待办/已办列表不更新。
2. **别人已经处理完了，下个节点是我的待办** —— 新待办生成后，待办列表不出现，需手动点刷新图标。

目标：让三个列表在数据变化时**按需刷新**（事件驱动，非定时轮询），同时评估长期资源消耗，并单独分析已办列表的查询性能隐患。

### 2.1 三个页面

### 2.3 现有实时基础设施（无需从零造）

**前端**：`ant-design-pro/src/utils/messageSocket.ts` —— STOMP over SockJS（`@stomp/stompjs` + `sockjs-client`），端点 `/api/blade-message/ws/message`，握手 `?token=` 透传 JWT。订阅 `/user/queue/message`、`/user/queue/unread`、`/user/queue/read`；导出 `onNewMessage`、`onUnreadChange`、`onReadChange`、`onConnectChange`。`connectMessageSocket()` 由头部 `MessageBell`（挂在 `app.tsx` 的 `actionsRender`）与全局壳层 `FloatingMessageBox` 调用，所有后台页都在连。

> 注意 `messageSocket.ts:88` 的 `if (client && (client.active || client.connected)) return;` 是**模块级单例**，作用域为单个浏览器标签页 —— 每个标签页各持一条 WS 连接。

**后端**：`blade-service/blade-message` 自研 STOMP 服务端 —— `MessageWebSocketConfig`（`@EnableWebSocketMessageBroker`，端点 `/ws/message`，broker `/topic`、`/queue`，用户前缀 `/user`），`RedisMessageRealtimePublisher` → Redis Pub/Sub（`message:*`）→ `RedisMessageSubscriber` → `SimpMessagingTemplate.convertAndSendToUser(uid, "/queue/message"|"/queue/unread"|"/queue/read", ...)`。网关 `blade-gateway/application-dev.yml` 已放行 `/api/blade-message/ws/**`。dev 实测 `blade-message` 端口 **8130 在监听**。

**流程通知链路**：`WfProcessNoticeListener`（Flowable 全局监听器，装配于 `FlowableConfig:169-179`）监听两个事件：

- `TASK_CREATED` → 取 `task.getAssignee()` 为收件人 → `INoticeClient.sendToUsers` → `MessageServiceImpl.sendNoticeToUsers` 落 `blade_message` + 未读数 +1 → Redis 发布 → `/queue/message` 推给**新办理人**。
- `PROCESS_COMPLETED` → 通知**发起人**（`bizRefType=WF_INSTANCE`，`BIZ_STATE_FINISHED`）。

`WfTaskServiceImpl.markNoticeHandled`（`:510,521-529`）在审批通过时只把旧通知回写「已处理」，不新增通知；下一条待办的通知由新的 `TASK_CREATED` 产生。

**已有复检范式**：`InstanceFlow.tsx:409-519`，20s 定时 + `visibilitychange` 调 `GET /instance/{id}/fresh`（`InstanceFreshVO.stale/staleReason`），含 1.5s 节流、3s 超时竞速；检查到过期只提示 + 禁用写操作 + 手动「刷新页面」按钮，**不刷新列表**。另有 `MessageBell` 的三条兜底经验：首屏拉、WS 推、**重连成功/切回可见补拉**（其注释明确「WS 断线期间服务端不会补推消息」）。

### 2.4 两个场景的判定

| 场景 | 现状 |
|---|---|
| **流程通知被点开** | `NoticeList/index.tsx:142-156` 只做本地置已读 + `POST .../read-one`，再 `window.open` 新标签跳审批页（`Message/index.tsx:360-365`）。**不刷新任何列表**，且 opener 是消息中心不是列表页。「已读」推的是 `/queue/read`（会话内已读回执），语义与待办列表无关，不能也不必作为刷新信号。 |
| **别人办完 → 下个节点是我的待办** | `TASK_CREATED` 触发时**一条实时消息已经推到「你」的浏览器**，前端也已有全局 `onNewMessage` 订阅口；但订阅方只有 `MessageBell`、`FloatingMessageBox`、`pages/Message`、`NoticeList` 四个消息中心组件，**三个 workflow 列表页一个都没订阅**。这就是「红点会亮、待办列表不动」的根因。 |

补充：`PROCESS_COMPLETED` 只在**办结**时通知发起人，中间节点流转不通知发起人 → 「我的请求」页的状态列在别人审批过程中没有推送源。

### 2.5 不能直接拿「流程通知消息」当刷新信号的 6 个洞

1. **候选组/候选人不通知**：`WfProcessNoticeListener.java:88-92`，`assignee` 为空直接跳过，但任务仍会进待办列表。
2. **测试实例不通知**：`:103-109` / `:141-145`，`is_test=1` 跳过。
3. **转办/抄送不通知**：`WfTaskServiceImpl` 的 `forward`/`circulate` 只 insert 一条 `wf_task`、沿用同一 `engineTaskId`，**不新建引擎任务 → 不触发 `TASK_CREATED`**；全文件只有 `:529` 一处 `noticeClient.markBizState`，无 `sendToUsers`。新待办静默产生。
4. **用户级屏蔽会吞掉消息**：`MessageServiceImpl.sendNoticeToUsers` 按 `blade_message_notice_config.flow_key` 过滤。用户在消息中心把某流程设为不接收，就收不到推送 → 列表不刷新。业务列表刷新不该受提醒偏好影响。
5. **尽力而为**：监听器 `isFailOnException()=false`、Feign 失败只记日志，通知不回滚引擎事务；不能作为唯一可靠信号。
6. **WS 断线不补推**：断线期间到达的消息服务端不主动重推。

**结论**：列表刷新应使用**独立的轻量「流程/待办变更」事件**（不落消息表、不受屏蔽配置影响），而不是复用通知卡片。

## 3. 主方案（已拍板）：L1 + L3

### 3.1 分层

| 层 | 内容 | 作用 |
|---|---|---|
| **L1（打底，纯前端）** | 三页各加 `visibilitychange`（`document.visibilityState === 'visible'`）→ 节流后 `actionRef.current?.reload()` | 零后端改动即可解决「新标签办完自动关闭 → 切回列表标签」「点通知跳走再回来」。WS 断线时仍保证数据正确 |
| **L3（真实时主线）** | 后端经 Feign → `blade-message` → Redis → STOMP 定向事件 `/user/queue/workflow-changed`；前端 `useWorkflowListRefresh(actionRef)` 订阅 + 首屏补拉 + 重连补拉 + `visibilitychange` | 覆盖「别人办完 → 我的待办」与「我的请求」状态流转，**绕过 2.5 的第 1~4 洞**；第 5/6 洞由"尽力而为 + 兜底补拉"承担，不宣称消除（见 9.2 H7） |
| **L2（开启 push 时必需）** | `BroadcastChannel` 在办理页 submit/reject/forward 成功时广播，列表页订阅 | ① 同源多标签同步「自己办完」；② **承担 3.4.2 的跨标签节流收敛**（修订 9.2 H2）。必须用 BroadcastChannel 而非 `opener.postMessage`：从消息中心跳出的办理页 opener 不是列表页 |
| **L4（不采用）** | ProTable `polling` / `setInterval` 常驻轮询 | 消耗与业务量无关、随人数与历史数据量线性增长，明确排除 |

分页面优先级：`todo` 最需要 L3（新待办）；`done` 只有「自己办完」才变，L1/L2 已足够、L3 顺带覆盖；`request` 若要实时进度必须靠 L3 的「实例状态变更」事件（现有通知链路覆盖不到中间流转）。门户首页 `TodoElement`/`MessageElement` 是一次性批量取数 + 手动刷新，要实时需单独接。

### 3.2 后端事件设计（已按 9.1 S1/S2、9.2 H1/H7 修订）

#### 3.2.1 跨服务发布链路（修订 S1）

`RedisMessageRealtimePublisher` / `MessageRealtimePublisher` **只存在于 `blade-service/blade-message`**，`blade-workflow` 无 `StringRedisTemplate` / `convertAndSend` 能力，不能"直接扩一个频道"。完整链路定义为：

```
blade-workflow : WfListChangePublisher（开关判定 + 组装 payload）
      │  afterCommit（见 3.2.3）
      ▼  新增 Feign 契约 IWfListChangeClient（仿 INoticeClient，走 /feign/client/...，网关 InnerFilter 隔离）
blade-message  : 新增 Feign 端点 → RedisMessageRealtimePublisher.publishListChange(...)
      │  Redis Pub/Sub，频道必须落在 message:* 内
      ▼  MessageWebSocketConfig 的 PatternTopic("message:*") / RedisMessageSubscriber 新增 LIST_CHANGE 分支
      └→ SimpMessagingTemplate.convertAndSendToUser(uid, "/queue/workflow-changed", payload)
```

**两条硬约束**（漏任一都会静默收不到）：

1. `RedisMessageRealtimePublisher.java:41` 的 `CHANNEL_PREFIX = "message:"`，且 `MessageWebSocketConfig` 订阅 `PatternTopic("message:*")` —— 新频道必须形如 `message:list-change:{tenantId}`，**不能用 `workflow:*`**。
2. `MessageHandshakeHandler.java:61-67` 用 JWT 的 `user_id` 作 STOMP principal，与 `RedisMessageSubscriber:48-51` 的 `String.valueOf(userId)` 一致，定向推可行；但需保证 `userIds` 是用户 ID 而非账号名。

需在 `3.5` 改动清单中同步补齐：`IWfListChangeClient` Feign 契约、`blade-message` 侧 Feign 端点、`MessageRealtimeEvent` 新 `LIST_CHANGE` 类型与 `userIds` 字段、publisher 新方法。

#### 3.2.2 事件契约（修订 H1）

- **destination**：`/user/queue/workflow-changed`，**按 `userIds` 列表逐个定向** `convertAndSendToUser`，**禁止改成 `/topic` 广播**。
- **payload**：`userIds: List<Long>` / `type`（`TASK_CREATED`、`TASK_DONE`、`INSTANCE_STATUS`、`FORWARD`、`CIRCULATE`、`WITHDRAW`、`STOP`、`ARCHIVE`）/ `instId` / 可选 `taskId` / `seq`（见 3.2.4），几百字节。
- **接收人解析规则**（一次流转常影响多人，单 `userId` 不够）：

| 场景 | 接收人 | 备注 |
|---|---|---|
| 新待办（指定办理人） | 新办理人 | 主场景 |
| 转办 / 加签 / 抄送 | 目标人集合 | 不触发 `TASK_CREATED`，必须由业务写点显式推 |
| 实例状态变更 | 发起人 + 当前参与人 | 覆盖「我的请求」中间流转 |
| 候选组 / 候选人 | **本期不推** | 见下方边界说明 |

> **候选组边界（原验收项已修订）**：`/task/todo` 的过滤条件是 `COALESCE(BIZ_ASSIGNEE_, ASSIGNEE_) = ?`（`WfTaskActReader.java:110`），`assignee` 为空的候选组任务**本就不出现在任何人的待办列表**。「候选组待办列表刷新」因此不是 L3 能独立实现的验收项，需先做候选组可见性改造（按候选组解析当前用户可领任务），**作为独立缺口另立**，不列入本期 L3 验收。

- **约束**：**不落库、不查业务数据、不受 `blade_message_notice_config` 过滤**。
- **发布点**（独立于通知监听器）：收敛到 `WfListChangePublisher`，由 `WfTaskServiceImpl` 的 `doApprove`/`forward`/`circulate` 与 `WfInstanceServiceImpl` 的撤回/终止/归档调用，**不挂在 `WfProcessNoticeListener` 内**。原因有二：
  1. 该监听器由 `@ConditionalOnProperty(blade.workflow.notice.enabled)` 装配（`WfProcessNoticeListener.java:51`，注册于 `FlowableConfig.java:169-179`），挂进去会让"关流程通知"连带关掉列表刷新。
  2. 转办/抄送只 insert `wf_task`，不触发 `TASK_CREATED`（2.5 第 3 条），监听器方案覆盖不到。
- **开关**：发布前先过 3.3 的推送开关，关闭时短路返回，不构造 payload、不发 Feign、不发 Redis、不推 WS。

#### 3.2.3 事务边界（修订 S2，必须实现）

`WfTaskServiceImpl.java:218-266`：`approve()` 带 `@Transactional`，`doApprove()` 是其 private 方法，全流程处于**未提交事务**内。若在方法体内直接发布，前端 `reload()` 会读到提交前快照，且无第二次推送 → 永久陈旧；事务回滚还会产生"根本没发生"的假通知。

**强制要求**：发布动作注册为**事务提交后**执行，二选一：

```java
// 方案 a：TransactionSynchronizationManager（发布点内就地注册）
TransactionSynchronizationManager.registerSynchronization(new TransactionSynchronization() {
    @Override public void afterCommit() { publisher.publishAfterCommit(event); }
});
// 方案 b：Spring 事件 + @TransactionalEventListener(phase = AFTER_COMMIT)
```

- 无事务上下文时（如独立工具调用）降级为立即发布，但需打 warn；
- **发布失败只记日志、绝不影响流转结果**（事务已提交，无法回滚，也不能抛异常给调用方）；
- 单元测试必须覆盖「提交后发布」与「回滚不发布」两条路径。

#### 3.2.4 可靠性等级（修订 H7）

Redis Pub/Sub 是 **fire-and-forget**：无 ack、无持久化、无重放，`RedisMessageRealtimePublisher.java:76-82` 同样 `try/catch` 记日志。因此 `2.5` 第 5 条批评通知链路的"尽力而为"缺陷，**L3 原样继承**，`3.1` 不得再宣称"绕过 6 个洞"。定位为：

| 层 | 职责 |
|---|---|
| 事件推送 | 尽力而为的低延迟通知，**不保证送达** |
| `seq` 单调递增序号（随 payload，按 `instId` 维度） | 前端比对可识别"漏帧/乱序"，发现跳号即触发一次全量 `reload()` |
| 首屏补拉 + `visibilitychange` + 重连补拉（3.4） | **最终一致性兜底**，保证任何漏帧最终被覆盖 |

- `seq` 存进程内 `ConcurrentHashMap<instId, AtomicLong>` 即可（集群内各节点序号不全局有序时，前端只做"同 instId 跳号"检测，跨实例不比较）；
- **不引入 ack / 落库 / 重放队列**：成本与复杂度超出收益，最终一致性由 L1 与重连补拉保证；
- 文档 `4.4` 的"不会失控"结论与可靠性等级无关，但需在验收中明确"事件丢失由兜底覆盖，不要求 100% 送达"。

- **降级路径**（若本期不动后端）：列表页订阅 `onUnreadChange` 作粗信号，**会引发与流程无关的 reload（聊天消息也触发）**，仅作临时联调用，不作为正式方案（详见 9.2 H7 / 9.3 M8）。

### 3.3 推送开关设计（可开启 / 关闭）

> 需求：这套「按需推送刷新」必须能**整体开启和关闭**；关闭时回到既有行为、且不留下额外消耗。

#### 3.3.1 开关清单与命名（对齐项目现有 `blade.workflow.*.enabled` 范式）

| 开关 | 侧 | 作用域 | 建议默认值 | 语义 |
|---|---|---|---|---|
| `blade.workflow.list-refresh.push.enabled` | 后端 `blade-workflow` | **L3 推送总开关** | **`false`（已拍板，默认关）** | `true` = 提交后发布 `workflow-changed` 事件；`false` = 发布侧短路，零事件 |
| `blade.workflow.list-refresh.visibility.enabled` | 前端（由后端下发） | **L1 切回可见补拉** | `true` | `false` = 连 L1 也停用，回到「只有手动刷新图标」的现状 |
| `blade.workflow.list-refresh.fallback-to-poll.enabled` | 后端 / 前端 | **关闭推送时是否回退轮询** | `false` | **本期不实现该键**（见 9.3 M9）：它是无消费点的死配置，从 `8.1.1` 的 YAML 中移除；如需防止后人加轮询，用代码注释 + 评审清单约束 |

两个主开关都关 = **完全回到现状**（仅 ProTable 手动刷新图标 + 本页写操作后 reload），这是一键回退路径。

**默认关的语义（修订 9.1 S3）**：`push=false` 是**灰度交付态，不是最终态**。此状态下：

- L1 生效：切回列表标签会补拉，**覆盖"自己办完回来"**；
- L3 不生效：**别人办完、用户停在列表页不动**时，新待办不出现 —— 即第 1 章诉求 2 在默认态**未解决**，这与"上线即满足实时需求"不是一回事，需在发布说明中明确告知；
- 开启流程：由用户在指定环境显式置 `true`，**前置条件**为 9.1 S1/S2/S4/S5、9.2 H2 全部闭环且第 5 章分页已完成（见 9.4 第 3 点）；开启后按 `6.` 验收要点中标注「L3 用例」的项目验证；
- **禁止**在未完成分页前开启：否则 `E × 单次全量成本` 双线性增长。

#### 3.3.2 行为矩阵

| 配置 | 后端发布 | 前端订阅 | 列表刷新行为 | 推送增量消耗 |
|---|---|---|---|---|
| `push=false`（**默认状态 / 已拍板**） | 短路，不 publish | **始终订阅**，handler 内按开关短路（见 3.3.5 修订） | 仅 L1（切回可见补拉）+ 手动刷新 | **0** |
| `push=true`（显式开启后） | 按 `userIds` 逐个定向 publish | 始终订阅 + 节流 reload | L3 实时 + L1 + 首屏/重连补拉兜底 | 随业务事件数 `E`，按 4.2 修订口径乘会话数 |
| `push=true` 且 `visibility=false` | 定向 publish | 始终订阅 | 实时；WS 断线期间由**首屏补拉 + 重连补拉**覆盖，非"数据陈旧" | 随 `E` |
| `push=false` 且 `visibility=false` | 短路 | 始终订阅但 handler 短路 | 现状（手动刷新） | **0** |

**修订说明（9.2 H5 / 9.1 S4 / 9.5 D5）**：

- **订阅改为"始终注册 + handler 内短路"**，不再按开关决定"是否 `subscribe`"。原因：`messageSocket.ts:103-127` 的 `subscribe` 集中在 `onConnect` 回调中，而配置是异步拉取、连接由布局层先发起，按开关条件注册存在不可控竞态；STOMP 多一条订阅的成本可忽略，短路同样保证零刷新。
- `push` 开关只闸控**发布侧**（3.2.2）与**前端 handler 是否执行 reload**；`visibility` 只闸控 `visibilitychange` 回调。
- `onConnectChange` 补拉**不绑定 `visibilityEnabled`**（原矩阵第 3 行"数据陈旧"结论作废）：首屏补拉与重连补拉是可靠性兜底，始终生效。
- 关闭开关 ≠ 关闭 WS 连接。WS 是消息中心共用的（`MessageBell` / `FloatingMessageBox` 已在用），关闭后消息铃铛、通知中心不受任何影响。

#### 3.3.4 生效方式（两种，待拍板）

项目现有 20+ 个 `blade.workflow.*.enabled` 都是 `@Value("${...:false}")` 启动时注入（`WfTaskServiceImpl.java:170-194` 等），**改配置需重启**；另有 `@ConditionalOnProperty` 装配型（`notice.enabled`、`mi-empty-guard.enabled`），同样重启生效。本仓库 `blade-workflow` 内**没有** `@RefreshScope` / `Environment.getProperty` 动态读取的先例。

| 方案 | 实现 | 切换成本 | 代价 / 风险 |
|---|---|---|---|
| **A. 静态配置开关（推荐打底）** | `@Value` 注入 publisher；`application.yml` / `application-dev.yml` 声明默认值；Nacos `blade-workflow-dev.yaml` 可覆盖（项目约定「若 Nacos 也配了该键以 Nacos 为准」） | 改配置 + **重启 blade-workflow** | 对齐现有全部开关范式，零新增基础设施；**重启不会断 WS**，故必须配合 3.3.5 的配置感知修订 |
| **B. 运行时开关（可选增强，修订 9.2 H6）** | **只走数据库参数范式**：`blade-system` `/param/submit` + `/param/public-value`（参考 `captchaSetting.ts` 的 `captcha_mode` 按租户隔离），配 5s 进程内缓存 | **不重启即可开关**，可配管理界面 | 多一条配置读取路径；缓存失效时读一次参数表（非业务数据），与「不查业务数据」约束不冲突 |

> **修订说明（9.2 H6）**：原方案 B 的 `Environment#getProperty` + Nacos 动态刷新路径**已撤回** —— `3.3.6` 明令「不要改共享 dev 的 Nacos 配置」，该路径在 dev 不可验证，且与项目联调纪律冲突。B 统一走 DB 参数，dev 联调可直接用 `/param/submit` 切换，无需动 Nacos。
>
> 建议：先落 A（风险最低），把开关判定收敛到 publisher 一处私有方法；后续升 B 只改这一处。无论 A/B，**前端感知一律按 3.3.5 修订版执行**，不能依赖 `onConnectChange`。

#### 3.3.5 前端如何感知开关

后端新增只读配置下发（复用现有范式 `odocConfigApi.getConfig()` → `GET /api/blade-workflow/odoc/config`，见 `services/workflow/index.ts:1993-1997`）：

```text
GET /api/blade-workflow/config/list-refresh
→ { "pushEnabled": bool, "visibilityEnabled": bool, "version": long }
```

**修订版机制（解决 9.1 S4 / 9.2 H5 / 9.3 M5）**：

1. **订阅始终注册**：`/user/queue/workflow-changed` 的 `subscribe` 无条件注册（放在 `messageSocket.ts` 的 `onConnect` 内，与现有四组同构）；`pushEnabled` 只用于 **handler 内短路**，不用于决定是否注册订阅。这样既消除了"配置异步 vs 连接先发"的竞态，也保证后端开关翻转后前端无需重新订阅。
2. **配置随列表响应回带，而非只在首屏拉**：三个列表接口（`3.5` / `8.3.1`）在响应中回带 `listRefresh: { pushEnabled, visibilityEnabled, version }`（响应包装字段或响应头二选一）。前端每次 `reload()` 成功后以服务端值覆盖本地配置 —— **重启 blade-workflow 后，用户任意一次刷新（含手动点刷新图标、L1 切回可见）即可感知新配置**，不依赖 `onConnectChange`（重启 workflow 不会断 blade-message 的 WS）。
3. **首屏**：列表首次 `request` 即已带回配置，无需额外接口；`GET /config/list-refresh` 保留为独立读接口，供门户卡片 / 非列表页使用。
4. **fail-safe 修正**：接口或响应字段缺失时，一律按 **两个开关都关** 处理（`{pushEnabled:false, visibilityEnabled:false}`），不再硬编码 `visibilityEnabled:true` —— 避免故障态覆盖管理员「两开关都关」的一键回退意图。同时 `skipErrorHandler: true`，失败不阻塞列表渲染、不连坐登出（同 `captchaSetting.ts:34-38`）。
5. **不引入配置轮询**：配置随已有列表请求回带，零额外请求；`version` 仅用于将来做灰度/诊断，不驱动额外拉取。
6. **前端不需要开关也能正确工作**（后端不推就收不到帧），配置只控制 handler 短路、L1 是否注册 `visibilitychange`，以及界面展示。

> 实施要点：`visibilityEnabled=false` 时仍需保留 **首屏补拉 + 重连补拉**（可靠性兜底），只停用 `visibilitychange` 触发；否则断线后无任何恢复路径（见 3.4 修订版）。

#### 3.3.6 联调纪律（来自本项目既有约定）

- **不要为了跑通一次流程测试去改共享 dev 环境的 Nacos 配置**。Nacos 发布是**全服务广播**，历史上实测 `blade-dev.yaml` 发布后 `blade-auth` 路由一度 404，可能波及网关与其它服务。
- 联调期改用 `application-dev.yml` 本地覆盖或方案 B 的运行时开关；如确需动 Nacos，必须先用 v3 API 取回原值、准备一键回滚（`nacos.his_config_info`），并明确告知影响面、得到确认后再做。
- 开关是**项目级产品决策**，不是测试开关：上线默认值、灰度范围应由用户拍板，不由一次联调驱动。

#### 3.3.7 开关与消耗 / 分页优化的关系

- 关闭 `push` → 4.2 表中「L3 定向事件」整行归零，只剩 L1 的人工切标签请求；这是**降载开关**，不是「换个方式继续刷」。
- 开关与第 5 节 `/task/done` 分页优化**完全解耦**：分页是单次取数成本问题，开关是触发频率问题。即使 `push=false`，用户每次打开已办页仍会触发全量查询 —— 所以分页优化**不能靠关开关规避**。

### 3.4 前端 hook 设计（`useWorkflowListRefresh(actionRef)`，已按 9.1 S5、9.2 H2/H3/H5/H7 修订）

#### 3.4.1 触发源与可靠性分层（修订 S5 / H7）

| # | 触发源 | 是否可停 | 作用 |
|---|---|---|---|
| 0 | **首屏补拉（新增，关键）** | **不可停** | hook 挂载时无条件执行一次 `reload()`。ProTable 首次 `request` 已取数，此处指"挂载后基于当前配置做一次一致性校准"；**必须实现**，因为 `onConnectChange` 无回放（见下） |
| 1 | `workflow-changed` 事件 | `pushEnabled` 控制 handler 短路（订阅始终注册） | L3 实时 |
| 2 | `onConnectChange` 重连补拉 | 不可停（可靠性兜底） | WS 断线重连后补拉 |
| 3 | `visibilitychange` 可见 | `visibilityEnabled` 控制 | L1 切回可见补拉 |
| 4 | `BroadcastChannel`（L2） | 可选 | 同源多标签同步「自己办完」，并承担 3.4.2 的跨标签节流 |

> **S5 修订依据**：`messageSocket.ts:88` 单例 guard + `onConnect` 内 `connectHandlers.forEach(...)`（`:128-129`）+ `onConnectChange` 仅把 handler 加入 Set（`:158-161`），**没有"已连接则立即回调"的回放**；而 `MessageBell` 在布局层更早挂载并已建立连接。因此"首次连接补拉"在列表页挂载时通常不会触发，`2.5` 第 6 洞（断线不补推）必须由 **触发源 0 + 2** 兜住。
>
> 同时给 `messageSocket.ts` 的 `onConnectChange` 增加语义：注册时若 `client?.connected` 已为 true，**立即调用一次 handler**（与 `MessageBell` 首屏 `refresh()` 兜底同构）。这是双保险，不是替代触发源 0。

**可靠性分层**（3.2.4 的 `seq` 在此消费）：

- 收到事件的 `seq` 与本地 `lastSeq[instId]` 比对，跳号 / 乱序 → 触发一次全量 `reload()`；
- 首屏补拉 / 重连补拉 / L1 是**最终一致性兜底**，不依赖事件必达；事件丢失不要求 100% 送达。

#### 3.4.2 跨标签节流（修订 H2）

`4.3` 原方案用"1s 内去重合并"收敛多标签放大，但 hook 的节流窗口是**按页面实例化的**，三个标签是三个独立 JS 上下文，无法共享。修订为两层：

1. **标签内**：500ms~1s 节流，同一页多次信号合并成一次请求（保持不变）。
2. **跨标签**：用 `BroadcastChannel`（`3.1` 的 L2 因此从"可选"升为**开启 push 时的必需项**）广播 `{type:'refreshed', scope:'wf-list', ts, listKey}`；任一标签执行 `reload()` 后广播，其他同源标签在 **1s 窗口内**收到即**丢弃自己的待刷新信号**。窗口键用 `listKey`（`todo`/`done`/`request` 分开），避免无关列表被误合并。
3. Leader 兜底：`BroadcastChannel` 不可用时（旧浏览器 / 隐私模式）退化为"只刷可见标签"，并在 `4.2` 的容量估算中按**未收敛**口径预留余量。

> 该机制同时缓解 `4.3` 的"一人多标签 3 次全量 reload"，但**不能完全消除**：三个标签若分别显示不同列表（`todo`/`done`/`request`），按 `listKey` 分离后仍各有一次，这是业务上必要的。

#### 3.4.3 分页后的页码语义（修订 H3）

`8.3` 引入服务端分页后，事件刷新不能再统一 `actionRef.reload()`（ProTable 的 `reload()` **保留当前页码**，`reloadAndReset()` 才回首页）。按事件类型分派：

| 事件类型 | 刷新动作 | 理由 |
|---|---|---|
| `TASK_CREATED` / `FORWARD` / `CIRCULATE`（新行，按 `END_TIME_/CREATE_TIME_ DESC` 插在首页） | **`reloadAndReset()`** 回第一页 | 停在第 5 页时 `reload()` 看不到变化 |
| `TASK_DONE` / `WITHDRAW` / `STOP` / `ARCHIVE`（行消失或状态变化） | `reload()` 保留页码；若响应 `total` 减小导致当前页越界 → 自动回退到最后一页 | 避免整页跳动 |
| `INSTANCE_STATUS`（「我的请求」状态列变化） | `reload()` 保留页码 | 不改变排序 |

- 前端 `request` 需读取响应 `current/total`，在越界时主动改页码再取一次（或由 ProTable 的 `pagination.onChange` 处理）；
- 该规则写入 `8.3.3` 前端改动清单，并纳入 `6.` 验收。

#### 3.4.4 四条硬约束（修订版）

1. **定向推送**，不广播；订阅始终注册，开关只在 handler 内短路。
2. **只刷可见标签**：后台标签只置 `dirty`，切回可见时由触发源 3 消费；**触发源 0 / 2 不受可见性限制**（否则断线后无恢复路径）。`dirty` 若用户永不切回则该标签数据保持陈旧 —— 这是"后台零请求"设计的既定取舍，需在产品说明中告知。
3. **节流去重**：标签内 500ms~1s + 跨标签 1s `BroadcastChannel` 去重（3.4.2）。
4. **不常驻轮询**：以 L1 + 首屏/重连补拉替代 L4 兜底；关闭推送也**不**回退轮询。

> 参考 `InstanceFlow.tsx:510-512`：那里去掉了 `window 'focus'` 以规避 `/fresh` 死循环。列表页没有写操作门禁，可只用 `visibilitychange`；若加 `focus` 必须同样加节流，并处理同窗口切 DevTools / 最小化不触发该事件的边界（可加 `pageshow` 兜底，见 9.3 M13）。

4. **事务提交后**才有帧（S2）：在 `doApprove` 事务内打点，确认帧到达晚于 commit；回滚用例必须零帧。

## 4. 消耗分析

### 4.1 三类消耗

**① 已存在的固定开销（与本次需求无关，但现在就在花）**

| 项 | 单位成本 | 来源 |
|---|---|---|
| WS 连接 | 每个浏览器标签 1 条 | `messageSocket.ts:88` 模块级单例 |
| 在线心跳 | 30s 一次 publish（每标签 2 次/分） | `messageSocket.ts:56,71` |
| 在线用户列表 | 悬浮框展开时 15s 一次 REST | `FloatingMessageBox.tsx:35,172` |
| 办理页新鲜度 | 20s 一次 `/instance/{id}/fresh` + 切回可见复检 | `InstanceFlow.tsx:502-519` |

按 100 人在线 × 平均 3 标签估算：**300 条 WS 长连接 + 600 次心跳/分（10 QPS）**；悬浮框都展开再加 1200 次/分（20 QPS）。这是用户量上来后的大头，但不是刷新方案引入的。

**② 刷新增量（修订 9.2 H2，统一标签基准）**：

```
请求数 = 触发频率 × 受影响人数 × 会话(标签)数 × 打开的列表页种类数 ÷ 跨标签合并系数 × 单次取数成本
```

- 全文统一基准：**U=100 在线用户 × 平均 3 标签**（与 4.1 一致，不再用"每人 1 个列表标签"低估）；
- `跨标签合并系数`：3.4.2 的 `BroadcastChannel` 去重生效时按 `1/标签数` 估算，`BroadcastChannel` 不可用时取 1（未收敛，需预留余量）；
- 一次流转的接收人是 `userIds` 列表（3.2.2），**不再假设"1~3 人"**，抄送 / 会签场景可能显著更多。

**③ 存储/带宽**：现有通知链路每次 `TASK_CREATED` 会 insert 一条 `blade_message` + update `unread_count`（`MessageServiceImpl:273,286`），长期只增不减。L3 独立事件必须**纯信号、不落库**，避免双倍膨胀。

### 4.2 量级对比（估算模型，非压测）

统一基准：**U=100 在线用户 × 平均 3 标签 = 300 会话**，业务流转 E=100 次/分：

| 方案 | 请求量 | 空闲时 | 随数据增长 |
|---|---|---|---|
| L4 轮询 @30s | 300×2 = **600 次/分**，与业务量完全无关 | 仍在跑 | **线性恶化**（done 全量 + 历史累积）；@5s 再 ×6 |
| L4 轮询 @60s | 300 次/分 | 仍在跑 | 同上，只是慢一半 |
| L1 切回可见补拉 | ≈ 人工切标签次数（人均 1~2 次/分）→ 100~200 次/分 | **0** | 只在真需要时发生 |
| L3 定向事件（跨标签去重**生效**） | ≈ `E × 接收人数(1~3) × 列表页种类(1~3) ÷ 合并系数` → **100~900 次/分** | **0** | 与事件数成正比，与在线人数无关，但**受单次全量取数成本影响**（见 9.4） |
| L3 定向事件（`BroadcastChannel` 不可用，未收敛） | 上值再 `× 标签数(3)` → **300~2700 次/分** | **0** | 同上，需按此上界预留容量 |
| L3 复用现有通知（降级路径） | **非零**：`onUnreadChange` 每次变化都会 reload，且聊天消息也触发 | 0 | 与流程无关的无效 reload 持续产生，**不作为正式方案**（9.2 H7 / 9.3 M8） |

**关键差别不是数字大小，是增长因子**：轮询按 `U × 时间` 收费（人挂着不动也扣），事件驱动按 `E`（真实业务变化）收费，空闲用户成本为 0。这就是「按需」的本质。但修订后需明确：**事件驱动不等于请求数一定更少** —— 高事件量 + 多标签 + 未分页时，L3 请求量可能高于低频轮询，其优势在于"零空闲消耗 + 与业务量成正比"，而非绝对数量。

### 4.3 会出事的三个情形（修订 9.2 H2）

1. **惊群**：若做成全局广播（一个事件推给所有在线用户），复杂度从 `O(E)` 退化成 `O(E×U)` —— 100 事件 × 100 人 = 10000 次 reload/分，瞬间打爆网关。必须按 `userIds` 逐个定向推。
2. **一人多标签放大（原缓解措施不成立，已修订）**：同一人同时开 todo/done/request 三个标签，`3.4` 原方案的"标签内 1s 节流"**无法跨标签生效**（三个独立 JS 上下文）。修订为 3.4.2 的两层节流：标签内节流 + `BroadcastChannel` 按 `listKey` 跨标签去重；`L2` 因此升为**开启 push 时的必需项**。不同 `listKey` 的刷新不合并（业务上必要），不能指望降到 1 次。
3. **接收人集合膨胀（新增）**：抄送 / 会签 / 候选组解析出的 `userIds` 可能远大于"1~3 人"，按 3.2.2 逐个 `convertAndSendToUser` 会线性放大发布次数。需在 publisher 侧对 `userIds` 去重并按上限告警，避免异常配置打爆 Redis 与 WS。

### 4.4 开关对消耗的影响

`list-refresh.push.enabled=false` 时，3.3.2 行为矩阵第一行生效：发布侧在 `WfListChangePublisher` 入口短路，**不构造 payload、不发 Feign / Redis、不推 WS**；前端**订阅仍注册但 handler 短路**（修订 9.2 H5），L3 那一整行消耗归零；只剩 L1 的人工切标签请求与**首屏补拉**（空闲为 0）。即开关是真正的**降载开关**：关闭后退回「现状 + 切回可见补拉 + 首屏校准」，不会以轮询形式继续消耗。

若把 `visibility.enabled` 也设为 `false`，则回到"仅手动刷新图标 + 首屏补拉 + 重连补拉"（可靠性兜底不可停），刷新增量趋近 0 —— 这是排查线上负载问题时的**一键回退路径**。

**结论（已按第 9 章修订为有条件结论）**：按 L1+L3 并遵守 3.4 的四条约束，**消耗随业务事件走、空闲为零**；且任何时候都能通过关闭 `push.enabled` 把这份增量降为 0。按常驻轮询做，会随人数与已办历史量双重增长，后期一定失控。

**该结论成立的四个前提（缺一不可）**：

1. **分页已完成**（`8.3`）—— 否则 `E × 单次全量取数成本` 双线性增长，见 **9.4** 第 3 点；**这也是 `3.3.1` 把"开启 push"前置条件设为分页完成的原因**；
2. 9.1 S4 的前端配置感知已改为"随列表响应回带"、9.1 S5 的首屏/重连补拉已实现；
3. 9.2 H2 的跨标签放大已按 3.4.2 收敛，或按 4.2 的"未收敛上界"预留容量；
4. 事件可靠性按 3.2.4 的"尽力而为 + `seq` + 兜底补拉"实现，不追求 100% 送达（追求送达若引入 ack/落库，成本模型需重算）。

### 5.2 问题一：全量无分页

- `/task/todo`、`/task/done` 返回 `R<List<WfTaskVO>>`，**接口没有 `current`/`pageSize`，SQL 没有 `LIMIT`**（`WfTaskActReader.java:135-162`、`wfTaskQuery:981-1037`）。
- 后端虽支持 `title/defId/formId/beginTime/endTime`（`WfTaskController:61-68`、`WfTaskListFilter`），**前端一个都没传**：`Done.tsx:105-110` 的 `status`/`title` 是在**全量数据到前端之后**用 `Array.filter` 在内存里过滤。筛选完全不能减少 DB 查询量、不能减少传输量。
- 前端 `pagination={{ defaultPageSize: 20 }}` 只是 ProTable 对已拿到的全量 `data` 做切片渲染，`total = list.length` —— **伪分页**。
- 对照：`/instance/mine` 是服务端分页（`WfInstanceServiceImpl:839-887`，`Page` + `pageSize≤200` + 草稿合并），这块是健康的。

### 5.3 问题二：历史单调增长

`doneFromAct` 读 `ACT_HI_TASKINST`（历史表，`END_TIME_ IS NOT NULL`），**已办数据只增不减，且无归档/清理策略**。单人积累 5000 条已办时，一次刷新 = 5000 行全查、全序列化、全传输、全量 `ORDER BY` 排序、前端重新渲染整个表格。这是唯一会随时间线性恶化的地方，且被 L3 的每次事件放大成「每次流转都付一次」。

#### 5.3.1 索引失效：已用 `EXPLAIN` 实测确认（非推断）

现有索引（`doc/sql/blade/blade1101.sql:472,474,1541`、migration `V2026.10.01_002__act_ledger_tenant_indexes.sql:66`）：

```sql
KEY `IDX_HI_TASK_ASSIGNEE_END` (`ASSIGNEE_`,`END_TIME_`,`IS_TEST_`),
KEY `IDX_HI_TASK_T_ASSIGNEE`  (`TENANT_ID_`,`ASSIGNEE_`),
KEY `IDX_RU_TASK_ASSIGNEE_TEST` (`ASSIGNEE_`,`IS_TEST_`)
```

而 `WfTaskActReader.java:110,145` 的过滤条件是 `COALESCE(BIZ_ASSIGNEE_, ASSIGNEE_) = ? AND COALESCE(IS_TEST_,0)=0`。`BIZ_ASSIGNEE_` 是 blade 自定义加列（`:466`、`:1531`）；**函数包列使索引连候选都进不去**。

用只读脚本 `log/wf_explain_done_query.py` / `...2.py` 连 dev 库（MySQL 8.0.23，`ACT_HI_TASKINST` 326 行、`ACT_RU_TASK` 37 行）实测：

| SQL | type | possible_keys | key | rows | Extra |
|---|---|---|---|---|---|
| **原始（已办列表）** | `ALL` | 仅 `IDX_HI_TASK_T_ASSIGNEE` | `None` | 326 | `Using where; Using filesort` |
| 原始 + `FORCE INDEX(租户索引)` | `ref` | `IDX_HI_TASK_T_ASSIGNEE` | 该索引 | 326 | `Using where; Using filesort` |
| **OR 展开**（上版建议） | `ALL` | 两个办理人索引都出现 | `None` | 326 | `Using where; Using filesort` |
| OR 展开 + `FORCE INDEX` | `ALL` | `IDX_HI_TASK_ASSIGNEE_END` | `None` | 326 | `Using where; Using filesort` |
| **`ASSIGNEE_` 单列 + `FORCE INDEX(IDX_HI_TASK_ASSIGNEE_END)`** | `range` | `IDX_HI_TASK_ASSIGNEE_END` | 该索引 | 104 | `Using index condition; Using where; Backward index scan`（**无 filesort**） |
| 待办原始 `ACT_RU_TASK` | `ALL` | 仅租户/到期类索引 | `None` | 37 | `Using where; Using filesort` |
| 角标 `countFromAct` done COUNT | `ALL` | 仅 `IDX_HI_TASK_T_ASSIGNEE` | `None` | 326 | `Using where` |

结论与两处**撤回/修正**：

- ✅ **索引失效坐实**：原始 SQL 连 `IDX_HI_TASK_ASSIGNEE_END` 都进不了 `possible_keys`；全表扫描 + filesort 成立；`countFromAct`（`:220/228/237/253` 共 4 处）同源中招，角标计数也全表扫。
- ❌ **撤回上版建议「改写成 `(BIZ_ASSIGNEE_=? OR (BIZ_ASSIGNEE_ IS NULL AND ASSIGNEE_=?))`」**：实测即使 `FORCE INDEX` 仍是 `type=ALL`。OR 跨两列、且 `BIZ_ASSIGNEE_` 上根本没有索引，优化器无法走单一索引。
- ⚠️ **dev 表太小（326/37 行），`type=ALL` 部分是优化器的正常代价判断**，不能据此断言"改了没用"；判据应看 `possible_keys` 变化 + 在**生产量级数据**上 `EXPLAIN`。候选 D2 用 `FORCE INDEX` 模拟大表，证明 `(ASSIGNEE_, END_TIME_, IS_TEST_)` 这个索引本身**能同时满足过滤与 `ORDER BY END_TIME_ DESC`**（Backward index scan，filesort 消失）——问题不在索引设计，而在查询条件写法让索引不可用。

#### 5.3.2 为什么不能简单改成 `ASSIGNEE_` 单列

实测数据分布（`ACT_HI_TASKINST` 326 行）：`BIZ_ASSIGNEE_ IS NULL` 40、`ASSIGNEE_ IS NULL` 44、两列都有值且**值完全一致** 282（`both_set_but_differ = 0`）、`BIZ有值但ASSIGNEE_为NULL` 4 行；`ACT_RU_TASK` 37 行两列全一致。

看似可以改 `ASSIGNEE_=?` 复用现有索引，但 **`WfTaskActWriter:139,150` 只回写 `BIZ_ASSIGNEE_`，不写 `ASSIGNEE_`**（该列由 Flowable 引擎维护），写入器 `:129` 注释明确「未开多实例时引擎 `ASSIGNEE_` 常为 NULL，读源须以 `BIZ_ASSIGNEE_` 为准」。dev 两列一致只是当前已开引擎多实例下的巧合，**换环境/关多实例即失效**，改单列会漏单。此路否决。

#### 5.3.3 建议修法（按优先级，均需 `EXPLAIN` 验证后再上线）

| 方案 | 做法 | 评价 |
|---|---|---|
| **① 给权威列 `BIZ_ASSIGNEE_` 补复合索引（推荐）** | `IDX_HI_TASK_BIZ_ASSIGNEE_END (BIZ_ASSIGNEE_, END_TIME_, IS_TEST_)`、运行表 `(BIZ_ASSIGNEE_, IS_TEST_)`；SQL 改为以 `BIZ_ASSIGNEE_ = ?` 为主的条件，并把 `COALESCE(IS_TEST_,0)=0` 改为 `(IS_TEST_=0 OR IS_TEST_ IS NULL)` | 与写入口径一致、不依赖引擎列；索引含 `END_TIME_` 可消 filesort。需 DDL（建议沿用 `blade_add_idx` 幂等 `ALGORITHM=INPLACE, LOCK=NONE` 范式） |
| ② 兼容旧数据 | 对 `BIZ_ASSIGNEE_ IS NULL` 的历史行做一次性回填（沿用 `act_backfill_task_biz_columns.sql` 范式），之后 SQL 可只用 `BIZ_ASSIGNEE_=?`；若必须保留 `ASSIGNEE_` 兜底，改用 `UNION ALL` 两条各自走索引的子查询，而非 OR | 先回填再简化，避免长期背 OR |
| ③ 同步修 `countFromAct` | 4 处 `COALESCE` 与列表同批改写，否则角标仍全表扫 | 必须随 ① 一起做，不能只修列表 |
| ④ 租户列顺序 | 现有 `IDX_HI_TASK_T_ASSIGNEE(TENANT_ID_, ASSIGNEE_)` 仍建在 `ASSIGNEE_` 上；多租户大表下建议评估 `(TENANT_ID_, BIZ_ASSIGNEE_, END_TIME_)` 是否更优 | 用生产数据 `EXPLAIN` 对比选择性后定 |

> **不要只加 `LIMIT`**：`ORDER BY h.END_TIME_ DESC` 在没有可用索引时，排序发生在全量结果集上，`LIMIT` 只减少返回行数、不减少扫描与排序成本。必须先解决索引可用性，分页才有意义。
>
> 同理 `wfTaskQuery:991-1013` 在传 `title/defId/formId` 时先 `selectObjs` 取实例 ID 再 `IN`，命中多时 `IN` 列表会膨胀（SQL 长度/参数上限风险）；当前前端未传这些参数，属潜在雷。

### 5.4 问题三：`toVO` 的 N+1 —— 口径校准（实测）

`WfTaskServiceImpl.toVO()`（`:1039-1083`）每条记录至少两次额外访问：

```java
WfInstance inst = instanceMapper.selectById(t.getInstId());     // :1052  每行一次
WfProcessNode node = loadNode(inst.getDefId(), t.getNodeKey()); // :1065  每行一次
```

`loadNode()`（`:1102-1127`）在 `definitionFromBpmn` 开启时走 `bpmnReader.node()` → `findFlowNode()`（`WfBpmnExtensionReader:606-621`）；`BpmnModel` 有 `procDefId → BpmnModel` 的 `ConcurrentHashMap` 缓存（`:66-67,621`），**不会重复解析 XML**，但仍是每行一次模型遍历；回退路径是 `nodeMapper.selectOne(...)` 每行一次 SQL。

#### 5.4.1 关键：当前 dev 残留 = 0，N+1 一次都没触发

`WfTaskActReader.fillCommon:282` 把 `BIZ_TASK_ID_` 塞进 `WfTaskVO.id`；`list():941-943` 用它构造 `seen` 排除集，再查 `wf_task` 兜底残留。**`WfTask extends TenantEntity extends BaseEntity`，而 `BaseEntity.isDeleted` 带 `@TableLogic`**（`blade-tool/.../BaseEntity.java:105-107`，全局 `logic-delete-value:1 / logic-not-delete-value:0` 见 `doc/nacos/blade.yaml:133-138`），所以 `taskMapper.selectList` 会自动附加 `is_deleted=0`。

只读复算（`log/wf_explain_done_query3.py` / `...4.py`）：

| 口径 | 结果 |
|---|---|
| 裸 SQL 按 `status IN (2,4)` 且 ACT 未覆盖 | 178 行 |
| 其中 `is_deleted<>0` | **178 行（全部）** |
| 加 `is_deleted=0` 后的真实残留 | **0 行** |
| `wf_task` 已办非删除行 | 212 行，**全部被 ACT 覆盖** |
| `ACT_HI_TASKINST` 已办行（`END_TIME_` 非空） | 288 行 |

> 上版文档据"代码注释说残留逐步趋零"判断为潜伏风险，方向对但缺实证；本轮复算给出确定性结论：**当前 dev 的 `toVO` 一次都不执行**，N+1 是 0 次而非"少量"。中间那次"178 行 / 单次 52 行"的估算是漏加逻辑删除条件导致的**高估**，已作废。

#### 5.4.2 校准后的完整口径（避免两个方向都夸大）

| 维度 | 结论 |
|---|---|
| 主路径是否走 `toVO` | **否**。`merged` 由 `jdbcTemplate` 直接映射 `WfTaskVO`（`WfTaskActReader:117-124,153-161`），无逐行查询 |
| 当前 dev 残留触发量 | **0**（212 行已办非删除行全被 ACT 覆盖，178 行未覆盖的全是逻辑删除） |
| `BpmnModel` 缓存 | **存在**（`procDefId` 键），不会重复解析 XML；`loadNode` 每行至多一次模型遍历 |
| 何时会真实触发 | ① ACT 读源异常 → 整条降级走 `wf_task` 全量（`:966-969`，此时才是真·全量 N+1）；② 将来出现 ACT 未覆盖的**未删除** `wf_task` 行（存量 N:1 会签、孤儿、草稿合成待办、双写失败）；③ 逻辑删除策略变更/物理清理前残留回潮 |
| 定性 | **潜伏风险，当前零触发**。不应与 5.3 的索引失效、5.2 的全量无分页并列为"当前性能问题"；但降级路径一旦发生，代价是 `2 × 行数` 次查询 |

#### 5.4.3 处理建议（顺手做，不单独排期）

- 在分页改造（方案 A）中，把 `toVO` 改为**批量**：一次性 `instanceMapper.selectBatchIds(instIds)` + 一次 `loadNodes(defId)` 建 `nodeKey → node` 映射，替代逐行 `selectById` + `loadNode`。改动集中在 `toVO` 调用处，降级路径与兜底路径同时受益，属于低风险内聚改造。
- `list():951-954` 的合并后全量排序，在分页改造后应改为两源各取候选再归并，避免"先全量排再切页"。
- 前端次要放大点保留但不必优先：`Done.tsx:112` 的 `setStarterIds` 收集全量发起人 ID；`fetchUserNames` 有模块级 `userNameCache` 且按 50 个/片批量查（`personOrg.ts:334,409,490-495`），仅首次加载触发，后续命中缓存不发请求。

**验证脚本（只读，可复跑）**：`log/wf_explain_done_query.py`（索引 + EXPLAIN 基线）、`...2.py`（候选改写法 + 残留复算）、`...3.py`（`statuses` 精确口径 + N+1 上界）、`...4.py`（逻辑删除条件校准）。均为 `SELECT` / `EXPLAIN`，不建索引、不改数据。

### 5.5 候选方案对比

| 方案 | 做法 | 优点 | 代价 / 风险 |
|---|---|---|---|
| **A. 后端真分页（推荐主干）** | `/task/todo`、`/task/done` 增 `current/pageSize`，返回 `R<IPage<WfTaskVO>>`；`doneFromAct` 加 `LIMIT/OFFSET` + 独立 `count`，`wf_task` 兜底残留也分页；筛选条件**下推到 SQL**（不再内存 filter）；前端 `request` 消费 `params.current/pageSize` 并改用 `page.total` | 单次响应恒定（20 行）、传输与渲染恒定；彻底解决历史增长；与 `/instance/mine` 同构 | 改动面最大：Controller、Service、DTO、ActReader SQL、前端三页；**ACT 主表 + wf_task 兜底合并后分页**需仔细处理（两源各自分页无法直接合并排序，建议先各自取 `pageSize` 上限再归并，或统一到一个视图/单次 SQL）；深分页 `OFFSET` 仍慢 |
| **B. 上限截断（最小止血）** | SQL 加 `LIMIT N`（如 500）+ 按时间倒序，前端提示「仅显示最近 N 条，请用筛选缩小范围」；把 `title/beginTime/endTime` 下推 | 改动极小、见效快 | 语义不完整（用户以为列表是全部）；筛选下推仍要处理 `COALESCE` 索引；属过渡方案 |
| **C. 增量 `updatedSince`** | 前端记上次刷新时间戳，只拉其后变更行；复用 `WfTaskListFilter.beginTime/endTime`（已办按 `END_TIME_`、待办按 `CREATE_TIME_`） | 与 L3 事件驱动天然契合，正常刷新几乎零传输 | **无法表达「删除/失效」**：待办被办结后从 `ACT_RU_TASK` 消失、被撤回/终止，增量接口不会返回 tombstone → 必须配合事件里的 `taskId` 做本地移除，或定期全量对账；状态变更（已办→办结）也需 `update_time` 而现有表只有 `END_TIME_`；**不能替代分页**，只能作为 A 之上的增量补充 |

> 另有一条与 L3 联动的最优解：`workflow-changed` 事件已带 `taskId/instId/type`，前端可**只新增/移除/更新那一行**（`actionRef` 的局部更新或维护本地 row 状态），多数情况连 `reload()` 都不用。这样既把刷新消耗压到接近零，也顺带绕开 `/task/done` 全量查询。但这要求列表数据可局部维护，且仍需首屏与兜底走分页 —— **建议作为 A 之上的增强，不是 A 的替代**。

## 6. 验收要点

**通用前置（修订 9.1 S3）**：以下标注 **【L3 用例】** 的项目，必须先按 `3.3.1` 的开启前置条件完成（S1/S2/S4/S5、H2 闭环 + 分页完成），并显式置 `push.enabled=true`；**默认关配置下这些用例不适用**，不得作为默认态回归失败的依据。

**L1（默认态即可验收）**：

- 默认配置下，新标签办完自动关闭 / 点通知跳走再切回 → 列表自动补拉；
- **首屏补拉**（修订 S5）：新开列表标签时抓 Network，确认挂载后有一次校准请求，且 `onConnectChange` 未触发也能完成；
- 后台标签切回 → 补拉一次且不重复请求（标签内节流生效）；
- 空闲 5 分钟不产生任何列表请求（抓 Network 验证「空闲为零」）。

**【L3 用例】实时链路**：

- 别人 A 审批通过 → B 的待办标签在 1s 内出现新待办（不需手动刷新）；

- **事务顺序**（修订 S2）：在 `doApprove` 内打点，确认 WS 帧到达**晚于事务提交**；构造回滚用例，确认零帧、零假通知；

**8.3.2 两源归并口径（最需评审的一点）**：

```
ACT 主表分页  +  wf_task 兜底残留分页  →  归并
```

`WfTaskServiceImpl.list():934-955` 目前是"两源各取全量 → 合并 → 全量排序"。改为分页后不能各自 `LIMIT` 再直接拼（跨源全局顺序会错）。可选：

| 口径 | 做法 | 代价 |
|---|---|---|
| a. 各取 `pageSize` 上限再归并 | 两源各取 `LIMIT pageSize` 候选，归并后截前 `pageSize` 行；`total` 按下方修订公式计算 | 实现简单，深页可能少取；`total` 为估算 |
| **b. 统一视图 / 单次 SQL（推荐，修订 H4）** | `UNION ALL`（两源列对齐）+ 外层 `LIMIT/OFFSET` 与 `count` | 语义最准、`total` 天然正确；SQL 最复杂，需处理 `COALESCE` 读源与状态映射对齐 |
| c. 兜底残留优先 | 先展示残留再展示 ACT 主表 | 实现最简，但排序语义与现状不一致 |

**落地实现（2026-11-08，已编码）**：选了**口径 a 的修正版**——`total` 由两源各自**同口径 count 相加**
（残留 count 的 SQL 内含 `NOT IN (SELECT BIZ_TASK_ID_ FROM ACT_*)` 排除条件），**绝不用「减 seen」**。
配套落地了**读侧残留合并开关** `blade.workflow.task-residue-merge.enabled`（默认 `true`，零行为变化）：

- `true`：列表 + 角标都合并 `wf_task` 残留（保证零丢单），残留只在**第一页**并入、深页取 ACT 连续切片
  → **两源有交集时深页可能重复/漏行**（口径 a 的固有取舍，代码内已打 `log.warn` 留痕）；
- `false`（纯 ACT 单源）：列表与角标 100% 来自 `ACT_*`，`total` 严格等于 ACT count
  → **消除深页漏行**，并真实暴露 ACT 覆盖率缺口。

这是「去 wf_ 表 P6 退役」的第一个可回退台阶，详见 `去wf_表-任务读源翻源上线检查.md` §7。

**`total` 公式修订（9.2 H4）**：原口径 a 写「两源各自 `count` 之和减去 `seen` 去重」是**错误的** —— `WfTaskServiceImpl.java:941-943` 的 `seen` 是**当前页** ACT 返回的 `BIZ_TASK_ID_` 集合（用于 `notIn` 排重当前页），不是全量交集，两个 `count` 也没有对应 exclude 条件，会重复计数。正确做法二选一：

```sql
-- 方案 a 修正：把排除条件下推到 wf_task 的 count 里，而非减 seen
SELECT
  (SELECT COUNT(*) FROM ACT_HI_TASKINST h WHERE <同口径条件>) +
  (SELECT COUNT(*) FROM wf_task t
    WHERE <同口径条件>
      AND t.id NOT IN (SELECT BIZ_TASK_ID_ FROM ACT_HI_TASKINST WHERE BIZ_TASK_ID_ IS NOT NULL))
  AS total;

-- 方案 b（推荐）：UNION ALL 后一次 count，天然去重、无公式误差
SELECT COUNT(*) FROM ( <两源 UNION ALL 子查询> ) u;
```

> 当前 dev 残留 = 0（5.4.1），三种口径在 dev **测不出差异**，必须用造数验证（含"两源有交集"的用例）。产品需确认是否接受 `total` 为估算值；若不接受，必须选口径 b。
>
> **补充权衡（9.4）**：`count` 本身随年份增长；可评估"不返回精确 `total` / 只给 `hasNext`"与**游标分页**（按 `(END_TIME_, ID_)`）作为 A 的进一步优化，后者还能缓解 3.4.3 的新数据插页漂移。

### 9.1 严重：链路不成立 / 功能失效（P0）

**S1. L3 发布链路跨服务断裂，`8.1.2` 的 publisher 在 workflow 侧不存在**

- **证据**：`MessageRealtimePublisher.java` / `RedisMessageRealtimePublisher.java` 仅存在于 `blade-service/blade-message`；`blade-workflow` 全模块无 `StringRedisTemplate` / `convertAndSend`，现有跨服务通道只有 `INoticeClient`（Feign）。另有两处硬约束：`RedisMessageRealtimePublisher.java:41` 的 `CHANNEL_PREFIX = "message:"`、`MessageWebSocketConfig` 的 `PatternTopic("message:*")` —— 新频道不以 `message:` 开头，`RedisMessageSubscriber` 收不到。`3.5` 改动清单既没列 Feign 接口/端点，也没列 `MessageRealtimeEvent` 新 type 与 publisher 新方法。
- **触发场景**：按 `8.1.2` 直接编码 → bean 注入失败启动报错；或勉强发到 `workflow:*` → 订阅端静默无帧。
- **影响**：L3 主线完全不可落地，且 `3.6` 的「WS 三环验证」只验证既有通知链路，测不出新频道缺口。
- **方向**：在 `blade-service-api/blade-message-api` 新增 Feign 契约（仿 `INoticeClient`），由 `blade-message` 侧 `RedisMessageRealtimePublisher` 代发，频道必须落在 `message:*` 内；补全 `3.5` 改动清单。

**S2. 事件发布落在事务内，存在「推送先于提交」的读旧数据竞态**

- **证据**：`WfTaskServiceImpl.java:218-266`，`approve()` 标注 `@Transactional(rollbackFor = Exception.class)`，`doApprove()` 是其调用的 private 方法 —— 全流程在同一未提交事务内；而 `8.1.2` 明确把发布点放在 `doApprove` / `forward` / `circulate`。
- **触发场景**：审批提交 → 事务内发布 `workflow-changed` → 前端 1s 内 `reload()` → 后端事务尚未提交，列表读到提交前快照 → **之后没有第二次推送**，列表永久停在旧数据。若事务随后回滚，还会收到一条"根本没发生"的变更通知。
- **影响**：摧毁"实时刷新"的正确性，偶发且难复现。现有 `WfProcessNoticeListener` 是 Flowable 全局监听器、靠"尽力而为"容忍，不能照抄。
- **方向**：改为 `TransactionSynchronizationManager` 的 afterCommit 或 `@TransactionalEventListener(phase = AFTER_COMMIT)`；同时定义"发布失败是否影响流转"的语义。

**S3. 「默认关」与第 1 章目标脱节，交付态不解决用户核心诉求**

- **触发场景**：上线后按默认配置验收，`push=false` 时 L3 不工作，只剩 L1（切回可见补拉）；用户**停在列表页不切标签**，别人办完产生的新待办依然不出现。
- **影响**：`1.` 背景的诉求 2 在默认态下未解决；`6.` 验收首条「A 审批通过 → B 的待办标签 1s 内出现」未注明「需先开启 push」，按默认配置必然失败。文档未定义：默认关是最终态还是灰度阶段、由谁在何时开启、开启的验收标准、开启前是否必须完成分页（见 9.4）。
- **方向**：明确"默认关"的语义与开启流程，并在验收要点标注 L3 相关用例的前置条件。

**S4. 方案 A 重启 workflow 后，前端永远拿不到新配置**

- **证据**：`3.3.5`「配置只在首屏读取，运行中变更由 `onConnectChange` 重连时重新拉一次生效」；`8.5` 步 4「显式开启 `push.enabled=true`（方案 A 需重启）」。但 WS 连的是 **blade-message**，重启 blade-workflow **不会断 WS** → `onConnectChange` 不触发 → 前端仍持有 `{pushEnabled:false}`。
- **触发场景**：运维把开关改为 true 并重启服务，后端正常发布，前端一个都不订阅；除非每个用户手动 F5。
- **影响**："开启"操作实际无效；现象极难定位（后端有 publish、Redis 有帧、前端就是没反应）。方案 B 用 `Environment#getProperty` 同样解决不了前端感知。
- **方向**：配置下发改为随列表接口返回 / 短 TTL 缓存 / 由服务端在事件里携带开关版本；或明确"开启 push 必须通知用户刷新页面"。

**S5. `onConnectChange` 在本方案里基本不触发，断线补偿形同虚设**

- **证据**：`messageSocket.ts:88` 单例 guard、`onConnect` 内 `connectHandlers.forEach(...)`（`:128-129`）、`onConnectChange` 只把 handler 加入 Set（`:158-161`）—— **无「已连接则立即回调」的回放**。`MessageBell` 是布局层组件、比三个列表页更早挂载并已调 `connectMessageSocket()`；它自己靠 `useEffect` 里的 `refresh()` 首屏兜底（`:38-44`），而 `3.4` 的 hook 只写了 `onConnectChange` 补拉、没有首屏补拉。
- **触发场景**：用户打开待办页时 WS 早已连接 → hook 注册的 handler 永远等不到"首次连接"；断线重连发生在页面卸载后也不补。
- **影响**：`2.5` 第 6 洞「WS 断线不补推」实际未被绕过，但 `3.1` 宣称 L3「绕过 2.5 的 6 个洞」，属过度宣称。
- **方向**：`onConnectChange` 增加"当前已连接则立即回调"语义，或 hook 自行做首屏补拉。

### 9.4 分页性能决策的论证充分性（专项）

`4.4` 给出「后期不会失控」的确定性结论，但论证链有 4 处未闭合：

1. **瓶颈归因未量化，A 的必要性缺证据**。`5.3` 把"历史单调增长"与"索引失效"并列，但 `EXPLAIN` 实测显示当前 `type=ALL` 的根因是**函数包列**而非数据量。全文只有 `type/rows/Extra` 定性结果，**没有单次响应时间、响应体字节数、5000 行下的对比数据**。修完索引后 5000 行全量返回（可能仅几百 KB）是否真不可接受？"必须做服务端分页"缺实测支撑，`5.6` 却直接"推荐 A"。
2. **遗漏的替代方案**（未列入 `5.5` 的 A/B/C）：
   - **游标 / 键集分页**（按 `(END_TIME_, ID_)` 游标）：同时解决深分页 OFFSET 慢与新数据插入导致的页码漂移，且与事件驱动刷新天然契合 —— 最该评估却完全未提，直接关联 H3。
   - **不返回精确 total / 只给 `hasNext`**：`5.6 #5` 只说"count 随年份增长"未给权衡；而 A 明确要"独立 count"，事件驱动下每次 reload 都会重算 count，`4.2` 的消耗模型只算列表请求、没算 count。
   - **读模型宽表 / 字段冗余**（把 title、starter、nodeName 冗余到任务行）：可一次性消除 JOIN 与 `toVO`，比 `8.4` 批量化更彻底。
   - **按时间分区 / 冷热归档与分页的组合**：`5.6 #5` 只把归档列为待拍板项，未与分页做取舍对比。
   - **`LIMIT N` 止血（B）与 A 的量化对比**：B 被称为"过渡"，但无「N=500 时单页耗时/字节数 vs A」的数据。
3. **A 与 L3 的耦合代价未论证**：分页后每次事件 reload 都要重跑 `count` + 两源归并，`E` 增大时这部分同样线性放大。`3.3.7` 说"开关与分页完全解耦"，但 `4.4` 的"不会失控"实际**依赖分页已完成**；若按 `7. #6` 选择"分期做、先开 push"，`E × 单次全量成本` 仍会失控。`8.5` 把分页排在开启 push 之前算隐含依赖，但 `4.4` / `7. #6` 未把它升级为**硬前置**。
4. **`5.5` 末尾「L3 局部更新」作为增强未评估代价**：与服务端分页冲突（H3），分页后前端不持有全量数据、无法维护排序与 total；文档以"要求列表数据可局部维护"一句带过，未说明在分页下是否可行。

## 10. 本期实施范围（2026-11-08 收敛，仅三项）

> **覆盖性声明**：本章为**最新范围决策**，覆盖第 0 章摘要与第 3 章「L1 + L3 主方案」的范围描述。
> **第 1~9 章原样保留**为设计与审查记录，本期**不修改、不实施**其中 L3 相关部分。
> 本期只完善并实施以下三项：① L1 切回可见补拉；② 分页 + 索引修复；③ 保持既有铃铛红点/流程通知。
> **其余一律不动**：L3 全链路、推送开关、L2、配置下发，以及第 9 章 P0/P1 闭环（因 L3 暂缓而自动失效，见 10.5）。

### 10.1 决策依据（大型企业适用性）

| 维度 | 判断 |
|---|---|
| 必要性 | 「有新待办」的感知已由 `WfProcessNoticeListener` → 消息中心 → 铃铛红点满足（`AvatarDropdown.tsx:50-52` 已明确把角标收敛到消息铃铛、"待办数量以待办事宜页面为准"）。L3 的唯一增量是"用户盯着列表页且不切标签时新行自动跳出"，占比极低 |
| 体感覆盖 | 用户看到红点 → 切回待办标签 → L1 自动补拉，已覆盖真实操作路径 |
| 容量风险 | 大型企业 1 万人在线 × 3 标签 = 3 万 WS 连接、心跳约 1000 QPS（既有开销）；业务高峰期若开 L3，按 `4.2` 修订模型可达数百 QPS 列表查询。**叠加 `/task/done` 全量无分页 + 索引失效（`type=ALL` + filesort）会直接打满 DB 连接池，且 ACT 表与业务表同库 `blade`，会拖垮同库其它业务** |
| 削峰 | 事件驱动无全局限流/背压，`3.4` 的节流按页面实例生效；业务越忙刷新越猛，恰逢最不能出问题的时段 |
| 副作用 | 自动 `reload()` 会打断用户正在进行的翻页/筛选；跨标签跳页需额外复杂度 |

**结论**：`push.enabled` 默认关从"灰度交付态"改为**长期态**；把资源投到"每次打开已办页都重"这一确定性痛点上。**砍掉 L3 顺带消灭第 9 章 12 项 P0/P1 缺陷**（无需新增 Feign 契约、无需事务后发布、无需跨标签节流、无需配置感知），前期工作量可全部转投分页/索引。

### 10.2 项 1：L1 切回可见补拉（纯前端，零后端改动）

#### 10.2.1 实施形态（与第 3.4 修订版的关系）

第 `3.4` 的 hook 混合了 L3 的 WS 订阅、配置读取、`seq`、跨标签节流。**本期不使用该 hook**，改为独立的纯前端 `useVisibilityRefresh(actionRef)`：

| 保留 | 剥离（L3 相关，本期不做） |
|---|---|
| `visibilitychange` 可见时补拉 | `/user/queue/workflow-changed` 订阅、`onConnectChange` 补拉 |
| 标签内 500ms~1s 节流 | `getListRefreshConfig` / `listRefresh` 配置字段 |
| 卸载清理 | `BroadcastChannel` 跨标签去重（L2） |
| `pageshow` 兜底 | `seq` 跳号检测、事件类型分派、开关短路 |

> 无 WS 事件源，因此**不需要 `dirty` 标记**、不需要跨标签节流：切回可见本身是用户主动动作，天然带人工节流，一次 `visibilitychange` 只对应一次请求。

#### 10.2.2 改动清单

| 文件 | 改动 |
|---|---|
| 新增 `ant-design-pro/src/hooks/useVisibilityRefresh.ts` | hook 本体：`visibilitychange` + `pageshow` 监听、节流、卸载清理 |
| `Workflow/Todo/Todo.tsx`（`actionRef` 见 L40）、`Done/Done.tsx`（L39）、`Request/Request.tsx`（L31） | 各接一行 `useVisibilityRefresh(actionRef)` |

**不改动**：`utils/messageSocket.ts`、任何后端接口、任何配置文件、Nacos。

#### 10.2.3 hook 骨架（片段级草案，未落盘）

```ts
export function useVisibilityRefresh(actionRef: React.MutableRefObject<any>) {
  useEffect(() => {
    let last = 0;
    const refresh = () => {
      const now = Date.now();
      if (now - last < 800) { return; }        // 标签内节流
      last = now;
      actionRef.current?.reload();             // ProTable reload() 保留当前页码
    };
    const onVisible = () => { if (document.visibilityState === 'visible') { refresh(); } };
    const onPageShow = () => { refresh(); };  // M13：同窗口切 DevTools / 最小化 / bfcache 兜底
    document.addEventListener('visibilitychange', onVisible);
    window.addEventListener('pageshow', onPageShow);
    return () => {
      document.removeEventListener('visibilitychange', onVisible);
      window.removeEventListener('pageshow', onPageShow);
    };
  }, [actionRef]);
}
```

- 用 `reload()` 而非 `reloadAndReset()`：切回补拉不应改变用户所在页码；`Request.tsx` 已是服务端分页，天然兼容。
- 分页完成后（10.3）单次成本恒定，切换标签的开销可忽略。

#### 10.2.4 边界与验收

- 已知取舍：用户长期不切回某后台标签，该标签数据保持陈旧（"后台零请求"的既定设计）；该产品行为需在发布说明中告知。
- 验收：新标签办完自动关闭 / 点铃铛通知跳走再回来 → 列表自动补拉；同窗口切 DevTools / 最小化 → `pageshow` 兜底生效；空闲 5 分钟 Network 零列表请求；连切 10 次标签仅产生节流后次数的请求；卸载后无残留监听。
