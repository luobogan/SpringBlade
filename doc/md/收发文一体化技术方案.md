# 收发文（公文）一体化技术方案

> **方案定位（以此为准）**
> 本方案以 **GB/T 9704 标准为底座**、以 **OFD/PDF 版式文件为载体**，结合 **AI 智能排版**与 **CA 电子签章**，形成收发文「真·电子公文」的一体化解决方案。
> **「Word 宏 / VBA 套红」与「图片叠加红头」两条旧路线明确淘汰**。
> **格式分级支持（本方案总纲）**：**Word + PDF 为初级支持格式（L1，默认交付）**——面向一般企业开箱即用，不依赖任何厂商 SDK 与国标规则库；**GB/T 9704 + OFD/PDF 版式为标准升级形态（L2）**——政务/信创场景通过配置开关叠加启用；AI 排版与 CA 签章为 L2 之上的增强（L3）。分级策略与升级路径详见 §2.2.1。

## 1.1 两个 Ecology 目录的定位与关系

| 目录 | 形态 | 能看到什么 | 看不到什么 |

**关键结论：二者不是「两套收发文实现」，而是同一套实现的「前端部署态」与「后端源码态」互补视图。**

- 收发文「正文如何套红」→ 前端触发 + 后端 `OdocFileAction` / `OfficedService` 合成

# 第二部分 方案定位与技术路线选型

## 2.1 套红技术路线演进（以此为准）

> **权威定义：最新的套红技术不再是单纯的「Word 宏」或「图片叠加」，而是以 GB/T 9704 标准为底座、以 OFD/PDF 版式文件为载体，结合 AI 智能排版与 CA 电子签章的一体化解决方案。**

| 代际 | 技术路线 | 实现方式 | 判定 |
|---|---|---|---|
| 一代 | **Word 宏 / VBA 套红** | Word 宏打开红头模板、替换书签、插入正文（E9 `WebOffice_odoc.js:589 WebUseTemplate`、iWebOffice 消息包属此类） | **淘汰**：强依赖 Windows + Office/插件，无法服务化，无法进入版式文件体系 |
| 二代 | **图片叠加红头** | 红头渲染成图片贴到正文上方 | **淘汰**：不可检索、不可复用、放大失真，不符合版式结构化要求 |
| 三代 | **版式文件一体化套红** | **GB/T 9704 底座 + OFD/PDF 载体 + AI 智能排版 + CA 电子签章**，全链路服务端完成 | **标准方案（本方案即按此设计）** |

> docx + 书签替换在本方案中定位为 **L1 初级支持格式的核心能力**：对一般企业是**正式交付形态**（Word 编辑 + PDF 预览/归档）；对政务 / 信创场景则是升级到 OFD/PDF 版式（L2）前的过渡形态。分级策略见 §2.2.1。

## 2.2 两条路线的本质差异

| 维度 | 路线一：docx 编辑态套红（过渡） | 路线二：**版式文件（OFD/PDF）**（标准） |
|---|---|---|
| 载体 | `.docx`（可编辑、流式） | `.ofd` / `.pdf`（**固定版式**） |
| 版面保真 | 依赖字体/版本，跨端可能偏移 | **一次定稿、处处一致** |
| 红头 | 套红时套进 docx | 红头是**版式的组成部分**，定稿即固化 |
| 法律效力 | 弱（可被篡改） | **强**（版式 + 电子签章 + 时间戳 + CA） |
| 归档标准 | 无国标要求 | **OFD-A（GB/T 33190-2016）**，档案级 |
| 信创适配 | Office 依赖 | **国产 OFD 厂商全栈** |
| 适用 | 企业内部流程、企业公文 | **政府 / 国企 / 事业单位** |

> **版式文件不是「更好的套红」，而是电子公文的「定稿与签发形态」。**
> 正确链路：`docx（编辑态）→ 定稿 → 版式文件（OFD/PDF）→ 电子签章 → 归档`。

### 2.2.1 格式分级支持策略（总纲：L1 Word/PDF 初级接入 → L2 OFD/PDF 标准升级）

> **原则：并非所有企业都采用 GB/T 9704 与 OFD。方案默认以一般企业常用的 Word + PDF 为初级支持格式，开箱即用；GB/T 9704 + OFD/PDF 版式作为标准升级形态，通过配置开关平滑叠加，代码与数据模型零改动。**

#### 分级定义

| 级别 | 格式 | 适用场景 | 定位 |
|---|---|---|---|
| **L1 初级支持（默认，全场景交付）** | **Word（.docx/.doc）+ PDF** | 一般企业、未采购 OFD/CA 的客户 | 开箱即用：正文编辑 + 服务端套红 + PDF 预览/归档，仅依赖开源组件（OnlyOffice / LibreOffice headless） |
| **L2 标准支持（升级形态）** | + **OFD/PDF 版式文件**（GB/T 9704 底座） | 政府 / 国企 / 事业单位、有信创要求 | 定稿 → 版式 → 签章 → OFD-A 归档的「真·电子公文」 |
| **L3 增强（可选叠加）** | L2 + AI 排版 L2/L3 + CA 增强 | 智能化要求高的客户 | 结构识别、国标合规校验（可私有化 LLM） |

#### 三条设计底线

1. **默认 L1，永不因缺组件而不可用**：`wf_odoc_process_set.layout_format = 0`（不启用版式文件）→ 流程自动止于 Word + PDF；OFD 转换、CA 签章组件未装配时（`available()=false`）前端隐藏对应按钮并自动降级。
2. **同一套数据模型承载多格式**：`wf_odoc_doc_version.doc_file_type`（3doc / 7docx / 12pdf / 13ofd）与 `wf_odoc_layout_file.format` 天然区分格式；L1 与 L2 共用正文、版本、模板、书签、状态机、文号、提交拦截——**业务代码不感知格式级别**。
3. **平滑升级，无迁移**：升级 = 配置切换（`layout_format` 0→12/13 + 装配 OFD 厂商 SPI + 启用 GB/T 9704 规则库），存量 Word/PDF 公文经同一 `to-layout` 接口批量转换，**不改代码、不迁数据、不产生格式孤岛**（指同系统自身 L1→L2 升级，与 §5.6 I7 的 E9 跨系统数据迁移无关）。

> L1 与 L2 的落地机制（接入 / 转换 / 流转 / 升级四环节）详见 §3.1.3。

### 2.2.2 双模式输出支持（混合模式）：docx 直出 与 GB/T 9704 + OFD/PDF 标准版式并存

> **决策：支持混合模式**——客户可按需灵活选择「**直接输出 docx**」（L1，一般企业）或「**采用 GB/T 9704 + OFD/PDF 标准版式能力输出**」（L2，政务/信创）；二者在同一套代码与数据模型内共存，按配置切换，互不干扰。

#### （1）接入形态（关键设计决策）：能力插件化 + 配置开关编排，而非「开关 vs 独立模块」二选一

1. **能力层独立成模块**：OFD 转换 / CA 签章 / AI 排版实现放独立 module（`blade-workflow-odoc-layout`；转换量大时升级为独立微服务），经 `IOdocFormatConvertor` / `IOdocSealService` SPI 装配——获得独立发版、扩缩容与厂商依赖隔离；
2. **编排层留在主流程**，由配置开关控制是否启用标准版式链路——获得低成本交付与流程级灰度；
3. **同步强动作（提交拦截、验章查询）留在主流程内**；重异步动作（批量转版式、归档推送）走异步任务/事件；
4. **明确禁止**复制一套收发文代码做「标准版」——双代码线是维护灾难。

#### （2）配置策略（三层粒度叠加）

| 层级 | 载体 | 控制什么 |
|---|---|---|
| **全局开关（部署级）** | `blade.workflow.odoc.layout.enabled` + `ofd.vendor`（`@ConditionalOnProperty`） | 「有没有」：SDK 未采购/未部署时 Bean 不装配，`available()=false`，前端隐藏对应按钮 |
| **流程级开关（业务级）** | `wf_odoc_process_set.layout_format / layout_node_key / sign_node_key` | 「用不用」：某流程走 docx 直出还是标准版式链路，支持流程级灰度 |
| **文种级规则（版式级）** | `wf_odoc_mould.gbt_profile_id` + `doc_type_code` | 「怎么排」：不同文种绑定不同 GB/T 9704 profile |

> 不设**文档级**开关：同一流程内单份公文格式级别不同会造成产物不一致、拦截语义混乱；文档的格式级别由「流程级开关 + 文种模板」派生。

#### （3）启用与关闭的行为差异

| 行为 | docx 直出（关闭） | 标准版式（启用） |
|---|---|---|
| 套红 | docx 书签合成 + PDF 预览 | 同左，再叠加「转版式」步骤 |
| 定稿 | `is_final=1`，止于 PDF | 冻结 docx → AI 排版 L1 → 转版式（元数据注入） |
| 签章 | 无按钮（或按 D10 轻量存证） | `mandatoryActions` 增加 SIGNATURE 项 |
| 归档 | PDF/PDF-A + `wf_odoc_meta` | OFD-A + 元数据 |
| 回退 | — | 已产出的 OFD/签章记录保留只读，新实例回退 docx 直出 |

存量实例保护：配置切换**只影响新实例**，进行中实例按发起时的配置快照执行。

#### （4）对下游系统的影响

- 档案系统：docx 模式推 PDF、版式模式推 OFD-A，接口按配置协商或做适配层；**元数据结构不变**（`wf_odoc_meta`），检索不受影响；
- 公文交换（GB/T 33477）：部分政务交换要求 OFD，仅版式模式可对接——这是「必须能开」的硬需求；
- 运维面：启用即引入厂商 SDK 部署清单、内网出网与授权到期管理，需配「授权到期告警」与降级预案（见 G7）；
- 测试隔离：`is_test` 两态一致；版式模式需「测试模式」跳过真实 CA（见 G9）。

#### （5）交付形态建议

| 场景 | 形态 |
|---|---|
| 单体部署、客户集中、转换量不大 | SPI jar 可选装配（同一进程，开关控制） |
| 政务大客户、转换量大、多客户交付需裁剪 | 版式能力独立微服务部署 |
| 不采购 OFD/CA 的客户 | 模块不交付/不装配，自动停留 docx 直出 |

## 2.3 一体化四要素

```
                ┌──────────────── GB/T 9704 规则库（底座）────────────────┐
                │  纸型/页边距/行数/字数/字体字号/红头/红线/页码            │
                └───────────────────────┬────────────────────────────────┘
                                        │
   正文(docx/HTML) ──► AI 智能排版 ──► 规范版式 ──► 套红(红头+公文要素) ──► OFD/PDF 版式文件
                                        │                                      │
                                  结构化工件                             CA 电子签章 + 时间戳
                                        │                                      │
                                  表单回填 / OFD 元数据                        │
                                        └──────────────► 归档（OFD-A）◄────────┘
```

| 要素 | 职责 | 缺失后果 |
|---|---|---|
| **GB/T 9704 规则库** | 定义「什么是合规的公文版式」——规则来源、审计依据 | 格式不合规，无法通过公文审核 |
| **AI 智能排版** | 把自由正文变成合规版式——自动化手段 | 依赖手工排版，效率低、易错 |
| **OFD/PDF 版式载体** | 承载最终版式——保真、可签章、可归档 | 无法固化版式，法律效力弱 |
| **CA 电子签章** | 赋予法律效力——可信 | 不构成「可靠的电子签名」 |

> **任一环节缺失，都不构成「真·电子公文」。**
> 该判定针对 **L2 标准形态（政务/信创）**；一般企业的 **L1（Word/PDF）** 场景不强制要求 OFD 载体与 CA 签章（详见 §2.2.1）。

## 2.4 GB/T 9704 公文格式底座

### 2.4.1 标准定位

- **GB/T 9704-2012《党政机关公文格式》**（替代 1999 版）是党政机关公文排版的国家标准，也是本方案的**唯一格式基准**。
- 国标规定的 15 个文种：决议、决定、命令（令）、公报、公告、通告、意见、通知、通报、报告、请示、批复、议案、函、纪要。
- **佐证**：E9 的 `mouldbookmark.json` 已按文种建立套红模板（通知 5042、函 5025、请示 5039、批复 5035、通报 5041、纪要 5026、令 5521、通告 5040、意见 5034、决议 5032、议案 5038、公告 5024、决定 5027）。我们的工作不是重新设计版式，而是**把每个文种模板升级为「GB/T 9704 合规版式」**。

### 2.4.2 三要素结构（版式分区依据）

| 区 | 要素 | 版式要点 |
|---|---|---|

```java
/** GB/T 9704 版式 profile：规则的唯一载体，可按机关微调 */
public class Gbt9704Profile {
    private PageSpec page;                        // A4、页边距、版心
    private LineSpec line;                        // 每面行数、每行字数
    private Map<ElementType, FontSpec> fonts;     // 要素 → 字体字号
    private boolean redSeparator;                 // 红色分隔线
    private PageNumberSpec pageNumber;            // 页码（奇右偶左 + 一字线）

    public enum ElementType {
        ORG_SIGN, DOC_NUMBER, SIGNER, CLASSIFICATION,   // 版头：红头/发文字号/签发人/密级紧急程度份号
        TITLE, RECIPIENT, BODY, H1, H2, H3, H4,          // 主体：标题/主送/正文/各级标题
        ATTACHMENT_NOTE, ATTACHMENT,                     // 附件说明/附件
        ORG_SIGNATURE, DATE, SEAL, NOTE,                 // 署名/成文日期/印章/附注
        CC, ISSUER, ISSUE_DATE                           // 版记：抄送/印发机关/印发日期
    }
}
```

要点：
1. **规则库是确定性的**——AI 只负责「把正文识别成哪个要素类型」，格式本身永远由规则库决定，保证国标合规可审计。
2. 版式模板 = **GB/T 9704 规则库 + 文种模板 + 机关信息**（红头名称、机关代字）三者合成，支持按机关定制。
3. 合规校验（L3）同样以规则库为依据，输出「国标符合性问题清单」。

|---|---|---|
| 第一步（无 AI） | L1 规则引擎 + 文种版式模板 | 已满足国标合规，可上线 |
| 第二步 | L2 规则式结构识别（正则 / 段落特征 / 序号推断） | 大幅减少手工排版 |
| 第三步 | 接入 LLM 做结构识别与 L3 合规校验（私有化部署） | 智能化增强，可选 |

## 2.6 场景化选型

> 分级总纲见 §2.2.1：所有客户**默认 L1（Word/PDF）开箱即用**；下表描述的是「在 L1 基础上是否叠加 L2 能力及配置要点」。

| 场景 | 推荐路线 | 关键配置 |
|---|---|---|
| **政府 / 国企 / 事业单位** | **路线二为主**（版式文件 + 电子签章 + OFD-A 归档） | `ofd.vendor` 按客户采购；`seal_required=1`；归档开 OFD-A |
| 大型集团（有信创要求） | 混合：内部审批 docx，对外报送/归档转版式 | 定稿节点触发 `to-layout` |
| 一般企业 | 路线一（docx 套红 + OnlyOffice） | 无需 OFD 厂商；PDF 仅作预览 |
| 移动优先 / 轻量公文 | 路线一 + PDF 预览 | 无需签章 |

**混合架构推荐（最实用）**：

```
节点链：拟稿(docx) → 审核(docx,留痕) → 定稿 → [套红] → 转版式(OFD) → 电子签章 → 归档(OFD-A)
                                                              ↑ 仅政务/信创场景启用
```

`wf_odoc_process_set.layout_format = 0` 表示该流程不启用版式文件（企业场景），链路自动止于 docx + PDF 预览。

```

  └─ 满足 N1/N2/N3/N4/N6/N7/N8；AGPL 需法务确认（政企私有化通常可接受，必要时采购商业授权）

国产化/OFD 输出：外部转换服务
  └─ docx → PDF / OFD 用 LibreOffice headless 或 WPS Linux 转换（对齐 E9 weaver/wps/view/linux/convert）

  └─ 复用现有 RichTextEditor(@opentiny/fluent-editor) 采集 HTML
  └─ 服务端 convertHtmlToDocx 后走同一套套红合成（对齐 E9 onlineEditStore.previewWithTempl 路径）
```

**决策 checklist（P1 启动前必须答完）**：
1. 是否需要修订留痕？→ 是：排除纯 C 方案。
2. 是否必须 OFD 归档？→ 是：确认 A 的 OFD 转换链或引入 B。
3. AGPL 是否可接受？→ 否：转 B 或采购 OnlyOffice 商业授权。
4. 移动端是否要编辑正文？→ 是：C 兜底方案必须一起做。

### 3.1.3 格式分级支持落地机制（L1 Word/PDF 初级接入、转换、流转与平滑升级）

> 落地原则：**默认 L1（Word + PDF）开箱即用，不依赖任何 OFD/CA 厂商组件与国标规则库；L2 通过配置开关叠加，代码与数据模型零改动**（分级定义见 §2.2.1；混合模式接入形态与三层配置策略见 §2.2.2）。

#### （1）接入机制：Word/PDF 如何进系统

| 途径 | 落地 |
|---|---|
| 上传正文 | 上传 `.docx` / `.doc` 作为首版本（`wf_odoc_doc_version.doc_file_type = 7/3`，`has_used_templet=0`） |
| 在线编辑 | PC：OnlyOffice iframe 编辑，回调落新版本；移动端兜底：`RichTextEditor` 采集 HTML → 服务端 `convertHtmlToDocx` |
| 模板生成 | 由编辑模板（`wf_odoc_mould.mould_type=1`）生成正文首版本 |
| 附件类文档 | Word/PDF 附件作为 `is_ext_file=1` 版本或独立附件，不参与套红 |

#### （2）转换机制：Word → PDF（L1 内置，无厂商依赖）

- **引擎**：LibreOffice headless 或 OnlyOffice 内置转换（开源即可，对齐 E9 `wps/view/linux/convert` 的转换思想但不绑定厂商）；仅在升级 L2 时才需要 OFD 厂商 SDK。
- **时机**：保存/套红后**异步**转 PDF 供预览（避免阻塞）；定稿节点**同步**产出正式 PDF。
- **落库**：PDF 记入 `wf_odoc_layout_file(format=12)`，`src_version_id` 溯源到 docx 版本——**与 L2 的 OFD 记录（format=13）同一张表、同一套查询与前端分发**。
- **归档**：L1 归档形态 = PDF（可选 PDF/A，按 D10 决策）+ `wf_odoc_meta` 元数据——元数据不依赖 OFD，档案检索在 L1 同样可用。

#### （3）流转机制：L1 能力不缩水

套红状态机（S0–S4）、节点必做动作框架（套红/签章/清稿）、前端+后端双提交拦截、版本回滚、文号生成与回写、打印呈批表**在 L1 下全部可用**——与 L2 的唯一差异是「产物格式」：L1 产出 docx + PDF，L2 产出 OFD/PDF 版式。即：**一般企业拿到的是完整收发文能力，只是不含 OFD 与 CA**。

#### （4）升级机制：L1 → L2 平滑升级路径

```
L1: Word 编辑 + PDF 预览/归档                      （开箱即用，默认交付）
      │ 开关1：采购 OFD 厂商 + layout_format 0→12/13
      │ 开关2：启用 GB/T 9704 规则库 + 文种版式模板
      │ 开关3：接入 CA 厂商（可选，seal_required=1）
      ▼
L2: 定稿 → AI排版L1 → 套红 → OFD/PDF 版式 → CA 签章 → OFD-A 归档
```

升级四要点：

1. **配置驱动、代码不变**：`IOdocFormatConvertor` / `IOdocSealService` 按 SPI 装配（`@ConditionalOnProperty` / `available()` 自动降级），未装配自动停留 L1。
2. **存量平滑升级**：同部署内既有 L1 公文批量走同一 `to-layout` 接口转 OFD/PDF，元数据从 `wf_odoc_request` 补齐注入 `wf_odoc_meta`——无数据迁移、无格式孤岛。**（注：指本系统内部 L1→L2 升级，与 §5.6 I7 的 E9 历史数据迁移无关。）**
3. **流程级灰度**：`layout_format` 按流程配置——试点流程先升 OFD，其余流程保持 Word/PDF，双轨共存、逐流程切换。
4. **多格式共存**：同一正文可同时保留 docx + PDF + OFD（`wf_odoc_layout_file` 多行 + `wf_odoc_doc_version` 多类型），前端 `LayoutFileViewer` 按 `format` 分发到对应渲染器（PDF 用 pdfjs，OFD 用厂商控件）。

## 3.3 套红状态机

### 3.3.1 状态定义

| 状态 | 含义 | 落库表现 |
|---|---|---|
| `S0 无正文` | 尚未创建正文 | `wf_odoc_doc` 无记录 |
| `S1 未套红` | 有正文，未套红 | `doc.has_used_templet=0`，最新版本 `has_used_templet=0` |
| `S2 已清稿` | 已生成「套红前取消痕迹版本」 | 新增版本 `has_used_templet=0`，`version_detail='套红前取消痕迹版本'` |
| `S3 已套红` | 套红完成 | `doc.has_used_templet=1`，最新版本 `has_used_templet=1` |
| `S4 已取消` | 回滚到未套红版本 | 新增版本 `has_used_templet=0`，`doc.has_used_templet=0` |

### 3.3.2 状态转移与触发拦截

```
S0 --创建正文--> S1
S1 --进入套红节点且未套红--> S2(清稿) --> S3(套红)
S3 --取消套红--> S4  (S4 ≡ S1 语义, 但保留版本痕迹)
S1 --非套红节点保存--> S1(新版本, has_used_templet=0)
```

```
自动套红条件（四者同时满足）:
  docId > 0
  AND currentNode == wf_odoc_process_set.taohong_node_key
  AND taohong_mould_id > 0 (或按权限/字段解析出 mouldId)
  AND doc.has_used_templet != 1

提交拦截（前端 + 后端双保险）:
  IF must_taohong = 1 AND currentNode == taohong_node_key AND has_used_templet != 1
     → 阻断提交, 提示「请先执行套红操作」
```

> 后端必须复检（对齐 E9 `RequestUseTempletManager.ifHasUseTempletSucceed`）：前端校验不可信，流转提交时由 `RequestManager` 等价物再判一次。

### 3.3.3 套红流程（服务端，逐步）

```
① 前置校验：docId / nodeKey / mouldId / has_used_templet / 正文类型可编辑(.doc/.docx/.wps)
② 清稿（若开启留痕）：acceptRevisions(最新版本) → 生成新版本 S2(has_used_templet=0)
③ 取书签值 Map：
     a. 读 wf_odoc_mould_bookmark(mould_id) → 书签清单
     b. 按 wf_odoc_mould_field_map(def_id, mould_id, select_value) 取 field_key
     c. 从 renderForm 的 dataJson（或 wf_form_snapshot）取字段值
     d. 日期按 date_show_type 格式化；金额按千分位
     e. 跳过 is_content=1 的书签（Content）
④ 合成：
     replaceBookmark(模板文件, 除Content外所有书签, bookmarkMap)
     insertContent(Content 书签, 正文文件内容)
     → 生成套红后 docx
⑤ 转预览：docx → PDF（必需）/ OFD（政务）
⑥ 落库：
     file_id = 上传(套红后docx)
     INSERT wf_odoc_doc_version(doc_id, version_id+1, file_id, has_used_templet=1, '套红版本')
     UPDATE wf_odoc_doc SET has_used_templet=1, doc_edition_id=新版本id
⑦ 返回 { versionId, previewUrl, fileId }
```

### 3.3.4 取消套红（版本回滚）

```
① 查最新未套红版本: SELECT * FROM wf_odoc_doc_version
     WHERE doc_id=? AND is_ext_file=0 AND has_used_templet=0 ORDER BY version_id DESC LIMIT 1
② 复制该版本文件为新版本（version_id+1，version_detail='取消套红回滚'）
③ UPDATE wf_odoc_doc SET has_used_templet=0, doc_edition_id=新版本id
④ 返回 { versionId, previewUrl }
找不到未套红版本 → 抛业务异常（对齐 E9 10005498）
```

## 3.4 版式文件链路（五态）

```
① 编辑态      docx（OnlyOffice/富文本）          可编辑、可留痕
      │  提交定稿
② 定稿态      docx 锁定（不可再改）              版本冻结
      │  AI排版 + 套红 + 转版式
③ 版式态      OFD / PDF（固定版式 + 元数据）      一次定稿处处一致
      │  电子签章 + 时间戳
④ 签发态      已签章版式文件                     具有法律效力
      │  归档
⑤ 归档态      OFD-A（GB/T 33190-2016）           档案级、长期可读
```

### 3.4.1 职责重划

| 环节 | 路线一（docx，过渡） | 路线二（版式，标准） |
|---|---|---|
| 红头来源 | Word 红头模板 + 书签替换 | **版式模板**（红头 + 版式 + 元数据区） |
| 字段填充 | Word 书签（`fld_Mark` 等） | 版式渲染时填充（或写入 OFD 元数据） |
| 正文插入 | `Content` 书签 | 版式正文区 |
| 输出 | docx（+PDF 预览） | **OFD（+PDF 预览）** |
| 签章 | 需先转 PDF/OFD 再签 | **直接签** |
| 归档 | 不适用 | **OFD-A** |

- 配置：`wf_odoc_print_set`（按节点）+ `printflowcomment`（2始终打印流转意见 / 0始终不打印 / 其它放入模板但不打印，`PrintInfoBiz.java:35-56`）。

## 3.7 清稿 / 留痕

- 配置：`wf_odoc_process_set.clean_copy_node_keys`（清稿节点）、必须留痕标记、`isHideTheTraces`；表 `wf_odoc_clean_trace(workflowId, ISCLEARTRACEDISABLE)`。
- 实现：编辑器/WPS 的 `acceptRevisions` / `clearRevisionAndComent`；流程 Action 等价物（`CreateTraceDocument` / `CreateTraceDocumentByClear`）。
- **语义冲突（重要）**：套红前**必须清稿**（生成「套红前取消痕迹版本」，`hasUsedTemplet=0`），但业务又要求保留修改痕迹——所以清稿结果本身要**存为一个版本**，而非丢弃。
- **与编辑器选型绑定**：选 OnlyOffice/WPS → 有原生 track changes，可同时满足清稿与留痕；选自研 HTML→docx → **无原生修订**，需自行设计痕迹（意见式修订记录或 diff），否则只能放弃留痕。**这是选型的硬约束，必须在 P1 前定稿。**

### 3.8.3 节点必做动作框架（套红/签章/清稿统一）

> E9 中套红、签章、清稿是三个独立 if；SpringBlade 应抽象为统一框架，避免重复实现提交拦截。

```
NodeMandatoryAction（节点必做动作）
├─ actionType: TAOHONG(套红) / SIGNATURE(签章) / CLEAN_COPY(清稿)
├─ nodeKeys:   生效节点
├─ mustBeforeSubmit: 提交前是否强制完成
├─ stateResolver:   状态解析器（各自查自己的状态）
└─ onCompleted:     完成后的副作用（回写 has_used_templet / 签章记录 / 新版本）

流转提交时的统一复检（RequestManager 等价物）:
  for (action : currentNode.mandatoryActions) {
      if (action.mustBeforeSubmit && !action.stateResolver(instance)) {
          throw new ServiceException(action.blockMessage);   // 「请先执行套红操作！」
      }
  }
```

前端只需消费一个统一契约：`mandatoryActions: [{type, done, blockMessage, actionUrl}]`，按钮区按 `done` 渲染「去执行/已完成」。

```json
    "mouldList": [{"mouldId":4022,"mouldName":"发文套红模板"}],
```

## 3.11 收文差异点落地

- 收文**默认不配套红节点**（`taohong_node_key` 为空）→ 正文页走普通编辑分支，无套红按钮。
- 收文编号用 `receive_num`，字段语义走 `wf_odoc_request` 的收文列。
- 收文链路（登记 → 拟办 → 批阅 → 承办）用同一套节点/出口建模，只是环节配置不同。
- 转文（收文 → 发文）：实现为「以源实例为模板新建目标实例」，记录来源关系（`source_instance_id`），并继承表单数据与正文。

2. 进入套红节点 → 自动/手动套红成功；`fld_Mark`(文号)、`fld_zsdw`(主送)、`fld_csdw`(抄送)、`fld_yfrq`(印发日期) 书签值正确取自表单字段。

10. 政务场景：可输出 OFD，`.ofd` 只读展示正常；PDF/OFD 双轨内容一致。
11. 电子签章可在系统内验章，签章后文档被篡改可被检测。
12. 版式文件含公文元数据，可按元数据检索。
13. **混合模式**：`layout_format=0` 的流程全程 docx + PDF，无 OFD/签章按钮；`layout_format=13` 的流程产出 OFD——同一部署下两类流程互不干扰（流程级灰度，§2.2.2）。
14. **配置切换回退**：启用版式后关闭开关，已产出的 OFD/签章记录只读可查，新实例回退 docx 直出。
15. **存量实例保护**：进行中实例在配置切换后按发起时的配置快照执行，不受新配置影响。

# 第五部分 遗漏与风险分析（重点）

> 本章为整合后专项复查结论。按用户关注的七个维度逐项分析，并在末尾给出风险矩阵与应对优先级。

## 5.1 标准符合性

| # | 风险 | 说明 | 应对 |
|---|---|---|---|
| S1 | **标准版本差异** | GB/T 9704-2012 替代 1999 版，关键变化包括成文日期改用阿拉伯数字、页码规则、增加份号/紧急程度等。客户可能仍按旧习惯或地方细则执行 | D9 明确执行版本；`wf_odoc_gbt_profile.standard_ver` 记录；规则库参数化，可切换 |
| S2 | **地方 / 行业 / 党委系统标准差异** | 政府机关与党委机关在发文机关标志、字号、版记上存在差异；部分行业（军队、高校、国企）有自有规范 | `wf_odoc_gbt_profile` 按 `org_scope` 定制多套 profile；模板资产按机关分套 |
| S3 | **联合行文处理不足** | GB/T 9704 对联合行文有专门规定（主办机关标志在前、协办在后且字号不超主办机关；版记需列所有印发机关）。单一「发文机关标志」模型难以表达 | 模板增加「多机关标志」要素类型；`wf_odoc_mould` 增加 `is_joint` 标记；P2 需专项验证 |
| S4 | **上行文 / 下行文 / 平行文版式差异** | 上行文须标注签发人、发文字号居左；下行文发文字号居中。当前 `Gbt9704Profile` 未区分行文方向 | 增加 `docDirection` 参数，规则库按方向返回不同 FontSpec/布局 |
| S5 | **文种覆盖不全** | 国标 15 文种，实际客户常用子集可能只有 5–8 个，但也可能出现国标外的内部文种 | 文种可配置化（`doc_type_code`），不限 15 种；内部文种走自定义 profile |
| S6 | **电子公文系列国标遗漏** | 除 GB/T 9704 外，还应关注 GB/T 33190（OFD）、GB/T 33476（电子公文格式）、GB/T 33477（电子公文交换接口）、GB/T 33478（系统建设规范） | 信创清单已列；交换接口（GB/T 33477）在 P6 公文交换时专项对齐 |
| S7 | **版记 / 页码 / 红线等细节易错** | 红色分隔线宽度、页码一字线、奇偶页位置等细节极易被忽略，而公文审核对这些极敏感 | 由 L1 规则库确定性生成 + L3 合规校验输出问题清单；提供「国标符合性报告」 |

## 5.2 版式文件兼容性

| # | 风险 | 说明 | 应对 |
|---|---|---|---|
| F1 | **国标字体缺失（最大坑）** | 小标宋、仿宋_GB2312、楷体_GB2312 是 Windows 字体，**Linux 信创环境默认没有**。缺失会导致 docx→OFD/PDF 后字体替换、版面偏移、行数/字数不符 | ①采购/安装国标字体授权（方正小标宋、仿宋_GB2312 等）并纳入部署清单；②转换服务统一挂载字体目录；③验收时在信创环境实测，不只在 Windows 验证 |
| F2 | **字体嵌入问题** | docx 嵌入字体体积大且部分字体禁止嵌入；OFD/PDF 不嵌入则依赖阅读端字体 | PDF 用 PDF/A 子集嵌入；OFD 依赖厂商字体方案；需在 P5 做跨端一致性测试 |
| F3 | **跨厂商 OFD 兼容性** | 数科/福昕/永中生成的 OFD 可能无法被其他阅读器正确解析（私有扩展差异） | 每个项目只用一家生成；验收必做「生成厂商 → 客户实际阅读器」交叉验证；保留 PDF 作为通用兜底 |
| F4 | **PDF/OFD 双轨不一致** | 同一公文输出 PDF 与 OFD 两种版式，若分别转换可能出现分页、字号差异 | 同一引擎同批次输出；落库时记录 `src_version_id` 溯源；验收项 10 专项比对 |
| F5 | **复用客户既有红头模板成本（可选）** | 客户可能希望复用其现有 .docx 红头模板（带书签）；这属可选配置资产导入，与 E9 数据迁移无关 | D4 决策：优先支持 Word 书签方案以直接复用既有模板；占位符作为自研路线兜底；提供模板导入工具自动识别书签。不强制复用、不纳入数据迁移范畴 |
| F6 | **移动端 OFD 渲染能力弱** | 各厂商 H5 SDK 兼容性、性能、授权差异大；低端机渲染大版式文件易卡 | 移动端默认转图片分页流；OFD 原生渲染仅 PC；明确降级路径 |
| F7 | **附件版式处理** | 附件中的表格、图片、扫描件在自动排版下的分页与缩放易错 | 附件单独转版式并按 `ATTACHMENT` 要素编排；P5 专项测试 |
| F8 | **自动分页规则** | 孤行、寡行、标题与正文同页等国标排版细节，纯规则引擎难以完全覆盖 | L1 规则库内置分页约束；L3 校验报告提示；允许人工微调后重转 |
| F9 | **L1（Word/PDF）归档效力偏弱** | 一般企业以 Word/PDF 归档，若无签章/时间戳，防篡改与长期验证能力弱，存在「被改了没人发现」的风险 | 归档时计算文件哈希入库存证（扩展 `wf_odoc_meta` 或专表）；可选轻量 RFC 3161 时间戳（不依赖 CA）；归档格式建议 PDF/A；按 D10 决策基线 |
| F10 | **存量 Word/PDF 升级 OFD 的转换风险** | 历史 docx 批量转 OFD 时字体缺失、版面偏移、批量性能问题集中爆发 | 先试点抽样比对（页数/要素完整性），分批异步转换；转换前补装国标字体（见 F1）；确实无法达标的存量件保留 PDF 归档、不强行转 OFD |

## 5.3 签章有效性

| # | 风险 | 说明 | 应对 |
|---|---|---|---|
| G1 | **缺时间戳导致长期失效** | 电子签章若只依赖 CA 证书，证书过期后将无法证明「签章时证书有效」。这是归档后 10 年验章失败的最常见原因 | 签章时**必须同步盖 RFC 3161 时间戳**；`wf_odoc_seal.tsa_token` 存储令牌；P5 验收含「模拟证书过期后验章」 |
| G2 | **验章能力内建不足** | 只依赖 CA 厂商侧验章，厂商服务不可用时无法验证；且无法入审计 | `IOdocSealService.verify` 由主系统实现（证书链 + 哈希 + 时间戳三重校验），不 solely 依赖厂商 |
| G3 | **签章后文档可被篡改** | 版式文件若不校验完整性，替换文件即可伪造 | 签章时对文件哈希签名；验章时重算哈希；`wf_odoc_seal.verify_result` 记录 |
| G4 | **签章位置漂移** | 坐标盖章在模板/分页变化后会偏移，压错位置（如压住正文） | 位置做成模板级配置 `seal_config`（锚定到 `DATE`/`ORG_SIGNATURE` 要素而非绝对坐标）；优先用「要素锚定」而非硬编码坐标 |
| G5 | **联合行文多章** | 联合行文需多个单位盖章，且需处理多章位置与顺序 | `seal_config` 支持多签章项；与 S3 联合行文一并设计 |
| G6 | **签章与修改的冲突** | 签章后若允许再编辑 docx 并重新转版式，签章即失效但用户可能不知 | 定稿（`is_final=1`）后**禁止**任何 docx 修改；再修改必须撤销签章并留痕，交互明确提示 |
| G7 | **厂商依赖与降级** | 契约锁等 SaaS 不可用、或客户内网无法出网时签章阻塞流程 | 支持私有化部署的 CA；`available()=false` 时降级为 PDF 预览 + 线下盖章回填，**不阻断流程** |
| G8 | **法律效力依据不足** | 《电子签名法》第 13/14 条对「可靠电子签名」有明确条件（专有性、控制性、改动可发现性） | 签章设计逐条对齐；验收含「改动可发现性」测试；必要时法务出具意见 |
| G9 | **测试环境污染真实 CA** | 测试流程若走真实签章，会产生无效/冗余签章记录 | `is_test=1` 时走「测试模式」跳过真实签章，或使用厂商沙箱环境；签章记录同样带 `is_test`，随 `/test/cleanup` 清理 |
| G10 | **国密算法要求** | 政务信创常要求 SM2/SM3/SM4 而非 RSA/SHA | D8 决策；`wf_odoc_seal.algorithm` 字段已预留；需确认 CA 厂商支持国密 |

## 5.4 AI 排版准确性

| # | 风险 | 说明 | 应对 |
|---|---|---|---|
| A1 | **LLM 幻觉改写正文（致命）** | 公文内容一个标点都不能改。LLM 若「顺手优化」措辞、改数字、补句子，后果严重 | **铁律：AI 只做「识别与建议」，禁止直接改写正文内容**。`analyze` 只输出结构与要素定位，正文文本原样保留；任何内容级修改必须人工确认并留痕 |
| A2 | **结构识别错误** | 标题层级误判（如把正文第一段当标题）、序号混乱、表格内标题、法规条文引用等边界情况 | 先规则后 AI；识别结果必须可视化并允许人工修正；修正结果可反哺规则库 |
| A3 | **要素完整性校验误报 / 漏报** | 误报导致用户反复改；漏报导致不合规公文流出 | L3 校验输出「问题 + 依据条款」，允许人工豁免并记录豁免理由；误报率作为持续优化指标 |
| A4 | **AI 服务不可用** | 内网无 LLM、或服务故障时排版功能瘫痪 | 分层降级：L3 → L2 → L1。**L1 纯规则引擎可独立满足国标合规**，AI 故障不影响主流程 |
| A5 | **敏感内容外发** | 政务正文发往外部 LLM 服务存在严重泄密风险 | 涉密场景禁用外部 LLM；LLM 必须私有化部署；提供「禁用 AI」开关，仅用 L1 |
| A6 | **可审计性不足** | AI 的每次排版/识别无留痕，出问题无法追溯 | 记录 `typeset` 输入输出、使用的规则库版本与模型版本、人工修正记录；保留排版前后 docx 以便 diff |

## 5.5 编辑器与套红流程衔接

| # | 风险 | 说明 | 应对 |
|---|---|---|---|
| E1 | **编辑器回调丢失** | OnlyOffice callback 失败/超时 → 用户以为保存了，实际没有 → 版本丢失、后续套红基于旧内容 | 回调必须幂等 + 可靠投递（重试 + 对账任务）；保存后前端强提示「已保存/保存失败」；提供版本列表供用户核对 |
| E2 | **并发编辑冲突** | 两人同时打开同一正文编辑，后保存者覆盖先保存者 | 正文档级乐观锁（版本号 + `draftRevision` 机制复用）；进入编辑器时校验版本，过期则拒绝并提示刷新 |
| E3 | **书签位置不可见** | 用户在编辑器里看不到哪些位置会被套红替换，套红后才发现格式不符预期 | 编辑器中以只读标注显示书签/占位符位置（OnlyOffice 可通过 DocumentBuilder 或前端覆盖层实现）；套红前提供「预览替换值」 |
| E4 | **清稿行为不透明** | `acceptRevisions` 会清除修订痕迹，用户可能不知情，事后无法追溯 | 清稿前弹窗确认 + 明确告知「将生成『套红前取消痕迹版本』，原版本仍可查看」；版本列表清晰标注 |
| E5 | **docx 与版式双源不一致** | 定稿后用户改了 docx，但版式文件未更新，导致看到的与实际签发的不一致 | 定稿后 docx 冻结（`is_final=1`）；任何修改必须重新走「定稿 → 转版式 → 签章」全链；UI 显著标注当前生效的是哪个版本 |
| E6 | **节点切换时正文锁定状态混乱** | 节点流转后正文应锁定/解锁，若状态不同步会出现「只读节点还能编辑」 | 正文可编辑性完全由 `nodePermission` 驱动，与套红节点/签章节点解耦；节点变更时前端重新拉 `renderForm` |
| E7 | **移动端编辑能力缺失的引导** | 手机端降级为只读，用户可能困惑 | 明确提示「正文请在 PC 端编辑」+ 提供 PDF 预览；D7 决策是否投入 C 方案 |
| E8 | **大文件性能** | 带大量图片的几十 MB docx，编辑器加载与转换都很慢 | 文件大小上限 + 图片压缩；转换异步化 + 进度提示；超时兜底 |

## 5.7 数据安全与合规性

| # | 风险 | 说明 | 应对 |
|---|---|---|---|
| C1 | **密级标识与访问控制** | 秘密/机密/绝密公文必须最小权限，密级变更（如升密/降密/解密）需流程化管理 | `secret_level` 纳入字段权限；密级变更走独立流程；高密级公文限制下载/打印/编辑 |

| C7 | **日志留存与完整性** | 安全审计要求日志留存 6 个月以上且防篡改 | 接入统一日志平台；关键操作独立审计表；WORM 存储或哈希链 |

# 第六部分 结论

1. **方案定位**：本方案以 **GB/T 9704 标准为底座、OFD/PDF 版式文件为载体，结合 AI 智能排版与 CA 电子签章**，构成收发文「真·电子公文」一体化解决方案。Word 宏与图片叠加两条旧路线明确淘汰；docx + 书签套红是 **L1 初级支持格式（Word/PDF）** 的核心能力，对一般企业为正式交付形态。
2. **参考系统关系**：两个 Ecology 目录是同一产品的部署态/源码态互补视图，非两套实现；差异体现在「后端业务流转 / 前端表单渲染 / 两端数据契约」三个切面。
3. **收文/发文**共用同一套页面与渲染引擎，差异由 `officaltype` 与环节配置驱动；发文独有套红、文号、印发，收文独有登记、来文单位、交换。
4. **`flowtable` 澄清**：并非正文/明细表，而是后台设置页 CSS 类与「工作流程表」数据源，迁移时需重新定义术语。
5. **套红本质**：红头模板 + 书签替换 + 正文插入 + 生成新版本；SpringBlade 只能走服务端合成路径；E9 的三个「策略 + 解耦」设计（OFDConvertor 四厂商、契约锁反射签章、SmartOfficial 排版雏形）是最值得复刻的部分；公文元数据注入 OFD 是最易遗漏的关键能力。
6. **最大复用点**：表单渲染与字段权限（`ExcelPreview` + `FieldControl` + `nodePermission` 三维度已优于 E9 的 `perm` 单列）。
7. **最大工作量**：正文文档体系、服务端合成引擎、GB/T 9704 规则库、版式文件与签章体系。
8. **一票否决项**：正文编辑器选型（D1）直接决定留痕、清稿、OFD 等能力上限，必须在 P1 前定稿。
9. **风险重点**：国标字体缺失（信创环境最大坑）、时间戳缺失（长期验章失效）、AI 不得改写正文（铁律）、涉密环境零外网依赖、docx 与版式双源一致性——五项需在立项阶段即明确应对。
10. **格式分级支持是交付底线**：默认 **L1（Word + PDF）开箱即用**，覆盖一般企业收发文全流程（编辑、套红、版本、文号、拦截、PDF 归档）；**L2（GB/T 9704 + OFD/PDF + 签章）通过配置开关叠加升级**，存量 Word/PDF 公文经同一接口平滑转换——不存在「不采购 OFD 就用不了」或「升级即迁移」的问题。
11. **混合模式输出（已决策）**：docx 直出与 GB/T 9704 + OFD/PDF 标准版式并存，客户按需灵活选用；接入形态为「能力插件化（独立 module + SPI）+ 配置开关编排（全局/流程/文种三层）」，同一套代码与数据模型承载两种模式（详见 §2.2.2）。

## 附录 A 术语表

| 术语 | 定义 |
|---|---|
| **L1 / L2 / L3** | 格式分级：L1=Word+PDF 初级支持（默认）；L2=GB/T 9704+OFD/PDF 标准版式（政务/信创）；L3=L2+AI 增强（§2.2.1） |
| **docx 直出 / 标准版式** | 混合模式的两种输出形态：前者止于 docx+PDF；后者走定稿→版式→签章→OFD-A（§2.2.2） |
| **套红** | 红头模板 + 书签替换 + 正文插入 + 生成正文新版本的服务端合成动作 |
| **书签（bookmark）** | Word 模板中的命名占位（如 `fld_Mark` 文号、`Content` 正文插入点），套红时被替换/插入 |
| **文种** | GB/T 9704 规定的公文种类（决议/决定/…/纪要共 15 种），决定版式模板 |
| **版式 profile** | `Gbt9704Profile`：GB/T 9704 规则的参数化载体（纸型/页边距/行数字数/字体字号/红线/页码），按机关/文种可定制 |
| **定稿** | docx 冻结动作（`is_final=1`），此后任何修改必须重走「定稿→转版式→签章」 |
| **清稿 / 留痕** | 接受修订清除痕迹（清稿）与保留修改痕迹（留痕）；清稿结果必须存为独立版本 |
| **文号** | 发文字号，按规则（机关代字+年份+流水）生成并占用回写 |
| **呈批表** | 打印/呈批模板产物，书签值可来自流转意见（「意见进公文」） |
| **OFD / OFD-A** | 国产版式文件格式（GB/T 33190-2016）；OFD-A 为其档案级长期保存 profile |
| **GB/T 9704** | 《党政机关公文格式》国家标准，本方案 L2 的唯一格式基准 |
| **节点必做动作** | NodeMandatoryAction：套红/签章/清稿统一框架（配置节点+前置校验+提交拦截+状态回写） |
| **`is_test`** | 测试流程标记；测试产生的正文/合成产物/签章记录随 `/test/cleanup` 清理，不外溢 |
