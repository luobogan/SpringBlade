# 流程功能扩展对现有能力的影响评估与隔离策略

> **总索引**：[工作流分析文档总索引.md](工作流分析文档总索引.md)（分析文档的统一入口）
>
> **核心担忧**：要扩展到完整 flowtable（E9 风格全流程设计器/引擎）功能，会不会影响之前已经做好的流程功能？
>
> **直接结论**：**取决于扩展动的是"加法"还是"共享收口"。** 纯新增能力（新节点类型、新 listener、新动作、新监控）默认关闭时对现有功能零影响；真正有风险的是少数几处**所有流程共用的收口逻辑**（归档判定、事件失败策略、动作闸门、会签推进），这些一改就全量生效。前者可放心做，后者必须双轨验证。
>
> **本文边界**：只讲影响面、风险分级与隔离原则，不写实现步骤。证据用于证明"哪些是共享收口"。
>

## 0. 一句话回答

**现有能力（UserTask 主链、会签、退回、指定流转、自由流程、抄送、权限、超时、odoc、ACT 读源）可以全部保住**，前提是遵守一条分界线：

> **新增能力走"开关 + 默认关 + 新流程生效"；绝不直接改写 4 处共享收口逻辑（归档判定 / 事件失败策略 / 动作闸门 / 会签推进）——要改就必须双轨并行 + 回归基线。**

## 2. 扩展项的三维影响判定

判断任何一项 flowtable 扩展会不会影响现有功能，问三个问题：

1. **它是"新增"还是"改写"？**
2. **它是否落在共享收口上？**
3. **它对在途实例生效吗？**

按答案分三类：

### 2.1 🟢 安全类（加法，默认可对现有零影响）

| 扩展项 | 为什么安全 |
|---|---|
| 新增节点类型解析（ServiceTask/Script/DMN/CallActivity 的识别与落表） | `nodeTypeOf` / `syntheticNodeType` 是按元素类型分支的**新增 case**，不改 UserTask 分支 |
| 新增全局 listener（如 ACTIVITY_COMPLETED） | 现有 4 个 listener 各自独立注册（`FlowableConfig.java:146-178`），新增第 5 个不覆盖它们 |
| 新增动作前缀 / 自定义 Action 类 | `WfActionExecutor.java:38-61` 本就是前缀分派，加分支是纯加法 |
| 新增监控指标 / 历史查询 | 只读，不改写入路径 |
| 引入 Flowable Form / DMN 引擎作为**独立通道** | 自建 formmode 链路不动，两套并存 |
| 新增流程定义字段 / 设计器能力标记 | 不改运行时行为 |

**前提**：新增能力必须带开关、默认关（`blade.workflow.*` 现有 20+ 开关全是这个模式），且只对新发起流程生效。

### 2.2 🔴 高危类（共享收口，一改全量生效）

这四处是**所有流程都会经过**的收口，改动影响面是全量：

| 收口 | 为什么高危 | 现有证据 |
|---|---|---|
| **归档判定** | `advanceInternal` 是每条流程的终点收口，判定条件一改，所有流程的归档时机都变 | `WfInstanceServiceImpl.java:3113-3242` |
| **事件失败策略** | `isFailOnException` 决定 listener 失败是回滚还是吞掉，改一个值影响全部事件反写 | `WfEngineEventListener.java:94-100`、`WfMiEmptyGuardListener.java:130-134` |
| **动作统一闸门** | 所有节点前后置动作都过 `WfActionExecutor.execute`，加闸门可能拦住现有正常动作 | `WfActionExecutor.java:77-79`、`NodeActionExecutor.java:92-135` |
| **会签推进逻辑** | `isEngineMultiInstance` 分支决定走自研计数还是引擎 MI，改了现有会签行为全变 | `WfTaskServiceImpl.java:344-372` |

**这四处没有开关保护**——代码里找不到 `if (switch) 走新逻辑 else 走旧逻辑` 的双轨分支。所以"新增能力默认关"的保护伞对它们无效。

### 2.3 🟡 中危类（语义覆盖 / 需迁移）

| 扩展项 | 风险 |
|---|---|
| 原生 `callActivity` 替代业务 `triggerSubflow` | 两套子流程语义不同（变量传递 vs 动作触发），切换会改变现有子流程行为 |
| Flowable Form 替代自建 formmode | 表单渲染链全变，现有所有流程表单受影响 |
| 自研会签收敛到引擎 MI 一套 | 现有 `engine-multi-instance.enabled=true` 的流程行为需回归 |
| 测试态降级策略调整 | `neutralizeForTest` 影响所有测试流程的验证结果 |
| 自由流程池加节点类型约束 | 现有 `Free_1..Free_N` 定义若含非法节点会被拒 |

## 3. 现有保护伞（已经存在的有利条件）

| 保护机制 | 保护了什么 | 证据 |
|---|---|---|
| **20+ 特性开关，默认 false / yml 开** | 新能力可默认关、灰度放量 | 各 `@Value("${blade.workflow...}")`；详见遗漏清单 §11 |
| **在途实例钉 procDefId** | 改定义/改部署不影响已发起实例；新语义只对新流程生效 | `WfInstanceServiceImpl.java:506-539`；`application.yml:152-153` |
| **测试/正式双部署 + `__test` key** | 新能力可先在测试态验证，不污染正式 | `ProcessServiceImpl.java:296-309`；`WfDefinitionServiceImpl.java:2221-2296` |
| **direct 模式 + ACT 读源** | 状态投影层可回退，不必改业务表结构 | `WfStateProjector.java:61-69,157-168,217-228` |
| **事件反写可降级为 warn** | 反写失败不阻断主流程 | `WfEngineEventListener.java:94-100` |
| **发布门禁** | 不完整的定义发布前被拦，减少运行期事故 | `WfDefinitionServiceImpl.java:2454-2532` |

## 4. 保护伞的三个盲区（必须诚实面对）

1. **开关保护不了"共享收口"**：§2.2 那四处没有双轨分支，一改就全量生效——这是最大的盲区。
2. **钉版本保护不了"新发起但用旧设计"的流程**：新流程一发起就走新逻辑，若新逻辑有 bug，影响的是全部新单。
3. **`is_test` 守卫在引擎触发路径上缺失**：`WfActionExecutor` 自身零 `is_test` 过滤（`WfActionExecutor.java:38-43,77-79,274`），现有隔离靠调用方自觉；一旦 ServiceTask 由引擎直接触发动作，测试流程可能真实发外部请求——这是"扩展引入的新风险"，不是旧功能的问题，但会连带破坏测试态隔离这条保护伞。

## 5. 隔离策略（原则层，不写实现）

### 5.1 三条硬规则

1. **加法优先，能不改写就不改写**：新元素、新 listener、新动作一律走新增分支 + 开关默认关；只有在现有分支里"加一个 case"才动共享代码。
2. **共享收口必须双轨**：§2.2 四处若要改，必须同时保留旧路径，用开关选择；且新路径先在测试态跑通、再灰度放量。**没有双轨就不动。**
3. **在途实例不动**：靠钉版本天然保证；任何"迁移在途实例"的能力都必须显式授权（对应遗漏清单 P2-14）。

### 5.2 回归基线（扩展前后必须验证的能力）

把下列能力作为不可回退的验收基线，任何扩展后逐一验证：

- 发起 → 停在"创建/Free_1"、不秒归档
- UserTask 审批、退回、指定流转、多目标扇出
- 会签（自研 + 引擎 MI 两套）
- 撤回/暂停/恢复/撤销/强制归档
- 自由流程：发起 → 编排 → 逐步推进 → 末步归档；退回重提
- 抄送/字段权限/明细权限/超时提醒
- 测试态 vs 正式态隔离（`procKey__test`、动作不外溢）
- ACT 读源：待办/已办/实例列表/进度图正常
- odoc 正文/上传/套红/转 PDF-OFD

> 现成的自动化回归脚本：`log/e2e_freeflow_full.py`（自由流程全场景 26/26 PASS，自带清理可重复跑）。

### 5.3 放量顺序

```
新增能力（开关关）
   → 测试态验证（procKey__test）
   → 灰度开窗（按流程定义/租户）
   → 双轨对账（投影 vs 引擎事实源）
   → 全量开
   → 旧路径保留一个版本周期后再退役
```

## 6. 结论

- **会不会影响**：新增类扩展**不会**影响现有功能（前提是开关默认关）；共享收口类扩展**会**影响全量流程，但通过"双轨 + 灰度 + 回归基线"可以把影响控制到可发现、可回退。
- **最该防的三件事**：① 没双轨就改归档判定；② 没统一闸门就放行引擎触发的外部动作；③ 扩展后不跑回归基线。
- **一句话**：**不是"扩展会不会破坏旧功能"，而是"你有没有守住那四处收口"**——守住就是加法，守不住就是重构。现有开关体系、钉版本、测试态隔离已经给了足够的保护伞，缺的只是"不在无开关的共享收口上直接改"这条纪律。
