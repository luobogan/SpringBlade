## 0. 结论速览

| 问题 | 结论 |
|---|---|
| 核心矛盾 | 测试与正式**共用同一个 Flowable 引擎、同一套库表**；应用层已同源，**风险集中在「部署/实例」这一层** |
| 推荐策略 | **「版本隔离（定义级）+ 测试域隔离（实例级）+ 灰度切流（流量级）」三层叠加**，而不是单一手段 |
| 不推荐单靠 | 蓝绿部署（成本过高）、纯流量切分（无隔离即无回滚）、纯影子测试（覆盖不了交互态） |
| 引擎侧关键改造 | 启动方式由 `startProcessInstanceByKey` 升级为**可按 `processDefinitionId` 启动** —— 这是「绝对不会跑错版本」的技术根 |
| 入口统一 | 测试「节点审批情况（**预览 + 已建测试实例**）」与正式发起收敛到同一地址 `/workflow/create/start?defId=<流程定义ID>&mode=<preview|test|instance|prod>`（`instance` = 以同一组件/渲染包打开并办理某个**已存在**的测试实例） |
| **可见性结论** | ❌ **测试实例不仅可见、而且可办**：测试待办 `assignee` 就是节点操作者本人（`WfInstanceServiceImpl.java:1166`），而生产侧全部查询**零 `is_test` 过滤**（完整分析见 **§6**） |
| **最隐蔽缺口** | ⚠️ **标记断层（V10 / C2）**：`forward`/`circulate`/`addSign` 新建的任务**未继承 `is_test`** → 即使将来所有查询都加过滤**也漏得掉**，会实打实进真人生产待办 |
| **代跑留痕归属** | 代跑的"谁办的"**只落两处**：`wf_task.assignee` 与 `wf_approval_log.operator`，写的都是**节点接收人**（会签逐人各一条）；`create_user`/`update_user` 与 Flowable 的 `ASSIGNEE_`/`COMPLETED_BY_` **全为 NULL**（管理员零痕迹）。⇒ 代跑会在真人名下留"一条已办"，**已办列表是最易漏的外泄口**（C14） |
| **业务表污染**（易被忽略） | ❌ 测试态**照常在 `formtable_main_N` 建真实业务行**，且 `cleanupTestData()` **从不删** → 每次测试留下**永久无主脏行**（有行、无 `request_id`）。现状只做到"不回填 `request_id`" | V13 / C17 |
| **自定义操作**（最危险） | ❌ `POST /custom-operation/execute` **三无**：无 `is_test` 守卫、无实例可见性校验、无副作用豁免；`actionType=1` 时**真的对外发 HTTP**，在测试单上点按钮会打到生产第三方系统 | V12 / C18 |
| 引擎路由 | ✅ 测试实例绑定 `procKey + "__test"` 的 `processDefinitionId`（`WfDefinitionServiceImpl.java:330`），与正式定义物理隔离，**不会串到正式路由/节点/在途实例** |
| P0 缺口（必须先补） | ① 生产查询（待办/已办/我的请求/角标/详情）**未过滤 `is_test`**；② 转办/抄送/加签任务**未继承标记**；③ 超时扫描命中测试任务（`WfTimeoutJob.java:46-51`）；④ 测试面板动作直打生产接口 |

## 2. 策略对比与推荐

### 2.1 五种策略逐项评估（结合本项目）

| 策略 | 定义 | 本项目可行性 | 成本 | 能防住的事故 | 结论 |
|---|---|---|---|---|---|
| **① 流程版本隔离**（定义级） | 测试版本与生产版本在引擎里是**不同的 `processDefinitionId`**，实例按 id 绑定，互不干扰 | ✅ Flowable 原生支持（`ACT_RE_PROCDEF.ID_` + 实例绑定）；现有 `__test` key 已是雏形 | 低（改造启动方式即可） | A2 + 灰度回滚 | ✅ **必选（地基）** |

| **④ 蓝绿部署** | 两套完整环境（含引擎/库），整体切换 | ❌ 本项目**单库单引擎**（`FlowableConfig.java:60-62`），拆双引擎等于重构基础设施；且《一致性规范》§1.2 明确要求"测试与正式共用同一套表结构" | 高 | 环境级故障 | ❌ **不推荐**（与"同源"要求冲突） |
| **⑤ 影子测试**（Shadow） | 真实发起时**并行**用新定义跑一条影子实例（不产待办、不写业务表），比对路径与结果差异 | ✅ 可直接复用 `is_test=1` + `neutralizeForTest` + 覆盖率采集（`WfTestServiceImpl.java:1370-1414`） | 中 | A3（新旧行为漂移） | ✅ **推荐（灰度前的最后一道验证）** |

> 补充说明：**流量切分**不是独立策略，而是 ③ 灰度发布的**实现手段**（白名单 / 部门 / 角色 / 比例哈希）。

### 2.2 推荐组合（四阶段闸门）

```
设计 ──► ① L1 发布门禁 ──► ② 测试域验证（功能） ──► ⑤ 影子比对（行为） ──► ③ 灰度切流 ──► 全量
         硬拦不支持元素        真实引擎跑通+交互态      新旧路径零差异断言     白名单→1%→10%→全量
              ▲                      ▲                        ▲                    ▲
              └── 任一闸门不过 = 不放行；回滚 = 切回上一个 processDefinitionId
```

**推荐理由**：①+② 解决"不污染生产"（安全底线），⑤ 解决"行为不漂移"（正确性），③ 解决"上线可控"（可回滚）。三者叠加后，④ 蓝绿带来的额外收益很小、成本却最高，故不采纳。

## 3. Flowable 层：用 `processDefinitionId` 做定义隔离

### 3.1 为什么必须升级启动方式

现状（`ProcessServiceImpl.java:41-47`）：

```java
ProcessInstance instance = runtimeService.startProcessInstanceByKey(procKey, bizKey, vars);
```

`startProcessInstanceByKey` 由引擎解析"**该 key 的最新部署版本**"——即使测试用 `__test` 后缀避开了正式 key，**灰度/多版本场景下"最新"依然是不确定的**：任何一次重新部署都会改变"最新"，历史在途实例虽靠 `ACT_RE_PROCDEF.ID_` 原生隔离，但**新发起的实例跑哪个版本完全取决于部署时序**，这正是 `engineDeploymentMatched` 自检位（《一致性规范》§2-L3）存在的原因。

改为**按 `processDefinitionId` 启动**后：发起时显式指定"这一版的 `ACT_RE_PROCDEF.ID_`"，**与部署时序彻底解耦**——这是"绝对不会跑错版本"的技术根。

### 3.2 改造设计

| # | 改造点 | 文件:行号 | 内容 |
|---|---|---|---|
| 1 | 新增按 id 启动 | `service/IProcessService.java`（`startInstance` 后，参考 `:28`） | `String startInstanceById(String processDefinitionId, String bizKey, Map<String,Object> variables);` |
| 2 | 实现 | `service/impl/ProcessServiceImpl.java:41-47` | `runtimeService.startProcessInstanceById(processDefinitionId, bizKey, vars)` |
| 3 | 部署回写 procDefId | `WfDefinitionServiceImpl.java:299`（`deploy`）、`:330`（`deployForTest`） | `deployProcess/deployProcessForTest` 额外返回 `ACT_RE_PROCDEF.ID_` → 落 `wf_process_definition.proc_def_id` / 测试态落 `wf_instance.test_proc_def_id` |
| 4 | DTO 承载 | `StartProcessDTO`（`engineKey` 字段旁，现有用法见 `WfInstanceServiceImpl.java:278-281`） | 新增 `procDefId`；优先级：**`procDefId` > `engineKey` > `def.procKey`** |
| 5 | 发起侧选择 | `WfInstanceServiceImpl.java:301` | `procDefId` 非空 → `startInstanceById(...)；否则保持 `startInstance(engineKey, ...)`（向后兼容） |
| 6 | 灰度路由 | `WfInstanceServiceImpl.java:1296-1315`（`resolveDefinition`）之后新增 `resolveProcDefId(def, user)` | 命中灰度 → 返回灰度版本的 `proc_def_id`；否则返回激活版本的 |
| 7 | 实例留痕 | `WfInstanceServiceImpl.java:319-337` | `wf_instance.proc_def_id` 记录本次实际使用的定义 id（审计/回滚依据） |
| 8 | 迁移脚本 | `doc/sql/migration/V2026.09.21_015__wf_proc_def_id.sql`（幂等） | `wf_process_definition` 加 `proc_def_id VARCHAR(64)`；`wf_instance` 加 `proc_def_id VARCHAR(64)` + `is_gray TINYINT` |

### 3.3 key 启动 vs id 启动对比

| | `startProcessInstanceByKey` | `startProcessInstanceById` |
|---|---|---|
| 版本确定性 | 取最新部署（随时序变化） | **精确绑定某一版** |
| 灰度/回滚 | 需靠"重新部署"实现，风险高 | 改路由即可，秒级回滚 |
| 测试隔离 | 依赖 key 后缀（绕路） | 天然隔离（不同 id） |
| 兼容性 | 现有全部链路 | ✅ 保留为兜底（`procDefId` 为空时） |

### 3.4 测试域如何用 id 隔离（改造后的测试链路）

```
deployForTest(defId)
   └─ key = procKey + "__test"           （WfDefinitionServiceImpl.java:330，保留）
   └─ 返回 procDefId（__test 版本的 ACT_RE_PROCDEF.ID_）
      └─ 写入 wf_instance.test_proc_def_id
          └─ start(startDto{ procDefId = 测试版 id, testFlag = true })   （WfTestServiceImpl.java:843-848）
             └─ startInstanceById（测试版 id）     ← 与正式版本物理隔离
```

**收益**：即使 `__test` key 因历史原因残留部署，只要发起时按 id 启动，也**不可能**跑到正式版本；反过来正式发起按激活版本的 id 启动，也**不可能**跑到测试版本。双重保险。

### 4.3 灰度实现（最小可用设计）

**规则载体**（新增表，或先用 Nacos；建议落库以便审计）：

```sql
CREATE TABLE IF NOT EXISTS `wf_definition_gray` (
  `id`             BIGINT NOT NULL,
  `tenant_id`      VARCHAR(12) NOT NULL DEFAULT '000000',
  `def_id`         BIGINT NOT NULL COMMENT '流程定义ID（版本组锚点）',

  `ratio`          INT NULL COMMENT 'ratio 策略下的百分比（1-100）',
  `scope_value`    VARCHAR(512) NULL COMMENT '白名单用户/部门/角色ID，逗号分隔',
  `status`         TINYINT NOT NULL DEFAULT 1 COMMENT '1启用 0停用',
  `start_time`     DATETIME NULL,
  PRIMARY KEY (`id`),
  KEY `idx_gray_def` (`def_id`, `status`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='流程定义灰度规则';
```

**路由逻辑**（在 `WfInstanceServiceImpl.java:1296-1315` 后新增）：

```java
// 伪代码：灰度路由（命中灰度 → 用灰度 procDefId；否则用激活版本 procDefId）
WfDefinitionGray g = grayService.active(def.getId());

    inst.setIsGray(1);
    return g.getGrayProcDefId();     // S6~S7 期间

```

- `ratio` 命中：`Math.abs(userId.hashCode()) % 100 < ratio`（同一用户稳定命中同一版本，避免来回跳）
- **回滚**：`status=0` → 全部走 `base_proc_def_id`；**在途实例不受影响**（Flowable 原生按 `ACT_RE_PROCDEF.ID_` 隔离，见《流程版本控制设计与改造说明》§6）

### 6.4 隔离设计要求（三域 × 三类约束）

**（0）先明确：隔离是按「入口」区分，不是按「用户身份」**

这是本章最关键的一条口径——**同一批用户、同一条测试实例，在两个入口下的结论必须相反**：

| 入口 | 可见性 | 可办性 |
|---|---|---|
| **生产入口**：`GET /task/todo`、`/task/done`、`/task/count`、`/instance/mine`、`/instance/{id}`、`/formmode/approval/*`、发起页 `?mode=prod` | 测试实例/测试待办**一律不可见**（含顶栏红点） | **不可办**：办理页/渲染接口对 `is_test=1` 直接拒绝（C8） |
| **测试入口**：`/test/**`、发起页 `?mode=test` | 按**测试域内的正常权限**可见：**节点操作者**（`wf_task.assignee`）、发起人、流程管理员 | **可办**：这就是「用相应用户去审批」的通道（C12） |

⚠️ **不要**把 `canVisible` 改成「`is_test=1` 仅允许管理员 + 测试发起人」——那等于把节点操作者挡在测试域之外，**测试就无法用相应用户审批**（本文 v1.0 曾如此表述，v1.1 已更正）。正确做法是三条并存：

1. `canVisible` **不按 `is_test` 收口**（保持"发起人 / 参与人 / 管理员"原口径）；
2. 隔离由两件事承担：**生产入口的查询过滤**（C1）+ **`/test/**` 对目标实例断言 `is_test=1`**（C11，防借测试入口读/改正式实例）；
3. **生产办理页**对 `is_test=1` 拒绝打开（C8）——测试办理不走生产页，走测试入口。

**测试域"用相应用户审批"的两种模式**：

| 模式 | 机制 | 现状 | 适用 |
|---|---|---|---|
| **代跑模式** | 流程管理员在测试面板点「提交」，后端**以节点接收人身份**提交：`autoApprove(taskId, opinion, vars, task.getAssignee())`（`WfTestServiceImpl.java:1102-1103`）；会签逐人各提交一次 | ✅ 已实现 | 快速跑通路径 / 覆盖率；**不需要真人到场**，也不打扰真人 |
| **真人模式** | 把测试待办下发给**对应的真实用户**，该用户从测试入口（`?mode=test`）看到并**自己办理** | ✅ **已落地（见 C12 / F8）**：`GET /test/my-todo` 按登录人过滤 + `POST /test/approve`（断言本人是 assignee）；前端提交前自动判定并切接口 | 验证「节点操作者是否解析正确」「真人操作体验 / 必填 / 表单版式 / 字段权限」 |

| `wf_approval_log` | 开始节点提交（`log_type=2`） | **测试发起人本人**（开始节点待办 `assignee` = `starter`） | ✅ operator = `wf_instance.starter` |

| Flowable `ACT_HI_TASKINST`、`ACT_HI_ACTINST` | `ASSIGNEE_` / `OWNER_` / `CLAIMED_BY_` / `COMPLETED_BY_` | **全为 NULL** —— 引擎侧不记操作人（人员只在业务表 `wf_task`） | ⚠️ 引擎历史不能作为"操作人"依据 |
| 前端「流程信息」时间线 | 渲染 `log.operator` → 用户名 | 显示为**各节点接收人已审批**（看不出是管理员代跑） | 由 `logs()` 返回 |

**一条硬结论**：代跑的"谁办的"**全项目只有两处落地** —— `wf_task.assignee` 与 `wf_approval_log.operator`，两处写的都是**节点接收人**；引擎与审计列均无痕迹。这带来两条必须守住的约束：

- **C14（代跑留痕不得外泄）**：代跑在**真人名下**留下"一条已办 + 一条流转意见"。必须靠 **C1（生产查询过滤）+ C2（标记全链路继承）+ C9（强制清理）** 三道同时成立，才能保证它不出现在该真人的生产「待办 / **已办** / 角标 / 我的请求」里。⚠️ **「已办」最易漏**：平时无人细看，一旦漏了就长期存在——`done()` 的状态集合含已办(2)/办结(3)/自动提交(4)/协办(7)/传阅(8)/已读(9)（`WfTaskServiceImpl.java:109-113`），**全部**都要排除测试任务。
- **C15（代跑需可追溯 + 留痕需自证）**：现状**完全无痕**——审计列与引擎列都是 NULL，合规/排障时无法回答"谁代跑的"。建议：① 管理面逐步记录执行人（`wf_test_log` 里记「谁在哪一步点了提交」）；② 代跑产生的**签字意见统一加「[测试]」前缀**——现状 `DEFAULT_TEST_OPINION = "流程测试提交"`（`WfTestServiceImpl.java:96`）仅在测试者**留空**时生效，一旦测试者手填（实测库里出现 `opinion='2'`、`'3'`、`'23'`），留痕就与真实审批无法区分。

**"看不到"的边界（真人模式）**：该用户**必须知道有测试任务**，但**不能**经生产待办或生产消息触达。做法：由测试组织者把 `?mode=test&instanceId=...` 链接直接给该用户；如确需站内提醒，必须带「【测试】」前缀且**默认关闭**（C13）。

**（1）通用原则**

1. **默认不可见**：生产查询**一律显式排除** `is_test=1`；测试态数据只经 `/test/**` 暴露（白名单式，而非黑名单式）。
2. **标记先行、过滤兜底**：`is_test` 必须随实例→任务→抄送/协办/转办**全链路继承**（现状已有，需覆盖到"转办/抄送新建的任务"）。
3. **VO 必须带标记**：`InstanceVO` / `WfTaskVO` 增加 `isTest`，前端才能在列表着色/分栏/禁用操作。
4. **驱动类任务（超时/定时）必须跳过测试**：扫描查询显式排除 `is_test=1`，而非"跑完再判断"。
5. **副作用与通知默认关闭**：测试态不触发任何对外动作（消息/短信/邮件/子流程/外部接口/转办建任务）。

### 7.5 所有审批节点统一引用示例（defId 动态填充）

**为什么不会"部分节点套用、部分遗漏"**：统一入口按 `defId + mode` 定位「流程 + 态」，而**流程内第几个审批节点**由 `nodeKey`（当前节点）+ `instanceId`（具体实例）决定，**不靠换地址**。因此——只要某个流程定义接了统一入口，它实例里的**每一个审批节点天然都走同一个地址**；所谓"遗漏某节点"只可能发生在「该流程定义根本没接统一入口」（仍在用旧的办理页），而不是入口本身按节点选择性生效。

> ⚠️ **这是「设计属性」，前提是入口真的被接上**。截至 2026-09-22 的代码实际只把统一入口套到了**测试页**；正式办理入口（待办 / 已办 / 我的请求）仍走旧的独立办理页，属于"部分节点套用"的真实缺口，详见下方「已知缺口」。

**`defId` 从哪里来（动态填充，不要硬编码）**：
- 测试页（`/formmode/test`）：取「当前正在测试的流程定义」的 `procDefId`，作为 `<StartFlow defId={...} embedded>` 入参内嵌；
- 正式发起：流程中心/发起入口拿到的 `procDefId`；
- 实例/办理态：由实例记录 `wf_instance.proc_def_id` 反查得到（与实例同源，不会错配）。

> 地址是**相对路径** `/workflow/create/start?...`；部署到具体环境时，**前面拼上该环境的 base URL**（如内网 `http://192.168.1.5:8000`）即可。下面以真实 `defId=2100918142244032513` 给出四种 `mode` 的可复制示例（节点差异靠 `nodeKey`，不在 URL 里换流程）：

### 7.6 测试态「保存」（同组件、同功能，仅落点不同）

> 目标（B 方案）：测试页右侧与独立发起页是**同一个 `<StartFlow>` 组件**，功能（提交 / 保存 / 返回 / ⋯）也一致；唯一保留的差异只有 §7.2 允许的「数据源 + 提交落点」。

- **生产态「保存」**：`POST /instance/save-draft` → 写业务行 + 建**正式**草稿实例（`status=5`）+ 发起人待办 + 快照。
- **测试态「保存」（新增 2026-09-22）**：**同一接口、同一组件**，入参 `FormSaveDTO.testFlag=true` → 后端**跳过 `formmodeClient.saveBusinessData`**、改用占位 `dataId`（`IdWorker`），草稿实例与合成任务均打 **`is_test=1`**，仍写 `wf_form_snapshot` 快照。因此**不写业务表（V13/C17）**、不进生产任何列表（待办/角标/我的请求均按 `is_test=0` 过滤）、随 `POST /test/cleanup` 一并清理。
- **防绕过**：`testFlag` 只在「**新建草稿**」时生效；一旦带了 `instanceId`，一律**以实例自身 `is_test` 为准**——防止用 `testFlag=true` 把既有生产草稿/实例伪装成测试态从而跳过业务行。
- **前端**：`Start.tsx#handleSaveClick` 按 `isTest` 下发 `testFlag`；测试态跳过草稿过期门禁（测试域无"草稿"概念，与 `handleSubmitClick` 同口径）；**内嵌态不回写宿主页 URL**（改写会污染测试页地址）；「保存」按钮由 `{!isPreview && canSave}` 控制（不再排除 `isTest`）。
- **落点**：`FormSaveDTO#testFlag`；`WfInstanceServiceImpl#saveDraft`（① 取既有实例 → ② 业务行/测试占位 → ③ 草稿实例 → ④ 合成任务 → ⑤ 快照）；前端 `Start.tsx`（`handleSaveClick`、按钮显隐）。

> 边界说明：测试态「返回」仍由宿主页（测试页）提供，不在内嵌组件内重复渲染——这是"**外壳由父页负责**"的既定分工，不属于操作集差异。另：测试态「保存」建出的测试草稿是**独立于"提交（`/test/start`）"的锚点**，提交仍会新建一条测试实例；草稿随测试清理一并删除。
