# 测试流程与正式流程一致性规范（开发规范）

> 版本：v1.0 ｜ 日期：2026-09-20
> 归属：《Flowable7真实引擎测试改造与验证说明》/《审批流程-数据库结构与迁移记录》
> 目的：保证「设计期测试」与「生产发起/办理」在**代码逻辑、数据结构、接口调用、配置参数**四层共用同一条路径，杜绝「测试通过但正式环境跑不了」。

## 0. 结论速览

| 层次 | 当前状态 | 依据 |
|---|---|---|
| 表单版式（排版） | ✅ 已同源 | 三页共用 `layoutJson`（`GET /form/render` / `/form/preview`） |
| 字段权限 / 操作菜单 / 意见必填 | ✅ 已同源 | `pkg.fieldPerms` + `WfNodeSettingsUtil`（`ext_json.settings`） |
| 表单值键（网关变量） | ✅ 已统一 | `collectFieldValues`：坐标键 + 字段名键一起下发 |
| 服务端校验 | ✅ 已统一 | 三页都调 `POST /form/validate` |
| 业务数据结构 | ✅ 已统一 | `data_id` / `request_id` / 列名 == 字段名 |
| **引擎部署** | ❌ **三处分叉，必须治理** | 见 §1.5 |
| 环境配置（Nacos） | ⚠️ 仓库与生效配置不一致 | 见 §1.4 |

一句话：**应用层已同源，剩下的风险集中在「部署」这一层**——测试用「关校验 + 消毒」的临时部署，正式用「完整校验」的正式部署，且二者**共用同一 procKey**。

### 1.1 代码逻辑（每项能力只允许一个实现，禁止旁路）

### 1.2 数据结构

| 结构 | 约束 | 说明 |
|---|---|---|
| `wf_instance.data_id` | **NOT NULL**，无默认值 | 语义 = 业务表 `formtable_main_N.id`；表单直发时由 `WfInstanceServiceImpl.createBusinessData()` 现场建行 |
| `wf_instance.biz_key` | `NOT NULL` + **`uk_biz_key` 唯一** | 值 = `formId:dataId`；不得写死 0（第二次发起会撞唯一键） |
| `wf_instance.form_id` | NOT NULL | 缺失时回退 `def.getFormId()`（`resolveFormId`） |
| `wf_instance.is_test` / `test_deployment_id` | 测试态标记 | 测试数据与正式数据**物理同表、逻辑隔离** |
| `formtable_main_N.id` | BIGINT，= `wf_instance.data_id` | 显式雪花 id 写入（非自增） |
| `formtable_main_N.request_id` | **BIGINT**（原 INT 已改） | 语义 = `wf_instance.id`（雪花）；由发起后 `bindRequestId()` 回填 |
| 业务表列名 | == `workflow_billfield.fieldname` == 布局 `fieldMeta.fieldName` | `fielddbname` 允许为 NULL，写入以**字段名**为准 |
| 业务表名 | `workflow_bill.table_name` | ⚠️ 迁移表单的表名与表单ID不同（表单 `2064530495200337922` → `formtable_main_5`），**禁止用 `formtable_main_{formId}` 推导** |
| `wf_process_node` / `wf_node_link` | 由 `saveBpmn` 从 BPMN 解析重建 | **引擎只认 BPMN**；画布改了必须保存并重新部署 |
| `form_layout` | `(formId, layoutType, nodeKey)` + `status=1` | 节点级优先、表单级回退 |
| `wf_task.view_time` | 已查看判定 | 「已查看 / 未操作」区分依据 |
| `wf_approval_log.opinion` | TEXT | 富文本 |

测试与正式**必须共用同一套表结构**（同库同表），不得另建测试库/测试表，否则结构漂移无法发现。

### 1.3 接口调用

| 环节 | 正式 | 测试 | 要求 |
|---|---|---|---|
| 发起 | `POST /instance/start` | 同（带 `testFlag=true`） | 同一 DTO、同一服务方法 `IWfInstanceService#start` |
| 审批提交 | `POST /task/{id}/approve` | `POST /test/step` | 同一套 `opinion` / `variables`(formData) 语义；测试态逐人提交（会签） |
| 待办查询 | `GET /task/todo` | `GET /test/todo` | 仅数据源不同（`is_test`） |
| 模板/权限 | `GET /form/render`、`/form/preview` | 同 | **完全共用** |
| 业务数据 | `POST /form-data/save-by-form`（Feign） | 不写业务表（占位 dataId） | 测试不污染业务表 |
| 部署 | `POST /definition/{id}/deploy` | `deployForTest(defId)` | 见 §1.5 |

约定：前端只经网关（`/api/...`）；服务间只走 Feign api 接口（`IFormmodeClient` / `IWorkflowClient`），**路径不带 `/api/<svc>` 前缀**（对齐 `getFormLayout`）。

### 1.4 配置参数

1. **同一套基础设施**：同一 Nacos 命名空间、同一 DB（`blade` + `blade_workflow`）、同一 Redis。禁止用不同 profile 造成 Feign 路径 / mapper / 过滤器行为不同。
2. **`xss.skip-url` 必须覆盖送 HTML 的接口**：`/api/blade-workflow/**`、`/api/blade-formmode/form-data/**`（含新的 `/form-data/save-by-form`）。
   ⚠️ 现状：Nacos 生效的 `blade.yaml` 里 `xss.skip-url` **只有 `/weixin`**，仓库 `doc/nacos/blade.yaml` 里那几条未发布 → 富文本字段值经 POST 可能被清洗。**需把仓库那份发布到 Nacos 并重启。**
3. **鉴权分两层（2026-09-20 改造）**：
   - **菜单 / 按钮授权**（`blade_role_menu`）只决定前端菜单与按钮是否显示：授给**要使用该功能的角色**即可。普通员工角色需授 `workflow_center / workflow_create / workflow_todo / workflow_done / workflow_request` 与按钮行 `workflow_create_start`（`is_open=2` 无壳页）、`workflow_create_submit`、`workflow_todo_forward`、`workflow_todo_sign`。
   - **接口鉴权**（`@PreAuth`）：流程中心**面向全体员工的接口只要求「已登录」**（`WorkflowConstant.HAS_AUTH` = `hasAuth()`）——发起、我的请求、待办/已办、办理（同意/退回/转办/加签/抄送/催办/标记已查看）、渲染包与校验（`/form/render|preview|validate`）、定义只读接口（列表/详情/BPMN/节点/出口/浏览框选项）、待办角标（`/monitor/count`）。
     **建模 / 部署 / 版本 / 启停 / 删除 / 节点与出口配置 / 字段与明细权限 / 模拟 / 测试（`/test/**`）/ 监控统计**仍要求 `workflow` 或 `administrator` 角色别名（`HAS_ROLE_WORKFLOW`）。
   - **formmode 侧同步放开两个「运行时 Feign 端点」**（否则普通员工进了发起页却拿不到布局）：
     `GET /form-layout/{formId}`（渲染包 / 预览 / 服务端校验取布局）与
     `POST /form-data/save-by-form`（发起时创建业务行 + 回填 `request_id`），改为 `HAS_AUTH`；
     Feign 会透传当前用户 token，故两侧必须同口径。其余表单管理接口（布局保存/删除、表单数据管理、
     字段定义、权限配置）仍限角色。
   - ❗**角色别名 ≠ 菜单授权**：`hasRole('workflow')` 读的是 **token 里的 `role_name`**（登录时写入的角色别名，逗号分隔；`blade_user.role_id` 支持多角色），改角色后**必须重新登录**；菜单授了不代表接口能过（401「请求未授权」= 角色不匹配）。
   - ❗**记录级鉴权兜底**（放开角色门的前提）：接口放开后「能不能动**这一条**」由服务层收口 —— `WfAuthUtil` + `WfInstanceServiceImpl#canView`：办理类动作校验「是否为该任务办理人（含代理 `original_user`）或管理员」；实例读取校验「发起人 / 参与人（有 `wf_task` 记录）/ 管理员」；待办 / 已办 / 角标的 `assignee` 入参对非管理员强制收敛为本人；`GET /definition/list` 对非管理员只返回 `status=1`。越权返回 **403 + 明确原因**（`WfAccessDeniedException`）。
4. **版本状态**：正式发起要求 `def.status=1` 且 `active_version_id` 指向本版本（发起页有校验）。
5. **环境差异白名单**：仅允许 `is_test` 标记、测试部署 ID、测试待办数据源三处不同；其余必须完全一致。

### 1.5 ⚠️ 引擎部署的三处分叉（重点治理项）

| | 测试 | 正式 |
|---|---|---|
| 入口 | `WfDefinitionServiceImpl#deployForTest` → `IProcessService#deployProcessForTest` | `WfDefinitionServiceImpl#deploy` → `IProcessService#deployProcess` |
| 部署用 XML | `neutralizeForTest(injectLinkConditions(bpmn_xml, links))` | `injectLinkConditions(bpmn_xml, links)` |
| 引擎校验 | **关闭**（`disableSchemaValidation` + `disableBpmnValidation`） | **完整校验** |
| 定义状态 | 不改 `status`、不激活版本 | `status=1` + `promoteActiveVersion` |
| 生命周期 | 临时部署，靠**手动** `cleanupTestData` 级联卸载 | 永久 |

**风险 1：同 `procKey` 顶版本。** `ProcessServiceImpl#startInstance` = `runtimeService.startProcessInstanceByKey(procKey, bizKey, vars)`，Flowable 取该 key 的**最新部署**。测试部署使用同一 procKey，而清理是手动的（仅 `POST /test/cleanup` 触发，测试结束不自动清）→ **未清理时，正式发起的其实是"关了校验 + 消毒过"的测试版本**。

> ✅ **已修复（2026-09-20）**：测试部署改用独立 key `procKey + WorkflowConstant.TEST_DEPLOY_KEY_SUFFIX`（`"__test"`）：
> - 部署侧 `WfDefinitionServiceImpl#deployForTest` 用该 key 部署；
> - 发起侧 `WfTestServiceImpl` 把 `StartProcessDTO.engineKey` 设为同一 key，`WfInstanceServiceImpl#start` 优先用它启动引擎；
> - 另加**正式发起守卫** `assertNoPendingTestData()`：同 procKey 版本组内存在未清理的 `is_test=1` 实例时，正式发起直接报错提示先清理。
> 因此「测试版本顶替正式」在机制上不再可能（历史遗留：改造前用同一 key 产生的测试部署，需按 §3.1 第 3 步清理一次）。
>
> ⚠️ **补充修复（2026-09-22）——上面这条当时并不完整**：Flowable 的「流程 key」取自 BPMN 的 `<process id="...">`，而 `deployProcessForTest` 只改了**部署名 / 资源名**（`.name()/.key()/.addString()`），**没改 XML 里的 `process id`**。后果有两个：
> - 引擎里**根本不存在 `__test` 这个流程 key** → `latestProcDefId(procKey__test)` 返回 `null` → 测试发起退回 `startProcessInstanceByKey("xxx__test")`，Flowable 报 **no processes deployed with key**（即测试日志里的 `no process definition`）。这就是"**同一条流程：正式能跑通、测试跑不通**"的直接原因；
> - 测试部署仍落在**正式 `procKey` 的版本序列**上（每次测试该 key 版本 +1，且内容是"关校验 + 消毒"的那份）→ **风险 1 实际并未消除**。
>
> ✅ **已修（2026-09-22）**：`WfDefinitionServiceImpl#neutralizeForTest(xml, testKey)` 在序列化前把 main process 的 id 改写为 `procKey + "__test"`（`deployForTest` 传入 `testKey`）。修好后：测试部署在**独立 key** 下（`latestProcDefId(xxx__test)` 有值 → 按定义ID启动），正式 key 的版本序列不再被测试污染。
> ⚠️ **升级后务必先 `POST /test/cleanup`（清理测试数据）一次**：此前历史测试部署已污染正式 key 的版本列表（可能使正式发起跑到"消毒 + 关校验"的那一版），需按 key 后缀 `%__test` 卸载掉；随后正式 key 的 latest 会回到真正的正式部署。

**风险 2：`neutralizeForTest` 会把 4 类元素降级为 `manualTask`（自动通过）。**

| 元素 | 原因 | 测试表现 | 正式表现 |
|---|---|---|---|
| `businessRuleTask` | Flowable 解析需 `org.kie`（Drools），本工程未引入 | 降级 → 自动通过 | **部署期即被拒**（完整校验） |
| `intermediateThrowEvent` | 未配置/不支持的抛出事件 | 降级 → 自动通过 | 运行期失败 |
| 含 timer 的 `intermediateCatchEvent` / `boundaryEvent` | 未配置会卡死、已配置测试不应真等待 | 降级 → 自动通过 | 运行期卡死/真等待 |

即：**测试"通过"不等于正式能跑**，这是"测试绿灯、正式发不出"的直接原因。

**风险 3：~~无法直接比对部署~~（✅ 2026-09-20 已消除）。** 此前 `WfProcessDefinition` 没有 `deployment_id` 列（`deploy()` 丢弃了 `deployProcess` 的返回），只能靠部署时间 / `manualTask` 消毒标记间接判读。现已落库该列（迁移 `V2026.09.20_005`），可直接比对"引擎 latest == 正式部署"：巡检 ⑦（精确比对）+ 发起自检标志 `engineDeploymentMatched`（巡检 ⑧）。

> ⚠️ 存量行 `deployment_id` 为 NULL（= 未落库 / 未知），比对与自检一律按"未知"处理、**不误报**；重新「发布」一次即回填。测试部署走独立 key，**不写本列**（本列语义 = 正式部署）；「另存为新版本」置空（新版本是未部署草稿）。

## 2. 一致性校验机制（按优先级分 4 级）

### L1 发布门禁（收益最大，建议优先实施）

> ✅ **已实施**：`WfDefinitionServiceImpl#validateForDeploy(def)`（由 `deploy()` 在部署前调用）实际规则：
> 1. **硬拦**：BPMN 含 `businessRuleTask`（正式环境无 Drools，部署期必失败）→ 报错并列出「节点名(节点id)」，提示改为自动处理/脚本任务后重新保存画布；
> 2. **强提示（记 warn）**：`ThrowEvent`、含 timer 的 `intermediateCatchEvent`/`boundaryEvent` → 正式环境运行期失败或真等待，不阻断发布；
> 3. **硬拦**：BPMN 中 `nodeTypeOf() != null` 的节点必须都存在于 `wf_process_node`（存活）→ 否则说明画布改了没保存 / 节点配置被删，发起后会卡住或无人可办；
> 4. **提示**：配置里有、BPMN 里没有的节点（多为已删除节点）记 warn 不阻断。

1. **正式部署前置校验**：`deploy()` 前扫描 BPMN，若存在 `needsNeutralize` 命中的元素（businessRuleTask / ThrowEvent / timer 事件），**拒绝发布**并列出节点名称与原因（提示「该元素正式环境不支持，请改为 ServiceTask/ScriptTask 或补齐配置」）。
2. **结构一致性校验**：`bpmn_xml` 中的节点集合 == `wf_process_node` 存活节点集合；每条物理连线都有对应出口行。复用 `saveBpmn` 的解析与测试覆盖率的口径（`WfTestServiceImpl` 覆盖率计算已实现相邻对 ↔ 物理出口比对）。

### L2 部署隔离 + 残留守卫

1. **测试部署改用独立 key**：`procKey + "__test"`（`procKey` 合法字符集 `^[A-Za-z_][\w.-]*$` 允许；历史活动按 `engineInstId` 查询，不依赖 key）→ 从根本上不再顶替正式版本。
2. **正式发起守卫**：`start()` 中检测存在未清理的 `is_test=1` 且 `test_deployment_id` 非空的实例时，返回显式提示「请先清理测试数据」，避免脏部署参与正式运行。

### L3 运行时自检

1. 发起：**业务行创建成功** + **`request_id` 回填成功** + **引擎 latest == 正式部署**。
   ✅ **已实施（2026-09-20）**：三个标志在 `start()` 里落 `wf_instance`
   （`business_row_ready` / `request_id_bound` / `engine_deployment_matched`，迁移 `V2026.09.20_006`），
   随 `InstanceVO` 返回前端 —— 发起成功页在有异常时直接把问题列出来（此前只在后端 `log.warn`）。
   取值一律 `1 正常 / 0 异常 / NULL 未知`（存量实例与测试态为 NULL，**不误报**）；
   巡检脚本第 ⑧ 项可按标志直接查全量异常实例。
2. 渲染：`layoutJson` 为空 / 该节点无布局时给出显式提示（而不是静默空白）。（⏳ 未做）
3. 校验：`POST /form/validate` 失败信息要带上字段标签与字段名（后端已带「标签(字段名)」）。

### L4 数据巡检 SQL（可定时执行）

```sql
-- ① 实例的业务数据行缺失（data_id 在业务表找不到）
--    业务表名以 workflow_bill.table_name 为准（迁移表单 ≠ formtable_main_{formId}），
--    故需「先取表名再逐表比对」，示例（formId = 2064530495200337922 → formtable_main_5）：
SELECT i.id AS inst_id, i.form_id, i.data_id, i.biz_key
FROM blade_workflow.wf_instance i
LEFT JOIN blade.formtable_main_5 b ON b.id = i.data_id
WHERE i.is_deleted = 0 AND i.is_test = 0 AND b.id IS NULL;

-- ② request_id 与实例不匹配（期望 formtable_main_N.request_id == wf_instance.id）
SELECT i.id AS inst_id, i.data_id, b.request_id
FROM blade_workflow.wf_instance i
JOIN blade.formtable_main_5 b ON b.id = i.data_id
WHERE i.is_deleted = 0 AND i.is_test = 0
  AND (b.request_id IS NULL OR b.request_id <> i.id);

-- ③ 活跃版本的 BPMN 与节点表不一致（数量口径）
SELECT d.id, d.name, d.status, d.active_version_id,
       (SELECT COUNT(*) FROM blade_workflow.wf_process_node n
         WHERE n.def_id = d.id AND n.is_deleted = 0) AS node_cnt
FROM blade_workflow.wf_process_definition d
WHERE d.is_deleted = 0 AND d.status = 1;

-- ④ 残留测试数据 / 测试部署
SELECT id, def_id, title, test_deployment_id, start_time
FROM blade_workflow.wf_instance
WHERE is_test = 1 AND is_deleted = 0 ORDER BY id DESC;

-- ⑤ 布局字段名未落到业务表列（会导致"填了不落库"）
-- 先取布局：SELECT layout_json FROM blade.form_layout WHERE form_id=? AND node_key=? AND status=1
-- 再看业务表列：SELECT COLUMN_NAME FROM information_schema.COLUMNS
--   WHERE TABLE_SCHEMA='blade' AND TABLE_NAME=?   → 两边取差集

-- ⑥ 引擎中该 procKey 的最新部署时间（判断是否被测试部署顶替）
SELECT pd.KEY_, pd.VERSION_, pd.DEPLOYMENT_ID_, d.DEPLOY_TIME_
FROM blade_workflow.ACT_RE_PROCDEF pd
JOIN blade_workflow.ACT_RE_DEPLOYMENT d ON d.ID_ = pd.DEPLOYMENT_ID_
WHERE pd.KEY_ = ? ORDER BY pd.VERSION_ DESC LIMIT 3;
```

## 3. 验证方法（「测试 → 正式」切换验收清单）

### 3.1 切换步骤（顺序不可颠倒）

> ⚠️ **0. 升级前置（一次性，做过一次即可）**：本次修复（`neutralizeForTest` 改写 `process id`，见 §1.5「补充修复」）之前，测试部署**没有独立 key**，会直接落进正式 `procKey` 的版本序列，可能把正式版本顶成"关校验 + 消毒"的那一份（表现为"正式能跑"其实跑的是测试版）。因此**从旧版本升级上来后，必须先执行一次清理**：`POST /test/cleanup`（卸载历史遗留的 `%__test` 部署）。核对：§2-L4-⑥ 查该 `procKey` 的 latest，其 `DEPLOYMENT_ID_` 对应的资源名**不应**带 `__test`。

1. **设计**：画布设计 → 保存 BPMN（`saveBpmn`，重建节点/出口）→ **部署**（`deploy`，`status=1` + 激活版本）。
2. **测试**：`/formmode/test` 一键测试跑到归档（覆盖率全绿）；再手动逐节点提交（含会签逐人）验证交互态。
   - **预期**：测试部署落在**独立 key** `procKey + "__test"`（`ACT_RE_PROCDEF.KEY_ = xxx__test`），正式 `procKey` 版本序列不受影响。
   - 若仍报 `no process definition`，说明测试部署没改写 `process id`（见 §1.5 补充修复）→ 确认后端已升级。
3. **清理测试数据**（`POST /test/cleanup`）——**硬要求**，否则触发 §1.5 风险 1。
   - **清理后复检**：§2-L4-⑥ 该 `procKey` 的 latest 必须是**正式部署**（资源名不带 `__test`）；`SELECT COUNT(*) FROM wf_instance WHERE is_test=1` 应归零。
4. **引擎核验**：执行巡检 ⑦（`wf_process_definition.deployment_id` 与引擎 latest 精确比对；
   无 deployment_id 时退回 §2-L4-⑥ 按部署时间 / 消毒标记人工判读），确认该 procKey 的 latest 部署不是测试部署。
5. **正式发起**：`/workflow/create/start?defId=...` 提交成功后核对业务表与实例（见 3.2）。
6. **正式办理**：打开待办办理页，按 3.3 对照表逐项核对。
7. **归档回归**：流转意见条数/顺序、流程图「操作者」面板、`request_id` 闭环。
