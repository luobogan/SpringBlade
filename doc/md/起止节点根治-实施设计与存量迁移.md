# 起止节点根治 · 实施设计与存量迁移

> 配套文档：[起止节点建模-开始结束事件本质与UserTask根治方案.md](./起止节点建模-开始结束事件本质与UserTask根治方案.md)
> 本文聚焦阶段二（根治）的**落地设计**：建模范式改造、存量迁移、灰度与回滚。
> 目标：把"申请人填单"从 `bpmn:StartEvent`（仅靠 `wf:node nodeType=0` 标记、引擎自动跳过、靠合成待办补位）改为真正的 `bpmn:UserTask`（`wf:node nodeType=0` 业务语义保留），让引擎为创建节点真实生成任务并停住 token，从而废除"合成待办""状态分裂"与一整组运行期特例。

---

## 一、拓扑决策（最关键，需确认）

### 1.1 旧模型（当前）
```
StartEvent(创建,nodeType=0) ──▶ UserTask(审批) ──▶ ... ──▶ EndEvent(归档,3)
```
- 引擎 `startInstance` 自动完成 StartEvent（Flowable 固有行为），token 落到第一个审批 UserTask。
- 创建节点**不是等待态**，无真实任务；"申请人待办"是 `wf_task` 合成行（`engine_task_id` 空串）。
- 退回发起人（`rejectToStarter`）、重新提交（`resubmitByCreator`）、草稿合成待办等特例全部为补偿这一"非等待态创建节点"而存在。

### 1.2 新模型（根治目标）
```
StartEvent(薄连接器,无业务语义) ──▶ UserTask(创建,nodeType=0) ──▶ UserTask(审批) ──▶ ... ──▶ EndEvent(归档,3)
```
- 多了一个**薄 StartEvent**（纯 Flowable 起点要求，不承载业务、不进 `wf_process_node`、不参与节点信息/出口/流转）。
- 创建节点是**真正的 UserTask**：`startInstance` 自动完成薄 StartEvent → token 停在创建 UserTask → 引擎生成真实任务、assignee=发起人（操作者取"创建人本人"）。
- 发起 = 完成创建节点的真实任务（填单提交），token 自然流入第一个审批 UserTask。
- 退回发起人 = 通用 `moveActivity(创建UserTask)` + `advance`（创建节点已是等待态，停得住、有真实待办），**不再需要** `rejectToStarter`/`resubmitByCreator`/合成待办。
- 创建节点与审批节点**同构**，全链路统一走 `advance`/`doApprove` 通用路径。

### 1.3 兼容性判据（新旧如何区分）
**"创建节点 = `wf:node.nodeType==0` 的元素"，且用"模型内是否存在创建型 UserTask"来区分 StartEvent 是薄连接器还是旧式创建节点：**

- 若模型内**存在** `UserTask` 且其 `wf:node.nodeType==0` → 新模型：该 UserTask 是创建节点；`StartEvent` 一律视为薄连接器（跳过，不写 `wf_process_node`、不合成 nodeType=0）。
- 若模型内**不存在**创建型 UserTask → 旧模型：`StartEvent` 即创建节点（`nodeType==0`），保持原行为。

> 这样**旧定义零改动即可继续工作**（其 StartEvent 仍是创建），只有用新设计器建模/发布的流程才走新模型。符合计划"新定义走新模型，存量与在途实例保留兼容分支"的灰度要求。

## 二、后端改动（读源/写源对齐 + 删特例）

所有改动均在 `blade-workflow` 模块。

### 2.1 `WfBpmnExtensionReader`（读源）
- `toNodes()`（`:189`）：
  - ②段 `StartEvent` 合成（`syntheticNode(e,0)`）改为：先 `hasCreateUserTask = 模型内任一 UserTask 的 wf:node.nodeType==0`；仅当 `!hasCreateUserTask` 时把 StartEvent 合成 nodeType=0，否则跳过（不写薄 StartEvent）。
  - `UserTask` 循环（①段）保持 `toProcessNode`（已读 `wf:node.nodeType`），创建型 UserTask 自然得 0。
- `node()`（`:99`）/ `nodeTypeByElement()`（`:244`）：单查 `StartEvent` 时，同样依据 `hasCreateUserTask` 判定——存在创建型 UserTask 则该 StartEvent 返回 `null`（薄连接器），否则返回 0（旧式创建）。需在该方法内对主流程做一次扫描（模型已可取得）。
- `nodeExtsComplete` 守卫（`:157`）：仅校验 UserTask 的 `wf:node` 完整性，薄 StartEvent 不要求扩展，**不受影响**。

### 2.2 `WfDefinitionServiceImpl`（写源 `saveBpmn`）
- `nodeTypeOf()`（`:1976`）：改为 `UserTask → (wf:node.nodeType==0 ? 0 : 1)`；`StartEvent → (hasCreateUserTask ? 跳过(null) : 0)`。
- `saveBpmn`（`:583-616` 遍历 FlowElement upsert `wf_process_node`）：循环前先算出 `hasCreateUserTask`；`nodeTypeOf` 返回 `null` 的元素（薄 StartEvent）跳过 upsert，避免凭空多出"创建"节点导致 `findStartNodeKey` 出现两个 nodeType=0。
- `defaultNodeName`（`:2027`）：`nodeType==0` 默认名"开始"保留（创建节点仍叫"创建/开始"）。

### 2.3 `WfInstanceServiceImpl`（发起/流转意见）
- `start()`（`:321`）：新模型下 `startInstanceById` 后 token 自然停在创建 UserTask，`advance()` 读活动任务生成真实 `wf_task`（assignee=发起人）。**无需"删合成待办"特例**（`:491-493` 的草稿提升删空 engineTaskId 分支仅对旧模型草稿成立，新模型草稿也是真实任务，需改为"完成创建节点任务"）。
- `findStartNodeKey()`（`:1859`）：按 `nodeType==0` 找创建节点——新模型下会找到创建 UserTask，逻辑不变。
- `:2515-2527`（"开始节点引擎自动完成、办理人=发起人"补录特例）：新模型创建节点有真实任务，可删（或仅作兜底）。
- `:1606-1625`/`1650-1666`（`awaitingCreatorResubmit`/`warnIfEngineTaskMismatch` 排除"引擎无对应 wf_task"的合法中间态）：创建节点真实化后该漂移态消失，排除逻辑可删。
- 草稿 `saveDraft`（`:557-662`）：旧模型草稿仍用合成待办（空串）；新模型草稿应为创建 UserTask 的真实任务（保存即完成任务 + 留草稿数据）。需按模型类型分流。

### 2.4 `WfTaskServiceImpl`（删运行期特例）
- `rejectToStarter()`（`:1033-1068`）：新模型下创建节点是等待态，`reject` 目标 `nodeType==0` 直接走通用 `moveActivity+advance` 即可停住并生成真实待办，**该方法可删除**。
- `isCreatorResubmitTask()`（`:1076-1082`）：判"nodeType==0 且 engineTaskId 空"=合成待办，新模型无此概念，**删除**；`doApprove` 的调用点（`:311-323`）回到普通完成路径。
- `resubmitByCreator()`（`:1091-1111`）：新模型重提即"完成创建节点真实任务"，通用 `doApprove` 即可，**删除**。
- `reject()`（`:469-473`）`nodeType==0` 分支：保留 `WfRejectManager` 把 0 列为合法退回候选（`:75-76,142`），但落点改为通用 `moveActivity+advance`（创建 UserTask 可停）。

### 2.5 `WfTestServiceImpl`（自动测试）
- `:292-298,308-314,387,840-843,909,924,1459-1464`：多处"创建节点=start 自动办结、不在待办循环"的假设需**反向**——新模型下创建节点是**第一个真实待办**（先填单完成它再流入下一节点）。首节点识别、必填校验、循环驱动口径改为"第一个待办即创建节点"。

## 四、数据处理：清库重建（不迁移）

> 用户决策（2026-10-06）：**不做存量迁移**，旧的工作流数据直接清空，再用新设计器重新创建流程。
> 前提：这是 **dev 环境**，可接受丢失历史流程实例/定义。

### 4.1 为什么不需要迁移
后端已硬切为「创建节点 = `UserTask(nodeType=0)`」，`StartEvent` 一律不落 `wf_process_node`、不承载业务。旧定义的"创建节点=startEvent"在新代码下会**失去创建节点**（`findStartNodeKey` 找不到 `nodeType=0`），导致无法发起/退回。既然旧数据可弃，直接清空重建比写迁移脚本更简单、也避免迁移脚本本身的风险。

### 4.2 落地顺序
1. 部署后端 + 前端（原子切换，两者缺一则不完整）。
2. 执行数据清理（按 [`docs/工作流清库-新模型验证.md`](../../docs/工作流清库-新模型验证.md) 走：优先用 `DELETE /blade-workflow/definition/{id}` 级联清引擎，再按需清扫 `wf_*` 残留）。
3. 在设计器里**重新创建流程**（默认模板已带"创建 UserTask(opType=17)"）→ 发布 → 发起验证。

### 4.3 清理范围（务必确认后再执行）
- **工作流台账**：`wf_process_definition` / `wf_process_node` / `wf_node_link` / `wf_node_operator` / `wf_node_field_perm` / `wf_node_detail_perm` / `wf_node_timeout` / `wf_instance` / `wf_task` / `wf_approval_log` / `wf_form_snapshot` / `wf_definition_gray` / `wf_subflow*` / `wf_coadjutant*` 等。
- **引擎数据**：`ACT_RU_*`（运行中任务/变量/身份链接）与 `ACT_HI_*`（历史）、`ACT_GE_BYTEARRAY`（含部署的 BPMN 工件）、`ACT_RE_*`、`ACT_PROCDEF` 等——建议优先用引擎 API（`RepositoryService.deleteDeployment` / `HistoryService`）或按脚本清，避免只删 `ACT_RU_TASK` 留下悬挂的 `ACT_HI_*`。
- **formmode 侧**：节点表单布局（`form_layout` 等，按 `def_id/node_key` 关联）与发起产生的业务行（`formtable_main_N`）。⚠️ 若只想清工作流、保留表单模板定义，需按 `form_id` 精确区分，勿整表清。

### 4.4 回滚
- 代码侧：硬切，回滚 = 前后端一起回退上一版本（`git revert`）。
- 数据侧：清库不可逆；回滚后新模型建的定义（创建=UserTask）在旧代码下会被当成普通审批节点，需重新清理并用旧版重建流程。

## 五、实施结果与遗留风险（2026-10-06 落地后更新）

### 5.1 已落地的关键决策
- **不做兼容，硬切改造**：删除全部兼容分支（`hasCreateUserTask` 判据未采用——后端直接以「创建=UserTask(nodeType=0)」为唯一口径，StartEvent 一律不落 `wf_process_node`）。
- **发起 UX = 方案 B「发起即完成创建任务」**（非原计划的"发起后停在填单任务"）：点发起 → `startInstance` 停在创建 UserTask → `completeStarterCreateTask` **程序立即 complete 该真实任务** → token 流入第一个审批 → `advance` 生成审批人待办。引擎真实流经创建节点（保留根治语义），但对用户无感、不二次填单。草稿仍是无引擎任务的合成待办态，提交草稿走同一路径。

### 5.2 已删除的运行期特例 / 死逻辑
| 位置 | 处理 |
|---|---|
| `WfTaskServiceImpl` | 删 `rejectToStarter` / `isCreatorResubmitTask` / `resubmitByCreator`；`reject` 统一 `moveActivity+advance`；`doApprove` 删重提分支 |
| `WfInstanceServiceImpl` | 删 `awaitingCreatorResubmit` + 其在 `warnIfEngineTaskMismatch` 的排除（已成死逻辑）；补录创建节点发起人的逻辑**保留**（方案B 下创建节点仍无 `wf_task` 行，且 act 读源下 `ACT_HI_COMMENT` 无 `USER_ID_`，此为唯一兜底） |
| `WfTaskActReader` | **删止血②屏蔽**（`RETURNED_TO_STARTER_INSTANCES` 常量 + 待办列表/角标两处使用）——⚠️新模型下它会把"退回发起人"时发起人的**真实**待办一并屏蔽 → 流程死锁，属必修 |
| `WfInstanceServiceImpl:491` | 修 bug：草稿提升删除合成待办由 `.isNull(engineTaskId)` 改为同时匹配 `= ''`（库中实际存空串，原逻辑漏删） |
| `WfTestServiceImpl` | 逻辑无需改（方案B 下创建节点不进待办循环，行为与旧模型一致）；仅更新「自动完成」等过时注释为「程序 complete」 |
| `drift_check.sql` | 排除条件保留（兼容存量旧行）但注释标注为「历史遗留，新模型不再产生该态」 |

### 5.3 遗留风险与待办
1. **旧数据需清空重建**（最高）：后端已硬要求创建=UserTask，"创建=startEvent"的旧定义会失去创建节点 → 无法发起/退回。按第四节清库（[`docs/工作流清库-新模型验证.md`](../../docs/工作流清库-新模型验证.md)）后用新设计器重建流程即可，无需迁移。
2. **前端设计器无法在本环境验证**：改动（`shapeTypeFor`、默认模板 `wf:node`/`opType=17`、`NodeDetail` 结束节点提示）逻辑已逐处核对，但 React+bpmn-js 运行时未验证，需在联调环境验收：新建流程→发布→发起→退回发起人→重新提交→归档。
3. **结束节点(endEvent)配置收敛未做结构变更**：目前仅在 `NodeDetail` 加了"仅标题显示/操作者生效"的提示（零风险）。把归档人/归档文案提升到流程定义级、endEvent 退回纯连接器，属独立高风险改动（会牵动归档行合成 `:1075-1110`、归档人解析 `:2582-2600`、预校验 `:898-931`/`:2937-2955`），建议单独排期。
4. **读源切换下的补录隐患**：`WfInstanceServiceImpl:2557`（补录）与 `:2582`（归档人）仍直读 `wf_process_node`，未走 `loadNodeReadOnly`；若后续把 BPMN 设为唯一源、退役 `wf_process_node`，这两处需同步改造。
5. **自动测试需回归**：虽逻辑未变，但因创建节点建模变化，建议重跑一次"开始自动测试"，确认必填校验与叙述块仍正常（历史上曾因 MI 子任务未同步关闭卡死）。
