## 1. 总览与规范

### 1.1 库分布

| 库 | 内容 | 说明 |
|---|---|---|
| `blade_workflow` | 9 张 `wf_*` 业务表 + Flowable 引擎 39 张 `ACT_*` 表 | `wf_*` 不依赖 `ACT_*`，仅弱关联（`wf_instance.engine_inst_id`） |
| `blade` | `mode_triggerworkflowset` 等 formmode 触发表、`workflow_bill`（表单）、`form_layout`（布局） | 表单域与流程触发配置 |

### 1.2 设计约定

| 项 | 约定 |
|---|---|
| 主键 | `BIGINT UNSIGNED AUTO_INCREMENT`（窄、单调，避免随机值做聚簇主键） |
| 字符集 | `utf8mb4` / `utf8mb4_0900_ai_ci` |
| 时间 | `DATETIME`（非 `TIMESTAMP`） |
| 审计字段 | 每张表必含 `tenant_id / create_user / create_dept / create_time / update_user / update_time / status / is_deleted`（实体统一继承 `TenantEntity`） |
| 索引命名 | 唯一键 `uk_` 前缀，普通索引 `idx_` 前缀，遵循最左前缀（等值列在前） |
| 外键 | **无**（跨库/跨模块靠逻辑关联，与 ecology 一致） |
| 逻辑删除 | `is_deleted = 0/1`，实体带 `@TableLogic` |

### 1.3 表清单

| # | 表名 | 域 | 说明 | 当前状态 |

| 名 | 类型 | 列 | 说明 |
|---|---|---|---|
| `PRIMARY` | 主键 | `id` | |
| `uk_proc_key_version` | **唯一** | `proc_key, version` | 同一流程标识版本唯一（另存版本时递增 `version`） |

| 列 | 类型 | 空 | 默认 | 说明 |

| `node_key` ⭐ | VARCHAR(64) | 否 | — | 节点 Key |
| `scope` ⭐ | VARCHAR(64) | 否 | — | **`main` ｜ `dt{idx}` ｜ `dt{idx}_r{row}`**（行级，迁移 003） |
| `field_name` ⭐ | VARCHAR(128) | 否 | — | 字段名，与前端 `data-excelp-field` 一致 |

- 无独立 `hidden` 列：`perm = 0` 即隐藏（《方案》§3.5 提到的 `hidden` 冗余列**未建**，属文档与实现差异）。

### 5.2 Flowable 引擎表（`ACT_*`，39 张）

- **来源**：`FlowableConfig` 在引擎构建时按 `blade.flowable.database-schema-update` 策略处理。
- **当前策略**：默认 `none`（表已存在，启动不碰 schema）。首启或换库时临时设为 `create`。
- **关键行为**（源码核实，Flowable 7.1.0 `SchemaOperationsEngineBuild`）：
  - `create-drop` / `drop-create` / `create` → `schemaCreate()`
  - `false` → `schemaCheckVersion()`（版本不符抛 `FlowableWrongDbException`）
  - `true` → `schemaUpdate()`
  - **其它值（含 `none`）→ 什么都不做**
- **⚠️ 坑**：`create` 在表已存在时会执行建表脚本撞已存在的表 → 引擎装配失败。因此库里已有 `ACT_*` 时**必须保持 `none`**。
- **建议**：生产改为 `none` + Flyway/Liquibase 管理（本项目暂无迁移框架）。

## 7. 结构漂移核对与维护规程

### 7.1 为什么需要

本项目**无 Flyway/Liquibase**，实体加字段后若忘记同步库表，会出现 `Unknown column` 运行时错误（本次 `bpmn_xml` 即因此产生）。

### 7.2 核对 SQL（建议每次发版前执行）

```sql
-- ① wf_* 表清单与行数
SELECT TABLE_NAME, TABLE_ROWS
FROM information_schema.TABLES
WHERE TABLE_SCHEMA = 'blade_workflow' AND TABLE_NAME LIKE 'wf\_%'
ORDER BY TABLE_NAME;

-- ② 全表列清单（与 workflow-schema.sql 逐列比对，找出实体有而库没有的列）
SELECT TABLE_NAME, COLUMN_NAME, COLUMN_TYPE, IS_NULLABLE, COLUMN_DEFAULT, COLUMN_COMMENT
FROM information_schema.COLUMNS
WHERE TABLE_SCHEMA = 'blade_workflow' AND TABLE_NAME LIKE 'wf\_%'
ORDER BY TABLE_NAME, ORDINAL_POSITION;

-- ③ 索引与约束
SELECT TABLE_NAME, INDEX_NAME, COLUMN_NAME, NON_UNIQUE
FROM information_schema.STATISTICS
WHERE TABLE_SCHEMA = 'blade_workflow' AND TABLE_NAME LIKE 'wf\_%'
ORDER BY TABLE_NAME, INDEX_NAME, SEQ_IN_INDEX;
```

### 7.3 维护规程（建议纳入开发规范）

1. **实体加字段 = 必须同时提交迁移脚本**到 `doc/sql/migration/`，命名 `V{YYYY.MM.DD}_{序号}__{简述}.sql`。
2. 脚本必须**幂等**（用 `information_schema` 判定 + `PREPARE/EXECUTE` 动态 DDL），可重复执行不报错。
3. 脚本头部必须写明：目标库、影响表、变更类型、是否幂等、是否丢数据、回滚语句、变更背景。
4. 在本文件《迁移记录》表格中登记并勾选执行状态。
5. 发版前执行 §7.2 的核对 SQL，与建表脚本比对。
6. **禁止**用带 `DROP TABLE` 的建表脚本对已运行库做"结构同步"。
